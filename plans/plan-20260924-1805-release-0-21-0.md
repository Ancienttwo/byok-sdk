## Agentic Routing
- Selected route: single writer in a dedicated worktree (`claude/release-0.21.0` off `origin/main` @ `644f8473`, the PR #226 merge); no fan-out, because every file in scope is a version authority or a document that states one, and two concurrent writers would desync the manifests from `bun.lock`.
- Routing reason: orchestrator dispatch 2026-09-24 — the next SDK train is `0.21.0` (PR #226's own body classifies it as "0.21.0, breaking"); keys `0.6.2` is a patch whose only change is the core edge.
- Due diligence:
  - P1 map: the two version authorities are unchanged from the 0.20.0 release — `packages/core/package.json` is the aligned dispatch train and `packages/keys/package.json` is the independent keys line (`scripts/api-surface/check-version-authority.mjs`, `scripts/release/check-package-graph.mjs`). Ten manifests must equal the train — `core`, `protocol`, `client`, `server`, `cloud`, `cloud-dataplane`, `ui-runtime`, `testkit`, `implementation-identity` and the `byok-sdk` umbrella — and `keys` must differ from it. `bun.lock`'s eleven `workspaces` records are the third physical copy, hand-edited and gated by `check:release-graph`. `README.md` and `docs/spec.md` are gated by regex. Ungated but co-owned: the README release-status block and row, `deploy/runbooks/release-responsibility.md`'s train pointer and version-selection paragraph, `CHANGELOG.md` and `docs/releases/`. Out of scope: `byok.piRuntimePin` and the `@byok-sdk/pi-*` alias in `packages/client/package.json` (the fork stays frozen at 0.86.1001), `api-surface/*.d.ts` (no version literal), every product source file, and every registry action.
  - P2 trace: `npm install @byok-sdk/keys@0.6.2` → keys' `"@byok-sdk/core": "workspace:*"` → `bun pm pack` resolves `workspace:*` from the `bun.lock` workspace record for `packages/core`, not from the manifest → the packed keys tarball pins `@byok-sdk/core@0.21.0`. That is the edge the spec's policy requires to equal "the exact current dispatch release", and it is why keys must be re-released at all: its source is unchanged since `v0.20.0` (`git diff --stat v0.20.0 HEAD -- packages/keys` is empty), but the published keys 0.6.1 tarball pins core 0.20.0. `check-package-graph.mjs` compares every manifest and lockfile record to the two authorities; `check:release-pack` packs the eleven real tarballs, installs them isolated and runs the real bins; `check:version-authority` closes the loop back onto `README.md` and `docs/spec.md`.
  - P3 decision rationale: the invariant is still "one version authority per line, and every other statement is a projection of it", so the manifests move first and every document is edited to agree. SDK takes a MINOR because PR #226 is a pre-1.0 breaking cut (the policy's MINOR clause). keys takes a PATCH: the policy limits PATCH to "corrections with no new public behavior, API, persistence, or security authority", and keys changes none of those — no `packages/keys` diff since `v0.20.0`, and neither `packages/core` nor `packages/implementation-identity` (keys' only workspace edges) changed since `v0.20.0` either, so the new core edge carries identical code. Nothing in the policy forces a keys minor when the dispatch train takes one. At 10x the first thing to break is still the lockfile record, the only copy no tool regenerates.

## Approach
### Strategy
Four commits in a fixed order, so that every check has a defined meaning at the commit it first passes:

1. **Register the work-package.** Plan + contract + notes/review projections, `plan-to-todo`, `check-task-workflow --strict`.
2. **Bump the authorities.** Ten aligned manifests to `0.21.0`, `packages/keys/package.json` to `0.6.2`, and the eleven `bun.lock` workspace records by hand. 3. **Point the documents at the new train.** `README.md` (release-status block, release-status row, both install examples, the license line), `docs/spec.md` (the two gated phrases, the core-edge sentence, the registry paragraph), `deploy/runbooks/release-responsibility.md` (train pointer and version-selection paragraph).

Then the full verification set. No push, no PR, no registry action from this work-package: the Task Breakdown carries the Owner's publication sequence as unchecked items so that the boundary is visible in the same ledger.

## Risk Assessment
| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| `bun.lock` workspace records left at 0.20.0 | High if done by hand without a gate | High — keys 0.6.2 would pack a core 0.20.0 edge, defeating the only reason it is released | `check:release-graph`'s lockfile drift guard plus `check:release-pack`'s packed-edge readback |
| `bun install` reformats `bun.lock` beyond the version records | Medium | Medium — an unreviewable lockfile diff inside a release commit | Hand-edit only the eleven `version` fields; assert the diff is exactly eleven lines |
| `check:api-surface` reports a diff | Low | Medium — would mean this "version-only" bump moved the public surface | Report the diff and stop rather than regenerating |
| An operator upgrades one side of the v6 cut with work in flight | Medium | High — an old prepared offer without `egressPolicy` fails strict parsing and freezes that device's long-poll cursor; a paired upgrade alone does not repair it | The drain-then-pair precondition and the operator-handling note lead the release notes and the handoff |
| A Host relies on `auto` + `allowTools: []` meaning Pi's full default tool table on the fresh lane | Medium | Medium — the Pi run now has zero native tools | Stated as a breaking change in the release notes, CHANGELOG and runbook |
| Someone reads this preparation as authorization to publish | Medium | High | "not published" is stated in the release notes, the handoff, the CHANGELOG heading and the README; the Owner steps stay unchecked |
