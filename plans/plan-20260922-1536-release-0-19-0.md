## Agentic Routing
- Selected route: single writer in a dedicated worktree (`claude/release-0.19.0` off `origin/main` @ `3872bbf0`); no fan-out, because every file in scope is a version authority or a document that states one, and two concurrent writers would desync the manifests from `bun.lock`.
- Routing reason: Owner ruling 2026-09-22 — the next SDK train is `0.19.0` (minor, explicitly approved; the wire change is breaking).
- Due diligence:
  - P1 map: there are exactly TWO version authorities in this repo, and both are manifests — `packages/core/package.json` is the aligned dispatch train and `packages/keys/package.json` is the independent keys line (`scripts/api-surface/check-version-authority.mjs`, `scripts/release/check-package-graph.mjs`: "Version authority: the manifests themselves, never a constant in this file"). Ten manifests must equal the train — `core`, `protocol`, `client`, `server`, `cloud`, `cloud-dataplane`, `ui-runtime`, `testkit`, `implementation-identity` and the `byok-sdk` umbrella — and `keys` must differ from it. `bun.lock`'s `workspaces` records are a THIRD physical copy that `bun install` does not rewrite on a version-only bump, so they are hand-edited and gated (`check-package-graph.mjs`, "bun.lock drift guard"). Two human documents advertise the authorities and are gated by regex: `README.md` (every `byok-sdk@x.y.z` and every `@byok-sdk/keys@x.y.z` mention) and `docs/spec.md` (the phrases "current aligned dispatch release is `X`" and "current independent keys candidate is `Y`"). Ungated but co-owned: the README release-status row, `deploy/runbooks/release-responsibility.md`'s train pointer, `packages/keys/README.md`'s candidate sentence, `CHANGELOG.md` and `docs/releases/`. Out of scope: `byok.piRuntimePin` and the `@byok-sdk/pi-*` alias in `packages/client/package.json` (a separate, non-SDK release channel), `api-surface/*.d.ts` (carries no version literal), and every registry action.
  - P2 trace: one real path, `npm install byok-sdk@0.19.0` → the umbrella's `workspace:*` edges → `bun pm pack`. `check-package-graph.mjs` reads `packages/core/package.json`'s version, compares all ten aligned manifests to it, then reads `bun.lock` and compares each `workspaces[dir].version` to the same manifest — this is the step that catches a bump that edited manifests only, because `bun pm pack` resolves `workspace:*` from the LOCKFILE records, not the manifests, and a stale record would publish a 0.19.0 tarball whose internal `@byok-sdk/*` edges name 0.18.0 (the split graph v0.4.1 actually shipped). `check:release-pack` then packs the eleven real tarballs, installs them into an isolated tree and runs the real bins, which is where a version desync surfaces as a resolution failure instead of a text diff. `check:version-authority` closes the loop back onto the two human documents.
  - P3 decision rationale: the current shape exists because the registry, not the repo, is the authority on what has shipped — and the repo drifted. `docs/releases/v0.18.0-handoff.md:3`, `README.md:139` and `docs/spec.md:76-80` still call 0.18.0 / keys 0.5.0 unpublished candidates while npm has served them as `latest` since 2026-09-10 (`tasks/todos.md` records exactly this as a deferred row). The invariant to preserve is "one version authority per line, and every other statement is a projection of it": the manifests move first and every document is edited to agree, rather than any document being allowed to state a different number. The smallest coherent change is therefore a version-only bump plus a documentation reconciliation — no product logic, no dependency change. `v0.18.0-handoff.md` gets a dated correction note at the top instead of a rewrite, because it is a historical receipt of what was true when it was written; rewriting it would destroy the evidence that the drift happened. keys takes a MINOR by the authoritative policy, not by preference: `docs/spec.md#pre-10-package-version-policy` says MINOR covers "any pre-1.0 breaking cut", and `--runtime-entry {pi-rpc, pi-prepared}` is now REQUIRED at the launcher's parser (`packages/keys/src/pi-provider-launcher-core.ts`), which is a breaking argv. At 10x the first thing to break is the lockfile record, because it is the only copy no tool regenerates.

## Approach
### Strategy
Four commits in a fixed order, so that every check has a defined meaning at the commit it first passes:

1. **Register the work-package.** Plan + contract + notes/review projections, `plan-to-todo`, `check-task-workflow --strict`.
2. **Bump the authorities.** Ten aligned manifests to `0.19.0`, `packages/keys/package.json` to `0.6.0`, and the eleven `bun.lock` workspace records by hand. No dependency range moves: the umbrella and keys both reach their siblings through `workspace:*`, so nothing pins an exact sibling version that a bump would have to follow. `byok.piRuntimePin` and the `@byok-sdk/pi-*` alias are untouched.
3. **Reconcile the documents with the registry.** `README.md` (release-status block + the release-status row + the two install examples + the license line), `docs/spec.md` (the two gated phrases + the prose mention of the core edge), `deploy/runbooks/release-responsibility.md` (train pointer and the version-selection paragraph), `packages/keys/README.md` (the "unpublished 0.5.0 candidate" sentence), a dated correction note at the top of `docs/releases/v0.18.0-handoff.md`, and the `tasks/todos.md` row that asked for exactly this.
4. **Write the release artifacts.** `docs/releases/v0.19.0.md`, `docs/releases/v0.19.0-handoff.md`, and the `CHANGELOG.md` Unreleased → `0.19.0` cut.

Then the full verification set, the push and the PR. The registry action is NOT part of this work-package: the Task Breakdown carries the runbook's publication sequence as unchecked Owner-only items so that the boundary is visible in the same ledger, not so that this plan executes it.

### Trade-offs
| Option | Pros | Cons | Decision |
|--------|------|------|----------|
| SDK `0.19.0` minor | Owner-approved; the input-preparation wire cut is breaking, which the pre-1.0 policy classifies as MINOR; 0.18.0 is taken on the registry | none material | **Chosen** |
| SDK `0.18.1` patch | smaller number | the policy limits PATCH to "corrections with no new public behavior, API, persistence, or security authority"; this train changes the wire, the record schema and the launcher argv | Rejected |
| Reuse `0.18.0` | no bump | the version is published and immutable on npm | Rejected |
| keys `0.6.0` minor | the policy's MINOR covers "any pre-1.0 breaking cut", and `--runtime-entry` is now required argv (+860/−115 across six `packages/keys/src` files since `v0.18.0`) | the Owner approved the SDK minor, not explicitly the keys minor | **Chosen, flagged for Owner confirmation in the PR body** |
| keys `0.5.1` patch | matches the runbook's "small updates default to patch" default | the runbook defers to `docs/spec.md` as the authoritative policy, and a required new flag is not a correction | Rejected |
| Rewrite `v0.18.0-handoff.md` to say "published" | one consistent document | destroys the historical receipt; the drift itself is evidence | Rejected — dated correction note at the top instead |

## Risk Assessment
| Risk | Likelihood | Impact | Mitigation |

| `bun.lock` workspace records left at 0.18.0 | High if done by hand without a gate | High — publishes tarballs whose internal edges name the previous train | `check:release-graph`'s lockfile drift guard is a required check here, and it is the one that fails closed on exactly this |
