## Approach
### Strategy
Prepare one clean 0.6.1 source candidate containing synchronized README and
CHANGELOG. Verify the already-authored package versions and Pi 0.84.2 closure,
then publish only through the repository release driver. A partial npm publish
is resumed at the same versions; no force tag, republish or compatibility shim
is allowed.

### Trade-offs
| Option | Pros | Cons | Decision |
|--------|------|------|----------|
| Publish directly from current main | Fewer commits | Public docs and durable release scope would lag the artifacts | Reject |
| Bump to another version | Avoid stale local-tag collision | Changes the user-authorized release identity | Reject; delete the unpushed stale local tag after proving no remote authority |
| Freeze 0.6.1 from an isolated worktree | Clean source SHA and reproducible artifact evidence | Requires one bounded prep/integration step | Adopt |

### Data Flow
`main candidate SHA -> packed tarballs/release-manifest.json -> npm registry -> registry-readback -> v0.6.1 annotated tag -> GitHub Release`. Production migration, Cloudflare deployment and Salesko consumption are not downstream steps in this flow.

## Risk Assessment
| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Stale local `v0.6.1` blocks or misbinds release | Observed | High | Prove remote tag/Release absent, delete only the stale local tag, recreate annotated tag through the driver at the frozen source SHA. |
| Partial npm publication | Medium | High | Release driver reads existing registry state and publishes only missing packages at the same immutable versions; registry readback must close the full graph. |
| Interactive npm authentication fails in non-TTY | High | Medium | Run the execute step in a PTY; never store or request credentials. |
| Pi pin drifts during release | Low | High | Assert manifest, lockfile, installed package, packaging probe and packed registry closure all equal 0.84.2. |
| Registry success is mistaken for deployment | Medium | High | Report source/registry/tag/Release separately and explicitly leave deploy, production migration and downstream cutover unverified. |

## Promotion Gate

- **Merge/PR unit**: README, CHANGELOG and release workflow evidence for exact 0.6.1 source candidate.
- **Rollback surface**: release documentation and candidate metadata before publication; immutable same-version completion after first registry write.
- **Verification boundary**: build, typecheck, full test, strict workflow, package graph, pack smoke, dry-run release plan, then external registry/tag/Release readback.
- **Review/acceptance boundary**: typed user-waiver receipt for the frozen source candidate plus release-script and registry evidence for publication.
- **High-risk surface**: npm publish, annotated tag push and GitHub Release creation; no production secrets, deploy or migration.
- **Why not checklist row**: publication crosses three external immutable authorities and needs exact-SHA recovery evidence.

## Evidence Contract

- **State/progress path**: this plan, matching contract/review/notes, checks and release manifest.
- **Verification evidence**: repo gates, `check-package-graph`, `pack-and-smoke`, publish driver output, `registry-readback`, git remote tag and GitHub Release readback.
- **Evaluator rubric**: all package versions/integrities/internal edges/imports and Pi 0.84.2 must match the frozen source; no external authority may point at a different SHA.
- **Stop condition**: stop before publish on any dirty source, version/tag collision or failed gate; after the first registry write, stop only on a concrete blocker and preserve exact partial-publication evidence for same-version completion.
- **Rollback surface**: revert unpublished prep; published npm artifacts are immutable and require completion/readback rather than rollback.
