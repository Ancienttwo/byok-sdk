# Resolve keys Pi launcher issues 323–325

## Scope and baseline

Base: `4c3078a7` (`origin/main`). Branch: `claude/keys-issues-323-325`.
Scope: issues #323, #324 and #325 in `@byok-sdk/keys`. All three are in the Pi
provider launcher and the Pi provider projection. No version change, package
publication or merge is part of this slice.

## P1: Boundaries

The keys package owns the credential-custody launcher. The client daemon
spawns the command in `piByokLauncher.command` with reserved flags. The bundled
`bin/pi-provider-launcher.ts` built the OS store itself. It held the only copy
of the profile, model, binding and admission sequence. `index.ts` is the only
public import path. It exported the projection, but no launcher entry.
`pi-provider-projection.ts` is the one place that turns a profile into Pi's
`models.json`. The launcher runs it for admission (`--validate-only`) and for
the launch. The direct `AnthropicMessagesClient` and `OpenAiCompatibleChatClient`
build their URLs with `modelApiUrl(base_url, suffix)`. The catalog documents
this suffix convention: an `anthropic` base ends in `/v1`. Pi runs in the
client package. Its `models.json` loader, its OpenAI and Anthropic clients,
and the durable worker's projection check are outside keys.

## P2: Paths

- #323: client `piByokLauncher.command` → `bin/pi-provider-launcher.ts`
  `run()` → `MacOsKeychainSecretStore({ keychainPath, servicePrefix })` with
  the default `byok-b64-v1:` storage prefix → `#decode` throws
  `KEYCHAIN_SECRET_DECODE_FAILED` for an `aiphabee-b64-v1:` value. The new test
  "fails closed with the default storage marker" shows this exact failure. A
  host could not reuse `run()`, because the package exported no part of it.
- #324: catalog `anthropic` `base_url: https://api.anthropic.com/v1` →
  `buildPiProviderProjection` copied it to `baseUrl` → pi-ai
  `anthropic-messages.js` `new Anthropic({ baseURL: model.baseUrl })` → SDK
  `post('/v1/messages')`. Offline check with the installed
  `@anthropic-ai/sdk@0.129.0` that pi-ai 1.1.0 resolves:
  `https://api.anthropic.com/v1 -> https://api.anthropic.com/v1/v1/messages`
  and `https://api.anthropic.com -> https://api.anthropic.com/v1/messages`.
  The keys client sends `modelApiUrl(base_url, 'messages')`, which is
  `https://api.anthropic.com/v1/messages`.
- #325: profile `auth_mode: 'none'` → projection had no `apiKey` → pi
  `provider-composer.js` composes no configured key → the pinned Pi model
  runtime refused the request with `Provider is not configured:
  byok-sdk-probe` (new client test on unchanged code). pi-ai
  `openai-completions.js` `getClientApiKey` also throws `No API key` when a
  request reaches it without a key. Pi's `docs/models.md` documents a fixed
  dummy `apiKey` for keyless servers such as Ollama. The durable worker
  (`client/src/bin/pi-durable-host.ts`) accepts only `apiKey`
  `byok:durable-ipc` or none. With none, it builds auth `{}` and the same
  pi-ai check fails after the child started.

## P3: Decisions

- #323: export `runPiProviderLauncher(options, { createSecretStore })` and
  `parsePiProviderLauncherOptions` from the package barrel. Move the bundled
  `run()` into the core as this entry, so the bundled executable and a host
  executable share one sequence: exact profile and model, exact binding,
  runtime-entry refusal, projection, custody lock, pending refusal, spawn,
  signal forwarding and cleanup. The bundled executable keeps its flags and
  only builds the platform store. No storage-marker flag is added. A host
  already selects its launcher with `piByokLauncher.command`, and the host
  store can set any option (`storagePrefix`, `account`), including the
  Windows store, which has no storage marker. A flag would be a second way
  to do the same thing. `startPiProvider` stays internal, because it skips
  the profile checks. The barrel is the only public path, so no new
  `package.json` subpath is needed.
- #324: keep one profile URL convention: the direct-client convention that
  the catalog documents. The projection translates it: Pi `baseUrl` is
  `modelApiUrl(base_url, 'messages')` without `/v1/messages`. An endpoint
  without that suffix has no Pi `baseUrl` that reaches it, so the projection
  throws `PROVIDER_URL_INVALID`. Admission now builds the projection for the
  requested runtime entry, so this refusal happens before a task claim. The
  rule is not in the profile schema, because the direct client can still
  serve such an endpoint.
- #325: Pi needs a key. The `pi-rpc` projection sets the fixed non-secret
  `apiKey` `byok-sdk-auth-none` (`PI_AUTH_NONE_API_KEY`), as Pi documents for
  keyless servers. The launcher still reads no credential. The `pi-prepared`
  and `pi-durable` entries require a launcher-delivered key, so the
  projection refuses a keyless profile for them with
  `PROVIDER_PROFILE_INVALID`. For `pi-durable` this replaces a failure in the
  worker after spawn with a typed admission refusal. Durable keyless support
  needs a change to the client durable worker, which is outside this slice.

## Scope limits

The client durable worker still cannot run a keyless profile; keys now refuses
it at admission. The bundled executable gets no storage-option flag. Existing
Anthropic profiles whose `base_url` lacks `/v1` keep working with the direct
client, but fail Pi admission until the operator sets the `/v1` form.
