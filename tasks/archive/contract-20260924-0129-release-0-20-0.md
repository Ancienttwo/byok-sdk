## Why

`@byok-sdk/{client,protocol,core,sdk,server,cloud,cloud-dataplane,implementation-identity,testkit,ui-runtime}` and `byok-sdk` have been published at `0.19.0` on npm since 2026-09-22, and `@byok-sdk/keys` at `0.6.0`; the `v0.19.0` tag at `9408ed7b` is their source. Since then `main` has taken PR #223 (bounded admission, merged as `c61615f8`), a BREAKING input-preparation cut: wire version 5, record schema version 6, the capability token renamed to `agent-input-preparation-v5`, `counted`→`prepared`, `not_counted`→`not_prepared`, `counter_missing` and the counter `kind` removed, and the new typed failures `context_overflow` and `usage_unavailable`, with no dual read. The cut has an operator precondition — drain in-flight input-preparation rows, then upgrade cloud and devices as a pair — because a cross-version in-flight row gets a 422 in either direction and stalls that device's whole mailbox. If this ships wrong — manifests bumped but `bun.lock` left behind — `bun pm pack` resolves `workspace:*` from the lockfile, and keys 0.6.1 would pack a `@byok-sdk/core@0.19.0` edge, which is the one thing its re-release exists to change. If the release notes omit the precondition, an operator upgrades one side with rows in flight and stalls a mailbox.

## Goal

The repository is prepared for the `0.20.0` / keys `0.6.1` train and NOTHING is published. Ten aligned manifests read `0.20.0`, `packages/keys/package.json` reads `0.6.1`, and every `bun.lock` workspace record agrees with its manifest. `README.md` and `docs/spec.md` advertise exactly those two versions, still name `0.19.0` / keys `0.6.0` as the registry's `latest`, and state that `0.20.0` / keys `0.6.1` are prepared and unpublished. `docs/releases/v0.20.0.md` and `docs/releases/v0.20.0-handoff.md` exist; the notes carry every residual risk from PR #223's body (v5-cut precondition, token rename, stale record log lane-off, wire renames, optional counter, Pi terminal may omit `usage`, the two new typed failures, and the two known unrelated CI timing flakes), and the handoff gives the Owner's exact publication commands, including the interactive npm 2FA step in Terminal.app and the tag push. `CHANGELOG.md` gains a `0.20.0 / @byok-sdk/keys 0.6.1` section. The root required checks plus `check:release-graph` and `check:release-pack` pass. No `npm publish`, no `publish.mjs --execute`, no tag, no push, no GitHub Release.

## Falsifier

Direction is wrong if `0.20.0` / keys `0.6.1` are not free on the registry, if keys' source or its workspace edges' code changed since `v0.19.0` (which would make a patch the wrong keys increment), or if some third version authority exists outside the manifests and `bun.lock`. Cheapest proof points, in order: `npm view byok-sdk versions` shows no `0.20.0` and `npm view @byok-sdk/keys versions` shows no `0.6.1`; `git diff --stat v0.19.0 HEAD -- packages/keys packages/core packages/implementation-identity` is empty; then `bun run check:release-graph` and `bun run check:release-pack` after the bump — the pack check installs the eleven real tarballs into an isolated tree, so a missed authority surfaces as a resolution failure or a wrong packed edge.
