## Why

The npm registry now serves the aligned BYOK SDK `0.8.0` train and
`@byok-sdk/keys@0.3.1`, while the root README and CHANGELOG still describe
`0.7.0` / `0.3.0`. Leaving those public projections stale gives downstream
consumers incorrect exact-pin guidance even though the published artifacts and
release tag are already immutable.

## Goal

Update only the root release documentation so it accurately names the published
versions and the two accepted 0.8.0 capability slices, without changing package
bytes, moving the release tag, or claiming deployment.

## Scope

- In scope: root README current-release/install pins, one top-level CHANGELOG
  entry, and this work-package's plan/contract/notes/review/ledger projections.
- Out of scope: product source, tests, manifests, lockfiles, package republish,
  tag rewrite, GitHub deployment, production migration, downstream pinning, and
  secrets.
- Taste constraints: describe registry/source truth precisely; keep
  publication, downstream adoption, and live rollout as separate states.

## Stop Conditions

- Stop and hand back to the parent if the change would require editing a path outside Allowed Paths.
- Stop if an Exit Criteria command cannot be run in this environment.
- Stop if Goal, Scope, or Exit Criteria are internally contradictory.

## Falsifier

This direction is wrong if the release manifest or live npm dist-tags do not
identify the aligned train as `0.8.0` and keys as `0.3.1`, or if the remote
`v0.8.0` tag no longer peels to the frozen release source. The cheapest proof is
the existing release manifest plus exact registry/tag readback before the docs
commit is pushed.

## Root Cause Evidence

Required when Task Profile is `bugfix`; leave as-is otherwise.

- root_cause: one sentence naming file:line/condition (testable, not "a state issue").
- repro: the command or UI path that reproduces the symptom.
- regression_guard: path to a test that fails on the unfixed code and passes after the fix (must also appear under exit_criteria.tests_pass).
