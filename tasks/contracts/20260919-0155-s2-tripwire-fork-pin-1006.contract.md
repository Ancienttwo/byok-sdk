## Why

The S2 release-containment suite (`pi-s2-bundle-resolution.test.ts`) is the worktree's only red: the pinned Pi fork 0.85.1005 eagerly loads `@mariozechner/clipboard` during module-graph load, so the sealed release bundle's startup fires bun auto-install registry GETs outside the release and trips the local registry tripwire. The fix ships inside the fork (build 6: lazy clipboard load + fail-closed `__byok_sdk_helper`), already published as `@byok-sdk/pi-coding-agent@0.85.1006`; the SDK must consume it, and the two guards that hardcode the coding-agent version must stop re-breaking on partial fork releases (coding-agent moves while pi-ai/pi-agent-core hold at 0.85.1005).

## Goal

`packages/client` pins and installs `@byok-sdk/pi-coding-agent@0.85.1006` from the real npm registry (no local overrides), `pi-s2-bundle-resolution.test.ts` is green with `registryAttempts: []`, the full required-check set is green, and the manifest guards derive their expectations from the installed fork's own manifest instead of hardcoded version literals.

## Scope

- In scope: the pin authority pair in `packages/client/package.json` (`byok.piRuntimePin` + the `@earendil-works/pi-coding-agent` alias), the regenerated `bun.lock`, the asset pin metadata in `packages/client/src/adapters/pi/pi-export-assets.source.json` (version/forkBuild only — digests must not move), the single-authority rework in `packages/client/scripts/check-adapters-entry.mjs`, the stale version literal in `packages/client/src/__tests__/pi-rpc-packaging-probe.test.ts`, and the two current-state pin mentions in `docs/spec.md`.

- Taste constraints: no compatibility shims — no dual reads of old/new pins, no 0.85.1005 fallback, fail closed when the installed manifest is missing or not a byok fork.
