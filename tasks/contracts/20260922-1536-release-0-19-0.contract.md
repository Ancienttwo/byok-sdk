## Why

`@byok-sdk/{client,protocol,core,sdk,server,cloud,cloud-dataplane,implementation-identity,testkit}` and `byok-sdk` have been published at `0.18.0` on npm since 2026-09-10, and `@byok-sdk/keys` at `0.5.0`; the git tag `v0.18.0` at `7b26ef5f` (PR #181 merge) is the source they were built from. Three repo documents still call that train an unpublished candidate, so anyone reading them concludes `0.18.0` is still free — and the next publish attempt would hit an immutable, occupied version. Since `v0.18.0`, `main` has taken a BREAKING input-preparation wire cut (request version 4, record version 5, compiler/projection 3) and a BREAKING keys launcher argv (`--runtime-entry` is now required), so a device or Host that upgrades one half without the other fails closed at readiness or at argv parsing. If this ships wrong — manifests bumped but `bun.lock` left behind — `bun pm pack` resolves `workspace:*` from the lockfile and publishes `0.19.0` tarballs whose internal `@byok-sdk/*` edges name `0.18.0`, which is the split registry graph `v0.4.1` actually shipped.

## Goal

The repository is prepared for the `0.19.0` / keys `0.6.0` train and NOTHING is published. Ten aligned manifests read `0.19.0`, `packages/keys/package.json` reads `0.6.0`, and every `bun.lock` workspace record agrees with its manifest. `README.md` and `docs/spec.md` advertise exactly those two versions, and no document in the repo still describes `0.18.0` / keys `0.5.0` as unpublished — each says published 2026-09-10 from `v0.18.0` (`7b26ef5f`) and points at the npm evidence. `docs/releases/v0.19.0.md` and `docs/releases/v0.19.0-handoff.md` exist, every line of them traceable to a merged PR, and they state the record-version-4 availability caveat with the exact on-disk path and its manual disposition. `CHANGELOG.md`'s Unreleased section becomes the `0.19.0` release section. The root required checks plus `check:release-graph` and `check:release-pack` pass. No `npm publish`, no `publish.mjs --execute`, no tag, no GitHub Release.

## Falsifier

Direction is wrong if `0.19.0` is not actually free on the registry, or if the two version authorities this bump assumes are not the real ones — i.e. if some third place (a constant in a script, a generated surface file, a template) also has to be edited for the packed tarballs to be coherent. Cheapest proof point, in order: `npm view byok-sdk versions` shows no `0.19.0` and `npm view @byok-sdk/keys versions` shows no `0.6.0`; then `bun run check:release-graph` and `bun run check:release-pack` after the bump — the pack check installs the eleven real tarballs into an isolated tree and runs the real bins, so a missed third authority surfaces there as a resolution failure rather than as a passing text diff.
