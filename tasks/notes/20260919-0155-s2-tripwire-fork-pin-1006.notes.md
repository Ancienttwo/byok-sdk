## Design Decisions

- Pin bump is two fields in one authority: `byok.piRuntimePin` and the `@earendil-works/pi-coding-agent` dependency alias both name `npm:@byok-sdk/pi-coding-agent@0.85.1006`; `check-adapters-entry.mjs` already asserts the first exactly projects the second, so neither can drift alone.
- `pi-export-assets.source.json` moves only `packageVersion` (0.85.1005→0.85.1006) and `byokFork.forkBuild` (5→6); the 5 asset digests/bytes stay untouched and `build-pi-export-assets.mjs` verifies them against the installed fork during `bun run build` — a digest change there is content drift and a stop, not an edit.
- check-adapters-entry rework: the installed fork's own manifest becomes the single authority — client alias must equal `npm:<installed name>@<installed version>`; the installed manifest must carry `byokFork` (fail closed otherwise) and its name must be the byok fork scope; the client `@earendil-works/pi-ai` dependency must equal the fork's own declared pi-ai edge, replacing the old "pi-ai version == coding-agent version" equality that fork-build-only releases break.
- `pi-rpc-packaging-probe.test.ts` drops only the stale version literal; the fork-scope name stays literal as the anchor, the version travels from `resolvePiRuntimeIdentity()` (the same manifest pin), and the installed-manifest comparison directly below remains the real pin-vs-installed drift check. UpstreamCommit literal kept — upstream base is unchanged and it is a different axis than the fork build.
- Literal sweep classification: docs/spec.md:614,616 claim the current pin → bumped; README.md:23 (Release status, "The bundled Pi runtime is pinned to the SDK's own fork, `@byok-sdk/pi-coding-agent@0.85.1005`") ALSO claimed the current pin → bumped in the gate-fix commit (gap: the dispatched sweep command covered packages/scripts/docs only, so README.md missed the first pass; precedent c1123a40 had updated exactly that line); CHANGELOG.md gained an Unreleased entry for this pin bump (precedent c1123a40 logged the 1005 pin); the CHANGELOG's released-section 1005 mentions are publication history → left; `@earendil-works/pi-ai` alias + `vendor/third-party-manifest.json` + `vendor/THIRD-PARTY.md` hits are the pi-ai pin → kept at 0.85.1005; test fixtures (`prepared-prompt-frame`, `input-preparation`, `control-protocol` ruledRuntime/SUPPORTED_IDENTITY) are opaque self-contained envelopes explicitly decoupled from the installed fork → left; empirical-history comments (`mcp-extension.ts:110`, `pi-prepared-launcher.test.ts:465`) → left; `dist/` hits are build outputs → regenerated.

## Tradeoffs Considered

| Option | Decision | Reason |
|--------|----------|--------|
| Hardcode 0.85.1006 in check-adapters-entry | Derive from installed fork manifest | a literal re-breaks on every partial fork release; the fork's own manifest is the authority that already exists on disk |
| Assert pi-ai version == coding-agent version (old) | Assert client pi-ai edge == fork's declared pi-ai edge | fork build 6 holds pi-ai at 0.85.1005; equality between the two versions is no longer an invariant, projection of the fork's edge is |
| Bump version literal in rpc packaging probe | Derive from pin authority | the test's real content is installed-manifest == client-pin; the version literal adds only staleness |
