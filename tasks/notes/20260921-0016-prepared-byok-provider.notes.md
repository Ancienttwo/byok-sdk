## Design Decisions

### S-1 / S-2 (2026-09-21)

**Falsifier, run first, before any parser was touched.** Composed the session
model the fork actually builds from a `buildPiProviderProjection` `models.json`
(`composeModelProvider` in
`packages/client/node_modules/@earendil-works/pi-coding-agent/dist/core/provider-composer.js`)
for a zai-coding BYOK profile, and compared its key set against what the wire
can carry after this change. Result: the composed session model's DEFINED keys
are exactly `{id, name, api, provider, baseUrl, reasoning, thinkingLevelMap,
input, cost, contextWindow, maxTokens, compat}` — nothing beyond the two fields
this work-package adds. Two further keys exist on the object, `headers` and
`samplingParams` (`provider-composer.js:74-75`), and both are `undefined` for a
projected provider; the session's equality is `canonicalPreparedValue(model)`,
which drops `undefined` entries
(`dist/core/prepared-session-input.js:66-77`), so neither participates.
Control: with the two fields removed the canonical forms differ — today's wire
provably cannot equal the session model, and after this change it can. The
plan's direction holds; no stop was required.

Second fact from the same read: the CURRENTLY PINNED fork already admits
`thinkingLevelMap` and `compat` in `nativeModel()`'s allowed key list
(`@earendil-works/pi-ai/dist/api/openai-completions.js:180-247`) — only
`model.provider !== "zai"` refuses. So the compiler pass-through is testable
today with the built-in provider, and no S-3-gated skip was needed anywhere.

**Restatement, not sharing.** `@byok-sdk/protocol` cannot import
`@byok-sdk/keys` (`scripts/release/check-package-graph.mjs` keeps the
device-local key authority and the dispatch packages disjoint), so the two
shapes are restated in `packages/protocol/src/input-preparation.ts` — the same
pattern `provider-profile.ts`'s `PROVIDER_PROFILE_REF_PATTERN` already uses.
The restatement is pinned by a test that can see both authorities.

**Carriers stay independent.** The two hand parsers were NOT collapsed onto a
shared helper. Each is an independent reader of a durable fact the native
verifier will compare, and a shared helper would be one reader agreeing with
itself; sharing one would also have added two exported functions to the
client's public surface, which the contract's api-surface necessity line
forbids. The parity test is what keeps them from disagreeing, exactly as the
plan's risk table specifies.

### S-3 (2026-09-21) — fork pin → build 7

**File set of the pin bump, derived rather than listed.** The previous bump
(`3f622650`, pi-coding-agent → `0.85.1006`) touched `bun.lock`,
`packages/client/package.json`, `packages/client/scripts/check-adapters-entry.mjs`,
`packages/client/src/__tests__/pi-rpc-packaging-probe.test.ts`,
`packages/client/src/adapters/pi/pi-export-assets.source.json` and `docs/spec.md`.
Two of those were one-time repairs, not recurring pin carriers: that commit
rewrote `check-adapters-entry.mjs` to DERIVE both the coding-agent alias and the
pi-ai edge from the installed fork's own manifest, and rewrote the rpc packaging
probe to anchor the scope name and let the version travel from the pin
authority. Neither carries a literal version any more, so neither moves here.
`scripts/release/pi-runtime-identity.mjs` likewise pins only
`PI_FORK_UPSTREAM_COMMIT` (`d981de12…`, unchanged in build 7) and derives the
version from the manifest.

What actually carries the pin, all four verified by a failing check when left
behind:

| Path | What moved | Authority that refuses drift |
|---|---|---|
| `packages/client/package.json` | `byok.piRuntimePin`, the `@earendil-works/pi-coding-agent` alias (1006 → 1007) and the `@earendil-works/pi-ai` alias (1005 → 1007) | `check-adapters-entry.mjs` (pin projection + installed fork's declared pi-ai edge) |
| `bun.lock` | regenerated by `bun install`, never edited by hand | `bun install --frozen-lockfile` in CI |
| `packages/client/src/adapters/pi/pi-export-assets.source.json` | `packageVersion` → `0.85.1007`, `byokFork.forkBuild` → `7` | `build-pi-export-assets.mjs` (deep-equals the installed `byokFork` and re-digests every export asset; digests unchanged) |
| `packages/client/vendor/third-party-manifest.json` | the `@byok-sdk/pi-ai` entry's `version` → `0.85.1007` | `build-todo-assets.mjs` (`third-party build input drift`) — **outside `allowed_paths`, see Deviations** |

`docs/spec.md:614,616`, `README.md:23,139` and `packages/client/vendor/THIRD-PARTY.md:42`
also state the current pin as prose. No gate reads any of them for the pin
(`check-version-authority.mjs` reads `docs/spec.md` only for the dispatch and
keys package versions), and all three are outside `allowed_paths`; they are
reported, not edited.

**Every installed `pi-ai` copy after `bun install`.** Live tree, by realpath:

| Resolution path | Version | `forkBuild` |
|---|---|---|
| `packages/client/node_modules/@earendil-works/pi-ai` | `0.85.1007` | 7 |
| `packages/client/node_modules/@earendil-works/pi-coding-agent` → its own `node_modules/@earendil-works/pi-ai` | `0.85.1007` | 7 |
| `packages/client/node_modules/@earendil-works/pi-agent-core` (`0.85.1005`) → its own `node_modules/@earendil-works/pi-ai` | `0.85.1005` | 5 |

The third row is NEW with this bump and is a direct consequence of publishing
pi-ai alone: `@byok-sdk/pi-agent-core@0.85.1005` declares
`"@earendil-works/pi-ai": "npm:@byok-sdk/pi-ai@0.85.1005"`, so with the top
level at `0.85.1007` bun can no longer dedupe and the lockfile gains an
`@earendil-works/pi-agent-core/@earendil-works/pi-ai` override. It does not
reach the prepared compile path: `pi-input-preparation.test.ts` walks the static
closure from `dist/core/prepared-session-input.js` and pins its non-fork edges to
exactly `openai` and `partial-json`, so pi-agent-core is not on it. The release
identity gate (`assertInstalledPiRuntime`) constrains the number of installed
`pi-coding-agent` copies, not `pi-ai`.

**Consume seam used, and why.** Two, both offline and both native:

1. `verifyPreparedSessionInput` from the fork's exported
   `@earendil-works/pi-coding-agent/prepared-session-input` subpath — the same
   admission gate the prepared launch calls before any transport. The
   expectation handed to it is the projected wire model re-read by
   `parsePreparedExpectedModel`, not the object given to the compile. Admission
   succeeds for `byok-sdk-zai-coding`; an expectation whose only difference is
   `provider: 'zai'` is refused as `prepared_expectation_mismatch`.
2. `composeModelProvider` from the fork's `dist/core/provider-composer.js`,
   reached by path because it has no `exports` subpath. This makes S-2's ad-hoc
   falsifier a real test: the SESSION model the fork composes from the projected
   `models.json` is canonically equal, under the fork's own
   `canonicalPreparedValue`, to the prepared expected model — the exact
   comparison `prepared_model_drift` makes — and unequal once the provider id
   changes.

The full prepared LAUNCH seam (`pi-prepared-launcher.test.ts`) was deliberately
NOT used for the BYOK case, and this is a finding rather than a preference. The
prepared host builds its `ModelRuntime` with `modelsPath: null`
(`bin/pi-prepared-host.ts`), so the launched process has no provider registry
entry for an opaque `byok-sdk-<ref>` id. Probed against the installed build 7:
`ModelRuntime.getAuth({...provider:'zai'})` resolves the key from `auth.json`,
while `getAuth({...provider:'byok-sdk-zai-coding'})` returns `undefined` even
with a `byok-sdk-zai-coding` credential present in `auth.json`.
`_getRequiredRequestAuth` turns that into `formatNoApiKeyFoundMessage`, which
fires BEFORE `consumePreparedOpenAICompletionsRequest`. So a real BYOK prepared
launch still cannot resolve its credential — a separate gap from the prepared
contract this work-package fixes, and one the Goal's "accepted at consume" will
need closed before the lane is usable end to end. Recorded here, not fixed.

**Falsifier for the new regression.** Run against both installed builds with the
same projected model: build 6 (`node_modules/.bun/@byok-sdk+pi-coding-agent@0.85.1006…`)
refuses `byok-sdk-zai-coding` with `Unsupported explicit model`; build 7 compiles
it, `kind: content_complete`, body 2129 bytes — byte-for-byte the same length and
content as the built-in `zai` compile of the same input. Whitespace-only
(`'   '`) is refused by both. The new cases therefore fail on the previous pin.

### Verification notes

- `packages/protocol/src/__tests__/golden/v1.frozen.json` was regenerated with
  `BYOK_PROTOCOL_UPDATE_GOLDEN=1`. The diff is purely additive (600 inserted
  lines, no `required` list touched), which is the freeze rule's
  additive/optional branch, not a `PROTOCOL_VERSION` bump.
- `api-surface/client.d.ts` and `api-surface/protocol.d.ts` were regenerated.
  The client diff is the two optional fields plus the two interfaces that ARE
  their types; the protocol diff is the same two optional fields wherever the
  model schema is inlined.
- `packages/client/src/__tests__/control-protocol.test.ts` used `compat: {}` as
  its example of "an unsupported model field". That premise is what this
  work-package changes, so the fixture now uses `samplingParams` (a native model
  field this wire still deliberately does not carry) and a separate row covers
  an unknown `compat` key.

## Deviations From Plan Or Spec

- The contract's `allowed_paths` names `docs/api-surface/`, which does not exist
  in this repository. The api-surface goldens this change must regenerate live
  at `api-surface/` (see `scripts/api-surface/check-api-surface.mjs:294`). They
  were regenerated so `check:api-surface` can pass; the contract needs the path
  corrected before the scope gate is re-run.
- S-3 stopped at the contract's own Stop Condition. The fork pin cannot be
  completed inside `allowed_paths`: `packages/client/vendor/third-party-manifest.json`
  is the frozen inventory `bun run build` compares every bundled third-party
  input against, and it keys each input by `name@version`. With pi-ai at
  `0.85.1007` the observed key becomes
  `@byok-sdk/pi-ai@0.85.1007/dist/utils/typebox-helpers.js` while the inventory
  still declares `0.85.1005`, so `build-todo-assets.mjs` fails with
  `third-party build input drift`. The required edit is one line — the version
  string; the file's bytes are identical between the two builds, so the recorded
  `sha256` (`f423ce8a…`) does not move. `packages/client/vendor/` is not in
  `allowed_paths`, so the file was left untouched and the contract needs the path
  before the build can go green. `packages/client/vendor/THIRD-PARTY.md:42`
  (shipped attribution heading `## @byok-sdk/pi-ai@0.85.1005`) is in the same
  directory and becomes stale for the same reason, though no gate reads it.
- `bin/pi-prepared-host.ts`'s model parser is now exported as
  `parsePreparedExpectedModel` so the parity table can reach it. The module is a
  private `#byok-pi-runtime-host` entry, so this adds nothing to the published
  API surface.
