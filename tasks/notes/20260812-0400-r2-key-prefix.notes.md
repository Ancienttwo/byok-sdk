## Design Decisions

- 布局权威留在 core：`tenantObjectKey(tenant, hash, prefix?)` 新增第三个可选参数，`prefix === undefined` 时返回原字符串模板，逐字节不变。
- 前缀是 branded type `ObjectKeyPrefix`，唯一 mint point 是 core 的 `objectKeyPrefix(value)`（对齐 `ContentHash`/`contentHash` 的既有写法）。adapter 拿不到未校验的前缀去拼 key。
- 校验只在构造期：`R2CloudBlobStore` / `R2ObjectMaintenanceStore` 构造函数里各调一次 `resolveKeyPrefix`，字段 `#keyPrefix` 是 `readonly`，无 setter。
- 错误码走 core 的 `object_key_prefix_invalid`（`errors.ts` 文档明说加 code 是 additive change），不新开 `R2BlobStoreError` code：key 布局是 core 的契约，adapter 再判一次就是第二个权威。
- 维护面 `R2ObjectMaintenanceStore` 同样接前缀（`R2ObjectMaintenanceOptions` 是 `Omit<R2BlobStoreOptions,…>`，自动带上），否则 HEAD/DELETE 会打在没有前缀的 key 上。

## Deviations From Plan Or Spec

- 派发口径写的是「默认（缺省/空）保持现布局」，但 contract 的 Acceptance Notes 与 exit 测试清单要求「空串前缀构造期抛错」。按后者实现：`keyPrefix` 缺省 = 现布局；`keyPrefix: ''` = 抛 `object_key_prefix_invalid`。理由是空串正是环境变量没设的样子，静默当默认值等于替部署决定对象放在哪。
- `R2ObjectMaintenanceStore.listTenantObjects` 的 ListObjectsV2 prefix 仍是既有的 `${tenant}/sha256/`，未接 keyPrefix。这与 `tenantObjectKey` 的 `tenants/<t>/objects/sha256/` 布局本来就对不上（main 上既有问题，`r2-blobs.test.ts` 里有断言固定了现行为），无论有没有前缀都匹配不到任何 key。属本 slice 之外的既有缺陷，只报告不修。

## Tradeoffs Considered

| Option | Decision | Reason |
|--------|----------|--------|
| 新旧前缀 dual-read | 拒绝 | steady-state 兼容路径，同一对象两套布局同时权威 |
| 前缀任意字符串 | 拒绝 | 需要百分号编码的值会让同一对象有两个拼法；空段让 `a//b` 与 `a/b` 在存储端同名、在配置里不同名 |
| 前缀校验放在 cloud-postgres | 拒绝 | 布局是 core 的契约，adapter 自带一份规则就是第二个权威 |
| `keyPrefix: ''` 视同缺省 | 拒绝 | 见上方 Deviations |
