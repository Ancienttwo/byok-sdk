**`typebox` 1.3.7 → 1.3.27 — a decision this slice had to make.** Not in the
dispatch. The 0.86 fork pins `typebox@1.3.27`; the client's own direct edge was
the exact `1.3.7` the 0.85 fork also pinned, so the two used to dedupe. After
the pin bump they no longer did, and the sealed todo bundle's frozen inventory
grew by 370 rows because the bundle imported typebox TWICE — once through the
vendored `rpiv-todo` schema builder (1.3.7) and once through `pi-ai`'s
`typebox-helpers` (1.3.27). Two registries for one set of values, with
`Type.Unsafe` objects from one crossing into `Type.Object` from the other.
Aligning the direct edge restores the pre-existing one-copy invariant instead of
shipping the two-copy state; the inventory's typebox rows were regenerated from
the installed package (664 rows) and its LICENSE is byte-identical to 1.3.7's.
`pi-sealed-factory-closure.test.ts`'s exact-version pin moved with it.

**`runtime_contract_superseded` — the exact producing path.**
`daemon/input-preparation-service.ts`'s `inputPreparationReadinessReasons`
compares `record.binding.runtime.compilerVersion` (observed from the verified
install at preparation time, frozen onto the record) against
`SUPPORTED_PREPARED_COMPILER_VERSION`. This is the readiness-level outcome the
Amendment asked for. It is a DIFFERENT gate from the store's own
`INPUT_PREPARATION_RECORD_VERSION` check, which refuses an older RECORD shape
at log replay with `InputPreparationUnsupportedRecordVersionError` before
readiness is ever computed; both are fail-closed and neither migrates anything.
For the 0.85 → 0.86 step both axes move, so a real 0.85 record is caught by the
store first; the readiness reason is reachable and tested for a record at the
current record schema whose binding declares another compiler contract
(`input-preparation.test.ts`, two cases).

**Frozen golden regenerated, deliberately, and it is NOT purely additive.**
`options.toolChoice` loses `required` and `projection.version` is retyped 2 → 3,
both of which docs/protocol.md's freeze rule calls breaking. The documented
procedure was followed by precedent rather than by bumping `PROTOCOL_VERSION`:
`d302b12a` made exactly this call for exactly this surface, with the reasoning
"the input-preparation wire surface is an unreleased candidate contract added
after the freeze — no released version carries it, and 0.18.0 is itself an
unpublished release candidate". README still records 0.17.0 as the published
release and 0.18.0 as an unpublished candidate, so the precedent's premise
holds. `PROTOCOL_VERSION` stays 1. Flagged for the gate.
