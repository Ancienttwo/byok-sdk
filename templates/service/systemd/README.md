# Service recipe: Linux systemd user unit

Run a BYOK SDK-based daemon as a background Linux service using a
[systemd](https://www.freedesktop.org/software/systemd/man/systemd.html)
**user unit** (`~/.config/systemd/user/`) — no root required, matching
macOS's per-user LaunchAgent and Windows' per-machine Windows Service each
doing the idiomatic "run this in the background for me" thing for their own
platform. This is a **reference recipe**: `@byok-sdk/client` is an npm library
(Decision-6 boundary — see the repo root docs).

## Quick start

```bash
byok-agent install --config /path/to/your/config.json
```

This writes the launcher `~/.byok/<productId>/service/<productId>.launcher.sh`
(which `exec`s `node <byok-agent entry> start --config <absolute path> --service`)
and the unit `~/.config/systemd/user/<productId>.service`, which runs only that
launcher. It then runs `systemctl --user daemon-reload`,
`systemctl --user enable` (survives logout/reboot) and
`systemctl --user restart` (starts it, or moves a running one onto the
rewritten launcher). Check on it any time:

```bash
byok-agent service-status --config /path/to/your/config.json
byok-agent service-stop    --config /path/to/your/config.json   # stop without uninstalling
byok-agent service-start   --config /path/to/your/config.json   # start again
byok-agent uninstall       --config /path/to/your/config.json   # stop + remove entirely
```

`--name <svc>` overrides the derived unit name (default: your config's
`productId`). See `packages/client/src/bin/commands/service.ts` for every
flag.

### Headless boxes: enable lingering first

A systemd **user** instance normally only runs while you're logged in. On a
headless server, enable lingering once (as root, or via sudo) so your user
unit survives logout and starts on boot:

```bash
sudo loginctl enable-linger "$USER"
```

Without this, `systemctl --user ...` may fail outright with something like
`Failed to connect to bus: No such file or directory` — that is an
environmental precondition, not something this SDK can paper over.

## What gets generated

A unit file along these lines (see
`packages/client/src/lifecycle/systemd.ts`'s `generateSystemdUnit` for the
exact, unit-tested template):

```ini
# byok-sdk-service-unit: generated by @byok-sdk/client; repair() reverts local edits
[Unit]
Description=Your Product Name

[Service]
Type=simple
ExecStart="/home/you/.byok/<productId>/service/<productId>.launcher.sh"
WorkingDirectory=/home/you
Restart=always
RestartPreventExitStatus=0
RestartSec=10
StandardOutput=append:/home/you/.byok/<productId>/service-logs/service-stdout.log
StandardError=append:/home/you/.byok/<productId>/service-logs/service-stderr.log

[Install]
WantedBy=default.target
```

- **The launcher** (#1097): `ExecStart=` names only
  `<storeDir>/service/<name>.launcher.sh`, which `exec`s
  `/path/to/node /path/to/byok-agent.js start --config <path> --service`. A
  new Node or a moved binary rewrites the launcher, never the unit. The
  marker comment lets `service-status` classify the unit as `exact`,
  `repairable` or `foreign`; the SDK never changes a unit without it.
- **`Restart=always` + `RestartPreventExitStatus=0` + `RestartSec=10`** is the
  exit-code contract: any exit but 0 restarts. It is delegated entirely to
  systemd — the SDK never runs its own in-process supervisor.
- **`--service`** (added by `byok-agent install`, or by
  `nodeAgentProgram({ service: true })`; the lifecycle itself never changes
  a program's arguments) makes `byok-agent
  start` capture your login shell's environment once (passwd shell, `-ilc`,
  10 s / 1 MiB caps) before it loads its config, so `claude`/`codex` and rc
  settings on your PATH reach the service. If the capture fails (the rc hangs, prints
  more than 1 MiB or exits non-zero; the shell is not sh/bash/zsh/ksh/dash), the daemon starts with systemd's inherited
  environment and `status`/`doctor` report `environment: unavailable
  code=<code>`. Reinstall an existing service to pick the flag up.
- The `ExecStart=` path is double-quoted (with embedded quotes/backslashes
  escaped) unconditionally, so a store path containing spaces is never
  misparsed.
- `StandardOutput`/`StandardError` are pointed at append-mode files under
  `~/.byok/<productId>/service-logs/` that hold only output from before the
  daemon's own rotated `daemon.log` opens. systemd's own native mechanism — the
  journal — still works unconditionally alongside this:
  `journalctl --user -u <productId> -f`.

## What the CLI does under the hood

| CLI command | systemctl calls |
|---|---|
| `install` | write launcher + unit file -> `daemon-reload` -> `enable` -> `restart` |
| `uninstall` | `disable --now` (tolerates already-absent; a **real** failure aborts and leaves the unit file intact so the service is never orphaned) -> remove unit file -> `daemon-reload` (best-effort) |
| `service-start` | `start` |
| `service-stop` | `stop` (best-effort) |
| `service-status` | `is-active` (exit code + stdout drive `running`); the unit file's presence on disk drives `installed` |

## Talking to the running service (M4 Phase 2: the control socket)

Once installed, the service is reachable through a local control socket at
`~/.byok/<productId>/control.sock` (a Unix domain socket; falls back to a
short, deterministic path under `$TMPDIR` if the natural one would be too
long), authenticated by a per-run token at `~/.byok/<productId>/control.token`
(mode 0600 — never transmitted over the socket itself, only used to compute
an HMAC proof each side shows the other). `byok-agent status`, `tasks
--follow`, `unpair`, `approve`, and `reject` all talk to the running service
through this socket automatically — no separate flag needed — falling back
to a persisted-state view (or, for `unpair`, the OS-service-state check
described above) whenever the socket isn't reachable (the service isn't
running, or predates this feature).

## Verifying it yourself

Unit-test the exact generated content
(`packages/client/src/__tests__/lifecycle-systemd.test.ts`) run on every
push regardless of host OS. If you have systemd tooling available locally
(any Linux desktop, or WSL with systemd enabled), you can additionally lint
a generated unit with systemd's own validator:

```bash
systemd-analyze verify /path/to/generated-unit.service
```

For native lifecycle verification, build the client and run:

```bash
bun run build
node templates/service/systemd/smoke-test.mjs
```

The smoke requires Linux with a working systemd **user manager**, a reachable
user D-Bus, `systemctl`, and the built `packages/client/dist/index.js`.
Set `XDG_RUNTIME_DIR=/run/user/$(id -u)` and
`DBUS_SESSION_BUS_ADDRESS=unix:path=$XDG_RUNTIME_DIR/bus` for that user.
Missing preconditions fail the command; they never skip it. A container
without systemd cannot provide this proof.

On a disposable GitHub-hosted Ubuntu runner, provision the user manager
explicitly in a workflow step before running the smoke (the step uses the
runner's existing user, not root):

```yaml
- name: Provision systemd user manager
  shell: bash
  run: |
    set -euo pipefail
    sudo apt-get update
    sudo apt-get install -y dbus-user-session
    uid="$(id -u)"
    sudo loginctl enable-linger "$(id -un)"
    sudo systemctl start "user@${uid}.service"
    export XDG_RUNTIME_DIR="/run/user/${uid}"
    export DBUS_SESSION_BUS_ADDRESS="unix:path=${XDG_RUNTIME_DIR}/bus"
    systemctl --user start dbus.socket
    systemctl --user show-environment >/dev/null
    echo "XDG_RUNTIME_DIR=${XDG_RUNTIME_DIR}" >> "$GITHUB_ENV"
    echo "DBUS_SESSION_BUS_ADDRESS=${DBUS_SESSION_BUS_ADDRESS}" >> "$GITHUB_ENV"
- name: Native systemd lifecycle smoke
  run: node templates/service/systemd/smoke-test.mjs
```

Checkout, Bun/dependency setup, and `bun run build` must precede the smoke.
Provisioning is unconditional and fails on errors; it does not substitute a
private D-Bus session, mock manager, system service, or another supervisor.
Lingering remains enabled only for this disposable runner's lifetime.

The fixture is a harmless Node process independent of pairing and daemon
network access. The smoke uses the public `createServiceLifecycle` API with
`program`, `storeDir`, and `owner`; proves `inspect`, install, stop, start,
unit/launcher repair, and uninstall; and checks real `systemctl` state,
enabled registration, MainPID, `/proc` command line, fixture readiness, and
process exit. Its store path contains spaces to exercise the stable launcher.
Only observation polling waits for Node readiness; lifecycle mutations are
never retried. A UUID unit name isolates every run. Cleanup stops/disables
only that unit, removes its unit and temporary files, and reports any failure
as a failed smoke. If stopping cannot be confirmed, control files remain for
diagnosis and the command fails. Local macOS execution cannot establish Linux
acceptance; retain the successful hosted Ubuntu run as the native evidence.

## What's explicitly out of scope

Per Decision-6, this SDK ships **only the npm library**. This recipe (and
the SDK) do not cover, and never will: packaging/distribution of your own
launcher, or auto-update. Those are your product's responsibility.
