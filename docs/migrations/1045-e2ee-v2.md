# Sealed payload v2: Agent messages and memory projections

0.33.0 adds two sealed categories to the hosted wire (#1045):
`agent-message` seals the body of `agent.message.publish`, and
`memory-projection` seals the hosted memory projection snapshot and the
memory evidence of a task terminal. They use the v1 suite, keys, member chain
and binding rules ([protocol §2.5](../protocol.md#25-sealed-payload-v1-654-gated-addition)).
Nothing is sealed unless the Host asks for it: a task seals a category only
when its offer's `sealing.categories` names it, and a projection is sealed
only under a grant with `sealing`. A Host that asks for neither sees the
0.32.0 behavior, apart from the type changes below.

The design and threat model are in
[docs/plans/2026-10-28-1045-e2ee-v2.md](../plans/2026-10-28-1045-e2ee-v2.md).
What a sealed task still shows the Host is in
[security.md, Sealed tasks](../security.md#sealed-tasks).

## Who has to do something

| Host | Action |
| --- | --- |
| Hosted cloud, no v2 categories | Update the type changes below. Postgres runs migration 0037. |
| Hosted cloud, sealed Agent messages | Register `agentMessage.consumeSealed`, and open messages on a member. |
| Hosted cloud, sealed memory projections | Issue grants with `sealing`, and return it from the authorizer. |
| Custom `AgentMemoryProjectionStore` | Handle the sealed commit input. |
| Embedded `@byok-sdk/server` | Nothing: it dispatches no sealed task and issues no sealing grant. |
| Daemon | Upgrade. It advertises `sealed-payload-v2` with `sealed-payload-v1`. |

## Capabilities

The daemon advertises `sealed-payload-v2` exactly when it advertises
`sealed-payload-v1`. The cloud advertises it on `GET /byok/events`. A Host can
offer a task whose `sealing.categories` names `agent-message` or
`memory-projection` only to a device that advertises the flag;
`requiredReceiverCapabilities` returns it. `memory-projection` is legal only
together with `task-output`, because its evidence rides on the terminal.

A daemon declines an offer that seals `agent-message` with
`sealing_policy_mismatch` when the server does not advertise the flags a
sealed publish needs. It needs a sealing key before such a task runs, as for
`task-output`.

## Sealed Agent messages

`ByokCloudOptions.agentMessage` is an `AgentMessageConsumers`:

```ts
agentMessage: {
  consume: async ({ payload }) => decidePlaintext(payload),       // plaintext body
  consumeSealed: async ({ payload }) => decideSealed(payload),    // payload.sealed only
}
```

Both are optional. `consumeSealed` receives the sealed member; the cloud
never sees the body, its `contentHash` or its `byteCount`. A product that must
read the body opens it on a member with `openSealedContent` and the binding:
family `agent.message.publish`, direction `daemon-to-server`, identity
`{ taskId, messageId, cursor }`, the task's categories. A product whose
backend must read message bodies server-side keeps `agent-message` out of
`sealing`.

- A submission that seals `agent-message` and carries `messageEgress` is
  refused with `agent_message_sealed_consumer_missing` before any write while
  `consumeSealed` is absent. `submitAgentExecution` asks for `consume` only
  when the task does not seal its message.
- The task's frozen sealing decides the form of its message: a sealed publish
  to a task that does not seal `agent-message` is refused with
  `sealed_payload_unsupported`, and a plaintext publish to one that does with
  `sealed_output_required`.
- A sealed message above the inline frame names a ciphertext blob, which the
  task holds while it lives.
- The disposition names a sealed message by `contentMac`, a plaintext one by
  `contentHash`. `readTaskAgentMessage` and `readAgentMessageDisposition`
  return either form, as in 0.32.0.
- `handleInboundEnvelope` takes the `AgentMessageConsumers` object in place of
  the `consume` function.

The daemon seals a message once, when the draft enters its outbox, and every
retry sends those bytes. Without a sealing key the message tool fails and
nothing is sent.

## Sealed memory projections

A Host that wants the projection sealed creates an Agent memory scope on the
member chain whose policy is exactly `['memory-projection']`, separate from
task scopes, and sends the device its key package as for any scope. It then
issues the device an `AgentMemoryProjectionGrant` with
`sealing: { scopeId, epoch }`, and its `AgentMemoryProjectionAuthorizer`
returns the same `sealing` on the authorized result:

```ts
authorize: async (input) => ({ outcome: 'authorized', sealing: { scopeId, epoch } })
```

- One writer epoch has one form. To change the sealing, issue a grant at a
  higher writer epoch.
- The cloud refuses a snapshot whose form does not match the grant (plaintext
  under `sealing`, sealed without it, or sealed under another scope or epoch)
  with 409 `agent_memory_projection_sealing_mismatch`.
- The sealed snapshot is inline only: its opened content is
  `{"redactedBytes": …}`, at most 262,140 bytes. Without a usable key, or for
  a larger snapshot, the device appends no mutation.
- The receipt of a sealed snapshot carries `contentMac`, `paddedLength` and
  `metering.acceptedPaddedBytes`, and no `redactedHash` or
  `redactedByteCount`.
- A task redaction's scope shred does not reach the Agent memory scope.
  `eraseAgentMemoryProjection` and its epoch fence work as before.

### Custom projection stores

`AgentMemoryProjectionCommitInput` is a union. A plaintext input carries the
decoded `redactedBytes` to hash, as before. A sealed input carries
`mutation.sealed` and no bytes: store the member as received, meter its
`paddedLength`, and treat a replay at the same writer epoch and source
sequence as `idempotent` only when its form, `contentMac` and `paddedLength`
match. `commit` returns the receipt union.

### Postgres migration 0037

`deploy/sql/0037_agent_memory_projection_sealed.sql` adds
`agent_memory_projection_head.sealed_member jsonb` and
`agent_memory_projection_metering_receipt.content_mac` and `.padded_length`,
drops NOT NULL on the redacted columns, and checks that each row holds
exactly one form. Every existing row is plaintext, so it rewrites no data and
needs no backfill. Run it with the other 0.33.0 migrations before the new
code serves requests; it is forward-only.

## Memory evidence on the terminal

When a task's `sealing` names `memory-projection`, the sealed `task.complete`,
`task.fail` and `task.cancelled` carry `agentHomeMemoryChange` inside the
`task-output` ciphertext, and the Host refuses a plaintext terminal that
carries it. A member reads the changed memory paths after opening the
terminal. Without the category, the terminal is unchanged.

## What stays plaintext

Agent message drafts, `agent.egress.reliable` payloads, truth `memory`
records, input preparation and the routing metadata listed in
[security.md](../security.md#sealed-tasks) are not sealed by v2.
