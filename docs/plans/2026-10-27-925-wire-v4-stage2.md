# #925 阶段 2 设计稿：wire v4 的 offer 合并与 sealed 属性化

状态：设计稿。owner 2026-10-27 按推荐通过 Q9 的 O1–O10，O6 选 (b)：一次性 receipt 迁移由阶段 1 的 PR 实现，阶段 2 补类型改名的映射（[#925 的评论](https://github.com/Ancienttwo/byok-sdk/issues/925#issuecomment-6422184243)）。实施起点是阶段 1 合入之后的 `main`。
事实的行号取自 `ccff1eee`（`packages/` 与 `examples/` 和 `1be38893` 相同，#1011 只改了文档）。没核实的标 `[inferred]` 或 `[unverified]`。

## 结论

- v4 的 `EnvelopeSchema` 从 47 个分支收到 28 个。阶段 1 删 5 个（`conn.ack`、legacy `task.offer`、`task.offer_with_toolsets` 及其两个 sealed 孪生），阶段 2 再删 14 个：4 个 Agent offer 合并成一个 `task.offer`，11 个剩下的 `_sealed` 类型并回各自的明文类型。
- 合并后的 `task.offer` 是两个 strict 分支的联合：明文分支（带 `NO_SEALED_MEMBER`）和 sealed 分支（带 `sealing`）。fresh/resume 改为必填的 `session` 判别联合，prepared 由 `preparation` 字段决定。原来由类型表达的差异变成 `task.offer` 上的 13 行手写 `WIRE_ADDITIONS`，加 1 行由 split table 生成的 `sealing` 行。每个 (字段, 值, capability) 只出现一次。`requiredReceiverCapabilities` 的算法不变，只换表。
- sealed 的判别字段分两种：offer 用 `sealing`，`task.steer` 和 7 个 daemon→server 类型用 `sealed`。只加密 task-output 的任务，offer 带 `sealing` 和明文 `instruction`，没有 `sealed` 成员（`sealed-payload.ts:296-315`），所以 #925 正文里「由 `sealed` 字段区分」只对 steer 和输出类型成立。
- `SEALED_SPLIT_TABLE` 改为按明文类型做 key，删掉 `plainType`。AAD 的消息族就是 wire `type`。输出类型、`task.steer`、`routine.template` 的消息族不变，E1c 的 `fieldPath` 规则不变。只有 sealed offer 的消息族从三个旧类型名变成 `task.offer`。「prepared 不能 sealed」写进表：`task.offer` 条目的 `forbidden` 包含 `preparation`。
- 门的取舍：v4.0 内部没有版本差，v3 daemon 在 `v` 上就拒绝了。类型门只防版本差，配置差一直靠发送方准入加 daemon 自查。建议保持整个 offer payload `.strict()`（未知键走 `connection-manager.ts:243` 的停游标），并给 daemon 加一条通用自查：`requiredReceiverCapabilities('task.offer', payload)` 必须是自己声明的 flag 的子集，否则非重试 decline。
- 「只通过 SDK API 入队的 Host 不受影响」不成立。`TaskOfferReadback.type`、`DeviceTerminal.envelope.type`、所有 `Enqueue*Input` 的 payload 类型名都会变。只用 `@byok-sdk/server` 的 `dispatch()` 的 Host 只需要重新编译。AiphaBee 要重新 vendor host-execution-core，还要把 K4 ledger 里的 v3 冻结输入清空或迁移。
- 最大的风险不在阶段 2 本身：升到 v4 以后，v3 时期落盘的 offer receipt 和终态 receipt 都读不出来，`tasks.get`/`tasks.list` 碰到旧任务会抛错。阶段 1 的版本号已经让终态 receipt 失效，阶段 2 的类型改名又让 offer receipt 失效。K7 没有先例可循，需要 owner 决定（见 Q9 的 O6）。
- 实施：阶段 2 在阶段 1 合入后单独一个 PR，按包分 4 个 commit，0.31.0 之前两个 PR 都要合入，中间不发版。车道 A（#1013）先合。

## Q2 合并后的 `task.offer`

### payload 形状

```ts
// 两种都要的字段
const OfferCommon = {
  agentRef: AgentRefSchema,                                   // 必填：阶段 1 之后所有 offer 都绑定 Agent
  session: z.discriminatedUnion('mode', [
    z.object({ mode: z.literal('resume'), sessionRef: z.string().min(1).max(512) }).strict(),
    z.object({ mode: z.literal('fresh') }).strict(),
  ]),                                                          // 必填
  preparation: InputPreparationOfferBindingSchema.optional(),
  agentMemory: AgentMemorySelectionSchema.optional(),
  homeAccess: AgentHomeAccessSchema.optional(),
  requiredToolsets: RequiredToolsetsSchema.optional(),
  runtime: RuntimeIdSchema.optional(),
  harnessId: HarnessIdSchema.optional(),
  dispatchSelection: DispatchSelectionSchema.optional(),
  terminalProjection: TerminalProjectionSelectionSchema.optional(),
  limits: z.object({ maxDurationMs: …, maxTokens: … }).strict().optional(),   // v4 改为 strict
  egressPolicy: AgentEgressPolicySchema.optional(),
  messageEgress: AgentMessageEgressRequirementSchema.optional(),
};

// 明文分支
TaskOfferPlainPayloadSchema = z.object({
  ...NO_SEALED_MEMBER,                    // sealing、sealed 都是 never
  routineRef: z.never().optional(),
  instruction: z.union([z.string(), InstructionBlobRefSchema]).optional(),
  ...OfferCommon,
}).strict().superRefine(offerRule);

// sealed 分支
TaskOfferSealedPayloadSchema = z.object({
  instruction: z.union([z.string(), InstructionBlobRefSchema]).optional(),
  sealing: TaskSealingSchema,             // 判别字段
  sealed: SealedTaskInputSchema.optional(),
  routineRef: RoutineRefSchema.optional(),
  ...OfferCommon,
  preparation: z.never().optional(),      // prepared 不能 sealed，来自 split table 的 forbidden
}).strict().superRefine((p, ctx) => { offerRule(p, ctx); sealedOfferRule(p, ctx); });

TaskOfferPayloadSchema = z.union([TaskOfferPlainPayloadSchema, TaskOfferSealedPayloadSchema]);
```

`offerRule` 把现在由类型表达的跨字段约束写成校验规则：

| 规则 | 现在的出处 | v4 |
| --- | --- | --- |
| prepared 没有 `instruction` | `messages.ts:462-466`（omit） | `preparation` ⇒ `instruction` 缺省 |
| 非 prepared 必须有 instruction | 各 offer 的 `instruction` 必填 | ¬`preparation` 且明文分支 ⇒ `instruction` 必填；sealed 分支交给 `sealedOfferRule` |
| prepared 永不 resume | `messages.ts:455-456` | `preparation` ⇒ `session.mode === 'fresh'` |
| prepared 的 `agentMemory` 必填，且只能是 prepared 模式 | `messages.ts:469` | `preparation` ⇒ `agentMemory ∈ PreparedAgentMemoryModeSchema` |
| prepared、fresh 必有 `egressPolicy` | `messages.ts:436`、`:470` | (`preparation` 或 `session.mode === 'fresh'`) ⇒ `egressPolicy` 必填 |
| `messageEgress` 只出现在 egress offer 上 | `messages.ts:422`、`:437`、`:471` | `messageEgress` ⇒ `egressPolicy` |
| 只有 fresh 的 sealed offer 带 `routineRef` | `messages.ts:1435-1442` | `routineRef` ⇒ `session.mode === 'fresh'` |

收紧了两处，都只在 major 里允许：resume 的 `sessionRef` 统一为 `min(1).max(512)`（`task.offer_for_agent` 原来是不限长度的 `z.string()`，`messages.ts:403`）；「fresh 且没有 egress」不再能表达（原来是不带 `sessionRef` 的 `task.offer_for_agent`）。SDK 的入队路径都不产生这两种 payload：cloud 的 resume lane 要求 `sessionRef` 非空（`cloud.ts:543-551`），server 的 Agent dispatch 也要求（`server/src/index.ts:584-592`）。

`session` 必填，就是为了消掉 fresh 孪生类型要防的歧义：缺了 resume 引用的 offer 不会被当作 fresh 执行（`messages.ts:426-431`）。

#925 正文列的 4 个字段：

- `agentRef` → `agent-home-contract`。`agentRef` 必填，字段门和类型门效果一样。建议写成类型行（#1），免得读者以为 `agentRef` 是可选的。
- `egressPolicy` → `agent-egress-policy` 和 `agent-egress-reliable-ack` 两行（#9、#10）。
- `session.mode: 'fresh'` → `agent-egress-fresh-session` 值门（#12）。prepared 必须 fresh，原来 prepared 上的那一行（`:129`）自动由它覆盖。
- `preparation` → `agent-input-preparation-v9`（#13）。

`harnessId` 在 v3 的 Agent offer 上没有门（`AGENT_OFFER_FIELDS` 里没有，`:59-64`；`custom-harness` 只门控 legacy offer，`:103-104`）。阶段 2 不加，行为不变。

### `requiredReceiverCapabilities` 怎么算

函数（`wire-additions.ts:171-187`）不用改。它已经支持带点的嵌套字段和值比较，`session.mode = fresh` 直接可用（`:177-182`）。两个分支共用 `task.offer` 的行，字段不出现就不触发。原来 `sealedRows` 要做的事（sealed 类型继承明文类型的行，跳过移走或丢弃的字段，`:81-97`）因此自然成立：移走的 `instruction` 没有门，sealed 分支上不存在的字段不会触发。

和 v3 的差别只有一处：prepared offer 现在还要 `agent-memory-selection`（#6），v3 没有这一行（`wire-additions.ts:54-57` 的注释）。daemon 在 `agentHomeConfigured` 时一起声明 `agent-home-contract` 和 `agent-memory-selection`（`client/src/daemon/create-daemon/support.ts:185-190`），能收 prepared offer 的设备一定有 `agent-home-contract`，所以准入结果不变。PR 用一条跨版本测试证明等价：对 v3 corpus 的每个 offer 行，用 `byok-protocol-previous`（指向 0.30.2，导出了 `requiredReceiverCapabilities`，`protocol/src/index.ts:5`）算 v3 的集合，用当前代码对映射后的 v4 payload 算 v4 的集合，两者相等，prepared 行多出的 `agent-memory-selection` 单独断言。

## Q3 sealed 改成属性

### 判别和 schema

每个可加密的类型，payload 都是两个分支的联合：明文分支带 `NO_SEALED_MEMBER`，sealed 分支 strict。判别字段写在 split table 里：

| 类型 | 判别字段 | 门 |
| --- | --- | --- |
| `task.offer` | `sealing` | device 的 `sealed-payload-v1` |
| `task.steer` | `sealed` | device 的 `sealed-payload-v1` |
| `task.complete`、`task.fail`、`task.decline`、`task.cancelled`、`task.progress`、`task.artifact`、`task.await_approval` | `sealed` | server 的 `sealed-payload-v1` |

- `type` 保持明文，cloud 照常按 `type` 推进生命周期。
- 明文分支保留 `NO_SEALED_MEMBER`（`messages.ts:299-307`）。它存在的理由在 v4 仍然成立：输出类型的明文 schema 是宽松的（例如 `TaskCompletePayloadSchema`，`messages.ts:1253`），不显式拒绝的话 `sealed` 会被剥掉，sealed 内容就会被当作明文接受。offer 的明文分支再加 `routineRef: never`。
- 联合的顺序是明文在前。输入里出现判别字段时，明文分支一定失败，然后走 sealed 分支。zod 4 没有「按字段是否存在」的判别联合，用 `z.union` 即可；错误信息会列出两个分支的 issue，可以接受。TS 侧用 `payload.sealed !== undefined`（offer 用 `payload.sealing !== undefined`）收窄，因为明文分支的这两个字段类型是 `never`。
- 明文和 sealed 的差异仍由 split table 决定：sealed 分支 = 明文字段去掉 `moved` 和 `forbidden`，再加 `sealed`（offer 加 `sealing`、`sealed?`、`routineRef?`）。现有的 sealed schema 构造（`messages.ts:1407-1511`）几乎照搬，只是不再注册成独立类型。

### `sealed-split-table.ts`

改动：

- key 从 sealed 类型名改成明文类型名，删掉 `plainType`（`sealed-split-table.ts:32`）。新增 `marker: 'sealing' | 'sealed'`。
- 5 个 offer 条目合成一个 `task.offer` 条目：`category: 'task-input'`、`identity: []`、`moved: ['instruction']`、`forbidden: ['preparation']`、`marker: 'sealing'`。digests 取原来最大的 `EGRESS_OFFER_DIGESTS`（`:67-73`），再加 `preparation.requestDigest`、`preparation.artifactDigest` 为 `forbidden`。现有的完整性测试（`:48-51` 描述的那条 schema 测试）会要求列全。
- 「prepared 不能 sealed」从一条测试断言（`sealed-payload.test.ts:193`）变成表里的 `forbidden: ['preparation']`，schema 和门都从这里读。
- 删除 `SealedMessageType`、`isSealedMessageType`（`:146-150`）。新增 `SealableMessageType` 和 `isSealedPayload(type, payload)`（读 `marker`）。`isSealedTaskPlainOutput`（`sealed-payload.ts:81-95`）改用 key。
- `wire-additions.ts` 的 `sealedRows` 变成：对表里每个条目生成一行 `{ field: marker, capability: 'sealed-payload-v1' }`，对 server 方向且不是 `inlineOnly` 的条目再生成一行 `sealed.ciphertextRef → sealed-output-ciphertext-ref`。表里有 9 个条目（`task.offer`、`task.steer` 和 7 个输出类型），所以生成 9 行判别字段门（其中 `task.offer` 的就是 Q2 的 #14，不再手写）和 5 行 `ciphertextRef` 门（complete、fail、decline、cancelled、artifact）。4 个 sealed decline 值门（`:98-99`、`:160-163`）不变。不再需要「继承明文行」的逻辑。

### AAD、消息族和 E1c

- AAD 的消息族（#654 设计 §8.2，`docs/plans/2026-10-22-654-hosted-wire-e2ee.md:431`）定义为 wire `type`。core 对消息族只做正则校验（`core/src/sealed-payload/sealed-content.ts:212`），不需要改 core。
- 消息族不变的：7 个输出类型和 `task.steer` 原来就用明文类型名作消息族（`client/src/daemon/sealed-task.ts:328`、`:178`）；`routine.template` 不变（`sealed-routine-template.ts:24`、`examples/host-execution-core/src/sealed-routine.ts:25`）。Host 存的 routine 模板密文升级后仍能打开。
- 消息族改变的：sealed offer 从 `task.offer_for_agent`、`task.offer_for_agent_with_egress`、`task.offer_for_agent_with_egress_fresh` 变成 `task.offer`。升级前封装的 sealed offer 打不开，靠排空处理。本仓库里不在 daemon 侧封装 offer 的只有测试 fixture；AiphaBee 只用 `routine.template`（`aiphabee/packages/byok-host/vendor/host-execution-core/src/sealed-routine.ts:25`）。
- 少了一层附带的绑定：v3 里 Host 不能把 resume offer 的 sealed instruction 换到同一任务的 fresh offer 或去掉 egress 的 offer 上，因为消息族不同。v4 里这些字段只是明文。AAD 要保护的是 (tenant, task, device, Agent, categories)，`sessionRef` 和 `egressPolicy` 本来就是 Host 写的明文，v3 里 Host 也能改 `sessionRef`。见 Q9 的 O2。
- E1c 的 blob AAD 规则不变：外层 AAD 的其余 16 个成员，加 blob 自己的 `paddedLength` 和 `fieldPath`（#654 设计 :423-425）。`fieldPath` 的根是移走字段组成的对象，offer 移走的仍是 `instruction`，所以 `/instruction/blobRef`、`/events/0/spill/blob`、`/artifactRefs/1` 都不变。变的只是外层 AAD 里的消息族值。

### daemon→server 的 7 个类型

处理方式和 offer 相同，判别字段是 `sealed`。cloud 侧把「是不是 sealed 类型」的判断从类型名改成 `isSealedPayload`：

- `inbound.ts` 里 22 处 `_sealed` / `isSealedMessageType` / `SEALED_SPLIT_TABLE`，包括 `plainTypeOf`（`:477-479`）、`inboundAgentRef`（`:455-470`）、`sealedOutputRefusal`（`:512-525`）、`ciphertextRef` 的 `inlineOnly` 检查（`:617-618`）、`task.fail_sealed` 的 `recovery` 拒绝（`:746`）、活动和审批的 switch（`:874-950`）、`terminalReceiptBinding`（`:1084-1100`）。
- `terminal-result.ts`：`DEVICE_TERMINAL_TYPES` 从 8 个降到 4 个（`:18-27`），`projectTerminalResult` 的 sealed case（`:208-250`）改成在明文 case 里按 `payload.sealed` 分支。
- `approval-timeline.ts:23-28`、`activity.ts:24-66` 已经按 `'sealed' in` 判断，只改注释。

## Q4 门的取舍与严格校验

### 判断

v3 的类型门防的是版本差：旧 daemon 不认识新类型，按 #137 停住游标，不会剥掉字段后按旧类型运行（`messages.ts:339-346`）。v4.0 内部没有这种版本差：v3 daemon 在 `v` 上拒绝 v4 envelope（`envelope.ts:46-48`），每个 v4.0 daemon 都认识 v4.0 的全部字段。

现有 device 门几乎都在表达配置差：daemon 只在配置了 Agent home、egress、input preparation 时才声明对应 flag（`create-daemon/support.ts:185-210`），`sealed-payload-v1` 只在验证过的成员和 KEM epoch 齐备时声明（`create-daemon/presence.ts:57-61`）。配置差在 v3 里也只靠发送方准入：没配置 egress 的 v3 daemon 照样认识 `task.offer_for_agent_with_egress`，类型门对它不起作用。daemon 对每个面各有一条自查：

- egress 没启用或 policy 不一致时 decline（`client/src/daemon/task-runner/offer.ts:92-96`）；
- 没有 preparation lane 时 decline（`offer.ts:53-54`）；
- message egress 不可用时 decline（`offer.ts:98-100`）；
- 打不开 sealed offer 时 decline（`task-runner.ts:1202-1207`）。

这些检查已经按字段判断，不看类型名。合并以后 daemon 侧不会少一层兜底。

### 选择

1. **整个 offer payload 保持 `.strict()`**（两个分支都是），嵌套的控制对象也是：`agentRef`、`session`、`dispatchSelection`、`terminalProjection`、`egressPolicy`、`messageEgress`、`preparation`、`InstructionBlobRefSchema` 已经是 strict；唯一宽松的 `limits`（`messages.ts:404-409`）在 v4 改成 strict。`BlobRefSchema`（`blob.ts:19-25`）在很多消息里共用，不在本次范围内。依据：长轮询对「未知类型」和「已知类型但校验失败」走同一条停游标路径（`connection-manager.ts:243-244`），strict payload 上的未知键就等于 v3 的未知类型。以后在 v4.x 加一个 offer 字段，旧 v4 daemon 一定停住，不会剥掉字段后运行。
2. **daemon 加一条通用自查**：`handleOffer` 入口算 `requiredReceiverCapabilities('task.offer', payload)`，不是自己当前 `conn.hello` 声明的 flag 的子集，就非重试 decline，reason 写缺了哪个 flag，不启动 adapter。理由：上面的逐面检查是分散写的，以后加一个门很容易漏掉对应的 daemon 检查；这条规则让 `WIRE_ADDITIONS` 同时成为发送方和接收方的准入依据，替代类型门原来提供的那层兜底。成本约十行，加一条测试。是否加由 owner 定（O4）。

### 验收测试「发送方漏掉一个门时，旧 daemon 不会运行这个 offer」

v4.0 发布以前没有「旧 v4 daemon」可用。测试分两半，覆盖两种「旧」：

**(a) 版本差：一个不认识该字段的 decoder。**

- protocol 层的性质测试：遍历 `WIRE_ADDITIONS` 里 `surface === 'task.offer'` 且带 `field` 的每一行，取 v4 corpus 里带这个字段的 offer 行，用 `.omit({ [顶层字段]: true })` 的分支 schema（模拟这个字段加入之前的 decoder，仍是 strict）解析，断言失败。这条证明「strict + 任意一个门控字段 = 旧 decoder 解析失败」。
- daemon 层的端到端测试，放在 `client/src/__tests__/unknown-message-type-tolerance.test.ts` 旁边，沿用它的 R1 测试结构：
  1. 测试 server 直接往 mailbox 追加一条 `task.offer`，带一个当前 schema 没有的字段 `futureGate`，绕过 cloud 的 `requiredReceiverCapabilities`（模拟忘了加门的发送方）；
  2. 断言：没有 `task.claim`，adapter 的 `prepare`/`start` 没被调用，持久化游标没前进（`stalledAtSeq` 等于这条的 seq）；
  3. 同一 seq 上投递一条去掉 `futureGate` 的正确 offer，断言它被认领、运行，游标前进。
- 0.31.0 发布以后，`byok-protocol-floor` 指向 0.31.0。之后每个 v4.x 加的门都由 `published-compat.test.ts` 用真实发布的 decoder 证明，和现在 v3 对 0.27.0 的做法一样（`docs/releases/README.md:63-70`）。

**(b) 配置差：认识字段、但没声明 flag 的 daemon。**

参数化测试，每个配置门一例：

- 没配置 egress 的 daemon 收到带 `egressPolicy` 的 offer；
- 没配置 input preparation 的收到带 `preparation` 的；
- 没声明 `sealed-payload-v1` 的收到带 `sealing` 的；
- 声明了 `agent-home-contract` 但没声明 `agent-egress-fresh-session` 的收到 `session.mode: 'fresh'`。

每例都绕过发送方准入直接入 mailbox，断言：daemon 发出非重试 `task.decline`，adapter 从未启动，游标正常前进（decline 是终态，不需要停住）。前两例今天的逐面检查已经满足（`offer.ts:53-54`、`:92-96`）。后两例要靠 O4 的通用自查，或补逐面检查。

## Q8 实施切片与冲突排期

**阶段 2 一个 PR，PR 内按 commit 切，不再拆 PR。** wire 改动不能半合：protocol 的类型一删，cloud、server、client、examples 当场编译不过；拆 PR 会让 `main` 中间状态是坏的，或者要临时保留旧类型（这正是要消掉的双轨）。PR 内的 commit：

1. `feat(protocol)!`：schema、split table、`WIRE_ADDITIONS`、导出、protocol 测试、v4 corpus。
2. `feat(cloud,server)!`：入队 lane、inbound、terminal-result、readback、server dispatch 与 snapshot、测试。
3. `feat(client)!`：daemon 分派、sealed-task、journal、adapter 输入类型、Q4 的两半测试、可选的通用自查。
4. `docs,examples`：protocol.md、升级说明、ADR 状态、examples、api-surface golden、CHANGELOG。

前提和顺序：

- 阶段 1 先合入。阶段 2 从阶段 1 合入后的 `main` 开分支。
- 阶段 1 和阶段 2 之间不发版。0.31.0 要等两个 PR 都合入；阶段 2 拖期，0.31.0 跟着等，或者由 owner 决定把阶段 2 移到 v5。
- **车道 A（#1013，draft）先合。** 它改的 `inbound.ts`、`docs/protocol.md`、`api-surface/cloud.d.ts`、`CHANGELOG.md`、`cloud/src/__tests__/sealed-task-surface.test.ts` 和阶段 2 重叠；`stores/ports.ts`、三种 task-attempt store、`tenant-stores.ts`、SQL 迁移不重叠（store 层不引用 offer 类型名，grep 无结果）。它不改 `cloud.ts`（`gh pr view 1013` 的文件列表）。它在 `inbound.ts` 的改动集中在 draft 路径，一次 rebase 就能解决。阶段 2 不碰 `TaskAttemptStore` 和 `recordFirstOutput`。
- 车道 A 如果晚于阶段 2 开工，阶段 2 的 cloud commit 先合，车道 A 在 `inbound.ts` 上 rebase，冲突面同样小。

## Q9 风险、未核实的假设和要 owner 决定的问题

### 风险

1. **历史 receipt 读不出来（最大风险，阶段 1 和阶段 2 叠加）。**
   - `readTaskOffer` 按存下的 `type` 查 `isTaskOfferType` 并用 `MESSAGE_PAYLOAD_SCHEMAS[stored.type]` 解析（`cloud.ts:2786-2790`），升级前的 offer receipt 一律 `coordination_input_invalid`。
   - 终态 receipt 是 `v:3` 的 `encodeEnvelope` 字节，`decodeEnvelope` 在版本上拒绝（`terminal-result.ts:40`、`:139`），抛 `terminal_receipt_unreadable`。

   - K7 没有处理 v2 receipt：`1519d53cc` 没改 `terminal-result.ts`，升级说明也只要求排空 mailbox 和结束执行（`docs/releases/k7-wire-v3.md:37-50`）。所以没有先例。

2. **阶段 1、2 之间发版**：`main` 上会出现一个只有阶段 1 的 v4。发出去之后，阶段 2 的改名就要再升一次 major。

4. **`z.union` 的错误信息**：两个分支的 issue 都会报出来，Host 看到的 `coordination_input_invalid` 详情变长。不影响判定。
5. **性能**：每个可加密的消息多一次分支尝试。明文在前，常见路径只多一次 `never` 检查 [inferred]。
