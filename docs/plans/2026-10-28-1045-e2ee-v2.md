## P1 — 边界与单一 authority

可信内容端是成员客户端和设备 daemon；不可信内容存储端是 Host、Postgres、对象存储及其备份。Host 仍拥有租户授权、路由、配额、幂等与 retention 的职责。内容 schema 验证只能移给获授权的接收端，不能让 Host 猜测密文语义。

当前协议的字段拆分 authority 是 `packages/protocol/src/sealed-split-table.ts`；category/schema 在 `sealed-payload.ts`。设计不另造一份运行时字段分类器。cloud 的 inbound/handlers 决定准入，dataplane store 持久化，client daemon 负责设备端读取和加密。`docs/security.md` 的 Sealed tasks 与 Measured sealed run 记录当前暴露面和测量边界。

## P3 — 推荐和需要 owner 选择的问题

| 决策 | 推荐（未批准） | 代价与另一个可选边界 |
| --- | --- | --- |
| Q1 C2 的消费端 | 仅对显式支持 sealed 消息的产品启用；可信成员解密，Host 仅保存密文并传递结构化 disposition | 产品需要新的可信消费端，后台全文处理不可继续。若产品必须在云端读消息，应明确保持该类别 plaintext，而不是声称 E2EE。需 owner 指定首个真实消费者。 |
| Q2 C4 scope | 使用明确的 Agent 级成员/scope 生命周期，绑定 writer epoch 和内容身份；与 task scope 分开讨论 | 增加跨 task 的 key 分发、轮换、撤销和历史可读性契约。另可暂缓 C4；不能默认任务结束就销毁仍供后续任务读取的 key。 |
| Q3 输入准备在哪里执行 | 第一版只选择一种可信端执行模式，优先调查设备端准备；Host 只拿不可变身份和密文引用 | Host 现有准备消费者需改造，设备离线时不能保持同样可用性。成员客户端准备是另一选项，需确认真实调用者后再选；本稿不定 schema。 |
| Q4 草稿归属 | 随 C2 一起设计明确的 sealed draft 能力，保留 seq/身份明文、正文密文；不让“任意 sealing”隐式开启 | 增加读取和流式更新成本。可继续禁用草稿；不能只删除当前拒绝条件。 |
| Q5 truth terminal | 优先设计显式 sealed truth 写入合同与 task 关联，再收紧旧 plaintext 写入口；整体作为同一批准批次 | 比简单禁止所有 sealed task 写 truth 更大，但保留密文记录需求。另可保留当前产品义务，或全面拒绝该类记录；需 owner 选，当前行为不变。 |
| Q6 名字/路径/摘要 | 把 runtime 自由文本 name 和 memory paths 移入密文；保留确有路由用途的固定身份；逐项审计内容摘要 | Host 将无法按路径展示或分类，需要成员端 UI。是否包括 contentType、failure.class 等其他字段另列明确范围，不能从本项推导无限扩大。 |
| Q7 usage 最小明文集 | 先列账务与观测的真实 reader，按用途决定 provider/model 是否移入密文；token、duration 不默认一并加密 | 可能减少 Host 模型诊断信息，或影响按模型计费。owner 可以保留现有暴露并明确承诺；在 consumer 证据齐前不能定最终字段表。 |
| Q8 对象控制面 | 扩展现有 tenant-scoped 对象生命周期，新增受权控制面提交/读取入口；使用 ciphertext hash/size，不另建存储 authority | 需处理上传失败、重试、引用建立和清理；可继续产品直连对象存储，但应承认 SDK 公共 API 的闭环缺口。不得为此给 Host 解密 key。 |

兼容/部署：任何 approved wire、公开 port、SQL 变化需要明确版本边界。禁止长期双写、双读或 plaintext fallback；历史数据如需处理，应单独批准一次性迁移并删除旧 authoring path。现在没有迁移批准。

10× 压力：C2/draft 的帧频率、C4 的完整快照、对象字节传输会先增加 DB 写入、网络和配额压力。设计验收必须给出消息/对象最大字节、并发上限、分页及 retention 的定量界限；当前没有工作负载测量，不能宣称足够，也不能用无限放大 inline 帧规避对象路径。并发重试仍必须保持一条不可变事实和一致的 quota 归属。
