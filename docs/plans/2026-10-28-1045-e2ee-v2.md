## 待定决策（需 owner 回答，未回答前不编造答案）

**O1 — AiphaBee 走哪条拓扑消费 v2。** AiphaBee `main` 只依赖 `@byok-sdk/server` 0.30.2（`packages/byok-host/package.json:55`），消息由内嵌 server 的 `agentMessage.consume` 消费（`apps/local-agent/src/research-pass-host.ts:460`），升级计划写明“内嵌 server 不声明 `e2ee.member`，AiphaBee 也不封装 key package”（`docs/plans/local-agent-byok-sdk-dependency-upgrade.md:42`）。按现行 spec，sealed 任务只走 `@byok-sdk/cloud`，内嵌 server 以 `coordination_input_invalid` 拒绝 `sealing`。可选：

- (a) AiphaBee 为 sealed 任务接入 hosted `@byok-sdk/cloud` 并做成员 keyring。SDK 切片不变，验收消费者在 AiphaBee 侧。
- (b) 给内嵌 server 增加 sealed dispatch。扩大范围，并改变 spec 中“`@byok-sdk/server` has no sealed dispatch”的产品真相，需要单独的设计和威胁模型（Host 与设备同机时 E2EE 保护的对象不同）。
- (c) SDK 以仓库内 `examples/hosted-bot-collaboration` 为本批验收消费者，AiphaBee 在接入 hosted 后消费。

推荐 (a)+(c)：S1–S5 不依赖 O1 的答案，S3/S4 的验收用仓库内 hosted 示例；“AiphaBee 首个消费者”的端到端证据挂在 AiphaBee 自己的接入工作上。AiphaBee 现在的 `consume` 读取正文并发布 transcript（同文件 :706），sealed 后这部分要移到成员端，这是 Q1 已接受的产品代价，需要 AiphaBee 侧排期。

**O2 — sealed 内容的大小上限。** v1 规定 padded 长度 ≤ 256 KiB 只能 inline，以上只能 `ciphertextRef`（`sealed-payload.ts` `SEALED_INLINE_MAX_PADDED_LENGTH`）。明文上限：消息正文 256 KiB（`AGENT_MESSAGE_MAX_BYTES`），记忆快照 512 KiB（`AGENT_MEMORY_PROJECTION_MAX_REDACTED_BYTES`）。两者 sealed 后的帧都可能超过 inline 上限。可选：

- (a) 两类都 `inlineOnly`，sealed 的可用上限低于明文（消息约 256 KiB 帧减去 JSON 转义开销，快照约 256 KiB）。Host 在提交时拒绝 `messageEgress.maxBytes` 超过 sealed 上限的 sealed 任务；设备在帧超限时 fail closed（消息不发、投影不写），不降级。
- (b) 允许 `ciphertextRef`，沿用 v1 terminal 的 blob reserve/commit 检查。消息 admission 行与 terminal 一样持久到 redaction，可行；记忆投影 head 每次覆盖都要回收旧 blob，`erase` 也要回收，需要新的对象生命周期。
- (c) 消息用 (b)，投影用 (a)。

推荐 (c)：消息保留现有 256 KiB 能力且复用已有 blob 规则；投影避免为 Agent 级 latest-value 行新建 blob 回收。需要 owner 确认投影 sealed 上限下降到约 256 KiB 是可接受的产品限制，以及 sealed 消息上限的具体常数。

**O3 — C2/C4 的边界是否包含相邻落点。** `docs/security.md:827` 把 `agent.egress.reliable` payload 和草稿正文也列在 C2 行，`:830` 把 truth `memory` 记录（`attested_record.body_inline`）列在 C4 行。本计划按 owner 措辞只做 `agent.message.publish` 正文和 `agent_memory_projection_head` 快照：草稿已由 owner 延后；egress 在 spec 中与 Agent 消息分列；truth `memory` 记录由 Host 产品写入，与延后的 truth terminal（第 5 项）同一路径。请 owner 确认这两项留在明文，S5 把 security 表拆行写清。

## P2 — 追踪（基线 `cdd0f54c1`）

### C2 `agent.message.publish`

1. 设备构造 publish：`body`、`contentHash`（正文的明文 SHA-256）、`byteCount`（`messages.ts:601`）。`SealedTasks` 目前只封装 `task-output` 类型；publish 不经过它。
2. Host：`/byok/messages` 把 `deps.agentMessage?.consume` 交给 inbound（`handlers/messages.ts:192`）。`handleAgentMessagePublish`（`inbound.ts:230`）核对 offer 冻结的 binding，用明文 `byteCount` 查 `maxBytes`（:268），以 `JSON.stringify(payload)` 预留 admission（:282），调用产品 `consume` 拿 disposition（:306），再 finalize（:309）。disposition 由产品决定，回显 `contentHash`（`messages.ts:622`），追加到设备 mailbox（`handlers/messages.ts:201`）。
3. 存储：`agent_message_admission.payload_body` / `terminal_body`（`deploy/sql/0017_agent_message_admission.sql:16`），都是 text 存 JSON，存 sealed payload 不需要改列。
4. 读取：`readTaskAgentMessage`（`task-agent-message.ts:28`）返回解析后的 payload 和 disposition。
5. 草稿：任何 `sealing` 的任务都拒绝草稿（`inbound.ts:591`），本批保持。
6. #1113 activity log 不承载 Agent 消息，本批不改 activity store。

压力点：明文 `contentHash` 让 Host 能确认猜测的正文；明文 `byteCount` 抵消 padding；`maxBytes` 检查和 disposition 都读这两个字段。

### C4 记忆投影与 `agentHomeMemoryChange`

1. 设备：`AgentMemoryRedactedOutbox` 用嵌入方的 redactor 生成字节，填 `redactedHash`（明文 SHA-256）、`redactedByteCount`、`redactedBytes`（`client/src/daemon/agent-memory.ts:897`），经嵌入方的 `AgentMemoryProjectionPort.publish` 发出。授权来自 Host 签发的 `AgentMemoryProjectionGrant`（:89，含 `grantRef`、`writerEpoch`、`policyRevision`）。更高 writer epoch 的 grant 清空旧 pending（`admitGrant`）。
2. Host：`POST /byok/agent-memory-projections` 解码 `redactedBytes`（`handlers/agent-memory-projections.ts:44`），嵌入方 `AgentMemoryProjectionAuthorizer` 授权，store 重新计算 hash 后写 head（`cloud-dataplane/.../agent-memory-projection.ts:99`）。SDK 不提供读取接口（`cloud/src/agent-memory-projection.ts:6`）；AiphaBee 用自己的端口实现（`packages/byok-host/vendor/host-execution-core/src/memory.ts`）。
3. 存储：`agent_memory_projection_head.redacted_snapshot bytea NOT NULL`、`redacted_hash text NOT NULL`（`deploy/sql/0014_agent_memory_projection.sql:22–23`），metering receipt 也存 `redacted_hash`。
4. `agentHomeMemoryChange` 在 `task.complete`/`task.fail`/`task.cancelled` 上（`TerminalAgentHomeMemoryChangeSchema`，`messages.ts:1329`），sealed terminal 不移动它；设备在无法 seal 时的明文 `task.fail` 还会保留它（`sealed-task.ts:114`）。`docs/security.md:855` 记录了这个暴露。

压力点：记忆投影跨任务，不能用某个 task 的 scope；`redactedHash` 与 `contentHash` 同样是确认猜测的预言机；paths 由 runtime 自选，可能泄露任务内容。

## P3 — 设计

### 类别与门控

- `TaskSealingSchema.categories` 接受全部四类。新规则：含 `memory-projection` 必须同时含 `task-output`（paths 随 terminal 的 `task-output` 密文走，否则无处可放）。`agent-message` 不依赖其他类别。
- 新能力标志 `sealed-payload-v2`，设备和 server 各自声明。门控行：
  - `task.offer` 的 `sealing.categories` 含 `agent-message` 或 `memory-projection` → 设备标志。旧 daemon 的 offer 是 strict 的，看到新类别会停下游标，所以必须门控。
  - `agent.message.publish` 的 `sealed` → server 标志；`sealed.ciphertextRef` 另需 `sealed-output-ciphertext-ref`（若 O2 选 (b)/(c)）。
  - `agent.message.disposition` 的 sealed 形态（见下）→ 设备标志。
- `requiredReceiverCapabilities` 目前只支持“字段存在”和“字段等于值”。新增一条语义：字段是数组时，`value` 表示“数组包含该值”。这是对 wire-additions 规则本身的改动，与新行一起交 coordinator 签字。
- 记忆投影走 HTTP，由嵌入方端口发送，没有 envelope 门控。门控由 grant 承担：Host 只有在接受 sealed 快照时才签发带 `sealing` 的 grant。cloud 的 `CLOUD_PROTOCOL_CAPABILITIES` 加入 `sealed-payload-v2` 作为可观察的声明。

### C2：sealed publish

split table 新增 `agent.message.publish`：marker `sealed`，category `agent-message`，identity `['messageId', 'cursor']`，moved `['body']`，forbidden `['contentHash', 'byteCount']`，digests `{ contentHash: 'forbidden' }`。`contract`、`contentType`、`sessionRef`、`agentRef` 保持明文：它们在 offer 上已冻结，不带新信息。

- Host 的 `maxBytes` 检查改为对 `paddedLength` 做上界（padded(`maxBytes` 的最坏帧)）；精确的 `byteCount ≤ maxBytes` 由设备在 seal 前、成员在 open 后检查。
- disposition 增加 sealed 形态：用 publish 的 `sealed.contentMac` 代替 `contentHash`。字段含义一一对应，不复用旧字段名装新含义。
- 产品显式启用（Q1）：cloud 配置的 `agentMessage` 新增 `consumeSealed`，入参为 sealed payload，返回 `accepted | held | refused`。未提供 `consumeSealed` 时，提交 `sealing` 含 `agent-message` 的任务在建任务前被拒绝（新拒绝码，fail closed）。`consume` 的类型保持明文 payload，不出现联合类型。
- `readTaskAgentMessage` 返回明文或 sealed 两种 payload，成员用 `openSealedContent` 和 §2.5 的 binding 规则打开（family `agent.message.publish`，direction `daemon-to-server`，identity 为上表字段）。
- Host 准入：任务冻结的 `sealing` 含 `agent-message` 时，明文 publish 拒绝；不含时 sealed publish 拒绝（`sealed_payload_unsupported`）。复用 `frozenOfferSealing`，不新增读取路径。
- 设备：`SealedTasks` 对 `sealing` 含 `agent-message` 的任务封装 publish。缺 key 时 publish 不发出，runtime 的消息工具得到错误；不发明文。

### C4：Agent 级 scope 的 sealed 投影

- `AgentMemoryProjectionGrant` 增加可选 `sealing: { scopeId, epoch }`，由 Host 签发。一个 writer epoch 的 sealing 固定；改 sealing 必须签发更高 epoch（已有 `admitGrant` 会清空旧 pending）。同 epoch 下 grant 的 sealing 与 pending 记录的形态不一致时，outbox 报错并停住，不发送。
- 该 scope 是成员链上的普通 scope，与 task scope 分开（Q2）。不新增密钥管理：建 scope、发 key package、轮换 epoch、撤销成员都用 v1 的成员链。设备用 `SealedScopeKeyring.sealingKey(scopeId, epoch)` 取 key；scope 策略的类别必须含 `memory-projection`，否则 fail closed。
- binding：family `agent.memory.projection`，direction `daemon-to-server`，identity `{ agentId, writerEpoch, sourceSeq, mutationId }`，deviceId 为写入设备，agentRef 为任务的 AgentRef，categories `['memory-projection']`。Host 无法把一个快照挪到别的 Agent、别的 epoch 或别的序号。
- mutation sealed 分支：`snapshot` 换成 `sealed`；`redactedHash`、`redactedByteCount` 不出现。receipt 相应地有 sealed 形态（`contentMac`、`paddedLength`，不含 `redactedHash`）。
- Host：`AgentMemoryProjectionAuthorization` 的 `authorized` 结果带上该 grant 的 `sealing`（授权方是 authority）。store 在 grant 要求 sealed 而收到明文、或反之时拒绝（新错误码，409）。幂等重放按 sealed 成员的外层字段比较。
- 存储：迁移 `0037`（以合入时下一个空号为准）：head 加 `sealed_member jsonb`，`redacted_hash`/`redacted_snapshot`/`redacted_byte_count` 改为可空，CHECK 恰好一种形态；metering receipt 的 `redacted_hash` 可空并加对应 CHECK。旧行全部是明文形态，迁移只放宽约束，不改数据。

### `agentHomeMemoryChange`

split table 条目增加按类别移动的字段：`task.complete`、`task.fail`、`task.cancelled` 在任务 `sealing` 含 `memory-projection` 时，把 `agentHomeMemoryChange` 整个移入 `task-output` 密文。只移 `paths` 需要嵌套移动规则，留下的 `outcome` 对 Host 没有读取方（`terminal-result.ts` 只做回显），所以整体移动。v1 任务（不含该类别）的 terminal 形态不变，不需要升协议版本。

- 设备无法 seal 时的明文 `task.fail` / `task.cancelled`：该类任务去掉 `agentHomeMemoryChange`（修改 `UNSEALABLE_FAIL_FIELDS` 的使用处）。
- `isSealedTaskPlainOutput` 与 Host 的 `sealedOutputRefusal` 读同一条规则：该类任务的明文 terminal 带 `agentHomeMemoryChange` 即拒绝。

## 威胁模型与密钥不变量

攻击者：Host 运营方及其数据库、对象存储、备份、日志、observer；可读全部存储，可重排、重放、替换、丢弃、延迟消息，可尝试降级为明文。

本批保护：Agent 消息正文；记忆快照字节；`sealing` 含 `memory-projection` 的任务的记忆变更 paths 与 outcome。

仍对 Host 可见：消息 `messageId`、`cursor`、`contract`、`contentType`、`sessionRef`、`agentRef`、分桶后的 padded 长度、时间、disposition 结果；投影的 `taskId`、`agentRef`、`sessionRef`、`runtimeId`、`grantRef`、`writerEpoch`、`sourceSeq`、`mutationId`、`policyRevision`、分桶长度；usage（owner 决定保持明文）；草稿、egress、truth 记录（O3）。

| # | 不变量 | 落点 |
| --- | --- | --- |
| K1 | Host 不持有明文 scope key；key 只在成员和设备内存 | 不改 v1 |
| K2 | 冻结策略含某类别时，缺 key、打不开、策略不匹配只产生：消息不发、投影 pending、terminal 用 v1 的封闭明文码；永不发正文明文 | S2、S3、S4 |
| K3 | AAD 绑定租户、family、identity、设备、AgentRef、类别；Host 换位、重放到别的消息/Agent/epoch 都打不开 | S1（split table、binding 规则） |
| K4 | sealed 内容不在线上或存储中留明文 SHA-256；只用 keyed `contentMac` | S1 forbidden 字段，S4 schema |
| K5 | scope 策略类别是下限：策略含 `agent-message`/`memory-projection` 的 scope，offer 或 grant 不含就拒绝 | S2（`#belowPolicy` 扩到 grant） |
| K6 | 一份内容只有一种合法线上形态（inline 或 ref，按 O2） | S1 |
| K7 | Agent 记忆 scope 与 task scope 分开；任务 redaction 的 scope shred 不触及它 | S4 文档与测试 |

剩余风险：Host 可以扣留或丢弃消息和投影（可用性）；被撤销但仍持旧 epoch key 的成员能读轮换前写入的 head，直到下一次覆盖或 `erase`；产品后台不能再处理正文（Q1 已接受）。

10× 压力：每条消息和每次快照多一次 HKDF + AES-GCM，开销可忽略。先到瓶颈的是投影 head 的整行重写（每次全量快照）和 disposition 的 mailbox 追加，两者与明文时同量级。O2 选 inline 会让大快照在设备端被拒，需要嵌入方的 redactor 控制输出大小。
