# #1022 设计稿：submit 出来的任务的按任务事件流（`tasks.events`）

状态：owner 已于 2026-10-27 按推荐批准 T1–T12（Q6）。实施起点是 #1019 合入后的 `main`。
行号默认取自 #1019 head `158e0744a`（`origin/claude/925-wire-v4-stage1-e245ba`）；标「main」的取自 `990abd602`。没核实的标 `[inferred]` 或 `[unverified]`。只读核对，没跑测试。

## 结论

- 数据已经在 server 里。`executions.submit` 和 `dispatch` 一样给任务开 relay feed（`packages/server/src/index.ts:728-730`；main `index.ts:817-819` 相同），之后的 progress、artifact、审批请求和状态变化都会进这个 feed（`relay.ts:199-243`）。这个 feed 唯一的读者是 `TaskHandle.events()`（`task-handle.ts:155-157`），而 `TaskHandle` 只能从 `dispatch` 拿到（`index.ts:610`、`:613-621`）。#1022 缺的是一个按 taskId 的读入口。
- 推荐方案 A：在 `ByokServer.tasks` 上加 `events(taskId, { after?, signal? }): AsyncIterable<TaskEventEntry>`，`TaskEventEntry = { cursor, event: ServerTaskEvent }`，直接读 relay。`TaskHandle.events()` 改走同一条路径。事件类型沿用现有的 `ServerTaskEvent`（`types.ts:313-318`），不新增事件种类。
- 它是通知流，cursor 只在同一个 server 实例、同一个 feed 内有效。任务事实仍然只从 `tasks.get`、`result()` 读（`relay.ts:42-48` 的不变量）。它不是新的读模型，也不和 `readActivity` 竞争（`docs/spec.md:1771-1776`）。
- 决定方案的约束：明文 `task.artifact` 在 cloud 侧哪里都不存（`packages/cloud/src/inbound.ts:823-829`，`applyLifecycle` 落到 `default`，`:922-923`）；SQLite 模式下 activity、审批时间线和草稿也只在内存里（`stores/sqlite/index.ts:1451-1458`，`packages/server/README.md:179-183`）。所以「读 activity tail」的方案在嵌入式 server 上丢 artifact，持久性也不比 relay 好。
- 不改 wire，不改 SQL/DDL，不动任何 store，`ByokCloud` 不加接口。托管 Host 已有 `readActivity`/`readApprovalTimeline` 和 `observer.onInboundCommitted`。
- sealed 在这一层不会出现：`ByokServer` 拒绝 sealed 入队（`index.ts:456-465`、`:721`），入站门拒绝非 sealed 任务上的 sealed 输出（`inbound.ts:519-525`）。redaction 也不适用：server 没有 redaction store（`index.ts:379-407` 没传 `taskRedactionStore`，`cloud.ts:2117-2120` 因此 fail closed），也不暴露 `redactTasks`。
- 进度会比 legacy dispatch 少：submit 的任务都带 egress policy，daemon 把每批进度合并成最后一条（latest-value，`client/src/daemon/agent-egress-controller.ts:113-137`）。artifact 不受影响。demo 页恢复后，进度行会比 main 上的旧 demo 稀疏，需要 owner 确认可以接受（Q6 的 T7）。
- 排期：#1019 合入后开工，在阶段 2 之前合。和阶段 2 的冲突面是 `relay.ts`、`types.ts`、`index.ts` 的 `tasks` 段和 api-surface 的 server 预算行，不碰 `cloud.ts`。阶段 2 自己也得改 `relay.ts`（它的设计稿 server 表没列这个文件），见 Q4。
- 规模：S–M。server 实现约 150 行，测试约 250 行，examples/basic 约 40 行，加文档 `[inferred]`。

## Q2 方案

### 2.1 选项

| | 方案 | 好处 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| A | `tasks.events` 读 relay，加 cursor | 数据现成；覆盖进度、artifact、审批请求、状态；和 `TaskHandle.events()` 同一条路径；不碰 store 和 wire | cursor 只在一个实例的一个 feed 内有效；server 重启后续不上，只能从当下继续 | **推荐** |
| B | 读 `readActivity` + `readApprovalTimeline` + `readTaskAttempt`/`readTaskResult`，relay 只当唤醒（照 `messageDraft` 的写法） | 每类事件有自己的 store cursor，符合 spec「不编造跨流顺序」；和托管侧的读法一致 | 明文 artifact 没有存储，要么不覆盖（不满足 #1022 验收），要么新增存储（新权威、redaction key 推导、保留期都要设计）；activity 只有 50 条；ByokServer 只有 memory 和 SQLite（`types.ts:33-43`），activity 和审批在两种模式下都在内存，重启后一样丢 | 否 |
| C | B 加 relay 补 artifact | 覆盖完整 | 一个 feed 两个来源，续读语义各不相同；违反一项事实一个权威 | 否 |
| D | 在 `ByokCloud` 上加推送流 | 托管 Host 也能用 | 托管是多实例，`onInboundCommitted` 只在收到 envelope 的那个实例触发；SDK 没有跨实例通知总线；托管侧已有拉取端口 | 否（0.31.0 不做） |

A 和 relay 的不变量一致：relay 只承载通知，任务事实都从 kernel 的 store 读（`relay.ts:42-48`）。`tasks.events` 只是把已有的通知按 taskId 交出去，不投影新状态，所以不构成 `docs/spec.md:1771-1776` 说的第二个投影权威。spec 里「`readActivity()` 是唯一的 host 读端口」（`docs/spec.md:1733-1739`）讲的是托管侧的有界读模型；嵌入式 server 现在没有暴露 `readActivity`，本设计也不暴露。

### 2.2 接口

```ts
/** One notification of a task's feed, and the position to resume after it. */
export interface TaskEventEntry {
  /** Opaque. Valid only for this server instance's current feed of this task. */
  readonly cursor: string;
  readonly event: ServerTaskEvent;
}

/** `tasks.events` cannot continue from where the caller asked. */
export class TaskEventsUnavailableError extends Error {
  readonly taskId: string;
  /** `cursor_unknown`: the cursor names no position in this feed. `feed_expired`: the task is terminal and its feed was reclaimed or never existed in this instance. */
  readonly reason: 'cursor_unknown' | 'feed_expired';
}

// ByokServer['tasks']
events(taskId: string, options?: { after?: string; signal?: AbortSignal }): AsyncIterable<TaskEventEntry>;
```

- 只提供订阅，不提供分页拉取。relay 本来就是推送，分页接口要另造一个读模型。Host 自己决定传输：SSE 的 `id:` 写 cursor，浏览器 `EventSource` 重连时带 `Last-Event-ID`，Host 把它作为 `after` 传回来。
- `TaskHandle.events()` 签名不变，内部改为同一实现、不带 cursor，只剩一条代码路径。这是一个公开行为变化：今天它在回收或 `close()` 后空结束、从不读 store（`types.ts:323-328`、`relay.ts:131-138`）；共用实现后，第一次 `next()` 会读一次任务投影，回收后抛 `feed_expired`。推荐接受这个变化（一套语义），写进 CHANGELOG；owner 也可以要求 handle 保留「空结束」，那样共享实现要带一个模式参数（T10）。
- 错误放在 server 自己的类里：cursor 的权威是 server 的 relay，和 `SteerRejectedError` 放在 server 的理由相同（`task-handle.ts:27-51`）。未知任务沿用 kernel 的 `ByokCloudError('task_not_found')`，和 `tasks.cancel`、`tasks.approve` 一致（`cloud.ts:2672`、`:1645`）。

### 2.3 读取流程

1. 先在 relay 上挂一个 feed（Host 发起），再读任务，避免读和提交之间漏事件。`messageDraft` 用的是同一个顺序（`index.ts:752-753`）。已有 feed（包括 submit/dispatch 正在入队时的 provisional feed，`relay.ts:99-102`）就直接用，不新建。
2. 读任务用 `tasks.get` 的同一个投影（`readTaskState` → `projectTask`，`index.ts:429-448`），不看 `attempt.status`。原因：Host 取消被接受后，快照立刻是 `Cancelled`，attempt 还停在 `cancel_requested`（`task-handle.ts:75-94` 讲了同一个差异）；按 attempt 判断，重启后一个已取消的任务会挂上一个只有设备发 `task.cancelled` 才关闭的 feed，设备不在时消费者会一直等。
3. 读回为空：抛 `task_not_found`。只撤掉本次调用在第 1 步新建的 feed；submit/dispatch 拥有的 provisional feed 一律不碰（Host 可以在自己的 submit 还没返回时就调 `tasks.events`，这时读回为空是正常的竞态，报 `task_not_found`，Host 重试）。现有的 `relay.abort` 只删 provisional feed（`relay.ts:105-112`），这里的撤销是另一个只删「本次新建、非 provisional」feed 的操作。
4. 任务已有 feed：从 `after` 之后读。
5. 任务存在但没有 feed：
   - 投影状态非终态（典型是 SQLite 重启后还在跑的任务）：保留第 1 步挂的空 feed，从现在起 relay 会把这个任务的入站事件写进来。挂之前的事件不补。重启前的 cursor 在这里会因 feed id 不同报 `cursor_unknown`。
   - 投影状态是终态（回收后，或重启前就结束了）：撤掉本次新建的 feed，抛 `TaskEventsUnavailableError('feed_expired')`。Host 读 `tasks.get` 拿终态。owner 可以改选「空 iterable 直接结束」，和 `TaskHandle.events()` 现在的文档一致（`types.ts:323-328`），见 T4。
6. 所有错误（`task_not_found`、`cursor_unknown`、`feed_expired`）都在第一条条目之前、第一次 `next()` 里抛出。开始产出条目以后只会正常结束。2.10 的回退写快照依赖这一点。
7. cursor 的内部形式是 `<feedId>.<seq>`。`feedId` 在每次开 feed 时随机生成，所以重启和「回收后重开」都会换 id；`seq` 是 feed 内单调递增的序号（`event-queue.ts:33-34` 已有）。`after` 解析失败或 `feedId` 不符：`cursor_unknown`。`feedId` 相符：返回 `seq > after.seq` 的条目；如果 `after.seq + 1` 之后的条目已经被丢弃，先给一条截断标记，标记的 cursor 指向保留的最旧一条之前。
8. 结束：终态事件之后结束（`relay.ts:279-287`）；`signal` 中止时结束；`close()` 时结束（`relay.ts:247-259`）。

截断标记要从「feed 截断过就给每个订阅者发一次」（`event-queue.ts:103-106`）改成按订阅者的起点判断。不带 cursor 的订阅从最旧一条开始，行为和现在一样。

### 2.4 顺序

- 同一个 feed 内 `seq` 严格递增，顺序是本实例观察到的顺序：kernel 提交后的同步回调顺序（`inbound.ts:541-547`），加上 Host 一侧的 approve/reject/cancel（`task-handle.ts:117-134`、`index.ts:786-791`）。
- 同一批 `task.progress` 里的事件保持原顺序（`relay.ts:208-209`）。
- 进度、artifact、审批之间没有协议层面的全序（`docs/spec.md:1697-1700`）。文档要写明：feed 的顺序是到达顺序，Host 不能从相邻关系推断因果。
- 第一个终态之后不再有事件（`relay.ts:261-265`）。

### 2.5 背压与上限

- `push` 从不阻塞。每个 feed 受 `taskEventBufferLimit` 约束（`types.ts:77-86`，默认 1000），丢最旧的。读得慢的消费者只会落后，最后收到截断标记，不会拖住入站路径。
- 终态后保留 `taskEventRetentionMs`（`types.ts:87-101`，默认 5 分钟）。
- 每个订阅者只占一个位置和一个等待者，不需要 `messageDraft` 那样的 250 ms 兜底计时器（`index.ts:774`）。
- 2.3 第 5 步挂 feed 只会发生在 Host 点名、且 store 里存在、投影状态非终态的任务上，设备无法借此让 map 增长（`relay.ts:59-63` 的约束不变）。一个永远不结束的任务，feed 永远不回收；submit 出来的 feed 现在也是这样。
- 不新增配置项。

### 2.6 覆盖范围

| 事件类 | 是否进 `tasks.events` | 说明 |
| --- | --- | --- |
| 状态（含终态） | 是 | 终态后 feed 结束；终态内容读 `tasks.get().result` |
| Agent 进度 | 是 | submit 任务是 latest-value 合并后的事件（1.5） |
| artifact | 是 | inline（base64，≤64 KB，`protocol/src/messages.ts:913-925`）或 blobRef，下载 URL 用 `blobs.getDownloadUrl` |
| 审批请求 | 是 | 建议给 `await_approval` 加 `approvalId`（T6）。v4 的 `task.await_approval` 已要求它（`messages.ts:930-938`），Host 可以直接用它调 `tasks.approve(taskId, { approvalId })` |
| 审批决定 | 只体现为 `state: Running` | 细节（`approvalId`、`decision`、`resolvedBy`）留在 `events.subscribe` 的 `task.approval_resolved`（`relay.ts:218-227`） |
| Agent 消息草稿与发布 | 否 | 有自己的 lane，按冻结的 `(deviceId, agentRef)` 绑定校验（`docs/spec.md:3248-3253`；`index.ts:228-232`） |
| reliable egress | 否 | `egress.get`（`index.ts:816-828`） |

### 2.7 sealed

- `ByokServer` 的 `dispatch` 和 `executions.submit` 都拒绝 `sealing`/`sealed`（`index.ts:456-465`、`:721`）。入站门对非 sealed 任务的 `_sealed` 输出回 `sealed_payload_unsupported`（`inbound.ts:519-525`）。relay 也不处理 `_sealed` 类型（`relay.ts:241-242`）。所以这一层不会有密文事件，文档写「不适用」。
- 将来如果给 `ByokCloud` 加按任务的流，sealed 条目只能原样交出密文：Host 云端和产品后端都没有内容密钥（`docs/plans/2026-10-22-654-hosted-wire-e2ee.md` §3 表第 4、6 行，§4 不变量 3，§5.3）。`readActivity` 现在就是这样返回 `SealedActivityBatch`（`activity.ts:50-69`）。

### 2.8 授权

- tenant 在构造时由 `productId` 决定（`index.ts:342`，`stores.ts:73`），只按 taskId 读，和 `tasks.get/approve/reject/cancel` 一致（`index.ts:786-797`）。
- 不要求 `(deviceId, agentRef)`。`messageDraft` 要绑定，是因为消息 lane 带产品目的地权威（`docs/spec.md:3250-3251`）；事件流没有产品准入。
- feed 里有原始工具输入输出。Host 在交给浏览器前自己做用户鉴权和脱敏（`docs/spec.md:1751-1755`），文档照抄这条边界。

### 2.9 保留期与失败语义

| 情形 | 行为 |
| --- | --- |
| 未知 taskId | 抛 `ByokCloudError('task_not_found')` |
| `after` 解析失败、或属于另一个 feed（重启、回收后重开、别的任务） | 抛 `TaskEventsUnavailableError('cursor_unknown')` |
| `after` 之后的条目已被丢弃 | 先发截断标记，再从保留的最旧一条继续 |
| 投影状态是终态（含已接受的 Host 取消），feed 已回收或本实例没开过 | 抛 `TaskEventsUnavailableError('feed_expired')`（T4） |
| 投影状态非终态，本实例没开过 feed（重启） | 挂上 feed，从现在开始，不补历史 |
| 已脱敏任务 | 不适用：server 不暴露 `redactTasks`，组装 kernel 时也没传 redaction store（见结论） |
| activity tail 过期 | 不相关：feed 不读 activity tail |
| `close()` 或 `signal` 中止 | 正常结束 |

### 2.10 Host 用法（examples/basic）

示意，`stream.onAbort` 等 Hono 细节以实现时为准 `[unverified]`：

```ts
app.get('/api/tasks/:taskId/events', async (c) => {
  const taskId = c.req.param('taskId');
  const after = c.req.header('Last-Event-ID');
  return streamSSE(c, async (stream) => {
    const abort = new AbortController();
    stream.onAbort(() => abort.abort());
    const follow = async (from?: string) => {
      for await (const { cursor, event } of byok.tasks.events(taskId, { after: from, signal: abort.signal })) {
        await stream.writeSSE({ id: cursor, data: JSON.stringify(event) });
      }
    };
    try { await follow(after); }
    catch (error) {
      if (!(error instanceof TaskEventsUnavailableError)) throw error;
      // Cannot resume: send the current fact, then follow from now if it is live.
      const snapshot = await byok.tasks.get(taskId);
      await stream.writeSSE({ data: JSON.stringify({ kind: 'state', state: snapshot?.state, at: snapshot?.updatedAt }) });
      if (error.reason === 'cursor_unknown') await follow();
    }
  });
});
```

页面不用改：它已经渲染 `agent`、`artifact`、`await_approval`、`state`（`public/index.html:286-296`）。`task_not_found` 由路由在开流前转成 404。

## 实施修正（2026-10-27）

实现时发现下面几处和上文不一致，以代码为准：

| 上文 | 实际 | 原因 |
| --- | --- | --- |
| 2.3 第 1 步：先挂 feed 再读任务 | 没有 feed 时先读任务；未知任务报 `task_not_found`、终态报 `feed_expired`，都不分配任何东西。只有非终态才挂 feed，挂完再读一次，这次读到终态就撤掉 feed 并报 `feed_expired` | 先挂再撤会在回收后的每次读取里写一次 relay 的 map，`task-event-retention.test.ts` 断言回收后的读取不分配 relay 状态。挂后重读同样能堵住「读完到挂上之间终态提交、feed 永远不结束」的竞态 |
| 2.3 第 3 步：撤销只删「本次新建、非 provisional」的 feed | relay 的 feed 多了 `dispatched` 标记。`detach` 只删 Host 读取挂上的 feed（既不 provisional 也不 dispatched），并且按对象身份比较；`noteDispatched` 改看 `dispatched`，不再看 `provisional`；`provision` 遇到已挂上的 feed 保持原样 | 原来的 `noteDispatched` 在已有非 provisional feed 时直接返回。Host 先对一个还没投递的任务调 `tasks.events`、再重新 submit（`execution-submit-restart.test.ts` 支持的恢复流程）时，`Offered` 和 `task.created` 会丢；被拒的重复 submit 调 `abort` 也不能删掉别人正在读的 feed |
| 2.3 第 4 步：已有 feed 就直接读 | 已有 feed 但是 Host 挂上的、任务按投影已终态、feed 没收到终态时，同样撤掉并报 `feed_expired` | 这种 feed 不会再有终态事件，读者会一直等 |
| 2.3 第 7 步：cursor 只校验格式和 `feedId` | 还要求 `seq` 是这个 feed 发出过的位置（`0 ≤ seq < 下一个序号`），否则 `cursor_unknown` | 否则伪造的 `<feedId>.999999` 会静默吞掉之后的事件。第 10 条 mutation 检查因此要先在新 feed 上推过旧 cursor 的位置 |
| 2.3 末段：截断标记按订阅起点判断 | 每次读者想要的下一个位置早于保留的最旧一条，就给一条标记；一个慢的实时读者掉队两次会收到两条 | 和带 cursor 的续读语义一致，每条标记的 cursor 都是保留的最旧一条之前 |
| 1.1：未知或已回收的 taskId 返回空的 iterable | `relay.events` 删除，`TaskHandle.events()` 走 `readTaskEvents`；`close()` 之后的新读取仍然空结束、不读 store | T10 |
| Q3：server 预算估 +1.5–3 KB | 实测 +3045 B（795655 → 798700）。类成员上的注释会进 bundle，relay 和队列新成员的说明放在类级注释里 | 预算是精确上限 |

| 未写 | Host 挂上 feed 之后，这个任务的状态变化也会出现在 `events.subscribe()` 的 `task.state` 里 | 两个 feed 共用 relay 的 `#transition` |
| 2.10：回退只发快照状态，再 `follow()` | 快照在等审批时按 `pendingApprovalId` 补发一条 `await_approval`；`cursor_unknown` 之后跟随时，跳过 `at` 早于快照 `updatedAt` 的重放 `state` | 页面靠 `await_approval` 事件显示审批面板。feed 已有历史时（伪造 cursor，或重启后另一个读者先挂上）重放的旧状态会排在快照之后；两边的时间都来自 server 的同一个系统时钟。relay 在 store 提交之后才打时间，产生快照的那次转换照样重放，状态和快照相同；Agent 的旧进度行仍会重复。`updatedAt` 只随 attempt 变，审批不动它：Running → AwaitApproval → 批准 → Running 之后，快照时间是第一次 Running 的，重放会再显示 AwaitApproval 和已批过的审批请求，直到后一次 Running。设备确认 Host 取消之后，feed 的 Cancelled 早于快照时间会被跳过，快照已经是 Cancelled |
