### 1. Child tool use and result reach the Host with session-prefixed IDs

The Host's read events were:

```json
{"type":"tool_use","tool":"read","toolCallId":"ses_e26b7dec1ffe7r6hCudr7vywiR:ses_e26b7dec1ffe7r6hCudr7vywiR:call_21","input":{"path":"<workspace>/child.txt"}}
{"type":"tool_result","tool":"read","toolCallId":"ses_e26b7dec1ffe7r6hCudr7vywiR:ses_e26b7dec1ffe7r6hCudr7vywiR:call_21","output":[{"type":"text","text":"Read file <workspace>/child.txt, lines 1-1\n1: BYOK_CHILD_READ_RESULT_2182"}]}
```

Only the workspace path is abbreviated. The repeated session prefix is the actual observed value: OpenCode already prefixes its native tool ID, and the SDK's `OpenCodeProjection` unconditionally adds the OAR record's child session identity. Thus the Host ID shape on 2.3.0 is `childSession:childSession:call`; it remains opaque and unique, matches on use and result, and has no product parser. No production change is needed. The case asserts the exact mapping and successful read content, with no `isError: true` result.

### 5. Late-child fence: not reproduced live

The final native capture has **zero child frames after the root answer at wire index 30**, and the complete captured warning list is `[]`. There is therefore no live observation here of an after-answer diagnostic, nor a live late-frame/non-delivery pair. The test neither inserts late frames nor holds the real adapter's automatic disposal open to manufacture that result.

The deterministic fixture case in [opencode-adapter.test.ts](../../packages/client/src/__tests__/opencode-adapter.test.ts), added by #2187, separately demonstrates the after-answer warning and absence of the corresponding Host tool events. Its native child IDs now carry the same child-session prefix as real 2.3.0 on both comparison channels; the Host sequences still match event for event, and the two after-answer frames still produce two diagnostics. That suite passed 65 tests locally. This is fixture evidence for item 5, not a claim of live reproduction.

A live reproduction of the fence needs OpenCode to send a child frame after the `session/prompt` answer but before the adapter's immediate disposal closes the connection. The native wire capture must establish that ordering, with a matching fence diagnostic and no corresponding Host event. A separate limit probe would keep the same connection open for prompt A and then prompt B, with A's child updating while B awaits its answer. The fence is per connection, so those updates are inside B's awaited window and are not suppressed by this fence; that probe would characterize the known limit, not prove fence suppression. The SDK uses one prompt per process, so this second condition is outside its current Host path. These reproduction conditions are also recorded on #2182.
