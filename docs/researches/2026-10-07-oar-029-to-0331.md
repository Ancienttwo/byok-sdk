# OAR 0.29.0 to 0.33.1 comparison

Scope: source comparison. No runtime test or upgrade was run.
Upstream range: `v0.29.0` (`f1a2b88`) to `v0.33.1` (`e1f91770`).
Source: https://github.com/botiverse/oar/compare/v0.29.0...v0.33.1

## P1 boundary

The current worktree vendors OAR 0.29.0 under
`packages/client/vendor/oar/f1a2b88`. It selects the Codex runtime and its
contracts. It does not use the OAR npm package or other runtime adapters.
The source manifest records six maintained BYOK files.
At inspection, `origin/main` (`756eb921`) still vendors OAR 0.25.0.
The current worktree also has unrelated minimal-guardrails changes.

## P2 trace

`CodexAdapter.start` calls the private `codexSession` bridge. BYOK supplies
the owned process transport. Native records enter BYOK `CodexProjection`.
This projection computes usage from native thread totals. It already reads
a pre-turn resume baseline and omits unknown spend. This overlaps the
upstream 0.30 fix. The vendored OAR projection still reports lifetime totals.
Thus the upstream bug must not be assumed to affect public BYOK billing.
No runtime reproduction was run.

BYOK currently adds MCP launch config through its own `-c` arguments and
helper process. It does not pass OAR `SessionOptions.mcpServers`.
OAR's new option is an alternative integration seam, not a missing BYOK MCP
feature. The operator-owned toolset registry remains the local authority.

`runtimes/codex/token-usage.ts`, and `shared/mcp-servers.ts`.
Only four of the six maintained BYOK files change upstream. Apply each
local delta to the new source and update the bridge declaration check.

## P3 decision

Reference verdict: retain the private Codex source integration.
An upgrade has value for source alignment and the MCP session seam.
It does not add Claude/Pi features to BYOK by itself.
Keep the BYOK process owner, native interaction bridge, required record
consumer, byte budget, and ES2022 contract. Do not import the upstream
process manager as a side effect of the version change.

Verification: live GitHub compare and tag source; local manifest and call
path inspection. No SDK check or runtime acceptance is claimed.
Required upgrade gates: build, typecheck, test, API surface, version
authority, bridge declarations, and real Codex resume/MCP readback.
