# Pi 1.5.0 upgrade

The owner asked on 2026-11-03 to move the Pi dependencies to 1.5.0. Upstream
`earendil-works/pi` published all packages at 1.5.0 on 2026-11-02 from commit
`f9a26365568127461c47a07a37dcb42c140a3ac5` (tag v1.5.0, from the SLSA
provenance; npm omits `gitHead`). The release fixes four undici advisories
(undici 8.10.2 → 8.12.3); the SDK already overrides undici to 8.12.3.

**Status: ruled and implemented.** 1.5.0 is not a pin-only bump. pi-durable
1.5.0 removes `watchEvents()`, which both durable lanes are built on, and
changes persisted state one way. The owner ruled E1–E7 on 2026-11-03, all as
recommended; the change is breaking and ships in the next MINOR (see
Decisions).

## P1: Boundary

Pi is pinned exactly in the root `overrides`, `packages/client` (coding-agent,
pi-ai, agent-core, pi-durable, chord, plus `byok.piRuntimePin`) and
`packages/cloud-do` (pi-durable, pi-ai, chord). The SDK touches Pi through:

- the Pi lanes in the client (prepared, RPC, native; `adapters/pi/*`,
  `bin/pi-*-host.ts`), including the A1' compile closure;
- the client durable lane (`adapters/pi-durable/engine.ts`, `events.ts`);
- cloud-do (`agent-do.ts`, `session-runtime.ts`, `storage.ts`, `tools.ts`),
  whose `CloudToolDefinition.parameters` and `DurableObjectSqliteDatabase`
  are part of its public surface;
- the keys package's table generated from the pinned pi-ai catalog;
- the vendored rpiv-todo build input and the HTML export assets.

OAR is SDK-owned vendored source and imports no Pi package; #1401 (OAR 0.86.0)
does not couple to this upgrade except through the `api-surface/entries.json`
budgets.

## Why OAR 0.86.0 keeps pi-durable and chord at 1.4.0

OAR #611 (`181d908`, in v0.86.0) moved pi-ai and pi-coding-agent to 1.5.0 for
the undici advisories and kept Durable and Chord at `~1.4.0`: "their 1.5 API
and persisted `pi.live` v3 migration belong in a separate minor release." Its
packed host needs an alias, `@earendil-works/pi-ai-durable` →
`npm:@earendil-works/pi-ai@1.4.0`, so pi-durable 1.4.0 gets its own pi-ai;
installing pi-ai 1.4.0 under its own name gave several 1.5.0 copies and an
`OAuth auth derivation failed … Cannot find module … anthropic.js` failure in
a single-file bundle. The reason is the breaking durable API and the one-way
state migration below, not a defect.

## API review

The `.d.ts` files of all nine packages were compared between 1.4.0 and 1.5.0,
then the JS where the SDK depends on behavior. Differing `.d.ts`/`.js` files:
pi-coding-agent 51/158, pi-durable 46/48, pi-ai 19/83, chord 15/17,
pi-tui 10/16, pi-mcp 1/3, pi-agent-core 1/1, pi-codemode and pi-telemetry
0/0 (manifest only).

Every subpath the SDK imports is still in the exports maps and resolves to a
file, except `@earendil-works/pi-ai/utils/typebox-helpers`: the `./utils/*`
pattern still matches, but the file is gone.

`bun run typecheck` with only the pins changed fails. Source errors (tests
excluded, cascades from the failed client build excluded):

- `client adapters/pi-durable/engine.ts`, `events.ts`, cloud-do `agent-do.ts`:
  `watchEvents` and `AgentEvent` are no longer exported.
- cloud-do `session-runtime.ts`: `SessionEnd.reason` is now `kind`.
- cloud-do `storage.ts`: `SqliteDatabase`/`SqliteExecutor` require
  `runCounted`.
- client `bin/pi-durable-host.ts`: pi-ai no longer exports `TSchema`.
- client build: the todo build cannot resolve `pi-ai/utils/typebox-helpers`,
  so `#byok-pi-todo-runtime` is missing.

### Durable event stream removed (blocking; decision E1)

pi-durable 1.5.0 removes `watchEvents()` and `AgentEvent`, `SnapshotEvent`,
`MessageChange` and `ToolEventCall`. Renderers read state instead: the
conversation view from `Conversation.watch(context, window?)`, whose `pi.live`
document carries the streamed answer (`generation.message`), tool slots
(`tools`, status, output, `entry` once done), `run`, `runFailure`,
`compactions` and `generation.retry`; the view's entries are a window (newest
50 to start; past 100 the oldest leave in one splice). The upstream changelog
maps every event to its state.

Both durable lanes project events today:

- client `projectDurableEvent`: `message_update` text deltas → `progress`,
  `tool_execution_start/end` → `tool_use`/`tool_result`, assistant
  `message_end` → `usage`, `task_failed`/`auto_retry_start`/`compaction_start`
  → failure. On resume it replays persisted assistant usage from the
  snapshot's entries.
- cloud-do `submit()`: rebuilds the answer text from message events and
  streams prefix deltas as `text_delta`; `task_failed` and an assistant
  `stopReason: 'error'` set the failure. The final text and error code
  already come from committed state (`conversation.context()`).

On 1.5.0 the same Host events can be derived from the view: text from
`pi.live.generation.message`, tools from `pi.live.tools` slots and appended
result entries, usage from appended `pi.assistant` entries, failure from
`pi.live.runFailure`, `compactions` and `generation.retry`. Resume usage must
page with `Conversation.entries()` (or read `context()`), because the first
watch value holds at most 50 entries. A tool slot stays listed as `done` until
its run ends, so a projection reports each slot's end once, not on every value
that still lists it. The cloud-do lane already treats
committed state as the authority, so it changes less than the client lane.

Watch shapes change across chord and pi-durable too: listeners receive a
tagged `WatchCall` (`{ kind: "value", value, ops, retired }` or `failed`), and
`WatchEnd` is tagged by `kind` (`aborted` replaces `cancelled`;
`listener_error` stays).

### Persisted state is one-way again (decision E2)

The SQLite migrations are byte-identical (schema version 2), so the D2 table
rebuild does not repeat. The documents and tasks inside change version:
`pi.live` v3 (`CompactionStatus.reason` → `trigger`, required `run.turns`;
older values migrate on read and are rewritten at the next commit),
`pi.tool` v3 and `pi.generation` v2. A 1.4.0 Harness cannot read a `pi.live`
that 1.5.0 wrote, and leaves 1.5.0 tool and generation tasks blocked
(`task_too_old`). A client durable replica or cloud-do Durable Object opened
by this release cannot roll back past it.

### Harness settings and crash behavior (decisions E3, E4)

`restartLimit: Infinity` (D4) still means "never end a task for restarts".
Parking is gone upstream (a limited task now ends visibly; `retryTask` and
`task_parked` are removed); the SDK used neither.

New: a generation whose model request was in flight when the host died is no
longer resent on open. The attempt counts as failed under `settings.retry`.
Both lanes disable retry (`maxRetries: 0`), so the run ends with
`pi.live.runFailure` reason `interrupted` and its inputs settle `unanswered`
with that reason. On 1.4.0, with `restartLimit: Infinity`, the request was
resent on every open, which upstream calls a defect (#11139). A Durable
Object eviction during a model request is the common case.

New: progress commits (partial answers, running tool output, tool slot
status) are deferred: watches see them at once, and Storage gets them with the
next commit that reads `pi.live`, at the latest after
`settings.progress.persistWithinMs` (default 1,000 ms). Neither lane sets it.
Upstream measures 5.7× fewer storage transactions with parallel tools and 27×
for long answers. A crash loses up to about one second of streamed content
instead of 100 ms.

`RunFailureReason` gains `interrupted`, `restart_limit`, `nothing_to_answer`
and `turn_limit`, also as an `unanswered` submission's `reason`. cloud-do
`#adjudicateRuns` maps any `unanswered` that is not `aborted` to `failed`, but
an interrupted request never reaches it: cloud-do's stale-run recovery aborts
the run first, so the execution still ends `interrupted` with
`CLOUD_EXECUTION_INTERRUPTED`. Only the native generation's own outcome
message changes (`The host stopped while the model was answering, on attempt
1`), and `beforeRequest` no longer runs for the request that is not resent.
The client lane maps the unanswered reason (`interrupted` or `restart_limit`)
to `DurableRunInterrupted`, which the session reports as `runtime_exited`.

### Tool argument validation moves to pi-schema (decision E5)

pi-ai, pi-agent-core, pi-durable and chord validate tool arguments with
pi-schema. Tool `parameters` are any JSON Schema object, typed through
pi-schema's `Static`; pi-ai no longer re-exports TypeBox (`Type`, `Static`,
`TSchema`), and its `StringEnum` (still exported) returns a pi-schema
`Schema`. Arguments are coerced before validation (`"42"`
→ 42, one value → an array, `null` → an omitted optional property).
TypeBox-only features (`Type.Refine`, codecs, `Format.Set` formats) no longer
apply. Validation messages the model sees change (`- path: missing` instead
of `must have required properties path`).

SDK impact: `pi-durable-host.ts` casts MCP tool schemas to
`ToolRegistration['parameters']`;
cloud-do's `validateToolArguments` gate now also accepts coercible arguments.
Host impact: cloud-do's public `CloudToolDefinition.parameters` is
`ToolRegistration['parameters']`, now pi-schema-typed; a Host that builds tools
with `Type` from `@earendil-works/pi-ai` no longer compiles.

Response-side only: OpenRouter usage now carries OpenRouter's billed cost

### Todo build input

The vendored rpiv-todo 2.15.0 `tool/types.ts` imports `StringEnum` from
`pi-ai/utils/typebox-helpers`, which 1.5.0 removed. pi-ai 1.5.0 has
`utils/string-enum`, but its `StringEnum` returns a pi-schema schema, which a
TypeBox `Type.Object` does not accept; the coding agent keeps a TypeBox
`StringEnum` only in the module it maps extension imports to
(`pi-ai-extension-view.js`, not exported). There is no newer rpiv-todo
release (2.15.0 is latest). See decision E7. With the local delta the todo

package and notice.

  takes one tagged `Report`; `DocumentCommitChange`, `TaskInspection.state`,
  `FileChange`, `ReportFrom` are tagged by `kind`; `HostCallback` gains

  added.
- chord: `traceIn` takes the context last; `chord/next` is exported again

## Decisions

Owner ruling, 2026-11-03: E1–E7 all as recommended. The change is breaking and
ships in the next MINOR, with the upgrade manifest entry `pi-150-closure` and a
CHANGELOG migration note. The options considered are kept below.

- **E1: durable event stream.** Options:
  (a) migrate both durable lanes to `Conversation.watch()` and `pi.live`,
  keeping the Host event contract (`progress`, `tool_use`, `tool_result`,
  `usage`, `turn_end`, `text_delta`, error codes);
  (b) hold pi-durable and chord at 1.4.0 as OAR did, which needs a second pi-ai
  under an alias and breaks the SDK's one-instance closure, closureDigest and
  direct exact-pin rules;
  (c) defer the whole upgrade.
  **Recommend (a)**, in this PR, because a split closure is the compatibility
  path the repository rules forbid. It is the largest part of the work: both
  projections, their tests, and resume usage paging.
- **E2: one-way persisted state** (`pi.live` v3, `pi.tool` v3,
  `pi.generation` v2). Options: accept with a breaking release note, or (b)/(c)
  above. **Recommend accept**, as D2 did.
- **E3: interrupted model requests are not resent.** Options:
  (a) accept, and map `runFailure` `interrupted` (and `restart_limit`) to the
  existing interrupted outcome: cloud-do `interrupted` with
  `CLOUD_EXECUTION_INTERRUPTED`, eligible for the existing wake requeue rule;
  the client lane ends the execution as interrupted, not as a model failure;
  (b) enable `retry: { enabled: true, maxRetries: 1 }`, which also resends
  after model errors (a second paid request) and changes failure timing;
  (c) accept with today's mapping, where an eviction during a request becomes
  a `failed` model error.
  **Recommend (a).**
- **E4: deferred progress persistence.** Options: accept the 1,000 ms default,
  or set `progress.persistWithinMs: 0` for the 1.4.0 storage cadence.
  **Recommend accept**: streaming to consumers comes from watches, final
  entries are stored at phase boundaries, and an interrupted partial is
  discarded anyway. If set, `CLOUD_HARNESS_SETTINGS` gains the field in the
  cloud-do golden.
- **E5: Host tool schemas on cloud-do.** Options: accept pi-schema's contract
  and document the migration (`Type` from `typebox`, or pi-schema builders;
  coercion; new validation messages), or put an SDK-owned schema type in front
  of `ToolRegistration['parameters']`. **Recommend accept and document**: an
  SDK type would be a second schema authority over pi's.
- **E6: closure membership.** Options: add pi-schema as the tenth closure
  package (indirect, like pi-telemetry) to `PI_RUNTIME_CLOSURE`, the collector,
  the root overrides and the closureDigest; or treat it as third-party.
  **Recommend add**: same workflow, tag and verified provenance, and pi-ai pins
  it exactly.
- **E7: todo build.** Options: a documented local delta in `tool/types.ts`
  defining `StringEnum` with TypeBox (`Type.Unsafe({ type: "string",
  enum })`, the same JSON), or drop the enum typing. **Recommend the local
  delta**, recorded in rpiv-todo's PROVENANCE and source manifest.

## Release classification

Host-visible, breaking:

- `check:upgrade-manifest` fails on the evidence tree:
  `store:pi-durable changed since 0.36.0 without a manifest entry`. The store
  item is the pinned pi-durable version by construction, and E2 makes the
  change one-way.
- cloud-do public types: `CloudToolDefinition.parameters` (E5);
  `DurableObjectSqliteDatabase` gains `runCounted` (golden change).
- keys: `PI_MODEL_CATALOG_PI_AI_VERSION` and 30 catalog entries that will
  return `not_in_catalog`.
- Default behavior: E3 (a crash during a model request ends the run),
  E4 (storage cadence), the tightened Pi system prompt in lanes that do not
  pass the Host prompt, and model-visible validation messages.
- Network request headers: unchanged apart from the `User-Agent` version.

`check:api-surface` golden changes: `keys.d.ts` catalog version,
`cloud-do.d.ts` `runCounted`, `entries.json` bundled packages (+pi-schema,
−typebox in the Pi runtime hosts) and budgets. The Pi runtime hosts grow by
14,623 bytes (pi-schema), the client root and `byok-agent` by 10,889 bytes,
cloud-do by 320 bytes. `CloudToolDefinition.parameters` keeps its declaration
text (it names `ToolRegistration['parameters']`), so only the changelog
records it.

The owner classified the change MINOR; the upgrade manifest entry
`pi-150-closure` covers the store, the cloud-do export and the keys export.
