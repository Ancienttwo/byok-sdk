# #519 Hermes ACP S0: gateway ownership, isolation and one real turn

Issue: [#519](https://github.com/Ancienttwo/byok-sdk/issues/519). Branch `codex/hermes-adapter-519`, base `main@b5a456f0`.
Hermes under test: `Hermes Agent v0.22.2+2364.g0b10b9f (2026.9.24)`, git install, HEAD `0b10b9f8155a`, ACP library `agent-client-protocol` 0.9.0 (protocol version 1).

Evidence labels: `(verified: …)` means a command ran on 2026-10-20. `(source: …)` means Hermes source was read at `0b10b9f`. Probe scripts were in `/tmp` and are not part of the repository.

## Scope and product position

On 2026-10-19 the external Bot beta made Hermes an MCP client of the byok MCP server ([plan](https://github.com/Ancienttwo/byok-sdk/pull/539)). That plan did not include an SDK adapter. The lane instruction of 2026-10-20 asks for `HermesAdapter` as a `RuntimeAdapter`. This adapter is an optional coding-agent runtime, the same kind of item as the optional Grok CLI runtime (#514, beta Q11). It does not change the MCP client plan or the Bot mode PRD.

No paid model call was made. Every real Hermes turn used a local fake OpenAI-compatible endpoint (`model.provider: custom`, `base_url` on `127.0.0.1`). Hermes itself, its gateway, its tool loop and its MCP client were real.

## Results

### 1. `hermes acp` is a viewer; the SDK must own the gateway

- `hermes acp` builds `GatewayACPAgent`, a viewer. Tools, MCP servers and the model loop run in a gateway daemon (source: `acp_adapter/entry.py:178-180`, `acp_adapter/server.py:244-248`).
- On the first session call the viewer runs `ensure_gateway_runtime(home, idle_exit=True)`. With no gateway it spawns a detached `gateway run --quiet --idle-exit` that lives up to 600 s after idle (source: `hermes_cli/gateway_client.py:288`, `hermes_cli/gateway_runtime_start.py:32-77`). That process leaves the caller's process tree.
- When a ready gateway already serves the home, the viewer attaches and spawns nothing (source: `hermes_cli/gateway_runtime.py` `_observe_replacing_stale`, `attachable`).
- Verified topology: the SDK starts `hermes gateway run --quiet --external-supervisor --force` as an owned process tree. It waits until the control socket `identify` verb reports `state: ready`, the owned pid, and the profile home in `served_profiles`. Then it starts `hermes --yolo acp`. After `session/new`, `gateway.pid` and `identify` still named the owned pid. No `--idle-exit` gateway appeared for the test home (verified: probe runs at 15:47, 15:50, 15:54, 15:55 HKT).
- `identify` answer shape (verified): `{"ok":true,"result":{"pid":…,"state":"ready","served_profiles":[{"home":…}],"supervisor":"external",…}}`. Socket: `<home>/gateway.sock`, else the path in `<home>/gateway.sock.path` (source: `hermes_cli/gateway_runtime_discovery.py:145-160`).

### 2. Isolation: one SDK root, one profile per execution

- A new `HERMES_HOME` builds a Python environment in `<home>/installs/<key>/environments/` (353 MB, 69 s) on first use (verified: `HERMES_HOME=/tmp/h519/home hermes acp --check`, `time` 1:09). A fresh home per execution is therefore not usable.
- A profile home `<root>/profiles/<name>` shares the root's environment (source: `pm/environments.py:25-38`). Verified: a new profile home grew to 9.8 MB and built no environment.
- Hermes serves every profile of a root from one host gateway. A profile refuses its own gateway (exit 78) unless its config sets `gateway.standalone: true` and the gateway runs with `--force` (verified). Hermes calls `standalone` a temporary compatibility setting. This is the main upgrade risk.
- The SDK root is a Host-given path (`HermesAdapterOptions.home`). The adapter refuses `~/.hermes`. The first `detect()` on a new root waits while Hermes builds the environment there (verified: 24 s on this machine, the uv cache was warm).
- The profile config turns off Hermes memory (`memory.memory_enabled`, `memory.user_profile_enabled`) and kanban dispatch (`kanban.dispatch_in_gateway`). It configures no messaging platform and no cron job. The default ACP toolset `hermes-acp` already leaves out `cronjob_manage`, kanban tools, `computer_use` and `clarify` (source: `toolsets.py:67,191-195`).
- Ambient `HERMES_*` variables are not forwarded. `HERMES_TUI_GATEWAY_URL` would send a turn to a remote gateway (source: `hermes_cli/gateway_client.py:272-283`).
- Every `hermes` command the adapter runs has `HERMES_HOME` set to the SDK root or to a profile, including `--version`. `hermes --version` runs a passive update check: it reads `<home>/config.yaml`, writes `<home>/source-checks/`, and can reach GitHub with a 10 s timeout (source: `hermes_cli/_startup_fast.py:224-228`, `hermes_cli/source_check.py:425-461`). The root config and each profile config set `updates.check: false`, which that check honors (source: `source_check.py:426`).
- Hermes caches resolve under `get_hermes_home()` (source: `hermes_cli/model_catalog.py:85`, `hermes_cli/models_reasoning_caps.py:75`). The test runs wrote no Hermes user state under `~/.hermes`. Files that changed there during the runs came from the user's own running gateway (hourly cache refresh, heartbeats).

### 3. Real turn, MCP toolset, edit policy, cleanup

Built `HermesAdapter` (`packages/client/dist`), fresh SDK root, scripted fake model (verified: `/tmp/h519-scripts/adapter-smoke.mjs`, 16:45 HKT):

| Step | Result |
| --- | --- |
| `detect()` | `available`, version line above, `authPresent: true`, 3.9 s on a built root |
| `start()` | 19.1 s to a running turn: gateway ready, `initialize`, `session/new`, `session/set_mode` |
| MCP toolset | The SDK stdio server got `initialize`, `tools/list` and `tools/call {"name":"echo","arguments":{"text":"ping-from-hermes"}}`. Hermes names it `mcp__editor_echo_<hash>__echo` and defers it behind `tool_search` / `tool_call` |
| File edit | `write_file` in mode `dont_ask` completed with no permission request and wrote the workspace file |
| Events | `tool_use` / `tool_result` pairs with `toolCallId`, reply text as `progress`, `usage` with context tokens, `turn_end` |
| `close()` | Gateway, viewer, MCP server and Hermes MCP supervisor gone; profile directory deleted |

Earlier probe facts (verified):

- `session/cancel` during a turn: the prompt answered `stopReason: "cancelled"` 0.4 s later.
- The gateway ignored SIGTERM for 3 s in one run. The SDK disposal path sends SIGKILL after its grace period.
- MCP servers run as gateway children in their own process groups. The SDK disposal reads descendants before SIGTERM, so it reaches them.
- A gateway in a new profile started `git remote-https` to GitHub (update check, before `updates.check: false` was added) and fetched model metadata. Seeding the model cache files from the previous execution cut `session/new` from 11.6 s to 3.3 s.

### 4. Capability decisions (issue question 3)

| Capability | v1 | Reason |
| --- | --- | --- |
| `mcpToolsets` | true | Verified above |
| Closing reply (`messageEgress`) | Works with no adapter flag | Reply text arrives as `agent_message_chunk` deltas; `progressEventsAreMessages` stays unset |
| `steer` | false | Hermes has no mid-turn steer in ACP |
| `resume` | false | Every execution has a fresh profile, so no native session survives it |
| `approvalInteractive`, `nativeInteractions`, `messageDraft` | false / absent | Downstream needs egress and toolsets only |
| `trajectoryEvidence` | absent | No count of dropped frames was qualified |

Permission policy: edits run in mode `dont_ask` and commands under `--yolo`, as Claude and Codex run without prompts (ADR-037). Hermes still asks for sensitive paths. The adapter answers such a request `cancelled`, so Hermes's own guard stands.

### 5. Admission and failure handling

- `prepare()` runs only `hermes --version`, as Codex admission does. The ACP probe, which can wait for a first environment build, runs only in `detect()`, and `detect(signal)` honors the signal.
- If the viewer attaches to a gateway other than the owned one, start fails. When that gateway serves the fresh execution profile, it was started for this execution, so the adapter kills its process group.
- If the Host process dies, the daemon's owned process ledger reaps the gateway process group at the next start (`adapters/process-tree.ts`, `daemon/owned-process-ledger.ts`). Hermes's MCP death supervisor watches that group. `detect()` deletes `byok-*` profiles that are older than 15 minutes, that this adapter does not hold open, and that no gateway answers for.

## Issue questions

1. ACP version: Hermes uses ACP protocol version 1 through the Python library 0.9.0. The adapter speaks version 1. The library version numbers on the two sides are independent. #514 vendors OAR `shared/acp` with `@agentclientprotocol/sdk` 1.4.0 (branch `codex/grok-adapter-514`, not on `main` at this time). Hermes uses only a small part of ACP (no `fs`, no `terminal`, one reverse request), and its gateway ownership sits outside ACP. This branch keeps a small ACP peer in `adapters/hermes/`. A move onto the shared layer is a follow-up after #514 lands.
2. Isolation: `HERMES_HOME` relocates the whole home. Per-execution profiles under one SDK root give isolation without an environment build per execution.
3. Capabilities: see §4.
4. Route: SDK first. There is no OAR Hermes runtime, and the gateway ownership is SDK policy.

## Not verified

- Windows. The gateway control channel is a named pipe there. `prepare()` refuses on `win32`.
- The three-turn read-only memory check with a real model. The instruction carries the read-only rule and the daemon measures the Agent home digest, but a fake model cannot show that a real model obeys. A paid run needs approval.
- Linux. All runs were on macOS (Darwin 25.5.0, arm64).
- Hermes builds after `0b10b9f`. `detect()` reports another build as an advisory only.
