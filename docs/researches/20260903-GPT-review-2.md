我看完了。这份 Claude 独立审查质量很高，尤其强在两点：一是基于当前 `4cc765f` 做了更细的代码地图与事实纠错；二是明确指出了哪些“看起来合理的重组”其实会过度设计。它采用代码、RAFT 对照、联网调研和两路盲审后再裁决，报告也区分了 verified、fetched、inferred 与 owner decision。

它会**实质性调整我上一版审查的优先级**，但不会推翻核心判断：项目方向正确，真正的问题集中在 **协调面双权威、Agent/legacy 双轨、Session 不可寻址、同一 Agent home 并发写入，以及公开集成面的快速漂移**。

# 一、我完全采纳 Claude 的几个关键发现

## 1. `server` 与 `cloud` 双协调权威，应升为核心架构问题

我上一版更关注领域对象和本地并发，低估了这一点。

当前：

* `@byok-sdk/cloud` 是无状态 handler + async stores。
* `@byok-sdk/server` 有独立的 `ConnectionHub`、TaskStore、pairing、auth、WS 和状态机。
* 两者服务同一套协议，但零共享实现。
* 这种重复已经不仅是代码冗余，而是安全和生命周期语义可能漂移的来源。

Claude 将它列为 V4，并指出已经出现安全姿态漂移，这个判断应采纳。

但我会稍微修改它提出的解决方式：

> 必须消除的是“双语义权威”，不一定必须同步删除所有传输方式。

目标结构应该是：

```text
coordination domain kernel
  pairing
  capability admission
  offer reservation
  inbound ownership
  cancellation
  first-terminal-wins
  message side-effect admission

      ├── hosted HTTP / long-poll composition
      └── embedded server / optional WS composition
```

最理想的是让 `server` 变成：

```text
cloud/domain kernel
+ in-memory or SQLite stores
+ TaskHandle convenience facade
+ optional WS transport adapter
```

不能再保留一个独立 `hub.ts` 状态机。

## 2. 1.0 前应切 Agent-only wire v2

这也是我现在非常赞同的结论。

目前 v1 下已经有：

* 5 种 offer 变体；
* 20 个 capability flags；
* legacy task offer 和 strict Agent offer 共用复杂分支；
* 两套 capability vocabulary。

报告指出，wire 的“冻结 + 只增”已经把 Agent-first 转向摊成消息类型和 feature flags 的组合爆炸。

这不是简单的“协议文件有点大”，而是 integration complexity 已经开始由版本号转移到：

```text
message type
× capability set
× daemon configuration
× runtime capability
× local policy
```

因此在 1.0 前应一次性切为严格 v2：

```ts
interface AgentOfferV2 {
  agentRef: AgentRef;

  session:
    | { mode: 'fresh' }
    | { mode: 'resume'; sessionRef: string };

  execution: {
    runtime: RuntimeRef;
    lane: 'subscription' | 'byok-profile';
    policy: PermissionPolicy;
    requiredToolsets?: string[];
  };

  projections?: {
    egress?: AgentEgressPolicy;
    terminal?: TerminalProjectionSelection;
    message?: AgentMessageRequirement;
  };
}
```

关键不只是“一种 offer”，还必须满足：

* v2 schema 整体 strict。
* 不认识字段时拒绝整个 offer。
* 不允许像 v1 tolerant reader 那样剥掉未知控制字段后继续执行。
* capability declaration 只有一份权威。
* legacy v1 是一次性迁移路径，不是长期 fallback。

Claude 将这列为 1.0 前的第三刀，我同意。

## 3. Session 应先做“最小只读投影”，而非完整云端 Session 状态机

我上一版提出完整：

```text
Computer → Installation → Agent → Session → Run → Attempt
```

作为长期领域模型是合理的，但作为当前重构计划，确实偏大。

Claude 的折中方案更合适：

* `TaskAttempt` 增加已确认的 `sessionRef`。
* 提供按 Agent 列举已建立 Session 的读模型。
* Session 投影从 first-terminal-wins 的事实派生。
* 不在云端维护 `running / idle / awaiting approval` 等可变 runtime session 状态。
* 本机仍是 native session 和 resume evidence 的唯一 authority。

建议的最小接口：

```ts
interface AgentSessionProjection {
  agentRef: AgentRef;
  sessionRef: string;
  runtime: RuntimeId;
  lastTaskId: string;
  lastTerminalState: 'complete' | 'failed' | 'cancelled';
  lastTerminalAt: string;
}

listAgentSessions(
  tenantId: TenantId,
  agentRef: AgentRef,
): Promise<readonly AgentSessionProjection[]>;
```

这里不应出现：

```text
running
current process PID
live turn
native session credential
current tool call
```

这使 SaaS 能真正实现 resume，又不会把本地执行态搬到服务端。

## 4. ACP 不应现在成为共享 adapter 边界

这一点我修正上一版建议。

我之前建议“ACP-like adapter interface”作为后续标准化方向。Claude 的调研指出，当前 ACP 生态里的 Claude/Codex adapter 并不等价于“驱动用户已经安装和登录的本机 CLI”，而且 ACP 的权限交互模型与 BYOK 的：

```text
prepare
→ seal immutable manifest
→ claim
→ start
```

并不完全一致。

因此更合理的结论是：

* 保留当前 `RuntimeAdapter`。
* Codex、Claude、Pi 继续使用各自原生机器接口。
* ACP 只作为某一个具体 runtime adapter 的内部 transport 候选。
* 只有出现一个具名下游要求 ACP-only runtime 时，才建立 PoC。
* 不提前新增公共 `AcpAdapter` 抽象。

Claude 对 ACP 的最终裁决是“不加”，我同意。

## 5. 不应现在合并 14 个 Store ports，也不应预先把 TaskRunner 拆成三层

这两点也是很好的“反过度设计”约束。

Store ports 虽然多，但其中很多代表的正是不同事务权威：

* first terminal wins；
* task cancellation tombstone；
* pairing enrollment；
* mailbox cursor；
* reliable egress ack；
* message reservation/finalization。

粗暴合并会隐藏而不是消除事务边界。Claude明确建议保留这些 ports。

`TaskRunner` 也不应为了减行数立刻拆成：

```text
AdmissionService
ExecutionService
TerminalService
```

它当前的 receive、dedup、pre-cancel、strict gate 顺序本身是正确性契约。更稳妥的顺序是：

1. 先删除 legacy offer 分支。
2. 再重新测量复杂度。
3. 只提取已经形成稳定生命周期边界的部分。
4. 优先拆 `create-daemon.ts` 的 composition，而不是搬动 TaskRunner 的状态顺序。

# 二、我修正上一版中的三处过度扩展

## 1. 不急于在 SDK 内新增完整 `Computer` aggregate

Claude 将当前 `computer` 近似视为 device；严格来说，当前 `deviceId` 更接近：

```text
某个产品在某台机器上的 Installation / Enrollment
```

而不是物理 Computer。

但这并不意味着现在必须在 SDK 中增加：

```ts
Computer {
  computerId;
  installations[];
}
```

更克制的边界是：

* BYOK SDK 对外把 `deviceId` 的语义逐步澄清为 `installationId`。
* 宿主 SaaS 自己决定多个 installation 是否属于同一 Computer。
* 只有未来真的出现跨产品 daemon、一个 Computer 多 installation 管理、机器级 supervisor/update 时，才把 Computer 提升为 SDK 一等对象。
* RAFT Computer 模型继续作为宿主产品层参考，不直接搬入 dispatch protocol。

所以我撤回“Computer 必须立即成为 BYOK cloud 一等实体”的强建议。

## 2. 不急于引入完整 Run / Attempt 树

当前 `TaskAttempt` 已经实际承担了 Attempt 的大部分职责。

只有出现以下真实能力时，才需要明确拆出 Run：

* 同一用户请求允许跨设备自动重试；
* 一个 Run 有多个 Attempt；
* 新 Attempt 建立后，需要 fence 掉旧 Attempt；
* 产品 UI 需要把逻辑请求和基础设施重试分开显示。

当前最小变更应先是：

```text
TaskAttempt + sessionRef
terminal-derived session index
```

而不是先迁移整套：

```text
taskId → runId + attemptId + leaseEpoch
```

完整 Run/Attempt fencing 仍然是合理的后续设计，但不应挡在当前 1.0 主路径之前。

## 3. OS isolation 仍重要，但不是本轮第一刀

我上一版把 isolation class 提到了很高的位置。安全判断本身没有错，但 Claude 这份报告更准确地指出，当前最便宜且最直接的发布风险是：

* subscription lane 无并发上限；
* 同 Agent 不同 session 共用 cwd；
* 厂商订阅使用边界不清晰。

因此 OS sandbox 应继续留在 security roadmap 和 capability matrix 中，但不是当前架构重组的首刀。

# 三、我不同意 Claude 报告中的一个关键推论

## “subscription lane 默认并发 2”不能解决同 cwd 竞争

Claude 建议第一刀增加：

```ts
maxConcurrentSubscriptionTasks
```

默认值建议为 2，并认为这同时关闭了 ToS 风险和同一 Agent home 的 cwd 竞争。

前半句成立，后半句不成立。

报告自己确认：

* 不同 Session 的 lease cwd 仍是同一个 canonical Agent home；
* subscription cap 只约束 subscription lane；
* 建议值是 2；
* `byok` 和 `byok-profile` lane 不受影响。 

因此仍然可能出现：

```text
Claude subscription Session A ─┐
                               ├─ 同时写 agents/foo/
Codex subscription Session B ──┘
```

也可能出现：

```text
Pi BYOK Session A ─────────────┐
                               ├─ 同时写 agents/foo/
Pi BYOK Session B ─────────────┘
```

正确做法是两个彼此独立的控制：

```ts
interface ConcurrencyPolicy {
  // 厂商订阅、额度、ordinary-use 和本机资源控制
  maxConcurrentSubscriptionTasksPerInstallation: number;

  // 文件系统和 Agent memory 正确性控制
  maxConcurrentMutableSessionsPerAgentHome: number;
}
```

建议默认行为：

```text
shared Agent home cwd
  → maxConcurrentMutableSessionsPerAgentHome = 1

isolated workspace per Session
  → 可以显式提高并发

subscription lane
  → 默认 1 更保守，或要求宿主明确配置
```

所以我采纳“并发上限作为第一刀”，但验收标准必须扩展为：

1. 第 N+1 个 subscription task 被 retryable decline。
2. BYOK lane 有独立资源上限。
3. 同一 Agent home 的第二个 mutable session 无论来自哪个 lane 都不得进入。
4. 不同 Agent home 可以并行。
5. 同一 Agent 只有在不同隔离 Workspace 下才可以提高并发。

报告已经把“同 Agent 并发是否是真实产品需求”和默认值列为 owner 决策，这一点是正确的。

# 四、`server/cloud` 合并与删除 WS 应拆成两个决策

Claude 建议：

```text
折叠 server 进 cloud
+ 删除 server WS
+ 删除 client WS transport
```

它的目标是正确的，但我不建议把它们做成一个原子重构。

真正的架构不变量是：

> pairing、task lifecycle、terminal、cancellation、message admission 等语义只有一份实现。

而不是：

> 系统只能存在一种 transport。

建议分两步。

## Step 1：先关闭双权威

```text
@byok-sdk/cloud/domain
  成为唯一 coordination semantics

@byok-sdk/server
  仅作为：
  - in-memory / SQLite composition
  - TaskHandle convenience API
  - transport adapter
```

## Step 2：再决定 WS 去留

若 consumer audit 确认：

* 只有 example 和测试使用；
* long-poll 已满足控制延迟；
* approval/steer 不依赖实时双向 socket；
* 没有下游依赖 WS；

那么删除 WS 是合理的。

但不能把“存在 WS”本身等同于“双权威”。一个共享 domain kernel 上可以安全地同时存在 long-poll 和 WS；有问题的是两套生命周期实现。

# 五、`contentful-trajectory` 不一定违背需求，但必须改写产品承诺

Claude 对这一点的裁决比我上一版更精确。

当前情况是：

* 默认 metadata-only。
* contentful trajectory 需要 capability 和 host policy 双门。
* 云端只保存 TTL-bounded activity tail。
* 但从字面上，它仍然把部分中间文本发到了云端。

因此只有两种一致的产品表述。

### 模式 A：严格 local-only

```text
中间过程永远不离开用户设备。
```

那就必须删除或在部署能力上彻底禁用 `contentful-trajectory`。

### 模式 B：local-first

```text
原始 transcript、workspace、tool trajectory 留在本地；
经显式授权的短期、脱敏活动提示可以进入云端。
```

那就可以保留 `contentful-trajectory`，但必须：

* 明确写成 opt-in exception；
* 有独立 retention；
* UI 显示正在共享什么；
* 宿主提供 `local-first` 固定 preset；
* 单个任务不能偷偷放宽 tenant policy。

Claude 把它保留为 D3 owner decision，而不是直接判为违规，我同意。

# 六、法务发现：方向基本正确，但不能只靠并发上限闭环

Claude 报告自己将联网法务内容标成 fetched，并要求 owner 重新阅读原文。 

我重新核对了当前 Anthropic 官方页面。它现在明确表示：

* 在产品或服务中预装或运行 Claude Code，除非另有协议，要求接受其 Commercial Terms。
* Claude Code binary 不得修改，也不能移除内建认证方式。
* 平台不能替终端用户付费、转售或中介 Claude usage。
* 每个终端用户必须使用自己的订阅、API key 或支持的第三方 provider credential。
* Pro/Max 的宣传额度假设 ordinary, individual usage。
* 第三方开发者不能在自己的应用中提供 Claude.ai login，或代表用户路由个人计划凭证。
* 但终端用户可以在未修改的 Claude Code binary 中亲自登录，即使该 binary 运行于平台提供的环境。([Claude][1])

所以 BYOK 当前的凭证隔离方向是对的：

```text
用户自己在厂商 binary 完成登录
BYOK 不读取、不存储、不转发 OAuth credential
不代付、不转售 token
```

但“加一个并发上限”并不自动等于法务放行。Claude lane 在正式公开推广前仍应完成：

```text
Commercial Terms review
+ 对具体产品模式取得 Anthropic sales / legal clarification
```

OpenAI 当前官方帮助页明确支持 Codex 客户端使用 ChatGPT account 登录，也说明 Codex 消耗账户的共享 agentic allowance；但在我检查的官方资料中，没有找到与 Anthropic 页面同等明确的“第三方产品运行用户自有订阅 Codex binary”的许可说明。OpenAI 当前个人条款同时禁止共享账户凭证、程序化提取数据或输出，以及规避使用限制。([OpenAI Help Center][2])

这不等于 Codex lane 已违规，但意味着：

> Codex subscription lane 不能以“官方没有禁止”为 release clearance。

它应成为独立的书面确认项。以上是架构风险判断，不是法律意见。

# 七、更新后的实施优先级

## 立即修复：低成本、发布风险高

### 1. 两套并发门

```ts

maxConcurrentMutableSessionsPerAgentHome
```

并增加：

* lane 维度 active count；
* Agent home 维度 active mutable writer count；
* retryable decline；
* status/diagnostic readback；

### 2. 公开集成面 golden

冻结并在 CI 比对：

```text
DaemonConfig
RuntimeAdapter
CloudStores
ByokCloud host read surface
protocol message inventory
capability declaration
```

Claude指出短时间内连续 breaking 和架构文档落后数百 commit，这已经直接影响 SDK 的可集成性。

## 1.0 前必须完成

### 3. Agent-only wire v2

* 一种 strict Agent offer。
* fresh/resume discriminated union。
* 删除 legacy task offer 稳态路径。
* 删除 `strictAgentOnly` 这种反向 opt-in。
* capability 只有一份 authority。
* Salesko 做一次性 cutover，无长期 dual-read。

* `server` 不再独立拥有 task/auth/pairing state machine。
* embedded 与 hosted 共享 domain semantics。
* WS 是否删除单独裁决。

### 5. 最小 Session read projection

* `TaskAttempt.sessionRef?`
* `listAgentSessions(agentRef)`
* 只从已持久化 terminal facts 派生
* 不建立云端 live runtime session status

## 后续改进

### 6. Codex app-server PoC

必须先证明：

* fresh；
* resume；
* cancel；
* close/quiescence；
* MCP exact grants；
* permission parity；
* macOS/Linux/Windows；
* native session identity；
* credential isolation。

只有全部通过才替换当前每轮 `codex exec` 进程模型。Claude把这列为 adapter 内部迁移而非协议重构，是正确的。

### 7. 再拆 `create-daemon.ts`

按生命周期组合拆：

```text
enrollment
transport
journal/storage
agent-home/egress
control-plane
presence
runtime composition
```

TaskRunner 等 Agent-only v2 删除 legacy 分支后再判断是否需要继续拆。

# 八、合并后的最终裁决

结合 Claude 发现，我会把之前的架构结论修订为：

## 真正的 P0

1. **同一 Agent home 的多 Session mutable writer 没有完整正确性约束。**
2. **subscription lane 没有独立并发治理和明确法务发布门。**
3. **`server` 与 `cloud` 对同一协议拥有两套协调语义。**
4. **legacy task path 与 Agent-first path 仍作为稳态双轨。**
5. **wire v1 的 additive 演进已经形成 message/capability combinatorial complexity。**

## P1

1. Session 缺少服务端可寻址只读投影。
2. Codex 的 session/steer parity 较弱。
3. 文档、版本和 public API 漂移。
4. `contentful-trajectory` 与“中间态留本地”的产品表述尚未裁决。

## 暂时不要做

1. 不新增 ACP 公共抽象。
2. 不合并所有 Store ports。
3. 不预先把 TaskRunner 拆成三段。
4. 不立即引入完整 Computer/Run/Attempt 数据模型。
5. 不先做大规模 package rename。
6. 不把删除 WS 当作消除双权威的唯一方案。

Claude 的报告最有价值的地方，是把下一步从“大规模理想架构重组”收敛到了几刀可验证的改变。唯一需要补强的是：

> **subscription 并发上限解决用量与法务暴露；Agent-home writer 上限解决状态正确性。两者不能混为一个控制。**

因此，最合理的下一刀不是单独增加一个默认值为 2 的 `maxConcurrentSubscriptionTasks`，而是一次完成一个小型、清晰的 **Concurrency Authority slice**：

```text
per-installation subscription cap
+ per-Agent-home mutable writer cap
+ lane-aware accounting
+ retryable decline
+ status readback
+ cross-lane concurrency regression tests
```

随后立即冻结 public integration golden，再进入 Agent-only wire v2。

# 一、Claude 独立发现中最有价值的部分

Claude 的独立报告补上了我上一轮没有充分处理的四件事。

## 1. `server` 与 `cloud` 是真正的双权威

这不是普通的“代码重复”，而是：

```text
同一套 pairing / task / terminal / cancellation / authorization 语义
由两套互不共享实现分别维护
```

其中一边修复安全问题，另一边可能继续漂移。修订版把它列为 V4，并指出已经存在安全姿态漂移记录，这是一个真实架构问题，不是代码洁癖。

我上一轮只建议把 legacy `dispatch()` 移到兼容面，没有进一步追到这 2,639 行 `ConnectionHub` 所代表的第二协调权威。Claude 这一点判断更强，应当采纳。

## 2. Frozen wire v1 已经失去“版本表达形状”的能力

同一个 wire major 下已经出现：

* 5 种 offer message；
* 20 个 capability flag；
* `strictAgentOnly` 作为本地拒绝门；
* fresh/resume 被拆成不同 offer；
* legacy task 与 Agent task 同时存在。

这说明“frozen + additive”正在把一次领域模型迁移摊平成越来越多的协议例外。修订版明确指出，我之前一方面建议“保留 frozen wire”，另一方面又建议 `deviceId → installationId`、`taskId → runId + attemptId`、增加 `leaseEpoch`，两者事实上互相矛盾：这些就是 wire v2。

这个纠正成立。**应当在 1.0 前切 v2，而不是继续为 v1 增加第六种 offer。**

## 3. Legacy 不是无害兼容，而是默认接纳路径

当前 `strictAgentOnly` 默认关闭，legacy `task.offer` 与 Agent offer 最终汇入同一个大型 `handleOffer()`。这意味着产品已经转向 Agent-first，但协议仍默认接受旧 task-first 语义。

如果已经没有实际下游依赖 legacy，这不是需要长期维护的兼容层，而是应该在 1.0 cutover 中删除的第二权威。

唯一需要保留的谨慎是：报告也承认“legacy 无独立消费者”目前是推断，因为这轮没有读 Salesko。删除前必须对真实下游做一次使用面审计。

## 4. 不应现在把 ACP 变成共享 adapter boundary

Claude 的社区调研指出，现有 Claude/Codex ACP adapter 并不符合本项目的核心要求：它们依赖各自 SDK 或内置 package，而不是控制用户已经安装、已经登录的本机原生二进制。

所以我修正上一轮的表达：

> 可以借 ACP 的 session、prompt、cancel、permission 等概念，但目前不应把 `RuntimeAdapter` 改造成 ACP adapter framework。

正确边界是：

```text
RuntimeAdapter
  ├── native Claude CLI adapter
  ├── native Codex adapter
  ├── native Pi adapter
  └── future AcpRuntimeAdapter（仅当出现具名 ACP-only runtime 消费者）
```

修订版提出的触发条件是合理的：有具名下游需要、ACP v2 脱离 draft、并且该 adapter 能驱动用户安装的本机 runtime，才做 PoC。

AHP 在 Claude 本轮调研中没有得到核实，也不应继续作为本次决策的 load-bearing evidence。

# 二、采纳后的版本最正确的新增部分

修订版采纳的以下六项，我认为都应该正式进入目标架构：

* `Computer` 与 `Installation` 分开：Computer 是逻辑机器，Installation 才是某 SaaS 产品在该机器上的 enrollment、认证与 capability 载体。
* `Session` 由 SDK/control plane 铸造 opaque identity；厂商原生 session locator 永远留在本地。
* `Run` 表示用户逻辑请求，`Attempt` 表示一次实际执行；重试产生新 Attempt，不重写 Run。
* `leaseEpoch` 对迟到 claim、terminal、message、artifact 和 result commit 做 fencing。
* AgentHome、Workspace、SessionState 分离；并发落在 Workspace writer lease，而不是简单放开同一 cwd。
* `local-first-v1` 变成可由 route inventory 和 capability readback 证明的部署 profile，而不是一条容易被 task policy 放宽的默认值。

修订版也正确保留了 keys 的进程边界、14 个 store ports、React-free fold 和当前包名，并拒绝了“为了架构感整体重命名 package”的无收益 breaking。

# 三、我不同意修订版当前的“下一刀”

修订版最终把下一刀定为：

```text
API surface golden + generated release manifest
```

理由是公开 surface 在 24 天内经历了 18 个版本，而 README 仍然指向旧 train。这个工作确实应该立即做。

但我不同意它是**第一刀**。

## 当前先存在一个运行时正确性问题

报告已经确认：

* 同一 Agent 的不同 session 可以并行；
* 所有 session 的 cwd 都是同一个 canonical Agent home；
* 没有并发上限；
* README 和本地存储文档仍声称 one mutable writer。

这意味着现在就可能发生：

```text
Session A 写 MEMORY.md
Session B 同时写 MEMORY.md

Session A 修改 repo 文件
Session B 同时修改相同 repo 文件

Session A 操作 .git/index
Session B 同时操作 .git/index
```

API golden 只能防止接口继续无意漂移，不能阻止当前文件状态损坏。

## 应先加一个临时 P0 writer gate

在 AgentHome/Workspace 尚未分离前，应把 canonical Agent home 暂时视作 mutable Workspace：

```text
一个 canonical mutable home
最多一个 active Attempt
```

这个约束应当：

* 覆盖 subscription、Pi BYOK、provider-profile 等所有 lane；
* 在 `prepare()`、`task.claim` 和进程启动之前拒绝；
* 使用现有 retryable decline；
* 不限制不同 Agent home 的并行；
* session 完成、取消或正确 disposal 后才释放；
* 等 WorkspaceRef 落地后，把锁从 Agent home 移到 Workspace。

不建议恢复 Claude 初版的：

```ts
maxConcurrentSubscriptionTasks
```

因为它只限制 subscription lane，无法阻止：

```text
一个 Claude subscription task
+
一个 Pi BYOK task
```

同时写同一个 Agent home，也无法阻止两个非 subscription task 竞争。Claude 初版后来主要基于厂商条款提出该限制，而修订版已经正确裁定厂商条款不是架构约束。 

因此，实际顺序应是：

```text
P0：same mutable home 单写者临时门
P1：API golden + release manifest
```

而不是反过来。

# 四、实施顺序存在一个更大的倒置

修订版当前排序是：

```text
4. 实现 wire v2
6. 再把 server 折叠进 cloud
```

这会导致一个明显浪费：

> 先在 `@byok-sdk/server` 和 `@byok-sdk/cloud` 两套协调权威中分别实现 Session / Run / Attempt / fencing / v2，然后再删除其中一套。

修订版自己的核心发现正是两套协调权威已经发生语义和安全漂移，因此不应让 v2 再复制一次。

## 正确顺序

设计工作可以先定义 v2，但代码实施应当是：

```text
先收敛协调权威
再实现一次 v2
```

具体为：

1. 用现有 v1 characterization/conformance tests 固定行为。
2. 让 `createEmbeddedCoordinator()` 使用 `cloud` 的同一 async domain kernel 和 in-memory/SQLite stores。
3. 把原 `TaskHandle` 降为对统一 store/read model 的便利 façade，不再拥有第二套 task state。
4. 删除重复的 pairing、auth、task、terminal、cancellation authority。
5. 按已经确认的 owner 决策删除 WS；需要低延迟时可另加非权威的 SSE wake hint。
6. 在这一个统一 kernel 上实现 wire v2。

因此，**D1 的实现必须先于 D2，至少必须先于 D2 的代码落地。**

# 五、Capability 不应被“合并成一个对象”

修订版把 V5 定义为：

```text
wire CAPABILITY_FLAGS
vs
core ADR-010 CapabilityDeclaration
没有交叉校验
```

这个问题存在。

但它建议“并入 ADR-010，成为单一 capability 权威”，这句话容易走得过头，因为这里实际上存在三种不同 authority：

```text
DeploymentCapabilities
  云端部署实际提供哪些 route/store/feature

InstallationCapabilities
  本机 daemon、runtime、toolset、isolation 实际能做什么

RunRequirements
  本次 Run 要求什么
```

它们不能成为同一份事实。例如：

* 云端支持 transcript read，不等于本机允许 transcript read；
* 本机支持 Codex sandbox，不等于部署允许把该内容上云；
* Run 要求某 MCP toolset，不等于设备当前一定配置了它。

正确模型是：

```text
一个 canonical FeatureRegistry
三种不同的 typed projection
```

例如：

```ts
interface FeatureRegistryEntry {
  id: string;
  version: number;
  dependencies: string[];
}

interface DeploymentCapabilities {
  supported: FeatureRef[];
}

interface InstallationCapabilities {
  supported: FeatureRef[];
}

interface RunRequirements {
  required: FeatureRef[];
}
```

准入结果：

```text
RunRequirements
  ⊆ DeploymentCapabilities
  ∩ InstallationCapabilities
  ∩ RuntimeCapabilities
```

所以要统一的是：

* feature ID；
* version；
* prerequisite；
* compatibility rule；
* readback schema。

不能统一的是各 actor 对能力事实的独立 authority。

# 六、wire v2 的方向正确，但目前装得太多

修订版把以下内容装进同一个 v2 work item：

* 单一 offer；
* Session / Run / Attempt；
* SDK sessionId；
* leaseEpoch；
* Installation → Connection → Attempt 三级 token；
* capability 系统合并；
* legacy 删除；
* git workspace 路径删除；
* SessionStore；
* result commit fencing。

方向都合理，但把它们作为一个实现单元，风险会非常高。

建议保持**一个最终 v2 cutover release**，但内部拆成四个独立 work package：

## WP-v2.1：身份与消息形状

```ts
interface RunOfferV2 {
  agentRef: AgentRef;

  session: {
    sessionId: string;
    mode: 'create' | 'resume';
  };

  runId: string;
  workspaceRef: WorkspaceRef;
  runtime: RuntimeSelection;
  requirements: RunRequirements;
  dataPolicyProfile: string;
}
```

目标 Installation 不应由调用者同时写进 payload 和路由参数形成双权威：

```ts
enqueueRunOffer(tenantId, installationId, offer)
```

`installationId` 由 mailbox target 和 coordinator-authored envelope metadata 固化。

## WP-v2.2：Attempt 与 fencing

Attempt 应由 store 原子创建：

```ts
interface AttemptRef {
  attemptId: string;
  leaseEpoch: number;
}
```

所有权威副作用验证当前 Attempt：

* claim；
* approval；
* message egress；
* artifact finalize；
* terminal；
* result context commit。

旧 epoch 的消息只进入 audit evidence，不能改变产品结果。

## WP-v2.3：Session 本地绑定

云端保存：

```text
SDK sessionId
AgentRef
Installation residency
WorkspaceRef
RuntimeRef
contextVersion
product lifecycle open/closed
```

本地保存：

```text
sessionId -> native provider session locator
```

不要把 `thinking / working / awaiting_approval` 存成 Session 权威状态。这些属于：

* 当前 Attempt 的执行状态；
* 或 TTL activity/presence observation。

## WP-v2.4：凭证分层

Buildkite 式 Attempt token 很有价值，但它不是 fencing 正确性的必要前提。

第一版 v2 可以先完成：

```text
device authentication
+
attempt ownership
+
leaseEpoch CAS
```

再增加：

```text
Installation credential
  -> Connection credential
       -> Attempt credential
```

否则 token issuance、renewal、revocation、retry 和 crash recovery 会把 v2 身份迁移拖成一个更大的安全项目。

# 七、不要删除 Git Workspace 能力，应删除旧 authority

修订版提出删除：

```text
git-workspace 路径
SessionWorkspaceStore
```

这里需要更精确。

应该删除的是旧的：

```text
legacy task-scoped gitWorkspace mode
作为与 AgentHome 并列且互斥的 workspace authority
```

不应该删除的是 Git worktree/checkpoint 能力本身。它正好可以成为新的 Workspace backend：

```ts
type WorkspaceBackend =
  | { kind: 'plain-directory' }
  | { kind: 'git-worktree'; repositoryRef: string }
  | { kind: 'copy-on-write'; sourceRef: string }
  | { kind: 'external-project'; approvalRef: string };
```

最终结构应是：

```text
AgentHome
  identity / profile / memory

SessionState
  SDK session mapping / local WAL

Workspace
  actual mutable task files
  backend can be plain or git-worktree
```

所以 v2 应退休的是旧 authority 和旧 store schema，不是 Git 的工作区实现能力。

# 八、Result CAS 不能直接等同于 core TruthStore CAS

修订版正确纠正了我上一轮“不存在 CAS”的表述：`core truth` 已经有 per-key `expectedRev` CAS；真正缺少的是 session-level context version 与 terminal/Attempt 的绑定。

但实现上不应简单变成：

```text
terminal 写完
然后随便向 TruthStore 写一个 ResultEnvelope
```

因为需要同时验证：

* 这是 winning Attempt；
* leaseEpoch 仍然有效；
* terminal 是 first-terminal-wins；
* `baseContextVersion` 等于当前 Session head；
* 同一 Attempt 的重放是幂等；
* context conflict 不覆盖已有结果。

应该增加专门的事务权威：

```ts
interface SessionResultCommitter {
  commit(input: {
    sessionId: string;
    runId: string;
    attemptRef: AttemptRef;
    expectedContextVersion: number;
    result: ResultEnvelope;
  }): Promise<
    | { outcome: 'applied'; contextVersion: number }
    | { outcome: 'idempotent'; contextVersion: number }
    | { outcome: 'context-conflict'; currentVersion: number }
    | { outcome: 'stale-attempt' }
  >;
}
```

Postgres 实现至少要在同一事务中：

```text
validate current Attempt / epoch
read winning terminal
check expected context version
insert immutable ResultEnvelope
advance Session context head
record idempotency receipt
```

可以复用 TruthStore 的 canonicalization/CAS primitives，但**不应让 generic TruthStore 直接成为 Session result transaction authority**。

# 九、D3 不必继续悬而未决：应选“可证明本地”

用户原始需求是：

> 中间态的记录留在用户本地。

这比“默认不上传”更接近一个产品级承诺。

当前实现允许 host 通过 capability 和 task policy 开启 contentful trajectory、workspace/transcript/artifact read 和 memory projection，因此只能证明“默认本地”，不能证明“部署保证本地”。

我的建议是直接裁决：

## 默认公开 profile

```text
local-first-v1
```

其约束：

* 不声明 contentful trajectory；
* 不挂载 transcript/workspace content-read route；
* 不配置 cloud memory projection store；
* ActivityStore 只接受无内容 status；
* task 不能临时放宽；
* capability/readback 可证明当前部署满足该 profile。

## 另一个显式 profile

```text
shared-observability-v1
```

它可以允许受控 trajectory 或 export，但需要：

* SaaS host 明示；
* 最终用户授权；
* retention policy；
* route inventory readback；
* export receipt；
* UI 明确显示哪些内容会离开本机。

这样不会删除已有可观测能力，但不会用一个隐藏的 host flag 稀释 Local Agent SDK 的主要隐私承诺。修订版提出的五级数据分类和 Relay/Store 分名是正确基础。

# 十一、我建议的最终实施顺序

## WP0：当前正确性止血

* 同一 canonical mutable Agent home 只允许一个 active Attempt。
* 所有 lane 统一计数。
* decline 必须发生在 `prepare()` 和 `task.claim` 之前。
* 不同 Agent home 继续并行。
* 加 cancellation、disposal failure、crash residue 测试。

## WP1：公开契约与版本 authority

* `DaemonConfig`、`RuntimeAdapter`、`CloudStores`、host reads 的 `.d.ts` golden。
* golden 是“有意 breaking 变更门”，不是宣称当前 API 已经稳定。
* 生成式 release manifest。
* README、各 package README、CHANGELOG、package version、Pi version、source commit 双向检查。
* 修复当前 0.8.1 / 0.12.0 文档漂移。

## WP2：领域与 v2 ADR

冻结：

```text
Tenant
Computer
Installation
Agent
Session
Run
Attempt
Workspace
ResultContext
```

同时冻结：

* 一事实一权威；
* native session locator 只留本地；
* Session 不保存 runtime 中间状态；
* store-minted Attempt/epoch；
* capability 一 registry、三 projection；
* local-first profile；
* legacy cutover policy。

## WP3A：本地执行边界

* AgentHome / Workspace / SessionState 三分。
* mutable Workspace 单写者。
* 同 Session Run 串行。
* Git worktree 变成 Workspace backend。
* Installation/resource concurrency quota。
* 终态后 memory/result CAS。

## WP3B：协调面收敛

* `server` 复用 cloud domain kernel。
* in-memory/SQLite 实现统一 async ports。
* `TaskHandle` 只做 façade。
* 删除重复 auth/pairing/task/terminal/cancellation 逻辑。
* 删除 WS 和 daemon WS transport。
* 保持 v1 行为完全通过 characterization tests。

WP3A 和 WP3B 可以并行，但都应在 v2 代码切换前完成。

## WP4：一次性 wire v2

* 一种 `run.offer`。
* Session create/resume 判别。
* Run/Attempt/leaseEpoch。
* exact Installation placement。
* current Attempt fencing。
* 删除 legacy offer、`strictAgentOnly` 和旧 workspace authority。
* Salesko exact-pin 后一次性迁移。
* 不保留长期 v1 fallback。

## WP5：结果和数据 policy

* `SessionResultCommitter`。
* `local-first-v1`。
* `shared-observability-v1`。
* ActivityRelay / ActivityStore 分离。
* content export receipt。

## WP6：runtime parity

* Codex app-server。
* IsolationClass 与 minimumIsolation admission。
* RuntimeRef 本地预注册。
* `create-daemon.ts` 按 lifecycle subsystem 拆分。
* 删除 legacy 后再判断 TaskRunner 是否需要进一步拆类。

# 最终结论

**采纳后的版本已经可以作为正式 Architecture Decision Packet 的主体，但还不应原样转成 Sprint。**

最重要的最终修正是：

```text
不是先冻结 API，再慢慢处理共享 cwd；
而是先关掉当前 mutable writer 竞争。

不是先在 server/cloud 两边实现 v2；
而是先消除双协调权威，再实现一次 v2。

不是把所有 capability 变成同一份事实；
而是一个 feature registry，多个独立 authority projection。

不是直接拿 generic TruthStore 当结果上下文；
而是建立 Attempt-fenced、terminal-bound 的 SessionResultCommitter。
```

完成这些修改后，这份联合报告的主线就会非常清晰：

> **短期先修复真实并发风险和集成漂移；中期收敛双协调权威与本地 Workspace 模型；1.0 前一次性切换到 Installation / Session / Run / Attempt 为核心、可证明 local-first 的 wire v2。**
