# #1619: DSH background settlement and wake probe

Date: 2026-11-12. Refs [#1619](https://github.com/Ancienttwo/byok-sdk/issues/1619), especially its evidence-first plan. Repository base: `77c38cb59` (`origin/main` at dispatch). This is step 0 evidence only.

**Result: the implementation gate is not satisfied.** The capture proves completion-triggered root turns occur, but it does not supply a terminal decision for cases 2–5. In particular, silence after `job_kill` or `job_output(wait: true)` cannot prove that no wake will follow. No adapter change is justified by these observations.

There is also a correction to the plan's definition of a wake: every captured completion-triggered `turn_active` has an `inputId`. Its preceding native inbox insertion identifies a generated completion notice, rather than another caller prompt. There are **zero** root `turn_active` records without an input ID across all five cases. That predicate would miss the wakes demonstrated here.

## Capture and timing limits

The five linked `.jsonl` files contain unmodified kernel records selected by event type, in received order: every turn, job, tool, inbox, subagent, status, and error frame. Sequence gaps represent omitted model stream/configuration frames, not reordered events. Kernel `seq` is global to the capture; `body.native.seq` is DSH's per-session sequence. Root and child session IDs are preserved. The [summary](2026-11-12-1619-dsh-wake-probe/summary.json) records each root ID and the pre-disposal observation cutoff.

Unfiltered kernel and bridge stdout captures remain locally at `_ops/1619-dsh-wake-probe-M3dsW4/<case>/{kernel,wire}.jsonl`. The committed lifecycle files retain the full payload of every record material to the gate, including notice sources and inbox targets.

Background commands wait on a file barrier. The observer releases it on the first root `turn_ended`, making completion after that record causal, without estimating the duration of a model turn. Both jobs in case 5 use the same barrier. The child is already running before the root ends; its shell starts after the release in this capture.

For case 4, the observer releases the barrier 100 ms after the native `job_output` tool-call record, so the real `wait: true` tool is exercised. The returned output contains `probe-finished`, not a timeout result. Each case has a 30-second watchdog to fail an incomplete measurement and a 1.5-second observation tail after the expected settlement(s) and initial root end have been seen. These are probe bounds, never an adapter grace period or proof that no later wake exists. Disposal occurs only after that tail; pre-disposal cutoffs are in `summary.json`.

### Case 1: background job

[Raw ordered records](2026-11-12-1619-dsh-wake-probe/background-job.jsonl).

```text
K28  job/registered -> task_started
K41  turn/end(turn=1) -> turn_ended(completed)
K43  job/settled(status=completed, cause=producer) -> task_ended
K44  inbox next-turn insertion, source.kind=tool-jobs, generated notice id
K46  turn/start(turn=2)
K47  inbox claim -> turn_active(inputId=<the generated notice id>)
K59  turn/end(turn=2) -> turn_ended(completed)
```

This is positive evidence of a wake after a job settles. The native `job/settled` data includes ownership, job status, cause, and producer reporting, but no field committing the notification outcome.

### Case 2: background subagent

[Raw ordered records](2026-11-12-1619-dsh-wake-probe/background-subagent.jsonl).

```text
K32  subagent/start -> task_started(agent)
K35  child turn/start
K50  root turn/end(turn=1)
K69  child job/registered
K70  child job/settled -> child task_ended
K83  child turn/end
K85  root inbox next-turn insertion, source.kind=subagent-settled
K87  root turn/start(turn=2)
K88  root inbox claim -> turn_active(inputId=<generated notice id>)
K89  subagent/end(stopReason=completed) -> parent task_ended(agent)
K101 root turn/end(turn=2)
```

`subagent/end` is not ordered before wake activation. An implementation that begins looking for a wake only after receiving that settle would miss the activation already delivered. Tracking an already-active root turn is necessary, but does not by itself establish terminality after its end.

### Case 3: job cancellation

K40  tool/call(name=job_kill, reason=probe cancellation)

The job settles while the initial root turn remains active. The observable trace ends cleanly, but there is no explicit record saying its completion notification was suppressed and cannot subsequently start a root turn.

### Case 4: waiting for output

[Raw ordered records](2026-11-12-1619-dsh-wake-probe/job-output-wait.jsonl).

```text
K28  job/registered -> task_started
K40  tool/call(name=job_output, wait=true, timeout_ms=10000)
K41  job/settled(status=completed, cause=producer) -> task_ended
K42  tool/result(text includes probe-finished; job status=completed)
K54  turn/end(turn=1)
K55  agent/status(idle)
```

The wait returns the completed job's output within the original turn. The records contain no explicit completion-notification decision. A timeout-based conclusion would exceed the evidence.

### Case 5: near-simultaneous completions

[Raw ordered records](2026-11-12-1619-dsh-wake-probe/two-background-jobs.jsonl).

```text
K28  first job/registered
K41  second job/registered
K54  turn/end(turn=1)
K56  second job/settled -> task_ended; finishedAt=1794463696837
K57  completion notice inserted into next-turn
K59  turn/start(turn=2)
K60  inbox claim -> turn_active(inputId=<generated notice id>)
K61  first job/settled -> task_ended; finishedAt=1794463696850
K62  completion notice inserted into next-step
K74  next-step inbox claim
K86  turn/end(turn=2)
K87  agent/status(idle)
```

Completion order reverses creation order. Both jobs have settled by K61, but the second notification has not yet been recorded: it appears at K62. Thus even an empty open-task set at K61 is not a notification-delivery barrier. Delivery may also extend an active turn instead of starting a separate one.

## Missing native contract

For safe termination without a grace timer, the consumer needs a native, causally ordered commitment for each settled item that its completion handling has finished: the notification is suppressed with no later completion wake, delivered into an identified active turn, or queued for an identified future turn that the consumer can track. That commitment must correlate with the job/subagent identity and be ordered before, or atomically with, the final task settlement used to decide completion. An authoritative drain/quiescence barrier with equivalent guarantees could serve the same purpose.

Those are semantic requirements, not a proposed product API or an upstream request. `cause`, `status`, `producerReported`, an idle status, and a finite quiet interval do not provide this contract. Asking DSH to expose it remains the owner's decision under #1619.
