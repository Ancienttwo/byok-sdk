# OAR 0.57.0 source upgrade

The client vendors OAR source rather than depending on its npm package. This
upgrade replaces tag `v0.56.0`, commit
`163d551200fde714a224619519df68f5b217495d`, with tag `v0.57.0`, commit
`0804b915ef511d2880e07d5329450c2484d8d62e`. v0.57.0 is the latest release. The
directory moves from `vendor/oar/163d551` to `vendor/oar/0804b91`. Package
manifests and the Bun lockfile need no change.

## Source and maintained boundaries

All 43 selected source files and LICENSE were compared against both upstream
commits. Five paths changed upstream: `contracts/failure.ts`,
`contracts/records.ts`, `runtimes/codex/session.ts`,
`runtimes/codex/token-usage.ts` and `shared/token-totals.ts`. The other 38
source files and LICENSE retain the same upstream bytes.

One file enters the inventory because a changed selected file imports it:
`shared/session-links.ts` (session). It imports types from
`contracts/session.ts` and `shared/session-kernel.ts`; both were already
vendored. The inventory is now 44 source files and LICENSE. No npm dependency
enters the closure.

Thirty-eight source files keep upstream bytes. The six maintained files do not
change as a set. One of them takes an upstream change:

- `session.ts`: take `newSessionLinks`. A derived frame now carries a
  `session_linked` event only for an edge that is new to the record stream,
  and only once within that frame. The three-way merge had one conflict, in
  the imports. Upstream adds its import next to `withSessionCredentials`,
  which BYOK does not import. The merged block keeps the BYOK imports and adds
  only `newSessionLinks`. The link line itself merged clean.

`app-server-client.ts`, `open.ts`, `rpc-control.ts`, `session-kernel.ts` and
`credential-redactor.ts` have no upstream change. Only their change notices
name the new base. The source manifest records both upstream and maintained
SHA256 values, and the `delta` text of `session.ts` names the 0.57.0 change.

The four other changed paths keep upstream bytes:

- `contracts/failure.ts` adds the `limit_reached` and `output_schema` failure
  classes. Upstream sets them for Claude and Grok. `runtimes/codex/failure.ts`
  did not change, so the Codex fold does not produce them.
- `contracts/records.ts` adds the optional `TokenTotals.reasoning` part of
  `output`.
- `shared/token-totals.ts` adds, subtracts and reads `reasoning` like the
  cache parts.
- `runtimes/codex/token-usage.ts` reads `reasoning` from codex's
  `reasoningOutputTokens` into the derived usage reading.

The JS bridges, their declaration checks, tests, the real Codex smoke script
and the build provenance copy use the new directory. The changelog, ADR,
third-party attribution and the current Codex source contract in the spec
identify 0.57.0. The 0.26.0 release notes, the README and spec release history
and the 0.54 and 0.56 upgrade notes keep their historical source version. The
historical 0.24 release provenance link now points to the retained history in
the new vendor directory.

## Behavior

The SDK behavior does not change. The SDK event projection and the native
interaction bridge read frames with `origin=byok-native` only. The new
`reasoning` part and the deduplicated `session_linked` events are in derived
frames. So they do not reach SDK events.

The SDK already reports Codex reasoning tokens. Its projection reads
`reasoningOutputTokens` from the native `thread/tokenUsage/updated` frame as
the usage event's `reasoningTokens`. That path does not change.

The private bridge declaration exposes no `TokenTotals`, `FailureClass` or
session graph type. The SDK Codex adapter does not call `records()` or
`graph()`. The bridge type check needed no new omission. Codex open, turn and
queue requests from the SDK are unchanged.

Derived frames are retained records. So their serialized size changes by a few
bytes: a usage reading can add `reasoning`, and a repeated edge adds no second
`session_linked`. The fatal retention budget, 16 MiB by default, does not change.

Upstream 0.57.0 also changes the CLI MCP results, the list-models contracts and
readers, Claude launch arguments, failure mapping and inventory, observe
display text and failure advice, the ACP recorder and other runtimes. These
modules are outside the selected closure.

## Validation

All commands ran with Node 24.18.0, Bun 1.4.3, `BYOK_REQUIRE_BUN=1`,
`VITEST_MAX_WORKERS=1`, `BYOK_TEST_BUN_BIN=$HOME/.bun/bin/bun` and a fresh
short `TMPDIR`.

- Targeted OAR session, app-server client, native event projection and owned
  process tests: 4 files, 78 tests passed. Two new cases cover one
  `session_linked` per record stream, with every native frame kept, and the
  native `reasoningOutputTokens` in the derived usage reading only. The link
  case fails when the old link line is restored.
- Every upstream/vendor manifest SHA256 was checked against both pinned
  upstream commits. The closure check found no relative import outside the
  inventory. Built provenance assets match their source files.
- `bun run build`, `bun run typecheck`, `bun run check:api-surface`,
  `bun run check:version-authority` and `bun run test:scripts` (68 tests,
  including the OAR JS/declaration bridge checks): passed. The bridge needed
  no new omission.
- `bun run test`: the client suite passed 3,681 cases and skipped 27, with one
  failure outside the OAR closure. The strict Agent case in
  `agent-memory-guidance.test.ts` waits for `activeTaskCount` 0 and reads 3.
  It uses a stub runtime adapter, not the vendored OAR. It fails in the same
  way alone on this change, on `origin/chore/oar-0.56` and on `origin/main`.
  The sequential run stops after the client, so the other 14 workspaces ran
  separately under the same environment, and all of them passed.
- `bun run check:release-pack` was not run. It is not a required check for
  this change.
- Live Codex provider sessions are outside this validation.
