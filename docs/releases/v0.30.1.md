# 0.30.1 — source candidate

This is release preparation, not a publication record or approval to merge,
tag or publish. Issue #872 holds the scope, the parallel lanes and the
release steps. All nine public manifests and their lock records name 0.30.1.

0.30.1 is a PATCH release under a one-release exception to the pre-1.0
policy. By that policy it would be a MINOR: it adds public API, gated wire
additions and Postgres migration 0028, and it has pre-1.0 breaking changes in
cloud, client and cloud-do. All nine public packages move to 0.30.1. Private
packages remain unchanged.

Registry state. Public npm metadata read on 2026-10-24 at 17:26 UTC reports
`latest` 0.30.0 for all nine packages. keys 0.30.0 depends on exactly
`@byok-sdk/core` 0.30.0. Version 0.30.1 was absent for all nine packages. Recheck before publishing. The published 0.30.0 record is in the
[0.30.0 release notes](v0.30.0.md).

Release rule for `sealed-payload-v1`. A daemon may advertise
`sealed-payload-v1` only in a release that also has E2d (#861, #863, #866)
and §58a (#859, #867, #908) (issue #872). 0.30.0 already had E2c-3 (#840),
`routineRef` (#843) and the daemon template check (#846). 0.30.1 has all of
them, so its daemon now advertises the flag. The daemon recomputes the flag
whenever its member or the deployment declaration changes
(`applyCapabilityDeclaration` in `packages/client/src/daemon/create-daemon.ts`).
It advertises the flag only when both of these hold:

- This run verified the device's E2EE member. The device was paired with
  `byok-agent pair --e2ee` or `pair(code, { verificationSecret })`, and the
  background resume at start verified the member on the chain. A daemon
  created with `DaemonOverrides.deviceCredentials` has no member custody. It
  refuses an E2EE pairing and never advertises the flag.
- The capability discovery of the current connection read a deployment
  declaration that names `e2ee.member`.

Each discovery pass starts by removing the flag, so the first `conn.hello`
of a run never carries it. A refreshed hello adds it when both conditions
hold. The flag is removed again when the member is lost, or when
a discovery fails or times out. The flag does not depend on the server flag
`sealed-output-ciphertext-ref`. Without that flag the daemon keeps sealed
output inline: a terminal over the 256 KiB frame becomes the sealed
`task.fail` with `terminal_result_unsealable`, and an artifact over it
becomes an error event. A device that was not paired with `--e2ee` does not
advertise the flag, so the Host refuses a sealed offer to it before the task
exists, as in 0.30.0.

## Upgrade notes for Hosts and deployments

This section collects the facts that a Host or a deployment must act on at
the upgrade from 0.30.0. The CHANGELOG is the source.

- **Postgres migration 0028.** Apply `deploy/sql/0028_e2ee_scope_shred.sql`
  before 0.30.1 runs on Postgres. It creates the table `e2ee_scope_shred`.
  SQLite adds the table when it opens. Migrations are forward-only (#857).
- **Scope shred (breaking, cloud).** A `shred` subject must be exactly
  `{ scopeId }`. A `shred` entry that a 0.30.0 Host already stored is not
  applied, so that scope keeps its packages and accepts new puts. A stored
  `shred` whose subject is not `{ scopeId }` makes every chain read that
  includes it fail with `e2ee_member_state_unreadable`. Store implementers:
  `E2eeMemberStore.appendChainEntries` takes `{ rows, shreds }`,
  `putScopeKeyPackages` takes `{ rows }` and can return `scope_shredded`, and
  `InMemoryE2eeMemberStore` takes the composition's `RequestReceiptStore`
  (#857).
- **`TenantStores.objects` (breaking, cloud).** `TenantStores` has a new
  required member `objects`. `tenantStoresFor` builds it, so only code that
  builds a `TenantStores` literal must add it (#859).
- **Single-use proof `requestId` (breaking, cloud).** On the three E2EE
  member writes, the device-proof `requestId` is single-use and at most 120
  characters (`TRUTH_REQUEST_ID_MAX_LENGTH`). A longer one, or the same one
  with another binding, gets 409 `proof_request_conflict`. A replay with the
  same binding returns the recorded result. Postgres uses the existing table
  `proof_request_receipt`; SQLite adds it when it opens. Store implementers:
  the append and put inputs take an optional `proof`,
  `E2eeMemberRegistrationInput` takes `request`, and the results can be
  `request_conflict`. `E2eeMemberChainWriter` is renamed `E2eeMemberWriter`,
  and `registerDeviceMemberKey(ctx, deviceId, input)` is now
  `registerDeviceMemberKey(ctx, proof, input)` (#860, #901).
- **One-way pi-durable SQLite schema v2 (breaking, client and cloud-do).**
  pi-durable 1.4.0 migrates a SQLite store to schema version 2 when it opens:
  the client durable store and the cloud-do Durable Object storage. A build on
  Pi 1.3.0 cannot open a migrated store, so there is no rollback to 0.30.0
  or Pi 1.3.0 past this release (#909).
- **Prepared Pi inputs.** A preparation compiled for Pi 1.3.0 declines with
  `preparation_runtime_identity_mismatch`. Prepare it again (#909).
- **Pi model catalog.** `piModelConfigFromPinnedCatalog` returns
  `not_in_catalog` for 11 entries it admitted before, and Together
  `Qwen/Qwen3.7-Max` returns `unrepresentable`. The CHANGELOG lists the
  entries. Saved profiles keep their own `pi_model` config (#909).
- **Runtime failure class.** A failed task carries `failure.class` only when
  the server advertises the new flag `runtime-failure-class`. The reference
  server and the hosted cloud advertise it. Read the class from `task.fail`,
  `TaskResult.failure` and `TerminalResult.failure`; `reason` stays display
  text (#869).
- **`agentMemory: 'read-write-if-admitted'`.** Server and hosted cloud refuse
  the value to a device without the capability
  `agent-memory-read-write-if-admitted`. Upgrade the devices before a Host
  sends it (#833).
- **`Session.events` (type change, client).** `Session.events` is now
  `AsyncIterable<AgentEvent | MessageDraftDelta>`. Code that types each item
  as `AgentEvent` must widen the type or skip `message_draft_delta` items
  (#870).
- **Sealed payload v1 on devices.** A 0.30.1 daemon paired with `--e2ee`
  advertises `sealed-payload-v1` under the rule above, so a Host can send it
  sealed tasks. A terminal sent by `ciphertextRef` that the Host refuses for
  good reaches the Host as no terminal; the journal replace operation comes
  in the next release (`docs/protocol.md` §2.5, owner batch §77b).
- **K8 (example).** K8 `rules/` imports `hash` and `canonical` from the K4
  `./canonical` entry. A Host that copies K8 must resolve that entry (#884).
  `drain()` rejects with `IntentOutcomeError` when a K4 terminal cannot
  apply; the owner call `failStuckIntent(key)` ends such an intent (#882).
- **Hosted example (H).** H has no migrations while it is unreleased. S4
  adds the `scope.due_at` column and the `scope_due` index. A schema that an
  earlier main created does not get them. Create the H schema again (#793).

## Preparation and dry run

Version preparation starts from main
`3623f49c`, the merge of #909. The v3 release registry appends 0.30.1
without changing existing entries, corpora or the published 0.27.0
compatibility floor. The 0.30.1 entry pins 320 envelope lines and 17 HTTP
lines. The envelope corpus grew from 288 lines in 0.30.0: #880 added 6 lines
for `read-write-if-admitted` (#833), and #894 added 26 for the runtime
failure class (#869). The HTTP corpus and its hash do not change. The
reviewed registry baseline moves to the 0.30.0 `latest` read above, for all
nine packages.

After this preparation merges, the owner dispatches the complete matrix
through an explicit `ci.yml` release dispatch, with `release_sha` equal to the
exact merged main SHA. Earlier-SHA, skipped or unexecuted checks are not
passes. The downstream acceptance then runs at that SHA (issue #872). After
the run passes and its accepted `npm-release-pack` artifact is downloaded,
the read-only publication plan is:

```sh
node scripts/release/publish.mjs --artifacts <accepted-final-SHA-artifact-dir>
```

Do not append `--execute` without separate publication authorization. A PR
merge-ref artifact or a local pack is not the accepted release-validation
artifact. This preparation claims no release dispatch, accepted-artifact dry
run, publication or tag.
