# 0.24.0 / keys 0.8.1 — host enrollment, device-proof and retirement surfaces

Prepared on branch `claude/s4-host-surfaces` from `main` at `050349af` (plan
`plans/plan-20260928-0450-web-sealed-provisioning.md`, work package S4). Not
published; publication needs separate Owner authorization.

## Why

On 0.23.0 a Host's local agent could not finish sealed provider provisioning
with `@byok-sdk/client` alone. It had no public way to read its own enrollment
identity (tenant, device, proof key) to fill the provisioning identity snapshot,
no public way to sign the sealing-key registration
(`provider-secret-sealing-key.register`) with the stored device key, and the v8
input-preparation retirement existed only as the `byok-agent` CLI, so a branded
host CLI could not own it and users would have needed `npx` and Node on the
device.

## Packages and version decision

The eight aligned packages `@byok-sdk/core`, `@byok-sdk/protocol`,
`@byok-sdk/client`, `@byok-sdk/server`, `@byok-sdk/cloud`,
`@byok-sdk/cloud-dataplane`, `@byok-sdk/ui-runtime` and
`@byok-sdk/implementation-identity` move to 0.24.0; `@byok-sdk/keys` moves to
0.8.1. The published set stays exactly nine packages.

- **Train: MINOR** under the
  [version policy](../spec.md#pre-10-package-version-policy): `@byok-sdk/client`
  adds public API. Only client source changes; the other seven packages move
  with the aligned train.
- **keys: PATCH.** keys source is unchanged, and it gains no new public
  behavior, API, persistence or security authority. It moves only because its
  packed `@byok-sdk/core` and `@byok-sdk/implementation-identity` edges must
  equal the current dispatch release; both resolve to 0.24.0, whose sources are
  unchanged from 0.23.0. The same reasoning produced keys 0.6.1 and 0.6.2 for
  0.20.0 and 0.21.0. (keys 0.7.0 was a MINOR because the train it bound changed
  accepted security authority; this train does not.)

## What is new (`@byok-sdk/client`)

- **`readDeviceEnrollmentIdentity({ productId, storeDir })`** returns
  `{ state: 'unpaired' } | { state: 're_pair_required' } | { state: 'paired',
  tenantId, deviceId, proofKeyId, proofKeyEpoch, enrollmentRevision }`, with the
  same classification as `readDeviceEnrollmentStatus`. It never returns the
  access token or a key and never writes. `enrollmentRevision` is
  `String(proofKeyEpoch)`: a Host issues the same value from its device row
  (`String(proof_key_epoch)`) as the sealed request's
  `expectedEnrollmentRevision`. It is monotonic across proof-key rotation for
  one device id, and re-pair mints a new device id. The pairing contract
  registers the enrollment key as `identity`/`0` (cloud
  `DEVICE_IDENTITY_PROOF_KEY_ID`/`_EPOCH`, the row's `proof_key_id`/
  `proof_key_epoch`). The pair response carries neither value, so the client
  projects that contract, and a test pairs against the real cloud and compares
  the result with the device row.
- **`createStoredDeviceProofSigner({ productId, storeDir, identity, operations })`**
  returns a frozen `{ operations, sign }` (`HostDeviceProofSigner`, which is
  also a `DeviceProofSigner` for `TruthMemoryClient`). `sign({ method, path,
  operation, resource, requestId, body, issuedAt?, expiresAt?, nonce? })`
  refuses an operation outside the host's non-empty allowlist before reading
  the enrollment. It re-reads the OS enrollment authority for every signature
  and refuses unless tenant, device and proof key still equal `identity`, then
  signs core's canonical device-proof bytes with the Ed25519 enrollment key.
  The signer holds no key material, and failures are `DeviceProofSignerError`
  closed codes (`invalid_options`, `operation_not_allowed`, `invalid_request`,
  `unpaired`, `re_pair_required`, `enrollment_changed`,
  `enrollment_unavailable`, `signing_failed`) with no cause. The allowlist
  scopes one signer instance; it is not a sandbox against code already running
  as the device account.
- **`retireInputPreparation({ productId, storeDir }, input)`** is the library
  form of `byok-agent retire-input-preparation`. `{ mode: 'preview' }` inspects
  and writes nothing. `{ mode: 'execute', confirmed: true }` makes the manifest-backed
  move. Execute refuses, typed and with zero writes, while the daemon control
  socket answers (`InputPreparationRetirementDaemonRunningError`) or another
  process holds the owner lease (new
  `InputPreparationRetirementStoreBusyError`). It also refuses a live pin,
  current, mixed, unknown or missing record versions, unparseable lines, orphan
  artifacts, unexpected entries and symlinks
  (`InputPreparationRetirementRefusedError.reason`). It never deletes or
  converts. The CLI now only renders this function.

## Changed behavior

- The retirement's owner-lease refusal was the internal `DaemonOwnerActiveError`
  in 0.23.0. It is now `InputPreparationRetirementStoreBusyError`, with the
  original as `cause`. The CLI still exits non-zero with zero writes.

## Operator and Host actions

- A Host local agent can now read identity, sign the sealing-key registration
  and run the v8 retirement from its own branded binary. The device needs no
  `npx`, and no separately installed Node for the SDK CLI.
- A Host must issue `expectedEnrollmentRevision = String(proof_key_epoch)` from
  the device row it paired.
