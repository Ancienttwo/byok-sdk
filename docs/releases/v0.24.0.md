## Why

On 0.23.0 a Host's local agent could not finish sealed provider provisioning
with `@byok-sdk/client` alone. It had no public way to read its own enrollment
identity (tenant, device, proof key) to fill the provisioning identity snapshot,
no public way to sign the sealing-key registration
(`provider-secret-sealing-key.register`) with the stored device key. Retirement
of eligible pre-v8 input-preparation records for the v8 cutover existed only as
the `byok-agent` CLI, without a public library call for a branded Host CLI.

A Host also had no way to change an Agent's device-local memory
(`MEMORY.md`, `notes/**`) after the owner approved an edit. The device home is
the only memory content authority, so the change has to be applied there, once,
with a receipt the Host can trust.

## What is new: host surfaces (`@byok-sdk/client`, #239)

- **`readDeviceEnrollmentIdentity({ productId, storeDir })`** returns
  `{ state: 'unpaired' } | { state: 're_pair_required' } | { state: 'paired',
  tenantId, deviceId, proofKeyId, proofKeyEpoch, enrollmentRevision }`, with the
  same classification as `readDeviceEnrollmentStatus`. It never returns the
  access token or a key and never writes. `enrollmentRevision` is
  `String(proofKeyEpoch)`: a Host issues the same value from its device row
  (`String(proof_key_epoch)`) as the sealed request's
  `expectedEnrollmentRevision`. Current source projects the fixed pairing
  contract `identity`/`0`, so the revision is `"0"`; re-pair mints a new device
  id. The pair response carries neither key ID nor epoch. A future proof-key
  rotation must carry the authenticated epoch into the local record and replace
  this projection in the same cut; this read does not currently observe rotation.
  The [enrollment source](../../packages/client/src/daemon/store.ts) and its
  pairing test keep the projection equal to the cloud implementation
  (`DEVICE_IDENTITY_PROOF_KEY_ID`/`_EPOCH` and the device row). That local
  integration test is not a production-cloud acceptance receipt.
- **`createStoredDeviceProofSigner({ productId, storeDir, identity, operations })`**
  returns a frozen `{ operations, sign }` (`HostDeviceProofSigner`, which is
  also a `DeviceProofSigner` for `TruthMemoryClient`). `sign({ method, path,
  operation, resource, requestId, body, issuedAt?, expiresAt?, nonce? })`
  refuses an operation outside the host's non-empty allowlist before reading
  the enrollment. It re-reads the OS enrollment authority for every signature
  and refuses unless tenant, device and proof key still equal `identity`, then
  signs core's canonical device-proof bytes with the Ed25519 enrollment key.
  The signer holds no key material, and failures are `DeviceProofSignerError`
  closed codes (`invalid_options`, `operation_not_allowed`, `invalid_request`,
  `unpaired`, `re_pair_required`, `enrollment_changed`,
  `enrollment_unavailable`, `signing_failed`) with no cause. The allowlist
  scopes one signer instance; it is not a sandbox against code already running
  as the device account.
- **`retireInputPreparation({ productId, storeDir }, input)`** is the library
  form of `byok-agent retire-input-preparation`. `{ mode: 'preview' }` inspects
  and writes nothing. `{ mode: 'execute', confirmed: true }` makes the manifest-backed
  move. Execute refuses, typed and with zero writes, while the daemon control
  socket answers (`InputPreparationRetirementDaemonRunningError`) or another
  process holds the owner lease (new
  `InputPreparationRetirementStoreBusyError`). It also refuses a live pin,
  current, mixed, unknown or missing record versions, unparseable lines, orphan
  artifacts, unexpected entries and symlinks
  (`InputPreparationRetirementRefusedError.reason`). It never deletes or
  converts. The CLI now only renders this function.
- **Input snapshot.** The signer's options and every `sign` request are copied
  once into inert plain data (own enumerable data properties only; accessors,
  Proxies, symbol keys and non-plain prototypes are refused as
  `invalid_options` / `invalid_request`, and `body` must be an exact
  `Uint8Array`). Only that copy is checked against the allowlist and signed, so
  the operation checked is the operation signed. `readDeviceEnrollment*` and
  `retireInputPreparation` read their inputs the same way and reject anything
  else with a `TypeError` that has no cause.

## Changed behavior

- **Tool-less prepared record.** `requiredToolsets: []` with `agentMemory: 'none'`
  is now admitted and launched with zero tools; the offer omits `requiredToolsets`.
  The launch attestation is still bound, and the policy must select no
  native tool (`auto` or `readonly` with `allowTools: []`). Admission binds only the toolsets the record names, and the Pi
  prepared session fails `prepared_registry_drift` when its registered tools differ
  from the manifest. No wire, record, digest, capability or version change.
- The retirement's owner-lease refusal was the internal `DaemonOwnerActiveError`
  in 0.23.0. It is now `InputPreparationRetirementStoreBusyError`, with the
  original as `cause`. The CLI still exits non-zero with zero writes.

## What is new: Agent memory intents (#240, #241)

Authoritative description: [protocol §2.4](../protocol.md#24-task-free-agent-memory-intent-notice),
[spec](../spec.md) "Durable Agent homes", and the
[device memory CAS contract](../researches/2026-09-28-hermes-device-memory-cas-contract.md).
The Host is the only approval authority for a memory change; the device-local
Agent home stays the only memory content authority.

- **Wire (`@byok-sdk/protocol`, `@byok-sdk/core`).** A task-free
  `agent.memory.intent.available` notice (`{ intentId, agentRef }`, strict)
  behind the device capability `agent-memory-intent.v1`. It is
  notice-and-fetch: path, operation, revisions and content never ride the
  mailbox or the device journal. `AgentMemoryIntentV1` plus fetch, completion
  and readback schemas. `operationDigest` is core
  `agentMemoryIntentOperationDigest`, a `sha256:` over the canonical JSON of
  tenant, device, intent, Agent, path, operation, base and target revisions and
  `approvalRef`; content is bound by `targetRevision`, never by the digest.
  All additive under the Freeze rule: `PROTOCOL_VERSION` stays `1`, and
  input-preparation v8 is unchanged.
- **Device (`@byok-sdk/client`).** The Host injects
  `DaemonConfig.agentMemoryIntents` (`fetch` and `complete` on Host routes). Per
  Agent, intents run serially under the Agent-home writer lease, and no network
  call runs while the lease is held. The ledger
  `.byok/agent-memory-intents-v1.json` is the at-most-once authority: `applying`
  is durable before the single sha256 CAS, the terminal (`applied`, `conflict`,
  `uncertain`, `rejected`) is durable before any completion is sent, and
  `ackedAt` is durable before the mailbox cursor advances. A leftover
  `applying` record is never re-executed; it becomes `uncertain`. The identity
  gate `requireBoundIntent` runs first on every `release` and `withheld`
  answer: an `agentRef` different from the notice, or an `operationDigest` that
  does not match a recompute with this device's enrolled tenant and device, is
  `fetch_invalid` with zero ledger writes, zero CAS, no completion and no ack.
  Failures surface as `AgentMemoryIntentNoticeError` with one closed reason and
  the `intentId`.
- **Cloud (`@byok-sdk/cloud`).**
  `ByokCloud.enqueueAgentMemoryIntentNotice(tenant, deviceId, { intentId, agentRef })`
  parses the strict payload, then refuses with `agent_capability_missing` and
  no mailbox row when the device's durable capability snapshot lacks the
  capability or the device row is missing or revoked. While the original
  mailbox row is retained, a retry returns the same row and seq, and a retry
  naming another `agentRef` fails `mailbox_receipt_mismatch`. After acked-row
  retention cleanup (`mailboxAckedRetentionMs`) a retry appends a new row and
  `agentRef` is no longer compared. Cloud records no intent receipt.

### When the capability is advertised

A daemon advertises `agent-memory-intent.v1` only when the Host configured
`agentMemoryIntents`, `agentHome` is configured, the secure memory filesystem
is available, and the ledger write is a proven strict barrier (temp-file fsync,
rename, directory fsync).

- **Linux (native descriptor backend):** advertised after a startup probe
  shows that the Agent-home storage root (`hostStorageRoot`) honors a directory
  fsync.
- **macOS (external filesystem helper):** not advertised. The helper cannot
  prove the barrier or conflict-before-rename ordering.
- **Windows:** not advertised, and fails closed: a notice that reaches a daemon
  without the capability fails `transport_unconfigured` or
  `filesystem_unavailable` before any fetch.

### Known limits

These were accepted as adoption risks, not defects, and are not resolved in
this candidate.

- **Unobservable `applying` residue.** If the target of a leftover `applying`
  record becomes structurally unobservable (a symlink, FIFO or directory leaf, a
  symlinked parent, a lost home identity, a persistent I/O error, an external
  filesystem backend), the notice stays `local_io_failed` and blocks later
  progress on that device's mailbox. There is no operator path. Manual
  filesystem repair is undesigned; deleting targets or the ledger, or skipping
  the cursor, is not authorized.
- **Probe scope.** The startup fsync probe covers only `hostStorageRoot`, once
  at startup. Per-write strict fsync is the execution guarantee, so a home on
  another mount, or a mount that changes at runtime, fails closed per write.

### Host obligations for WP2I-H1

- Send `intentId` as a canonical lowercase UUID. The S1 schema accepts other
  spellings and the cloud message id hashes the raw string, but the device
  compares `intentId` as an exact string, so two spellings are two intents, and
  echoing a different spelling fails `fetch_invalid` / `readback_invalid`.
- Keep `agentRef` fixed per `intentId`. After mailbox retention cleanup, cloud
  no longer compares it. A different `agentId`, or a different
  `profileRevision` once the device row is pruned, fails closed on the device.
  While the row is live, the device replays its stored completion without
  comparing the notice's `profileRevision`.
- Verify every completion against the approved intent; the S1 schema does not
  do this. An `applied` replace needs `result.exists = true` and
  `result.revision === targetRevision`. An `applied` delete needs
  `result.exists = false` and `result.revision` equal to the empty-bytes
  digest while `intent.targetRevision` stays `null`, and a legitimate delete
  must not be rejected as a revision mismatch. Never re-read the current file
  to overturn a historical receipt, and never infer `applied` from hash
  equality. Cover both positive and negative cases.
- Answer `complete` with a durable readback naming this tenant, device, intent
  and completion identity. `recorded` and `idempotent` must echo the completion
  exactly; a `conflict` readback contradicts the device fact and is reported as
  an integrity event.

## Upgrade order for Hosts on 0.23.0

Do not use the former "either order, no drain" instructions. The memory-intent
addition alone is capability-gated, but this candidate also changes runtime,
identity and storage boundaries. Choose and rehearse a coordinated cutover for
the affected composition before reopening admission.

1. **Inventory and fence.** Record Host and SDK source SHAs, exact packages and
   lock digest, Node/native-runtime versions, storage schemas and enabled lanes.
   Pause new affected admissions and memory-intent production. Drain or explicitly
   settle queued/prepared/in-flight work, required message dispositions, pending
   native interactions and old mailbox entries under the old supported stack.
   Do not interpret a disconnected device or missing response as completed work.
2. **Stop and back up.** Stop all affected device/server writers and retain
   consistent backups of durable cloud/device state. For SQLite, include WAL
   state or use its backup facility. The schema marker cannot stop an already-open
   old writer. Preserve Agent homes, journals, receipts, grants and memory ledgers.
3. **Prepare the storage boundary.** For embedded SQLite, check eligibility
   and use the explicit target-v4 adoption described in the server README.
   `v1-to-v4` / `v2-to-v4` require no task, mailbox-message, agent-admission or
   advanced-cursor history (a pristine poll cursor is allowed). `v3-to-v4`
   preserves receipts and identified built-in claims but refuses any owned task
   without `claimed_runtime`, including terminal tasks: do not infer a lost
   harness identity from the offer or current inventory. Remove the migration
   selector after one-shot adoption. Preserve refused databases for reconciliation;
   never reset markers/cursors or delete history to force success. For PostgreSQL,
   verify and apply only genuinely pending ordered migrations through the supported
   runner, in an authorized environment. A fully migrated 0.23 deployment already
   has 0021/0022; this revision adds no SQL file to that set.
4. **Switch the compatible application/runtime cohort.** Stage Node >=24.15.0,
   the selected exact SDK/keys packages and their matching identity closure.
   Update removed Claude approval imports/bin references and unsupported Codex
   policies explicitly; do not silently replace a restrictive policy with `auto`.
   Rebuild V2 runtime plans and launch bindings using the verified installation.
   Recreate stale preparations from current authority. The retirement operator
   only accepts eligible legacy record versions; it is not a general v8 cleanup
   command. Never edit record versions or weaken identity checks. Custom adapters and stores
   must compile against the current API goldens and qualify their own capabilities.
5. **Reconcile before enabling controls.** Start the new compatible components,
   then read canonical task/attempt, mailbox, device capability and pending
   interaction state. Enable memory-intent enqueue only after the configured
   device advertises the capability. A reconnect does not replay an approval,
   question response or other ambiguous mutation. Stale UI forms cannot reply
   to a new process generation. Apply the
   [Host reconnect boundary](../researches/2026-10-06-host-reconnect-boundary.md).
6. **Accept, then reopen.** Run the agreed real-Host scenarios with the same
   candidate tarballs and supported lanes. Record outputs and explicit unsupported
   scope. Reopen admission only after the storage/runtime/capability checks and
   Host acceptance required for that deployment are met.

Hosts still on 0.22.x must first satisfy the
[0.23 upgrade order](v0.23.0.md#upgrade-order-for-hosts-adopting-0230): drain the
v7 preparation boundary, retire old records using the staged newer CLI/library,
move to v8 with explicit `agentMemory`, and adopt the sealed-provisioning request
and custom-store interfaces. This is a coordinated one-time cutover, not a
maintained 0.22/0.23 compatibility mode. Do not skip it because the final target
version is 0.24.

## Rollback and failure handling

- An application downgrade is not a storage downgrade. Never point a schema-v3
  writer at v4 or edit the marker. Restore only through a separately approved,
  rehearsed recovery procedure; restoring an old backup can lose accepted state
  or revive old grants. PostgreSQL migrations are forward-only; validate the
  rollback application's schema contract rather than assume it can use the
  current tables.
- Do not roll a device below the candidate memory-intent implementation while an
  `agent.memory.intent.available` notice may be queued. The 0.23 daemon does not
  recognize it and leaves the executable notice unacknowledged, blocking the
  mailbox. Stop new intent production and reconcile outstanding receipts first.
- Never delete the intent ledger or jump the cursor to clear an `applying` residue.
  Follow the documented uncertain/readback semantics; structurally unobservable
  residue remains a fail-closed operational blocker, not permission to reapply.
- Daemon restart does not transparently resume durable Pi side effects. Old
  native forms and process-local reply channels also do not survive restart.
  Read canonical outcomes; an explicit new execution is a separate decision.
- npm versions are immutable history. Do not overwrite bytes, unpublish packages
  or delete tags as a recovery shortcut. After an uncertain publish, inspect the
  registry first. Partial stable publication and partial prerelease publication
  have different recovery rules; use the
  [release runbook](../../deploy/runbooks/release-responsibility.md).

## Release gates and downstream acceptance

**SDK release gates** retain the approved stable versions and complete ten-package
set, corrected API/migration/support contracts, required build/typecheck/
test/API/version checks and applicable platform/pack/install jobs, final exact-SHA
accepted artifacts, registry preflight/readback, and separate publication approval.

attested Pi package names to the approved closure. Root workspace overrides do
not constrain a downstream install: future upstream sibling range resolution
can fail closed. Decide whether to fix that structural risk or explicitly accept
it before making a longer-term fresh-install stability promise.

**Real-Host acceptance** is a separate evidence gate for product behavior. Fixture
CI, adapter conformance, packed install smoke, and a fixture-only reference Host
prove only their stated scope. They do not prove a real vendor login, paid request,
UI interaction roundtrip, production migration or deployment. Bind a live receipt
to Host SHA, SDK SHA, tarball hashes, consumer lock, OS, Node/Bun/native-runtime
versions, enabled lanes, actions and results. Approval/question testing includes
native IDs, legal replies, denial/cancel, duplicate/late replies, replacement
process generations, and reconnect/restart reconciliation.
