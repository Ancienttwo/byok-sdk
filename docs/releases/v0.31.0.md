# 0.31.0 — source candidate

This is the release preparation record, not a publication record. It does not
approve any merge, tag or publish. Issue #1008 holds the scope and the release
steps. The last published version is 0.30.2 (see the
[0.30.2 notes](v0.30.2.md)). This preparation made no npm registry read, so it
records no registry state; the publication record does. All nine public
manifests and their lock records name 0.31.0.

0.31.0 is a MINOR release under the default pre-1.0 policy, with no PATCH
exception. Issue #1008 states the reason:

> 0.31.0 是 MINOR，按 pre-1.0 规则发，不需要 PATCH 例外：#980 加公开类型和 Postgres 迁移，#925 是 wire v4 的 breaking cutover。

In English: 0.31.0 is a MINOR under the pre-1.0 rule, with no PATCH exception,
because #980 adds public types and a Postgres migration, and #925 is the
breaking cutover to wire v4. All nine public packages move to 0.31.0. Private
packages remain unchanged. `docs/spec.md` names 0.31.0 as the current aligned
release and records no exception ([version
policy](../spec.md#pre-10-package-version-policy)).

These notes do not say that 0.31.0, or a Host on it, is ready for production.
0.31.0 is a transitional release: it carries the wire v4 cutover and the
cleanup that had to ship with it, and the product loop gates (#977, #978) are
not evaluated against it. Until a gate records a result, no statement about
production use follows from this release.

## The owner's decisions

This section lists the owner's decisions for 0.31.0. Decisions 1 to 4 are
recorded in issues #925, #1008 and #1017 and in the PR #1049 description.
Decisions 5 to 8 were given to this preparation by the maintainer, the AiphaBee
one dated 2026-10-29; the publication record should link their issue
comments.

1. 0.31.0 is a MINOR, not a PATCH under an exception (issue #1008).
2. Wire v4 takes both stages of #925 in one release: stage 1 (ADR-034 items,
   `conn.ack`, the old approval peer paths; #1019) and stage 2 (one
   `task.offer`, sealed as a payload property; #1031). There is no release
   between them (issue #925, 2026-10-27).
3. There is no v3 migration. The owner decided on 2026-10-27 that no
   deployment holds wire v3 data, so the one-shot receipt migration planned
   for 0.31.x is not shipped, and #1017 is closed as fixed on main (#1031
   deleted the migration code). A v4 deployment starts on a new store.
4. The server SQLite schema v6 (#1049, for #1035) refuses an older file and
   has no migration; the Host keeps the old file and chooses a new path.
5. 0.31.0 is a transitional release. AiphaBee candidate acceptance is not
   done for 0.31.0 (owner decision, 2026-10-29). The 0.30.1 release had that
   acceptance and 0.30.2 did not; this release does not either.
6. #1092 (user-defined tool rules, #1061) is not in 0.31.0, because it has an
   unresolved P1 finding. The tool authorization of #1078 (`auto | all`) is in.
7. The architecture refactor work of #1093 goes to 0.32.0.
8. The #977 and #978 gates stay pinned to the published 0.30.2. This release
   does not move them.

Publication needs separate owner authorization, after the release matrix
passes on the exact `release_sha`.

## Known limitations

- The tool authorization classifier is lexical. It is not an OS sandbox or a
  file-scope grant, and it does not recognize indirect scripts, `eval` or
  encoded commands. The gate IPC does not isolate against trusted same-user
  extensions (PR #1078).
- Codex questions in `nativeInteractions` have fixture evidence only (PR
  #1078). A Pi extension is Host-authorized executable code (PR #1076).
- Reader-run retention can hold the maintenance lease for the rest of a
  pass's soft budget, which can delay a writer's admission. The default 10
  seconds is not a hard deadline for interruptible I/O (PR #1071).
- A Codex login can still request its own cloud services after plugins are
  disabled ([capability notes](../adapter-capabilities.md), #1060).
- The local checks in the PR bodies were targeted. The full suite and the
  release matrix run on the exact `release_sha`; their results go in the
  dry-run section below and in the publication record.

## Upgrade notes for Hosts and deployments

The [Host upgrade checklist](host-upgrade-0.31.0.md) lists each Breaking entry
and the steps to move from 0.30.2 to 0.31.0. The CHANGELOG is the authority;
when the two disagree, the CHANGELOG wins. In short:

**Order (wire v4).** Drain the v3 deployment, then start the v4 server and the
daemons together. There is no negotiation and no v3 reader.

1. Stop new submissions. Let every pending mailbox row be processed and
   acknowledged, every in-flight execution reach a terminal, and every daemon
   pending terminal be acknowledged.
2. Stop the v3 Host and the v3 daemons.
3. Start the v4 embedded server or hosted cloud on a new store, then the v4
   daemon clients. A Topology L application upgrades both sides together.

There is no v3 receipt migration. #1031 deleted it, and #1017 is closed as
fixed on main. Offer receipts, terminal receipts and mailbox rows hold wire
bytes, and a v4 build reads only v4 bytes. A pending v3 mailbox row stops
startup with `SQLITE_MAILBOX_PROTOCOL_UNSUPPORTED`,
`POSTGRES_MAILBOX_PROTOCOL_UNSUPPORTED` or
`DaemonJournalProtocolUnsupportedError`, and these checks rewrite nothing.
[The wire v4 note](925-wire-v4.md) has the wire changes, the Host API changes
and the Host example (host-execution-core) steps.

**New SQL.**

- Postgres: `0030_task_attempt_phase_times.sql` (#980) adds four nullable
  `timestamptz` columns to `task`: `offered_at`, `claimed_at`,
  `first_output_at` and `terminal_at`. Apply it before the new Host starts. The
  new stores select those columns, so every task query fails on an unmigrated
  database. The runner is forward-only. Attempts stored earlier are not
  backfilled. `git diff --name-status v0.30.2 HEAD -- deploy/sql` lists this
  one added file.
- Server SQLite: the schema is v6 (#1049). An older file is refused at open
  with `SqliteSchemaError` (`SQLITE_SCHEMA_UNSUPPORTED`) and is not rewritten.
  Keep the old file, choose a new path and pair the devices again. There is no
  migration, and the `migration` option is gone.
- The embedded SQLite store adds the `TaskAttempt` columns by itself when it
  opens a v6 file.
- cloud-do and the client journal: older Durable Object storage and a
  `daemon.db` without `withheld_bytes` are refused or must be cleared. No
  cloud-do Durable Object is deployed.

**Daemon config and store.** Delete `workspaceRoot`, `gitWorkspace` and
`strictAgentOnly` from daemon configs: they raise
`DaemonConfigFieldRemovedError`. `byok-agent retire-input-preparation` is gone;
a daemon whose input preparation record log holds an older record refuses that
lane at open, and the fix is to stop the daemon and move
`<storeDir>/input-preparation/` aside. A store configured through a Windows
name alias changes its control pipe name and Agent-home owner identity, so
restart the daemon after the upgrade (#1030).

**Tool approval through `nativeInteractions`.** In 0.30.2 a Host UI answered
Claude `can_use_tool` requests and Codex ran with `approvalPolicy: on-request`.
In 0.31.0 both relay structured questions only. Claude allows a non-question
tool request at once, and Codex runs `approvalPolicy: never` and refuses its
native approval requests. A Host that gated tools this way sets
`DaemonConfig.toolAuthorization` to return `auto` for Claude and Pi ordinary
RPC. Codex declines an `auto` task before claim, so a Host that gated Codex
tools has no tool gate for Codex in this release (#1061, #1078).

**Host code.** Move to the `session` field and the single `task.offer` type;
decide approvals by `approvalId`; build Postgres stores with `createByokPool`;
match the new `dispatch` refusal codes (`agent_capability_missing`,
`agent_task_already_exists`); replace `enqueueOffer`, `enqueueToolsetOffer`,
`enqueueSealedOffer` and `enqueueSealedToolsetOffer` with the Agent methods;
add `recordFirstOutput` to a custom
`TaskAttemptStore`. The checklist has the rows.
