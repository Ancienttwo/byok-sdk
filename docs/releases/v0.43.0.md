# 0.43.0 — release candidate

Prepared on 2026-11-14 from main `0a47fe1b7` (#2147), after the owner approved the 0.43.0 MINOR and selected “start release prep now” in t4 on 2026-11-14 ([decision record in #1933](https://github.com/Ancienttwo/byok-sdk/issues/1933#issuecomment-6869933872); the 2026-11-14 decision supersedes the earlier defaults). The previous published release is [0.42.0](v0.42.0.md). The preparation date must follow the prep merge date if it changes; the publication record will set the actual release date.

This PR prepares a candidate. It authorizes no npm publication, tag, GitHub Release or production rollout. After the preparation PR merges, main stays frozen until the publication-record PR merges. The approved candidate SHA, complete release-validation matrix, accepted tarballs, Host acceptance and publication authorization are still required. The 0.43.0 upgrade-manifest entries are fixed at the cut; later work belongs to the next release after rebaselining in the publication record.

## Version set and release gates

All **nine** public packages use 0.43.0: `@byok-sdk/core`, `@byok-sdk/protocol`, `@byok-sdk/client`, `@byok-sdk/server`, `@byok-sdk/cloud`, `@byok-sdk/cloud-dataplane`, `@byok-sdk/ui-runtime`, `@byok-sdk/bot-collaboration` and `@byok-sdk/keys`. The intended npm channel is `latest`. `@byok-sdk/cloud-do` was archived in #1959 and is excluded; no package joins the train for its first publication.

The [pre-1.0 policy](../spec.md#pre-10-package-version-policy) requires a MINOR for breaking changes and new public APIs. The [upgrade manifest](../../packages/client/upgrade-manifest.json) spans 0.42.0 → 0.43.0 with **15 breaking and 3 additive entries**. Wire remains v6; the protocol registry adds the candidate's 378 envelope and 31 HTTP corpus lines, preserving the published prefixes, the 0.40.0 rejection oracle and the 0.41.0 baseline tarball pins. There is no new Postgres migration or embedded-server SQLite schema version in this cut. Service receipts advance to version 2, and custom journal behavior changes as described below.

The [registry expectations](../../scripts/release/registry-expectations.json) use `priorPublication: existing`, `previousLatest: 0.42.0` for every package. The publisher must recheck registry state. Local prep checks and ordinary PR CI do not replace release validation on the owner-approved SHA. See the [release responsibility runbook](../../deploy/runbooks/release-responsibility.md#release-checklist).

**Additional behavior-only breaking change (#2084).** Default `runtimeEnvironment.base: 'login-shell'` task children now use the daemon's live `HOME`, even if the login startup file exports another home. `PATH`, `XDG_*` and other snapshot-derived values are unchanged and may disagree; pass the needed variables or use `base: 'allowlist'` to keep them consistent. Explicit `HOME` pass and allowlist policies already used the live home. `doctor` marks the pinned value as `sdk`. This is separate from the 15 structurally tracked entries: the manifest cannot yet represent behavior-only changes ([#2117](https://github.com/Ancienttwo/byok-sdk/issues/2117)). ## Changes since 0.42.0

- **Pi embedded extensions are pretranspiled (#1927, #2147).** Bundled Pi products and Bun background runners ship verified jiti templates for the embedded pi-subagents graphs. Each execution materializes its own private cache before Pi loads the extension. An unusable seed disables jiti fs cache for that process and its children before loading, uses in-memory transforms, and reports one local `pi_jiti_seed_unavailable` warning per Host process. Copy the matching runtime assets with the candidate; do not mix an old asset root with the new host.
- **Windows jiti cache keys (#2147).** Materialization and the zero-transform gate use jiti's own resolved filename spelling, which uses forward slashes on Windows. Earlier backslash keys missed the runtime cache. TMPDIR validation now uses jiti's actual recomputation on every platform.
- **New public helpers.** `@byok-sdk/bot-collaboration/host-kit` exports `botTurnInstruction` with `BotTurnInstructionOptions` and `InstructionLimits` (#1978); client exports `StoreCompatibility` (#2076); core's `system-tool` exports `assertNoNulSpawnInput` and `spawnStartError` (#2111). These are the three additive manifest entries.
- **OpenCode qualification (#1972).** The qualified version is 2.3.0. Other versions, including 2.2.6, receive the default warning advisory; Host-defined version policy remains authoritative. Pi stays 1.5.2 and OAR stays 0.103.0.

The Pi seed's measured client growth is **unpacked +8,474,298 B (+8.47 MB)** and **tarball +1,911,051 B (+1.91 MB)**. These are #2147's measurements against main `1c916cb19` at `a3bc052de` using plain build and npm pack dry-run, not measurements of this candidate. The later Windows fix added 245 B to the runtime-host entry and left the seed unchanged; the tarball/unpacked totals were not remeasured for that fix. Release-pack additionally builds native Agent-memory helpers, so its total archive size differs. See [measurement evidence](../researches/2026-11-14-1927-pi-jiti-seed-validation.md).

## Cancel selected Host intents (#2003, #2042)

A Host can replace freeze → individual `cancelHostIntent` calls → `abortSwitch` with `cancelHostIntents(keys, ...by)` for an explicit set of unsubmitted Host-intent keys. Keep freeze/abort if other device work must also be held. The batch validates and settles in one ledger transaction, commits all or nothing, and runs neither `process()` nor `drain()`. Input order is preserved; replay returns `already_settled` with the existing conclusion, and this API never returns `cancel_pending`.

If any key is unknown, a Bot Turn or inflight (including cancel-pending work), the whole batch is refused. `HostIntentError.rejected` lists every refused key/code in input order; `key` and `code` identify the first. Add `inflight` to exhaustive switches and use `cancelHostIntent` for inflight work. Duplicate keys and non-owner calls are refused before per-key checks. A frozen device permits the batch. Successors wait for the next pass; call `drain()` explicitly when they should start now. No ledger schema changes. AiphaBee's adoption remains tracked in [AiphaBee#1141](https://github.com/Ancienttwo/aiphabee/issues/1141).

## Fixes included in the release

- **Credential and process error boundaries (#1946, #2023, #2029, #2051, #2096, #2100, #2008, #2043, #2065).** Provider key changes roll back failed writes and report post-commit failures distinctly. Credential-store errors use fixed messages/codes without original secrets or causes. Spawn validation refuses NUL input and spawn failures expose only the error code; update matchers that depended on command paths. Provider status reads share the configuration lock and can reject `PROVIDER_CONFIGURATION_BUSY`; show busy and retry.
- **Enrollment isolation (#1964, #2033, #2034, #2055).** One store can no longer clear, renew over or replace another store's enrollment/member writes without the explicit replacement flow. This addresses the 0.42.0 multi-store warning.
- **Installation recovery (#2011 and its follow-ups).** `current` prevents startup while stores are partial; recovery respects the committed pointer and avoids restoring over a service's later writes. Same-id repair retains the payload on failure, install-root operations serialize, health checks and platform commands are bounded, symlinked snapshots are refused, and post-commit snapshot cleanup no longer fails the committed operation.
- **Task settlement and journal retention (#1944, #1990, #2054, #2097, #2137).** Offer-owned scratch cleanup does not report runtime disposal failure; settlement waits reread an offer that lands during a journal read and abort promptly; journal appends validate task identity; retention skips failed prunes and continues paging.
- **Runtime sessions (#1940, #1942, #1957, #1949).** Claude bookkeeping growth is reduced; Grok interrupt no longer cancels its next native turn; ACP cancel-write failures permit retry; Pi warming stops at task settlement.

The [CHANGELOG](../../CHANGELOG.md#0430--2026-11-14-candidate) records the full cut.

## Dependency security and Host overrides

The client declares **undici 8.12.4**, but upstream `@earendil-works/pi-coding-agent` 1.5.2 still pins **8.12.3**, affected by six advisories including a high-severity advisory. SDK workspace overrides do not propagate into a Host installation. Add an undici 8.12.4 override in the Host's root package manifest, reinstall and inspect every resolved copy, then rebuild shipped artifacts. npm/Bun use `"overrides": { "undici": "8.12.4" }`; pnpm uses `"pnpm": { "overrides": { "undici": "8.12.4" } }`. See the [complete instructions](host-upgrade-0.43.0.md#undici-in-the-host-dependency-tree-2081), [#2098](https://github.com/Ancienttwo/byok-sdk/issues/2098) and [earendil-works/pi#12159](https://github.com/earendil-works/pi/issues/12159). Built-in Node undici and separately bundled copies need their own runtime/package updates.

**Hono floors (#2118)** are `hono ^4.13.16` and `@hono/node-server ^2.1.6`; this lock resolves 4.13.18 and 2.1.8. The floor includes bot-collaboration's optional testing peer. Refresh old Host pins and lockfiles, reinstall and rebuild bundles; merely bumping SDK packages does not repair a retained vulnerable copy.

## Known issues

- **Pi installed and keys-profile paths (#2163).** These paths do not use the new seed. Their jiti loader still chooses its default cache, which can be adjacent `node_modules/.cache/jiti` shared by executions of one installation. The bundled-path private-cache guarantee does not cover them.
- **Grok attribution (#1942 residual).** A native Grok turn starting while an SDK reply is published can still contribute text and usage to that SDK reply; total usage remains unchanged. Account for this when displaying replies and attributing costs.
- **Retained text (#2056).** Text and reasoning remain unbounded by `maxRetainedBytes`. Set task duration limits where needed; this setting is not a total session-memory bound.
- **Existing snapshot and path hazards (#2102, #2106, #2028, #1962).** Older snapshots are not rechecked for overlap with installation/service state; inspect them before any installation method as the [guide requires](host-upgrade-0.43.0.md#upgrades-commit-through-current-2011). Snapshot restore re-resolves recorded paths: a candidate migration that changes a store symlink can redirect a later restore into service state (#2106). Payload verification also retains concurrent path-mutation limitations. Keep installation parents and payloads under exclusive control; Windows has no install-root owner check.
- **Store aliases (#2161).** Different path spellings of one daemon store can request its lease twice and report `store_busy`; supply each store once under one path spelling.
- **Host cancellation examples (#2142).** The desktop example and routine vector adapter can drop resolved `drainError`. Host integrations must check the actual SDK result before treating cancellation as fully drained.
- **Credential residuals (#2132, #2133).** `available()` can turn a transient backend probe failure into unavailability, consuming a sealed-provisioning generation. An injected store's synchronous `scope()` error can bypass the fixed-message boundary; injected backends must not put secrets in errors.
- **Spawn and wait residuals (#2151, #2134).** NUL `cwd` and synchronous spawn throws have incomplete error-boundary coverage. A Host `readTask` that aborts synchronously before listener registration can leave its wait pending; avoid that synchronous abort pattern.
- **Duplicate adapter ids (#2135).** `createDaemonWithAdapters` does not reject duplicate descriptor ids; Hosts must supply unique ids.
- **Refused steer visibility (#2009).** A refused `task.steer` is acknowledged/dropped and logged locally without a dedicated Host result; acknowledgment is not runtime acceptance.

These are release limitations to assess during candidate acceptance, not a claim that the owner has accepted every one for publication. macOS Developer ID signing/notarization/stapling (#1904), real Windows Agent-memory acceptance (#605), and real hosted Workers/two-device acceptance (#654, #794) retain their separate evidence and authorization requirements.

## Host upgrade order

1. Apply earlier checklists if coming from before 0.42.0. Retain matching binaries, assets and store snapshots. With SDK 0.42.0, finish any pending version-1 service receipt using `recover()` before replacing the SDK. Inspect older snapshots for service-state overlap before any new installation method.
2. Update all installed public packages together to the accepted 0.43.0 tarballs, remove or pin archived cloud-do, apply the undici override and Hono floors, and rebuild the Host with matching Pi assets. Implement the import, error-union, custom journal, credential-backend and committed-cancel changes above. Compile the Host against the candidate.
3. **On every macOS device, before its first upgrade or rollback, use the new SDK to call `install()` on the same installation with the payload id that is currently installed.** Read `currentVersion()` and keep the payload whose `readPayloadManifest(dir).id` matches it. This rewrites the launchd unit with the installation HOME; a different payload id is refused. Then perform the upgrade. [AiphaBee#1156](https://github.com/Ancienttwo/aiphabee/issues/1156) tracks the downstream step. Verify task HOME and any derived PATH/XDG variables (#2084).
4. Stop store owners, run candidate store inspectors (including `inspectLedger`), snapshot, perform any reported explicit migration and precheck again before serving. Run Host store migration programs only through the installation's preparation protocol; do not restore over a present committed `current`.
5. Exercise selected-set cancellation and post-commit failure handling, enrollment replacement, settlement/retention and installation recovery using the accepted candidate. Adopt the #2003 batch API where needed ([AiphaBee#1141](https://github.com/Ancienttwo/aiphabee/issues/1141)); call `drain()` separately if successors should start immediately. Inspect service timeout `exitConfirmed` and recovery receipts before retrying operations.
6. Complete exact-SHA release validation and Host acceptance, including the owner-controlled signing work. Obtain separate publication approval. After publication, record registry digests/tag/run evidence, archive and rebaseline the manifest in the publication-record PR, then reopen main when that PR merges. Downgrading binaries does not undo store or receipt changes: restore the matching pre-upgrade state and artifacts together.
