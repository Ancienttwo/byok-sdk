# 0.43.0 — release candidate

Prepared on 2026-11-14 from main `bd193cf82`, after the owner approved the 0.43.0 MINOR and selected “start release prep now” in t4 on 2026-11-14 ([decision record in #1933](https://github.com/Ancienttwo/byok-sdk/issues/1933#issuecomment-6869933872); the 2026-11-14 decision supersedes the earlier defaults). The previous published release is [0.42.0](v0.42.0.md). The preparation date must follow the prep merge date if it changes; the publication record will set the actual release date.

This PR prepares a candidate. It authorizes no npm publication, tag, GitHub Release or production rollout. After the preparation PR merges, main stays frozen until the publication-record PR merges. The approved candidate SHA, complete release-validation matrix, accepted tarballs, Host acceptance and publication authorization are still required. The 0.43.0 upgrade-manifest entries are fixed at the cut; later work belongs to the next release after rebaselining in the publication record.

## Version set and release gates

All **nine** public packages use 0.43.0: `@byok-sdk/core`, `@byok-sdk/protocol`, `@byok-sdk/client`, `@byok-sdk/server`, `@byok-sdk/cloud`, `@byok-sdk/cloud-dataplane`, `@byok-sdk/ui-runtime`, `@byok-sdk/bot-collaboration` and `@byok-sdk/keys`. The intended npm channel is `latest`. `@byok-sdk/cloud-do` was archived in #1959 and is excluded; no package joins the train for its first publication.

The [pre-1.0 policy](../spec.md#pre-10-package-version-policy) requires a MINOR for breaking changes and new public APIs. The [upgrade manifest](../../packages/client/upgrade-manifest.json) spans 0.42.0 → 0.43.0 with **21 breaking and 4 additive entries**. Wire remains v6; the protocol registry adds the candidate's 378 envelope and 31 HTTP corpus lines, preserving the published prefixes, the 0.40.0 rejection oracle and the 0.41.0 baseline tarball pins. There is no new Postgres migration or embedded-server SQLite schema version in this cut. Service receipts advance to version 2, and custom journal behavior changes as described below.

The [registry expectations](../../scripts/release/registry-expectations.json) use `priorPublication: existing`, `previousLatest: 0.42.0` for every package. The publisher must recheck registry state. Local prep checks and ordinary PR CI do not replace release validation on the owner-approved SHA. See the [release responsibility runbook](../../deploy/runbooks/release-responsibility.md#release-checklist).

## Migrating from 0.42

Apply the relevant steps in order, before serving traffic. Each item names the affected Host surface and points to the detailed checklist.

1. **committed-cancel-drain-error** — HostExecutionCore.cancel returns an object instead of void (#2004); update callers requiring `Promise<void>`. Its result and BotCollaboration.cancelTurn/cancelHostIntent/abortSwitch retain wakePending: true for wake-only failure and add drainError?: unknown for other post-commit failures (#2072, #2144). cancelHostIntent callers move post-commit failure handling from catch to the resolved HostIntentCancelResult, including later process failures. Its cancelled result confirms a committed cancel; conclusion can be absent until a later successful drain settles it. Replay after drain/recovery to read already_settled with the conclusion, or cancel_pending while a submitted intent awaits its terminal. The coalesced drain can fail on other Host work. Check property presence, report the unchanged rejection (the whole AggregateError for mixed failures), and retry pending work through drain/recovery, not the committed operation. cancelTurn and cancelHostIntent retain the first non-wake failure even if a later pass succeeds. Explicit drains and pre-commit failures still reject; job/outbox retry state is unchanged. See committed-cancel-wake-pending for WakeDispatchError and bot-collaboration-cancel-host-intents for the additional BotCollaboration cancellation API. [Host upgrade steps](host-upgrade-0.43.0.md#committed-cancellation-with-a-drain-failure-2072).
2. **sealed-provisioning-store-unavailable-retry** — @byok-sdk/keys applySealedProviderProvisioning() no longer records secret_store_unavailable or consumes operationGeneration when available() is false before any credential write (#2132). Hosts must use readSealedProvisioningResult() before completing a providerProvisioning notice: for absent, throw without completing or acknowledging and retain the request and ciphertext for retry after store recovery; for completed, submit readback.result; for conflict or interrupted, apply the same request again and submit that result, propagating throws to leave the notice unacknowledged. Retries still pass all admission checks. Credential-write failures remain recorded and pending; if the Host already stored an unrecorded rejection as terminal, submit a new request at the same generation. [Host upgrade steps](host-upgrade-0.43.0.md#sealed-provisioning-retries-an-unavailable-credential-store-2132).
3. **duplicate-injected-adapter-ids** — @byok-sdk/client createDaemonWithAdapters(config, adapters) now throws DaemonConfigInvalidError synchronously for duplicate descriptor.id values instead of accepting the array and selecting the first matching adapter (#2135). checkDaemonConfig(config, { source: 'embedded', adapters }) rejects the same input with ok: false and matching invalid_value issues at adapters[i].descriptor.id. Hosts must register one implementation per ID, or give distinct custom runtimes distinct IDs and update routing; correct the adapter list before retrying construction. [Host upgrade steps](host-upgrade-0.43.0.md#unique-injected-adapter-ids-2135).
4. **direct-command-start-errors** — @byok-sdk/client credential APIs now classify provider startup rejection as DeviceCredentialStoreUnavailableError with a sanitized code-bearing cause, and @byok-sdk/keys runCommand rejects startup failures instead of synthesizing exit 127. NUL input is refused before direct spawns, including cwd for durable Pi shell and lifecycle commands; startup errors discard original details while retaining string code. Hosts catch startup failures, inspect code/cause.code, handle keys CommandInputError separately, and let available() perform its own boolean mapping. Client device credentials, macOS keys and Windows Pi ACL queries distinguish real exit 127 from unavailable tooling. Linux keys distinguish signal/input failures but keep KEYCHAIN_UNAVAILABLE for non-absent nonzero exits, including 127. NUL preflight remains an input-validation rejection outside availability translation; boolean available() probes still catch failures (#2184). [Host upgrade steps](host-upgrade-0.43.0.md#command-startup-failures-and-real-process-outcomes-2184).
5. **command-process-outcomes** — @byok-sdk/keys CommandResult uses number|null exitCode with optional signal for signal termination. Hosts check signal before numeric exit status and update injected runners. @byok-sdk/client DeviceCredentialStoreUnavailableError accepts ErrorOptions and exposes a sanitized code-bearing cause for provider start failures (#2184). [Host upgrade steps](host-upgrade-0.43.0.md#command-startup-failures-and-real-process-outcomes-2184).
6. **task-home-live** — @byok-sdk/client DaemonConfig.runtimeEnvironment and `runtimes.<id>.runtimeEnvironment` now give task children the daemon's live HOME under the default login-shell base (#2084), instead of the startup snapshot's HOME. A startup file that exports another HOME no longer redirects task HOME. PATH, XDG_* and other snapshot-derived paths are unchanged: pass consistent live values explicitly or use base: 'allowlist'. Policies already passing HOME or using allowlist keep their behavior. [Host upgrade steps](host-upgrade-0.43.0.md#behavior-only-upgrade-notices-2117).
7. **service-store-release-failures** — Store lease and gate release failures preserve a refused ServiceInstallationError and its code, with the refusal and all release failures in its AggregateError cause; Hosts that matched the 0.42.0 AggregateError on first install must read cause instead. The code follows the outcome (#2010): a call that leaves its receipt pending or its stores unrestored throws upgrade_pending with every failure in its cause, so the Host runs recover(), first restarting the Host process if a stuck lease makes it fail with store_busy; a preparation error that is not the SDK's own is the new store_preparation_failed with the original error as its cause. The same type gains install_root_foreign_owner (#2001): every ServiceInstallation operation holds an install-root gate, so a second operation on one install root fails at once with lifecycle_owner_busy, and an install root owned by another user is refused before anything changes. An install root another user could rename or replace is install_root_ancestor_unsafe (#2028): on POSIX the root's path is resolved one component at a time, and every directory read must belong to the user or root and not be world-writable without the sticky bit, and every link on the way must belong to the user or root (at most 40 links). A .. in the install root, a directory on the way the user cannot read, or a .. after a missing directory in a link target is refused before anything is created; the root itself owned by another user stays install_root_foreign_owner. The receipt commit protocol (#2011) adds receipt_upgrade_required, receipt_state_inconsistent, switch_unhealthy, repair_interrupted and service_program_not_current (see service-upgrade-receipt-v2), and store_overlaps_service_state: a precheck store that is, holds or lies in the install root or a daemon store's service/ directory, after resolving links and without case on darwin and win32, is refused before it is snapshotted. Two stores that are or lie inside each other, as written or with links resolved, are precheck_failed (#2106) at the precheck and before a restore; split such stores. A snapshot SDK 0.42 took is snapshot_upgrade_required before anything changes (#2106): finish or abandon that upgrade with SDK 0.42, then upgrade. A manifest listing two paths that a volume ignoring letter case or Unicode normalization could store as one, byok-payload.json included, is payload_name_collision (#1962), and verifyPayload always receives a fresh staged copy, never `versions/<id>`. A daemonStores() list that names one store twice, also through a link or in another case, is daemon_stores_invalid before any lease (#2161); before, the second spelling failed with store_busy after stopTimeoutMs. [Host upgrade steps](host-upgrade-0.43.0.md#store-release-failures-name-the-next-step).
8. **service-upgrade-receipt-v2** — upgrade-receipt.json is version 2 (#2011): ServiceUpgradeReceipt.version is 2 and a pending receipt carries kind (upgrade, rollback or repair). recover() acts on the kind, the code and where current points, starting a present current as it is instead of restoring the snapshot over its writes; a candidate found unhealthy is failed with switch_unhealthy and nothing starts, and an interrupted same-version reinstall is repair_interrupted. A pending version 1 receipt is receipt_upgrade_required: run recover() with SDK 0.42 before upgrading the SDK; a final one reads as version 2 and the next write stores version 2. Hosts that parse the receipt accept version 2 and kind; Hosts that switch on codes handle the five new ServiceInstallationErrorCode values. createServiceInstallation refuses a program that does not run from current, and upgrade() and rollback() a unit the SDK did not write, with service_program_not_current. [Host upgrade steps](host-upgrade-0.43.0.md#upgrades-commit-through-current-2011).
9. **keys-secret-corrupted-code** — macOS Keychain and Linux Secret Service report an SDK entry that does not decode as the new KEYCHAIN_SECRET_CORRUPTED instead of KEYCHAIN_SECRET_DECODE_FAILED, and ProviderRegistry.replaceSecret/configure overwrite it with a new key. KEYCHAIN_SECRET_DECODE_FAILED now means an entry the SDK did not write; the registry never overwrites it and refuses before any write. A Host that offered 'enter the key again' for KEYCHAIN_SECRET_DECODE_FAILED offers it for KEYCHAIN_SECRET_CORRUPTED and shows delete, rename or other-profile guidance for KEYCHAIN_SECRET_DECODE_FAILED. ProviderRegistry.configure/replaceSecret/setDefaultModelProvider/delete reject with the new PROVIDER_CHANGE_COMMITTED when the change committed but a later step (the auth-none key delete, an unconfirmed profile-store write or the lock release) failed; treat it as success and read the status again. ProviderRegistry.configure without a secret reuses the stored key only for an authenticating profile with an unchanged base_url and otherwise rejects with PROVIDER_SECRET_MISSING. [Host upgrade steps](host-upgrade-0.43.0.md#provider-key-changes-roll-back-on-failure-1946).
10. **bot-collaboration-cancel-host-intents** — cancelHostIntents atomically cancels selected unsubmitted Host intents without a pass. HostIntentError.rejected lists all refused keys and code gains inflight; update exhaustive switches. Existing cancelHostIntent, drainForSwitch and abortSwitch retain their other behavior, and the store format is unchanged; see committed-cancel-wake-pending for the wake-dispatch change. Hosts may replace freeze, individual cancels and abort with this call, retaining freeze when other device work must be held. Successors wait for a later pass or an explicit drain(). [Host upgrade steps](host-upgrade-0.43.0.md#cancel-selected-host-intents-without-a-pass-2003).
11. **bot-collaboration-ledger-precheck** — The local bot-collaboration entry exports inspectLedger(path, tenant), a read-only precheck returning StoreCompatibility. It reports migration-required for would-do rows without turnId; run migrateWouldDo after snapshot and before serving. LocalStoreId gains bot-collaboration-ledger; Hosts with exhaustive switches or `Record<LocalStoreId, ...>` must add this member. [Host upgrade steps](host-upgrade-0.43.0.md#ledger-precheck-and-store-id-1981).
12. **journal-prune-cutoff** — Custom LocalTaskJournal implementations must accept the new cutoff argument of pruneConfirmedJournalTask(taskId, cutoff) (#1990) and recheck it in the delete transaction under the write lock. It returns false and deletes nothing when the task is valid but not prunable: a confirmed terminal last updated at or after cutoff, or a received offer whose first stored task.cancel sequenced above the offer was committed at or after cutoff (including evidence replaced under the same task id) or that has no such cancellation. For a received offer it throws and deletes nothing when the task.cancel that qualifies it fails its hash or enrollment check, names another task id, or carries a seq different from its row's. A confirmed terminal's envelopes, withheld rows and the task's other envelopes are not verified before deletion. An implementation that ignores cutoff still compiles but can delete unexpired or replaced evidence; the SDK does not repeat these checks. A custom LocalTaskJournal must also implement the new optional after argument of listPrunableConfirmedTasks(cutoff, limit, after) (#2137): list only tasks strictly greater than after's (at, task_id), and nothing when after is no longer listable. Confirmed-journal retention pages past tasks it could not prune with it; a page that returns such a task again fails the sweep with LocalStorageConfigError, reported as sweep_failed. [Host upgrade steps](host-upgrade-0.43.0.md#stored-cancellation-pruning-cutoff).
13. **path-gate-release-failures** — A path mutation gate release that fails while another error is thrown is kept: PathMutationGateBusyError, ServiceUnitError and LocalStateRelocation errors keep their class and code with an AggregateError of the original error and the release failures in cause, and an error of another class from a managed service lifecycle operation becomes that AggregateError. ServiceUnitError and the LocalStateRelocation error classes accept ErrorOptions. Hosts that read the original error of such a failure read it from cause. [Host upgrade steps](host-upgrade-0.43.0.md#gate-release-failures-join-the-thrown-error).
14. **service-command-timeout** — ServiceUnitErrorCode gains service_command_timeout (#1971): a platform command a service lifecycle or installation ran (launchctl, systemctl --user, WinSW, sc.exe, the Windows Startup launcher query and launch, the Host's Windows stop program, or icacls when a ServiceInstallation leases a store on Windows) outlived its fixed bound and was stopped, where the operation could hang before. Where it is reported: every ServiceInstallation operation's restore of an earlier install's repair snapshot (when current is absent) is upgrade_pending on a timed-out stop or lease; install() throws a timed-out stop or store lease before anything is installed as is, and a timed-out activation, start or cleanup removal is install_health_check_failed with it in cause (upgrade_pending when cleanup cannot restore the stores); a same-version reinstall throws a timed-out stop as is and keeps its pending repair receipt; upgrade() is upgrade_pending on a timed-out stop or lease before the switch, health_check_failed with it in cause on a timed-out candidate start (upgrade_pending when the rollback's stop or lease times out too), and keeps a store refusal's code when the restart of the previous version times out; rollback() throws a timed-out stop or lease as is but resolves with a failed rollback_unhealthy receipt on a timed-out start; recover() is upgrade_pending on a timed-out stop or lease before a restore but resolves with a failed receipt on a timed-out start; uninstall() throws a timed-out stop, unregistration or daemon-reload as is; the lifecycle's own operations reject with it as is. The service's state is then unknown, never "the change did not happen". ServiceUnitError gains exitConfirmed, set only with this code: true when the command is proven to have exited, false when it may still run and change the service, so a retry can race it. An exhaustive switch over ServiceUnitErrorCode needs the new case. [Host upgrade steps](host-upgrade-0.43.0.md#service-manager-commands-time-out-1971).
15. **secure-dir-command-timeout** — SecureDirHardeningError gains a code (secure_dir_hardening, or secure_dir_command_timeout) and exitConfirmed (#2116). On Windows an icacls run that outlives its 30 s bound while ensureSecureDir() or another SDK operation hardens a directory now rejects with SecureDirHardeningError code secure_dir_command_timeout instead of an internal, unexported timeout class. The ACL's state is then unknown, never "it was not applied". exitConfirmed is set only with the timeout code: true when the stopped icacls has exited, so run the operation again; false when it may still run and change the ACL, so a retry can race it. A Host that narrows ServiceUnitError | SecureDirHardeningError with `code in error` and then exhausts the service codes no longer compiles or routes correctly: SecureDirHardeningError now carries code, so branch on instanceof SecureDirHardeningError first, then on code (secure_dir_command_timeout versus secure_dir_hardening) and exitConfirmed. A ServiceInstallation store lease still reports a timeout as ServiceUnitError service_command_timeout. The public support-bundle export is unchanged: exportDeviceSupportBundle still rejects with DeviceOperatorError operation-failed. [Host upgrade steps](host-upgrade-0.43.0.md#windows-acl-hardening-timeouts-are-hardening-errors-2116).
16. **enrollment-clear-store-scope** — clearDeviceEnrollment and Daemon.unpair() no longer delete another store's credential or staged first pairing under the same productId: they hold a per-user productId lock from validation through deletion, and pairing takes it across its credential writes, each waiting up to 30 seconds. FirstPairingAttempt gains storeIdentity (DeviceStore.identity, the SHA-256 hex of the resolved storeDir); an injected DeviceCredentialBackend keeps every attempt field, or the store's own attempt is refused. A clear refuses another store's attempt as store_not_bound and an attempt that names no store (staged by 0.42.0) with the new DeviceEnrollmentClearErrorCode pairing_attempt_unattributed; clearDeviceEnrollment({ ..., clearUnattributedAttempt: true }) deletes it. Pairing applies the same rule (#2033): it reuses only its own store's staged attempt and otherwise throws the new FirstPairingAttemptRefusedError (store_not_bound, which replaceOtherStore discards, or pairing_attempt_unattributed). A running daemon's token renewal takes the same lock around its write and writes only while the OS entry still holds its store's enrollment; otherwise the daemon halts as store_not_bound or re_pair_required (#2034). Handle these halts while the daemon is running by pairing the store again, as at startup. If another store paired over it, re-pairing throws DeviceStoreBindingMismatchError; pair with replaceOtherStore to replace the other binding. [Renewal and re-pairing steps](host-upgrade-0.43.0.md#renewal-checks-the-enrollment-binding-2034). A renewal never holds the lock across a network request. A pairing is one critical section: it rereads the enrollment and staged attempt under the lock, never a cached record, refuses another store's or an unattributed attempt even beside its own enrollment, and holds the lock across its own request, because server registration has no fencing, and through its E2EE member entries. A running daemon's member resume and KEM rotation write the member entries only under the same lock while its enrollment still holds, otherwise they write nothing and the daemon halts the same way (#2055). BlobClient and InstallSkillPacksOptions change only through the types they reference (#1964). [Host upgrade steps](host-upgrade-0.43.0.md#enrollment-clear-is-scoped-to-its-store-1964).
17. **retained-records-one-policy** — maxRetainedBytes (default 16 MiB) bounds only native and tool payloads: past it the oldest are elided in place and the task keeps running; it also covers runtime request and reply native payloads. ## Changes since 0.42.0

- **Pi embedded extensions are pretranspiled (#1927, #2147).** Bundled Pi products and Bun background runners ship verified jiti templates for the embedded pi-subagents graphs. Each execution materializes its own private cache before Pi loads the extension. An unusable seed disables jiti fs cache for that process and its children before loading, uses in-memory transforms, and reports one local `pi_jiti_seed_unavailable` warning per Host process. Copy the matching runtime assets with the candidate; do not mix an old asset root with the new host.
- **Windows jiti cache keys (#2147).** Materialization and the zero-transform gate use jiti's own resolved filename spelling, which uses forward slashes on Windows. Earlier backslash keys missed the runtime cache. TMPDIR validation now uses jiti's actual recomputation on every platform.
- **New public helpers.** `@byok-sdk/bot-collaboration/host-kit` exports `botTurnInstruction` with `BotTurnInstructionOptions` and `InstructionLimits` (#1978); client exports `StoreCompatibility` (#2076); core's `system-tool` exports `assertNoNulSpawnInput` and `spawnStartError` (#2111). The manifest also records the additive `retention-failure-task-id`.
- **OpenCode qualification (#1972).** The qualified version is 2.3.0. Other versions, including 2.2.6, receive the default warning advisory; Host-defined version policy remains authoritative. Pi stays 1.5.2; OAR is 0.105.0 (#2187), fork `byok/0.105.0` at `261241f2`.

The Pi seed's measured client growth is **unpacked +8,474,298 B (+8.47 MB)** and **tarball +1,911,051 B (+1.91 MB)**. These are #2147's measurements against main `1c916cb19` at `a3bc052de` using plain build and npm pack dry-run, not measurements of this candidate. The later Windows fix added 245 B to the runtime-host entry and left the seed unchanged; the tarball/unpacked totals were not remeasured for that fix. Release-pack additionally builds native Agent-memory helpers, so its total archive size differs. See [measurement evidence](../researches/2026-11-14-1927-pi-jiti-seed-validation.md).

## Cancel selected Host intents (#2003, #2042)

A Host can replace freeze → individual `cancelHostIntent` calls → `abortSwitch` with `cancelHostIntents(keys, ...by)` for an explicit set of unsubmitted Host-intent keys. Keep freeze/abort if other device work must also be held. The batch validates and settles in one ledger transaction, commits all or nothing, and runs neither `process()` nor `drain()`. Input order is preserved; replay returns `already_settled` with the existing conclusion, and this API never returns `cancel_pending`.

If any key is unknown, a Bot Turn or inflight (including cancel-pending work), the whole batch is refused. `HostIntentError.rejected` lists every refused key/code in input order; `key` and `code` identify the first. Add `inflight` to exhaustive switches and use `cancelHostIntent` for inflight work. Duplicate keys and non-owner calls are refused before per-key checks. A frozen device permits the batch. Successors wait for the next pass; call `drain()` explicitly when they should start now. No ledger schema changes. AiphaBee's adoption remains tracked in [AiphaBee#1141](https://github.com/Ancienttwo/aiphabee/issues/1141).

## Fixes included in the release

- **Credential and process error boundaries (#1946, #2023, #2029, #2051, #2096, #2100, #2008, #2043, #2065).** Provider key changes roll back failed writes and report post-commit failures distinctly. Credential-store errors use fixed messages/codes without original secrets or causes. Spawn validation refuses NUL input and spawn failures expose only the error code; update matchers that depended on command paths. Provider status reads share the configuration lock and can reject `PROVIDER_CONFIGURATION_BUSY`; show busy and retry.
- **Enrollment isolation (#1964, #2033, #2034, #2055).** One store can no longer clear, renew over or replace another store's enrollment/member writes without the explicit replacement flow. This addresses the 0.42.0 multi-store warning.
- **Installation recovery (#2011, #2136, #2152, #2160, #2164, #2165).** `current` prevents startup while stores are partial; recovery respects the committed pointer. Restore refuses overlapping or changed canonical store paths and SDK 0.42 snapshots require SDK 0.42 recovery. POSIX install roots reject unsafe ancestors; payloads are freshly staged, verified and rechecked, and colliding names are refused. Same-id repair retains the payload on failure, install-root operations serialize, and health checks and platform commands are bounded.
- **Credential and adapter boundaries (#2167, #2170, #2175, #2176, #2193, #2195).** Synchronous `scope()` failures are sanitized; unavailable-store provisioning can be retried without consuming a generation, duplicate adapter IDs are refused, and direct spawn errors and command outcomes follow the migration steps above.
- **Task and Pi corrections (#2168, #2172, #2173, #2174, #2177, #2180, #2189).** Cancellation examples report committed drain failures; settlement waits respond to abort and runtime completion; unseeded Pi hosts use a private cache or disable filesystem caching. Retention failures identify the journal task, upgrade reports describe behavior-only changes, Codex drops delivered projection records, and retained text and reasoning use a separate 16 MiB limit.
- **Task settlement and journal retention (#1944, #1990, #2054, #2097, #2137).** Offer-owned scratch cleanup does not report runtime disposal failure; settlement waits reread an offer that lands during a journal read and abort promptly; journal appends validate task identity; retention skips failed prunes and continues paging.
- **OpenCode and Claude interrupts (#2088, #2036, #2090, #2037).** OpenCode reports a refused interrupt; Claude keeps the original turn state when its interrupt is refused or unwritten.
- **Runtime sessions (#1940, #1942, #1957, #1949).** Claude bookkeeping growth is reduced; Grok interrupt no longer cancels its next native turn; ACP cancel-write failures permit retry; Pi warming stops at task settlement.

## Dependency security and Host overrides

The client declares **undici 8.12.4**, but upstream `@earendil-works/pi-coding-agent` 1.5.2 still pins **8.12.3**, affected by six advisories including a high-severity advisory. SDK workspace overrides do not propagate into a Host installation. Add an undici 8.12.4 override in the Host's root package manifest, reinstall and inspect every resolved copy, then rebuild shipped artifacts. npm/Bun use `"overrides": { "undici": "8.12.4" }`; pnpm uses `"pnpm": { "overrides": { "undici": "8.12.4" } }`. See the [complete instructions](host-upgrade-0.43.0.md#undici-in-the-host-dependency-tree-2081), [#2098](https://github.com/Ancienttwo/byok-sdk/issues/2098) and [earendil-works/pi#12159](https://github.com/earendil-works/pi/issues/12159). Built-in Node undici and separately bundled copies need their own runtime/package updates.

**OAR (#2187):** The vendored fork is `byok/0.105.0` at `261241f2`, based on upstream 0.105.0. OpenCode child-session updates are recorded under the child session id.

**Hono floors (#2118)** are `hono ^4.13.16` and `@hono/node-server ^2.1.6`; this lock resolves 4.13.18 and 2.1.8. The floor includes bot-collaboration's optional testing peer. Refresh old Host pins and lockfiles, reinstall and rebuild bundles; merely bumping SDK packages does not repair a retained vulnerable copy.

## Known issues

- **Pi installed and keys-profile paths (#2163).** These paths do not use the seed and can still transform at runtime. Their filesystem cache is disabled unless its location is proven private to the execution.
- **Grok attribution (#1942 residual).** A native Grok turn starting while an SDK reply is published can still contribute text and usage to that SDK reply; total usage remains unchanged. Account for this when displaying replies and attributing costs.
- **Retained text (#2056).** Text and reasoning have a separate fixed 16 MiB limit; `maxRetainedBytes` is not a total session-memory bound.
- **Installation paths (#1962, #2028).** Payload verification retains concurrent path-mutation limitations; keep installation parents and payloads under exclusive control. Windows has no install-root owner check.
- **Refused steer visibility (#2009).** A refused `task.steer` is acknowledged/dropped and logged locally without a dedicated Host result; acknowledgment is not runtime acceptance.

These are release limitations to assess during candidate acceptance, not a claim that the owner has accepted every one for publication. macOS Developer ID signing/notarization/stapling (#1904), real Windows Agent-memory acceptance (#605), and real hosted Workers/two-device acceptance (#654, #794) retain their separate evidence and authorization requirements.

## Host upgrade order

1. Apply earlier checklists if coming from before 0.42.0. Retain matching binaries, assets and store snapshots. With SDK 0.42.0, finish any pending version-1 service receipt using `recover()` before replacing the SDK. Finish or abandon 0.42.0 snapshot-based operations using SDK 0.42.0; the new SDK refuses those snapshots with `snapshot_upgrade_required`.
2. Update all installed public packages together to the accepted 0.43.0 tarballs, remove or pin archived cloud-do, apply the undici override and Hono floors, and rebuild the Host with matching Pi assets. Implement the import, error-union, custom journal, credential-backend and committed-cancel changes above. Compile the Host against the candidate.
3. **On every macOS device, before its first upgrade or rollback, use the new SDK to call `install()` on the same installation with the payload id that is currently installed.** Read `currentVersion()` and keep the payload whose `readPayloadManifest(dir).id` matches it. This rewrites the launchd unit with the installation HOME; a different payload id is refused. Then perform the upgrade. [AiphaBee#1156](https://github.com/Ancienttwo/aiphabee/issues/1156) tracks the downstream step. Verify task HOME and any derived PATH/XDG variables (#2084).
4. Stop store owners, run candidate store inspectors (including `inspectLedger`), snapshot, perform any reported explicit migration and precheck again before serving. Run Host store migration programs only through the installation's preparation protocol; do not restore over a present committed `current`.
5. Exercise selected-set cancellation and post-commit failure handling, enrollment replacement, settlement/retention and installation recovery using the accepted candidate. Adopt the #2003 batch API where needed ([AiphaBee#1141](https://github.com/Ancienttwo/aiphabee/issues/1141)); call `drain()` separately if successors should start immediately. Inspect service timeout `exitConfirmed` and recovery receipts before retrying operations.
6. Complete exact-SHA release validation and Host acceptance, including the owner-controlled signing work. Obtain separate publication approval. After publication, record registry digests/tag/run evidence, archive and rebaseline the manifest in the publication-record PR, then reopen main when that PR merges. Downgrading binaries does not undo store or receipt changes: restore the matching pre-upgrade state and artifacts together.
