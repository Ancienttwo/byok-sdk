This is the release preparation record, not a publication record. It does not
approve any merge, tag or publish. The npm registry lists all nine packages at
0.37.0 as `latest` (see the Publication paragraph below). The sections below
record the state at preparation; they are not updated for the later CI and
publication. The previous

version commit, showed `latest` 0.36.0 for all nine packages.

`1ba3779fdca8839ca1003dec0ef737751f3d2aeb` on `main`, the squash merge of the

The tarballs are the release matrix artifact

0.37.0 is a MINOR release under the default pre-1.0 policy, with no PATCH

## Source and scope

`git log --first-parent v0.36.0..b5bc36ac8` lists 4 commits: #1392, #1391,
#1401 and the train merge #1406. The train merges six accepted heads with
`git merge --no-ff`: #1403 (which carries #1399), #1400, #1396, #1402, the
#1396 follow-up and #1397. The changes are grouped by area.

Protocol, core and examples:

- #1399 (#1375): `bot-turn-outcome.v1` runs every rule that reads only the
  outcome, so the device refuses a violating outcome on `submit_result` and
  the model corrects it in the same Turn. New `contract-mismatch` keywords:
  `duplicate-target`, `duplicate-local-id`, `duplicate-id`,
  `duplicate-member`, `admin-not-member`, `empty-update`, `schedule-invalid`,
  `schedule-unreachable`, `schedule-beyond-horizon` and `tz-invalid`. The
  routine calendar moves from `@byok-sdk/core` to `@byok-sdk/protocol`; core
  drops it and its `routine_schedule_invalid` code. A repeated `daysOfWeek`
  day is `schedule_invalid`. The schedule fragment has one closed shape, and
  `RoutineScheduleShape` and the `scheduleShape` option are removed. The room
  `mode` enum has only `mention`. K8 drops its apply-time copies of these
  rules. Breaking (manifest `bot-turn-outcome-stateless-rules`).
- #1403 (#1393): K8 publishes `room-seat:<roomId>:<seatId>` when a room seat
  becomes terminal and `room-root:<roomId>:<root>` when every seat of a round
  root is terminal; `advanceRoomSeats` takes a `publish` argument. In the same
  manifest entry.
- #1397 (#1394): K8 `retainRoots` also moves room messages out of the
  collaboration state into archived rows in namespace `roomMessages`, except
  the last `contextTurnLimit` messages of each room, and keeps every seat
  ContextPack the same. The `Room` shape and the state version do not change.
  In the same manifest entry
  ([K8 retention](../../examples/bot-collaboration/README.md#retention)).

Client:

- #1400 (#1317): on Windows the `login-shell` runtime environment base takes
  `PATH` and `PATHEXT` as Windows builds them at logon from the machine and
  user `Environment` registry keys, not from the daemon's live session. A
  failed read fails closed with the new `ServiceEnvironmentUnavailableCode`
  `logon-registry-unavailable`. Breaking (manifest
  `windows-logon-registry-path`).
- #1401: the SDK-owned OAR source moves from 0.83.0 to 0.86.0
  (`vendor/oar/47c2c3f/`). The API surface is unchanged.

Client and keys:

- #1396 and its follow-up (#1373): on Windows the keys launcher no longer
  starts PowerShell or reads the Pi projection directory's owner. It requires
  the OWNER RIGHTS (`S-1-3-4`) READ_CONTROL ACE that the client now grants
  when it creates the directory, so `@byok-sdk/client` and `@byok-sdk/keys`
  must run at the same version; when they differ, the launch fails closed.
  Breaking (manifest `pi-projection-acl-owner-rights`).

Client, cloud-do and keys:

- #1402 (Pi 1.5.0): the official Pi closure is pinned to exactly 1.5.0
  (upstream commit `f9a26365`) and adds `@earendil-works/pi-schema` as its
  tenth package. The closureDigest changes, so a preparation compiled for
  1.4.0 declines with `preparation_runtime_identity_mismatch`. pi-durable
  migrates a replica forward on open, and a 0.36.0 build cannot open it
  afterwards. A model request in flight at a crash, eviction or reset is not
  sent again. cloud-do tool schemas are pi-schema-typed, and a
  `DurableObjectSqliteDatabase` implementation must provide `runCounted`.
  keys: `PI_MODEL_CATALOG_PI_AI_VERSION` is `1.5.0`. Breaking (manifest
  `pi-150-closure`).

Release records and scripts:

- #1391: the 0.36.0 publication record, and the upgrade manifest rebaselined
  on 0.36.0.
- #1392: the repository scripts detect their CLI entry with
  `import.meta.main` (scripts and test tooling only).

Wire and persistence. The wire stays v5 (`PROTOCOL_VERSION = 5`).
`packages/protocol` changes the `bot-turn-outcome.v1` rules, the schedule
fragment and the routine calendar it now holds (#1375); none of them is a wire
shape. The golden corpus does not change since `v0.36.0`: the v5 corpus
still has 342 envelope lines and 30 HTTP lines, and `v5.releases.json`
registers that corpus for 0.37.0 next to 0.34.0, 0.35.0 and 0.36.0. There is
no new Postgres migration and no SQLite schema change. Pi 1.5.0 migrates
pi-durable replicas forward (`pi.live` v3, `pi.tool` v3, `pi.generation` v2),
so a device or Durable Object cannot roll back past 0.37.0.

## Upgrade notes for Hosts and deployments

The upgrade manifest (`packages/client/upgrade-manifest.json`, shipped in the
client package) lists each Host-visible API, config and example change from
0.36.0 with its impact, summary and migration link. The
[Host upgrade checklist](host-upgrade-0.37.0.md) covers a Host that moves from
0.36.0 to 0.37.0; a Host on an earlier release applies the
[0.36.0 checklist](host-upgrade-0.36.0.md) first. In short:

**No wire cut.** 0.37.0 speaks wire v5 like 0.36.0, so no drain is needed for
the wire. Pin all nine packages to exactly 0.37.0 together; on Windows,
`@byok-sdk/client` and `@byok-sdk/keys` at different versions fail the Pi
launch closed.

**No rollback past 0.37.0 for Pi durable state.** pi-durable replicas that
0.37.0 opened cannot be opened by 0.36.0.

**Host code.** Import the routine calendar from `@byok-sdk/protocol`, and
handle the new `contract-mismatch` keywords. Handle the new
`ServiceEnvironmentUnavailableCode` `logon-registry-unavailable`. Build
cloud-do tool schemas with `Type` from `typebox` or with pi-schema, and
provide `runCounted` in a custom `DurableObjectSqliteDatabase`. Prepare again
every preparation compiled for Pi 1.4.0.

**K8.** A Host that vendored K8 copies the changed files, handles the
`room-seat:` and `room-root:` projection prefixes before it upgrades, and adds
`archived(namespace, id)` to its `RetentionSubject`
([VENDOR.md](../../examples/bot-collaboration/src/VENDOR.md)).
