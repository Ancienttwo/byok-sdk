# 0.25.0 / keys 0.10.0: stable source candidate

The owner authorized stable source preparation on 2026-10-09. Publication is
pending. The candidate includes the published rc.1 and rc.2 changes plus the
OAR 0.45.1 update merged in [#316](https://github.com/Ancienttwo/byok-sdk/pull/316)
at `69f36d9b34d89b3837b44104a800a8c1aadf375b`.

## Version set and channel

Eight aligned packages use 0.25.0: core, protocol, client, server, cloud,
cloud-dataplane, cloud-do, and ui-runtime. Independently versioned keys uses
0.10.0 and packs an exact core 0.25.0 dependency. The public set is nine
packages. `@byok-sdk/implementation-identity` is retired and is not published.

All nine packages target npm's `latest` dist-tag. The registry baseline remains
0.24.0 / keys 0.9.0 until publication and readback succeed. The published
0.25.0-rc.2 / keys 0.10.0-rc.2 remains on `rc`; its tag and original artifacts
are retained. Stable artifacts must come from the final stable source commit.
Do not relabel, overwrite or republish RC bytes.

## Changes since 0.24.0

- Protocol v2 removes SDK permission policy, executable attestation, the trusted
  launch-cwd wrapper and egress sanitization; server and client upgrade together.
- Ordinary sessions use the user's local Claude, Codex and Pi configuration
  under the minimal-guardrails contract, and the Host selects Codex's sandbox.
- Pi moves to 1.1.0, and the private OAR source moves to 0.45.1 at
  `7dc98e08f9c0ba99158ddada29cb0d4c80ef7dc6` with the six maintained BYOK files.
- Direct adapter hosts can import `buildRuntimeEnv`, while injected-adapter
  construction rejects `codexSandbox` in favor of the adapter's own option.
- Embedded SQLite startup refuses unsupported pending mailbox wire majors,
  while keys refuses stale profile schemas before WAL setup or DDL.
- Client imports work in a single-file Host bundle, keys' OpenAI-compatible and
  Anthropic clients support `requestTimeoutMs`, SQLite open refusals expose
  typed codes, and undici is pinned to 8.11.2.

The raw OAR Codex session supports upstream launch arguments and service-tier
readback. The SDK bridge exposes neither option; ordinary task launches and SDK
events retain their existing behavior. See the
[OAR upgrade record](../notes/2026-10-09-oar-0.45.1-upgrade.md).

The [rc.1 record](v0.25.0.md#breaking-changes-since-0240) lists the removed APIs,
configuration keys and launcher grammar. The [rc.2 record](v0.25.0-rc.2.md)
contains the integration fixes and their original acceptance boundaries.

## Upgrade requirements

1. Stop new dispatch and drain pending v1 mailbox work with the previous SDK,
   then upgrade server and client together; protocol v2 has no v1 reader.
2. Preserve an undrained database for reconciliation; the startup check does
   not convert or remove mailbox rows, and custom writers must store envelopes
   with numeric `v: 2`.
3. Recreate preparations for record version 10, prepared binding and surface
   digests v3, the Pi MCP fingerprint v2 and the Pi 1.1.0 runtime identity.
4. Remove retired configuration and implementation-identity imports, and
   change keys launcher arguments to `--pi-projection-dir`.
5. Retain Node >=24.15.0 and the single-file Host's matching Pi asset root and
   self-executable helper configuration.
6. Preserve the device's product identity across directories; changing only
   `storeDir` keeps its OS credential, while a fresh server needs fresh enrollment.

See the [protocol inspection query](../protocol.md#sqlite-startup-check-for-wire-major-upgrades)
and [rc.1 upgrade steps](v0.25.0.md#upgrade-steps) for the full cutover contract.
This SDK release does not migrate or deploy a Host.

## Acceptance and remaining boundaries

The OAR baseline `69f36d9b` passed all 24 main push CI jobs. Its nine accepted
RC tarballs were downloaded and verified for source SHA, SHA-256/SHA-512,
package identities and frozen runtime dependencies during readiness review.
These are baseline results; final stable acceptance requires the stable
commit's own CI and artifacts after the version change.

The existing real-agent checks and downstream acceptance remain bound to the
subjects recorded in [rc.1](v0.25.0.md#qualification-evidence) and
[rc.2](v0.25.0-rc.2.md#acceptance-and-limits). This metadata preparation does
not rerun them or establish a new live Host receipt. Final-artifact Host/runtime
qualification follows the agreed scope in the
[release runbook](../../deploy/runbooks/release-responsibility.md#pre-publication-host-integration).
Fixture and packageability checks do not establish paid-provider, UI or
production acceptance.

The owner's existing report-only residuals remain: re-parented POSIX background
jobs can outlive disposal, timing flakes are tracked separately, Codex's
`inherit` sandbox has argv evidence only, and the Pi keys-profile lane was not
part of the recorded real-agent run. This preparation adds no disposal mechanism
or timeout changes. See [known residuals](v0.25.0.md#known-residuals).

Issues #194 and #195 retain the unfinished Host budget, SummaryJob/CAS,
ContextPack and native acceptance scope. SDK publication does not close those
product acceptance items or enable their lanes.

## Publication plan

1. Merge the stable preparation and wait for green main push CI on its exact SHA.
2. Download `release-pack-<sha>` and keep its original schema-3 manifest and all
   nine tarballs; verify hashes, versions and exact internal dependency edges.
3. Confirm npm's registry is `https://registry.npmjs.org/` and its configured
   tag is `latest`, then run
   `node scripts/release/publish.mjs --artifacts <dir>` from that exact checkout.
4. Retain the dry-run plan and agreed Host/runtime qualification evidence,
   then obtain separate authorization for the nine-package stable publication.
5. Publish the accepted bytes with `--execute` and no `--tag`, using an npm
   account with write 2FA; a local release carries no GitHub OIDC attestation.
6. Require exact registry versions, integrities, owners, dependency edges,
   `latest` tags and a clean installed-consumer readback before tagging `v0.25.0`.
7. Push the annotated tag and attach the original manifest, tarballs and
   publication receipt to the GitHub Release.

The publisher derives dependency order from the package graph. Follow the
[runbook](../../deploy/runbooks/release-responsibility.md#release-checklist)
for uncertain or partial publication; do not overwrite published bytes.
