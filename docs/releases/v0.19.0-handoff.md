# 0.19.0 / keys 0.6.0 release preparation

Status: prepared; NOT published. No npm publication, no tag, no GitHub Release,
no `scripts/release/publish.mjs --execute`. This handoff does not authorize any

## Scope and upgrade decision

Source: `main` @ `3872bbf0`, plus this preparation branch. The ten aligned
dispatch packages move 0.18.0 → 0.19.0 and `@byok-sdk/keys` moves 0.5.0 → 0.6.0.
No product logic and no dependency range changes in the preparation itself —
the diff is version literals plus release documentation.

Version selection follows the authoritative
[pre-1.0 package version policy](../spec.md#pre-10-package-version-policy),
which makes MINOR cover "any pre-1.0 breaking cut". This train carries two:

- the input-preparation wire (request version 4, record schema 5, compiler and
  structural projection 3, `skills[]` replacing `formattedSkills`,
  `toolGuidelines` added, `toolChoice` narrowed to `auto | none`, the new
  `runtime_contract_superseded` readiness reason);
- the keys launcher's now-REQUIRED `--runtime-entry {pi-rpc, pi-prepared}`.

The SDK 0.19.0 minor is Owner-approved (ruling 2026-09-22). **The keys 0.6.0
minor still needs the Owner's explicit confirmation**: the approval named the
SDK train, and although the same policy clause forces a minor for a breaking
argv (`packages/keys/src` moved +860/−115 across six files since `v0.18.0`),
the keys line versions independently and its number is a separate decision.
Settle it before the publish step; nothing else in this preparation depends on
which way it goes.

Release notes: [0.19.0](v0.19.0.md). The upgrade requirements are: upgrade
`@byok-sdk/client` and `@byok-sdk/keys` together; a Host composing prepared
requests must move to request version 4 and the new snapshot fields; and a
device that ran this repository's own builds may be holding a record-version-4
preparation log, which blocks daemon start until the log is moved aside (exact
path and disposition are in the release notes). No automatic migration or
live-store conversion is supplied or executed.

## Publication boundary after preparation — Owner only

Obtain explicit publication authorization first, and settle the keys 0.6.0
question above. Then run
[`deploy/runbooks/release-responsibility.md`](../../deploy/runbooks/release-responsibility.md)
checklist item 5, filled in for this train:

1. Confirm the CI run for the exact merged release commit is green, including
   its `npm-release-pack` job. Use the `push` run, not a `pull_request` run — on
   pull-request events `github.sha` is the merge ref, so that run's artifact is
   named after a commit that is not `HEAD` and the dry run refuses it.

   ```sh
   gh run list --branch main --workflow CI --event push --limit 1
   ```

2. Download that run's accepted tarballs, with `<sha>` the full 40-character
   commit id:

   ```sh
   git rev-parse HEAD                       # this is <sha>
   gh run download <run-id> -n release-pack-<sha> -D <dir>
   ```

3. Dry run. It refuses unless the frozen `release-manifest.json` names 0.19.0
   and was packed from the current `HEAD`, and unless every tarball the publish
   set needs is present and re-hashes to its recorded sha256. It then prints the
   ordered publish plan with those digests. Nothing is published, read back or
   tagged.

   ```sh
   node scripts/release/publish.mjs --artifacts <dir>
   ```

4. Release. It refuses if the tag already exists, if `npm whoami` reports no
   account, or if `npm profile get --json` does not report `tfa.mode`
   `auth-and-writes` — there is no override. It publishes each tarball in
   dependency order (`--provenance` only under GitHub Actions OIDC; a local
   release logs that no attestation is attached), reads the registry back, and
   only then creates the annotated `v0.19.0` tag carrying the source commit.

   ```sh
   node scripts/release/publish.mjs --artifacts <dir> --execute --otp <code>
   ```

5. Push the tag. A tag exists only for a train the registry has already
   confirmed.

   ```sh
   git push origin v0.19.0
   ```

CI artifacts expire after 30 days; past that, re-run CI on the same commit
rather than repacking locally. After a partial failure, preserve the original
bytes and inspect registry state before anything else; never blindly republish.
Record the outcome in `docs/releases/v0.19.0-publication.md` and update the
README release-status row to name 0.19.0 as published. Product updater and
deployment remain separately owned.
