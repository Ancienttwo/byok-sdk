# BYOK SDK 0.21.0 · keys 0.6.2

Published to npm on 2026-09-24/25 from the `v0.21.0` tag (`8b7a2121`); see the
[publication record](v0.21.0-publication.md) and the
[release handoff](v0.21.0-handoff.md). The eight aligned packages align at 0.21.0, and the train
publishes nine packages in total; `byok-sdk` and `@byok-sdk/testkit` are no
longer published (see [Packages no longer published](#packages-no-longer-published)).
Independently versioned keys 0.6.2 pins core 0.21.0; its source is unchanged
since 0.6.1, and it is re-released only so that its packed `@byok-sdk/core`
edge equals the current dispatch release. The bundled Pi runtime pin is
unchanged at `@byok-sdk/pi-coding-agent@0.86.1001` /
`@byok-sdk/pi-ai@0.86.1001`.

The previous train, 0.20.0 / keys 0.6.1, was published on 2026-09-23 from the
`v0.20.0` tag (`48605554`); see its [publication record](v0.20.0-publication.md). Read the registry back
with `npm view @byok-sdk/core version` and `npm view @byok-sdk/keys version`.

The product change in this train is PR #226 (prepared message egress, merged as
`644f8473`). `task.offer_prepared` can now run the chat lane: a prepared
Execution can publish its reply as a durable agent message, so a Host can run a
user Turn on the exact prepared document that bounded admission measured,
instead of a fresh instruction with a legacy transcript handoff. The
input-preparation wire moves to version 6 to carry it.

## Packages no longer published

Starting with 0.21.0, two packages are no longer published. This is a breaking
distribution change:

- `byok-sdk`, the unscoped namespace umbrella. It only re-exported the seven
  dispatch packages and had no capability of its own (ADR-035). Its
  `packages/sdk` source is deleted, and no empty umbrella, alias package or
  dual export replaces it.
- `@byok-sdk/testkit`, the headless device simulator. It stays in the
  repository as a private package for the private conformance suite.

Every version already on npm, up to and including 0.20.0, stays on the
registry and keeps installing; npm versions are immutable. Neither package
receives 0.21.0 or later.

To move off the umbrella, install and import the scoped packages directly, at
the same train version:

| Umbrella import from `byok-sdk` | Replacement |
|---|---|
| `client` | `import * as client from '@byok-sdk/client'` |
| `cloud` | `import * as cloud from '@byok-sdk/cloud'` |
| `cloudDataplane` | `import * as cloudDataplane from '@byok-sdk/cloud-dataplane'` |
| `core` | `import * as core from '@byok-sdk/core'` |
| `protocol` | `import * as protocol from '@byok-sdk/protocol'` |
| `server` | `import * as server from '@byok-sdk/server'` |
| `uiRuntime` | `import * as uiRuntime from '@byok-sdk/ui-runtime'` |

Named imports work as well, for example
`import { createByokServer } from '@byok-sdk/server'`. `@byok-sdk/keys` was
never part of the umbrella and is unchanged. `@byok-sdk/testkit` has no
published replacement.

Both known downstreams were checked: neither Salesko nor aip imports or
depends on either package. Salesko's root `package.json` still pins
`@byok-sdk/testkit` 0.20.0 under `overrides` with no workspace consumer; drop
that line when moving the other pins to 0.21.0.

## Operator precondition: the v6 cut

Input preparation moves to wire version 6 in one cut. The capability token is
now `agent-input-preparation-v6`; there is no dual token and no dual read. The
outer envelope stays v1 and the durable record schema stays at version 6; the
wire version is what moved.

**Before upgrading either side, drain the in-flight input preparations and
prepared Executions — every preparation receipt terminal, every required
message disposition settled, and each device's mailbox cursor past all old
preparation and prepared-offer entries — then upgrade the cloud and its devices
as a pair.** Existing v5 preparations are not read forward; recreate them under
v6.

The enqueue capability gate is the only guard. On long-poll, an unknown message
type and an unknown key in a strict payload both FREEZE the device's cursor,
which blocks that device's whole mailbox rather than skipping the entry. A
v5-only device is refused at enqueue with `agent_capability_missing`, before
any task or mailbox row is written. What the gate cannot cover is a row that
was already enqueued before the cut: an old `task.offer_prepared` without
`egressPolicy` fails strict parsing on a v6 device and freezes its cursor. A
paired upgrade alone does NOT repair that old payload; if the drain was
skipped, the stranded mailbox entry needs operator handling.

## Breaking: `TaskOfferPreparedPayload` requires `egressPolicy`

- `TaskOfferPreparedPayloadSchema` now REQUIRES `egressPolicy` and may carry an
  optional `messageEgress`. A prepared offer built without `egressPolicy` fails
  the strict schema.
- `enqueuePreparedOffer` requires the device to advertise
  `agent-home-contract`, `agent-input-preparation-v6`, `agent-egress-policy`,
  `agent-egress-reliable-ack` and `agent-egress-fresh-session`, plus
  `agent-message-egress` when `messageEgress` is present. All of these gates
  run before any task or mailbox row is allocated.
- `PreparedDispatchInput` accepts a host-only `agentMessageContext`. It is
  recorded with the immutable message requirement and is never sent to the
  daemon. One shared `agent-message-offer:` receipt writer now serves all three
  call sites.
- Prepared envelopes are sanitized: outbound activity and terminal envelopes
  of a prepared Execution pass through the same strict egress sanitizer as
  fresh Agent egress offers.
- The prepared lane injects no reserved helpers — no message MCP and no
  agent-memory helper — and runs no helper-bin precheck or helper preflight.
  The message tool never enters D; D and its fourteen admission comparisons are
  unchanged.
- The reply body is daemon-authored at turn end, from the final Pi text, in
  this order: the usage check, extraction of any selected result document, the
  immutable draft appended and published, the exact `accepted` disposition,
  and only then `task.complete` with `preparedObservation`. A context overflow
  or missing/unreadable usage fails the Execution BEFORE any body is written.
- Local `input_preparation.*` control requests and remote preparation
  completions carry version 6; `INPUT_PREPARATION_VERSION` is exported as `6`.

## Breaking: fresh Pi lane, `auto` + `allowTools: []`

Pi policy `{ mode: 'auto', allowTools: [] }` changed on the fresh lane from
"Pi's full default tool table" to "zero native tools, observed MCP only": the
Pi run gets no native tools, and the task's observed MCP toolset grants are
retained explicitly. The prepared lane has the same meaning. A Host that relied
on an explicit empty allowlist to get Pi's default tools must now omit
`allowTools` instead — omitting it still selects Pi's default native registry
on fresh execution, and remains inexpressible for prepared execution. Reserved
grants on fresh offers are admitted separately, as before; prepared offers have
none.

## The native-expressibility check runs before pin

The prepared lane's native-tool-selection validator now runs before the
preparation record is pinned, and again in the prepared host. A refused native
policy therefore never consumes a pinned record. A nonempty native selection is
still refused as `native_tools_uncounted`.

## Deferred: an empty `requiredToolsets`

A prepared offer still requires a nonempty set of MCP toolsets; an empty
`requiredToolsets` is not supported in this release. Accepting it needs a fork
change, because the frozen fork rejects a zero-tool prepared session
(`sdk.ts:547-548` in fork 0.86.1001). It moves to the official Pi 0.87.1
migration work-package.

## Pi fork: unchanged and frozen

The Pi fork is untouched: `@byok-sdk/pi-coding-agent@0.86.1001` /
`@byok-sdk/pi-ai@0.86.1001`, installed through the npm alias exactly as in
0.20.0. The fork is frozen; the next Pi change is the migration to official
Pi 0.87.1, as its own work-package.

## Known CI timing flakes (unrelated to this release)

- `packages/client/src/__tests__/pi-mcp-launch-cwd.test.ts` runs under the
  client suite's 10s test timeout and can trip it under heavy load.
- On Windows, `packages/client/src/__tests__/daemon-auth.test.ts` has a 750ms
  settle guard that a slow runner can miss.
- On Windows, the Credential Manager native smoke
  (`packages/client/src/__tests__/device-credential-store.native.test.ts`,
  gated by `BYOK_NATIVE_WINDOWS_CREDENTIAL_SMOKE=1`) has a 20s command timeout
  that a slow runner can miss.

None of these tests is touched by this train; a red on any one of them is a
timing flake, not a release regression.

## Host follow-up

A Host that builds prepared offers must add `egressPolicy` (and `messageEgress`
when the Execution should publish its reply as an agent message), pass
`agentMessageContext` through `PreparedDispatchInput` when it does, and wait for
the prepared terminal rather than for a message tool call — the daemon writes
the reply body itself. A Host that sends `{ mode: 'auto', allowTools: [] }` to
a fresh Pi run must decide whether it meant zero native tools (the new meaning)
or Pi's defaults (omit `allowTools`). Until the Host moves, the daemon and cloud
refuse the old shapes fail-closed; nothing is silently rewritten.

No Host data migration, live profile update, deployment, real credential use or
provider inference is part of this release preparation. See the
[release handoff](v0.21.0-handoff.md) for the evidence boundary and the
publication sequence.
