# 0.26.1 / keys 0.11.1: stable preparation

Date: 2026-10-12 (Asia/Singapore).
Status: source preparation. This candidate is not published.

The owner authorized preparation of 0.26.1. The target npm dist-tag is
`latest`. npm execution and release tagging require separate authorization.

## Changes since 0.26.0

- The client releases its Git lease if runtime launch admission fails or is
  cancelled. Prepared input stays pinned until the startup owner releases it.
- Shutdown waits for prepared offers. Active session cleanup shares one close
  attempt, so terminal cleanup can wait for the same result.
- A duplicate prepared offer cannot enter while its preparation store opens.
- Agent home, preparation store, artifact, runtime and MCP error reasons replace
  local absolute paths with `<local path>` before they leave the device.
- The private Codex bridge declares `launchArgs`. The public API does not change.
- The client uses vendored OAR 0.57.0. Its private records include reasoning
  token totals and deduplicated session links. SDK events still use native frames.
- Tests wait for transport confirmation and use bounded observations for task
  cleanup. Local Bun tests can find the executable in `~/.bun/bin`.

## P1: publication boundary

`packages/core/package.json` owns the dispatch train version.
`packages/keys/package.json` owns the independent keys version.
The public set has eight aligned packages plus keys.
`@byok-sdk/conformance` and `@byok-sdk/testkit` stay private.
`@byok-sdk/implementation-identity` stays retired.

The publisher reads these manifests and the reviewed registry baseline.
The package check reads packed metadata, rather than workspace overrides.
The Host owns deployment, device distribution and database operations.

## P2: source to installed package

The release path is:

1. Update the nine manifests and regenerate the Bun workspace lock records.
2. Run the five required checks and the package graph check.
3. Commit the candidate. Packing requires a clean source checkout.
4. Build and pack all nine packages. Check migration assets, dependency edges,
   Pi runtime identity, CLI entrypoints and an isolated consumer install.
5. Dry run `scripts/release/publish.mjs` against those frozen tarballs.
6. After the final release commit passes push CI, use that commit's accepted
   `release-pack-<sha>` artifact for publication.

The dry run checks hashes, package identity, runtime dependency maps and source
SHA. It does not publish, read back unpublished versions or create a tag.

## P3: PATCH decision

This train corrects cleanup and race handling. The outbound error correction
keeps the existing device-path privacy boundary. It changes no authorization.
There is no new public API, storage format, migration or protocol version.
OAR remains a private source dependency. The SDK does not expose its new
workspace-root or output-schema options.

keys has no source change. It needs 0.11.1 because its packed core dependency
must be exactly 0.26.1. Published keys 0.11.0 points to core 0.26.0 and cannot
be overwritten. This keeps one core version in the installed SDK graph.

## Upgrade

After publication, update each dispatch package used by the Host to 0.26.1.
Update keys to 0.11.1 if the Host uses it. For example:

```sh
npm install @byok-sdk/client@0.26.1 @byok-sdk/server@0.26.1 @byok-sdk/keys@0.11.1
```

Hosts already on 0.26.0 need no new schema migration. Keep the existing
[0.26 upgrade requirements](v0.26.0.md). This preparation does not perform
a Host rollout or live provider acceptance.
