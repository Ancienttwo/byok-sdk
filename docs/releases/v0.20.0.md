This train is one change, PR #223 (bounded admission, merged as `c61615f8`).
Input preparation no longer depends on a live provider tokenizer count before
admission:

- The exact size of the frozen request, `artifact.requestBytes`, is the SDK's
  upper-bound size evidence. The Host checks `requestBytes + C + max_tokens <=
  window` once, under its own budget ruling; the SDK carries no number of its
  own.
- The live counter becomes optional. With no counter, a preparation compiles,
  retains its artifact and settles as `prepared` with no counter call and no
  `maxCounterCallsPerScope` reservation. A counter that IS configured is a
  tightener, not the size evidence, and is still judged: it must be `provider`
  authority and cover the whole request, and a `test_fixture` counter never
  becomes ready.
- Pi usage is now observed. Every assistant `message_end` emits one usage
  event, with prompt = `input + cacheRead + cacheWrite`. A prepared Execution's
  `task.complete` / `task.fail` carries the new optional
  `preparedObservation {requestDigest, initialPromptTokens, maxPromptTokens}`,
  which the cloud `TerminalResult` copies verbatim, so the Host can check its
  byte bound after the fact.

## Operator precondition: the v5 cut

Input preparation moves to wire version 5 and record schema version 6 in one
cut, with no dual read and no cross-version parser. The capability gates
admission only: the `agent.input.preparation` payload and its completion receipt
carry no version field, so a row enqueued before the cut is still in flight
after either side upgrades.

**Before upgrading either side, drain the in-flight input-preparation rows —
every preparation receipt terminal, and each device's mailbox cursor caught up
past its last `agent.input.preparation` envelope — then upgrade the cloud and
its devices as a pair.** An in-flight row that crosses versions gets a 422 from
the strict receipt schema in either direction (`prepared` into a 0.19 cloud;
`counted` plus a counter `kind` into a 0.20 cloud). The device keeps the
envelope for redelivery, and its strictly seq-ordered cursor stalls, which
blocks that device's WHOLE mailbox, not only preparation, until the other side
is upgraded too. Recovery is exactly that: upgrade the other side; once both
speak v5 the redelivered completion is accepted and the cursor moves.

## Breaking: capability token

The device capability is renamed to `agent-input-preparation-v5`; the suffix is
`INPUT_PREPARATION_WIRE_VERSION`. The unversioned `agent-input-preparation`
token (0.19 and earlier) is accepted nowhere, and there is no dual token. A
daemon declares only the token of the version it speaks, and the cloud's
input-preparation and prepared-offer enqueue gates accept only theirs, so a
skewed device is refused at enqueue with `agent_capability_missing`, with no
receipt or mailbox row.

## Stale record log: the lane turns off

A device whose preparation record log still holds an older record schema no
longer fails daemon start. Replay refuses the old record, and only the
input-preparation LANE turns off, typed as
`input_preparation_record_log_unsupported`: every local `input_preparation.*`
call and every remote completion refuses with that code, the daemon stops
advertising the input-preparation capability (so the cloud refuses to enqueue
onto it), and a `task.offer_prepared` declines by name. Every other task runs
normally. Nothing is migrated, read forward or deleted automatically.

The disposition is manual, and it is the operator's:

1. Stop the daemon.
2. Move `<storeDir>/input-preparation/records.jsonl`, together with the
   `artifacts/` directory beside it, to an archive location. `<storeDir>` is
   the daemon config's `storeDir` when set, otherwise `~/.byok/<productId>`.
3. Start the daemon. The lane comes back empty under record schema version 6,
   and the archived records stay available for audit.

## Breaking: wire renames

- The successful terminal state `counted` is now `prepared`.
- The not-yet-terminal readiness reason `not_counted` is now `not_prepared`.
- The readiness reason `counter_missing` is removed: a missing counter is no
  longer a readiness failure.
- The counter result's `kind` is removed; its `bound` member was not something
  any adapter could honestly state.
- New readiness reason `request_content_not_text`: this release admits
  text-only requests, and a record that retains an artifact without a true
  `requestContentTextOnly` answer carries this reason. Every `messages[]` entry
  whose `content` is an array must hold only parts whose `type` is exactly
  `text`.

## The counter is optional

`DaemonConfig.inputPreparation`'s counter adapter is optional. A Host that
supplied a counter only to get past `counter_missing` can drop it; a Host that
keeps one gets a tightener whose evidence is bound to the artifact's projection
digest and the inference target, and refused as `counter_unavailable` when that
binding is missing or mismatched.

## A Pi terminal may omit `usage`

A Pi run that reported no usage, or whose usage carries no token count, omits
the terminal `usage` block rather than fabricating one from device facts.
Consumers must treat terminal `usage` from a Pi run as optional.

## New typed failures on the prepared lane

Two `task.fail` reason prefixes close the prepared lane. Both are
non-retryable, neither is accepted as success, and both are classified from
numbers only — no provider error text is read and the upstream runtime's
heuristic overflow detector is not consulted:

- `context_overflow` — a provider call reported prompt tokens at or above the
  `contextWindow` of the model the frozen request was compiled for. The
  Execution is torn down.
- `usage_unavailable` — the Execution settled with no provider usage observed,
  or a call reported no positive, representable prompt count. A prepared result
  without that observation cannot be checked against its byte bound.

## Known CI timing flakes (unrelated to this release)

- `packages/client/src/__tests__/pi-mcp-launch-cwd.test.ts` runs under the
  client suite's 10s test timeout and can trip it under heavy load.
- On Windows, `packages/client/src/__tests__/daemon-auth.test.ts` has a 750ms
  settle guard that a slow runner can miss.

Neither test is touched by this train; a red on either one is a timing flake,
not a release regression.

## Host follow-up

A Host that reads input-preparation state must move with the renames (`prepared`,
`not_prepared`, no `counter_missing`, no counter `kind`, the new
`request_content_not_text`), check `requestBytes + C + max_tokens <= window`
under its own budget ruling, and read `preparedObservation` on prepared
terminals to falsify that ruling after the fact. Until then the daemon and
cloud refuse the old shapes fail-closed; nothing is silently rewritten.

No Host data migration, live profile update, deployment, real credential use or
provider inference is part of this release preparation. See the
[release handoff](v0.20.0-handoff.md) for the evidence boundary and the
publication sequence.
