# 0.32.0 — published

This is the release preparation record, not a publication record. It does not
approve any merge, tag or publish. The npm registry lists all nine packages at
0.32.0 as `latest` (see the Publication paragraph below). The sections below
record the state at preparation, except the owner's decisions 2 and 3 and the
AiphaBee lines, which carry the owner's later revision. They are not updated
for the later CI and publication. The previous published version is 0.31.0
(see the [0.31.0 notes](v0.31.0.md)), npm `latest` for all nine packages from
2026-10-29 (UTC). This preparation made no npm registry read, so it records no
registry state; the Publication paragraph does. All nine public manifests and
their lock records name 0.32.0.

## Known limitations

- File scope v1 covers the SDK file tools of ordinary Pi RPC on darwin and
  linux. It is root validation and SDK-side path enforcement, not an OS
  sandbox. Shell, MCP and extension tools outside the file boundary ask on
  every call unless an `allowWithoutAsking` rule names them (manifest entries
  `tool-file-scope-policy`, `tool-file-scope-root-guard`,
  `tool-authorization-rules`).
- The tool authorization classifier is lexical, as in 0.31.0.
- The per-device rate budget of the Postgres composition is per process: N
  replicas admit up to N times the configured rate.
- The path-mutation gate excludes only processes with the same UID in the same
  Linux network namespace that reach a target through a consistent canonical
  path.
- The activity log of #1176 is the A1+A2a part of #1113. Its settlement
  boundary is not yet integrated into every canonical lifecycle transaction
  (A3), so its terminal retention is not the final one. The
  [migration note](../migrations/1113-durable-activity-log.md) and the
  [cutover runbook](../../deploy/runbooks/activity-tail-cutover.md) still
  describe A1 as not deployable and ask for final A1 to A5 acceptance before
  migration 0034. 0.32.0 ships 0034, and a Host that runs `migrate` applies
  it: it drops `activity_tail`, carries no pre-cutover activity history over,
  and has no application-only rollback. The two documents are not updated
  for the 0.32.0 scope; their cutover steps (stop old readers and writers,
  accept the history loss, verify through the new log) still apply.
- On macOS and Linux bash, the pi-durable shell gate can source the user's
  `~/.bashrc` before shell ownership is acknowledged, and rc output joins the
  tool output. The gate spawns `bash -c` with a socket stdin and no `SHLVL`,
  and closes stdin only after `own()`. The macOS client test
  `fix-pi-durable-shell-exit` (F16-2) hits this race intermittently: it
  failed attempts 1 and 2 of the release-validation run 41274113989, which
  passed on attempt 3. The fix (`--norc` on the gate spawn) targets 0.33.0.
- The local checks in the PR bodies were targeted. The full suite and the
  release matrix run on the exact `release_sha`; their results go in the
  dry-run section below.

## Upgrade notes for Hosts and deployments

The upgrade manifest (`packages/client/upgrade-manifest.json`, shipped in the
client package) lists each Host-visible change from 0.31.0 with its impact,
summary and migration link. The CHANGELOG 0.32.0 section names the breaking
changes by package. The [Host upgrade checklist](host-upgrade-0.32.0.md)
covers a Host that moves from 0.30.2 straight to 0.32.0 (AiphaBee moves from
0.30.2 to 0.33.0 instead); a Host on 0.31.0 reads its 0.32.0 sections only. In short:

**Order.** Upgrade the Host before its devices (`expiresIn`, #1114). Before
any participant moves, stop every SDK process that shares a protected target
with it: the path-mutation gate of 0.32.0 does not exclude a 0.31.0 or
earlier process on macOS and Linux (#1149).

**New SQL.**

- Postgres: 0031 (dead-letter retention policy column, pending-only quota
  index), 0032 (terminal task archive; the policy column is `NOT NULL` with no
  default, so stop policy writers from before #1120 first, and count terminal
  rows first), 0033 (closed device streams), 0034 (the activity log; drops
  `activity_tail`, no row conversion). Apply them before the new Host starts.
  The runner is forward-only.
- Server SQLite: a schema 6 file is upgraded to 7 in place. A schema 1 to 5
  file (0.30.2 or earlier) is still refused; start on a new path and pair
  again.

**Host code.** Pass `proofReceiptRetention` and, on Postgres, `rateLimit`;
adopt the new `InboundRateLimiter` signature in a custom limiter; add
`mailboxDeadLetterRetentionMs` and `terminalTaskArchiveMs` to a complete
`RetentionPolicy`; implement the new store ports (`taskArchive`,
`BoardStore.remove`, `MailboxStore.expirePending`, `closeStream`,
`reopenStream`, `TaskCancellationStore.abandon`) in custom stores; read
`task.fail` failures and decline codes with `readTaskFailure` and
`readDeclineCode`; move activity readers to the log cursor; import the Agent
memory contract from `@byok-sdk/protocol/agent-memory` and the K4 core from
`@byok-sdk/server/execution-core`.

**Device config and services.** Run `byok-agent config check --strict`;
replace a `toolAuthorization` function with the policy document and catch
`DaemonConfigInvalidError` for an invalid one; set
`localToolApproval: 'allow'` only to keep local tool approval; list Host-set
runtime variables in `runtimeEnvironment.pass`; set `maxConcurrentTasks` above
8 if the Host needs more; replace a service unit from 0.31.0 or earlier once
with `byok-agent install --replace-unmarked`; handle the halt reasons
`store_not_bound` and `cursor_unreadable`.

### Final cut

The version bump is the last commit of the release PR and holds only
derived changes, so it is made again on a new base instead of being carried
forward. These steps produced the version commit on `ccf8b2e4d`; repeat
them if the base moves again:

1. Bring the release branch up to date with main and drop the old version
   commit (revert it, or rebase without it).
2. Derive the scope again:
   `git log --first-parent --format='%h %s' v0.31.0..origin/main`, and add
   each new PR to its area.
3. Make the version commit again: the nine `package.json` versions and their
   `bun.lock` workspace records; `node scripts/release/check-upgrade-manifest.mjs --write`
   (the generated `to`, `changes` and items; authored entries from the new
   PRs come with those PRs); the CHANGELOG `Unreleased` entries into the
   0.32.0 section, with its intro updated from the manifest;
   `bun run --filter @byok-sdk/protocol test`, which prints the 0.32.0
   `v4.releases.json` entry for the final corpus, appended unchanged in
   place of the draft entry; the README, spec, runbook, cloud-do README,
   `docs/protocol.md` and `docs/releases/README.md` candidate lines;
   `registry-expectations.json` and its test pin after a fresh registry
   read; and `bun run docs:device-setup`, whose generated migrations block
   prints the manifest transition (`check:device-setup` fails without it).
4. Recount this page and the Host checklist from the final manifest (the
   breaking rows, the migration table, the counts in the version policy).
5. Run `check:version-authority`, `check:api-surface`,
   `check:upgrade-manifest`, `check:release-graph` and `typecheck`, then CI
