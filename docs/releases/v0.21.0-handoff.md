# 0.21.0 / keys 0.6.2 release preparation

Status: prepared; NOT published. No npm publication, no tag, no GitHub Release,
no `scripts/release/publish.mjs --execute`. This handoff does not authorize any
of them; it states what the Owner must run when publication is authorized.

## Scope and upgrade decision

Source: `main` @ `644f8473` (the PR #226 merge), plus this preparation branch.
The eight aligned packages — `@byok-sdk/core`, `@byok-sdk/protocol`,
`@byok-sdk/client`, `@byok-sdk/server`, `@byok-sdk/cloud`,
`@byok-sdk/cloud-dataplane`, `@byok-sdk/ui-runtime` and
`@byok-sdk/implementation-identity` — move 0.20.0 → 0.21.0, and
`@byok-sdk/keys` moves 0.6.1 → 0.6.2. The published set is exactly these nine
packages.

The Owner chose to stop publishing two packages in this train (option B): the
`byok-sdk` umbrella (`packages/sdk` is deleted; ADR-035) and
`@byok-sdk/testkit` (now private, kept for the private conformance suite). No
product logic and no dependency range of a published package changes in the
preparation: the diff is version literals, the removal of those two packages
from the publish set and its gates, and release documentation. See
[Packages no longer published](v0.21.0.md#packages-no-longer-published).

Version selection follows the authoritative
[pre-1.0 package version policy](../spec.md#pre-10-package-version-policy):

- The dispatch train takes a MINOR, because MINOR covers "any pre-1.0 breaking
  cut" and PR #226 is one: input-preparation wire version 6, capability token
  `agent-input-preparation-v6` with no dual token or dual read,
  `TaskOfferPreparedPayload` requiring `egressPolicy`, and Pi `auto` +
  `allowTools: []` on the fresh lane reinterpreted as zero native tools.
- keys takes a PATCH. PATCH is limited to "corrections with no new public
  behavior, API, persistence, or security authority", and keys changes none of
  them: `packages/keys` source is unchanged since `v0.20.0` apart from the
  version literal, and so is the source of `packages/core` and
  `packages/implementation-identity`, its only workspace edges. It is
  re-released only because the same policy requires keys' packed and published
  `@byok-sdk/core` edge to be the exact current dispatch release, and the
  published keys 0.6.1 pins core 0.20.0.

Release notes: [0.21.0](v0.21.0.md). The upgrade requirements are: drain the
in-flight input preparations and prepared Executions, and then upgrade the cloud
and its devices as a pair (on long-poll an unknown key or type freezes the
device cursor, the enqueue capability gate is the only guard, and an old
prepared offer already enqueued without `egressPolicy` needs operator handling
that a paired upgrade does not supply); recreate v5 preparations under v6;
expect the `agent-input-preparation-v5` token to be refused everywhere; add
`egressPolicy` to every prepared offer a Host builds; and re-check any fresh Pi
policy that sends `{ mode: 'auto', allowTools: [] }`, which now means zero
native tools. No automatic migration or live-store conversion is supplied or
executed.

## Publication boundary after preparation — Owner only

Obtain explicit publication authorization first. Then run
[`deploy/runbooks/release-responsibility.md`](../../deploy/runbooks/release-responsibility.md)
checklist item 5, filled in for this train, from a checkout of the exact merged
release commit:

1. Confirm the CI run for the exact merged release commit is green, including
   its `npm-release-pack` job. Use the `push` run, not a `pull_request` run — on
   pull-request events `github.sha` is the merge ref, so that run's artifact is
   named after a commit that is not `HEAD` and the dry run refuses it.

   ```sh
   gh run list --branch main --workflow CI --event push --limit 1
   ```

2. Download that run's accepted tarballs, with `<sha>` the full 40-character
   commit id:

   ```sh
   git rev-parse HEAD                       # this is <sha>
   gh run download <run-id> -n release-pack-<sha> -D <dir>
   ```

3. Dry run. It refuses unless the frozen `release-manifest.json` names 0.21.0
   and was packed from the current `HEAD`, and unless every tarball the publish
   set needs is present and re-hashes to its recorded sha256. It then prints the
   ordered publish plan with those digests. Nothing is published, read back or
   tagged.

   ```sh
   node scripts/release/publish.mjs --artifacts <dir>
   ```

4. Release — run this yourself, interactively, in Terminal.app. npm's write
   2FA needs a human at a real TTY, so this step cannot be delegated to an
   agent or a non-interactive shell. It refuses if the tag already exists, if
   `npm whoami` reports no account, or if `npm profile get --json` does not
   report `tfa.mode` `auth-and-writes` — there is no override. It publishes each
   tarball in dependency order (`--provenance` only under GitHub Actions OIDC; a
   local release logs that no attestation is attached), reads the registry
   back, and only then creates the annotated `v0.21.0` tag carrying the source
   commit.

   ```sh
   node scripts/release/publish.mjs --artifacts <dir> --execute
   ```

   Without `--otp`, npm prompts for its web 2FA confirmation in the terminal;
   open the URL it prints and approve in the browser whenever it asks. This is
   the route the 0.17.0, 0.19.0 and 0.20.0 releases used. To use an
   authenticator code instead, pass it with `--otp`; the script hands the same
   code to every `npm publish`, so enter a fresh one right before starting:

   ```sh
   node scripts/release/publish.mjs --artifacts <dir> --execute --otp <code>
   ```

   If step 7's registry readback fails with E404 right after all nine PUTs
   returned 202, that is registry propagation (it happened on 0.17.0, 0.19.0
   and 0.20.0). Do NOT republish. Wait a minute or two, re-run the readback
   alone, and then create the tag exactly as step 8 would:

   ```sh
   node scripts/release/registry-readback.mjs --manifest <dir>/release-manifest.json
   git tag -a v0.21.0 -m "v0.21.0" -m "sourceGitSha <sha>"   # same message step 8 writes
   ```

5. Push the tag, only after the registry has confirmed the train.

   ```sh
   git push origin v0.21.0
   ```

CI artifacts expire after 30 days; past that, re-run CI on the same commit
rather than repacking locally. After a partial failure, preserve the original
bytes and inspect registry state before anything else; never blindly republish.
Record the outcome in `docs/releases/v0.21.0-publication.md` and update the
README release-status block and row to name 0.21.0 / keys 0.6.2 as published.
Product updater and deployment remain separately owned.

## Optional post-publication step — Owner only

After step 5, and only if the Owner wants installs of the retired packages to
print a pointer, deprecate their existing versions. This is optional, does not
remove or change any version, and is not part of the release gate. Run it
interactively in Terminal.app (npm write 2FA):

```sh
npm deprecate 'byok-sdk@<=0.20.0' 'byok-sdk is no longer published as of 0.21.0. Install and import the scoped @byok-sdk/* packages directly, for example @byok-sdk/client and @byok-sdk/server.'
npm deprecate '@byok-sdk/testkit@<=0.20.0' '@byok-sdk/testkit is no longer published as of 0.21.0; it is now internal to the BYOK SDK repository.'
```

Read back with `npm view byok-sdk@0.20.0 deprecated` and
`npm view @byok-sdk/testkit@0.20.0 deprecated`; undo by re-running either
command with an empty message (`''`). Salesko should also drop its root
`overrides` pin on `@byok-sdk/testkit` when it moves to 0.21.0.
