# 0.45.1 — candidate, 2026-11-23 (UTC)

0.45.1 is the PATCH after 0.45.0 on `release/0.45`. It keeps wire v8 and
carries zero breaking and zero additive entries in the upgrade manifest. The
public API surface and the Wire v8 corpora are unchanged. Hosts on 0.45.0 keep
their server databases, daemon journals, provider stores, and device pairings.
Hosts upgrading from wire v7 still follow the
[0.45.0 Host upgrade checklist](host-upgrade-0.45.0.md).

## Version set and release gates

All nine public packages move together to 0.45.1 (`core`, `protocol`, `client`,
`server`, `cloud`, `cloud-dataplane`, `ui-runtime`, `bot-collaboration`, and
`keys` under `@byok-sdk`). Publication requires separate authorization,
exact-SHA release validation, and registry readback.

## Fixed

### Windows user-scope service on non-elevated desktops

On 0.45.0, a `windows.scope: 'user'` lifecycle failed `start()`, `stop()`,
`status()`, and `install()` on an ordinary non-elevated desktop. The launcher
query treated any `cmd.exe` whose command line it could not read as a failure.
A non-elevated query cannot read the command line of another user's process, a
Session 0 process, or an elevated process in the same session, so any one of
them failed the query. 0.45.1 skips those processes: none of them can be the
calling user's launcher. A WMI or PowerShell error still fails the query
closed. [Refs #2452](https://github.com/Ancienttwo/byok-sdk/issues/2452)

### User-scoped `inspectStoreServiceState`

`install()` now records the current Windows user's SID with the `windows-user`
registration. `inspectStoreServiceState` queries the launcher only when the
caller runs as the recorded user. For any other user, or when the current SID
cannot be read, it reports `unknown`, or `running` while the store's daemon
lock is held. It no longer reports a false `stopped` because another user's
launcher is invisible.

A 0.45.0 record has no SID. For such a record, a running launcher reports
`running` and a launcher that is not visible reports `unknown`. Run `install()`
on 0.45.1 to rewrite the record in place with the SID; `stopped` is then
available again for the recorded user.

## Residual boundary

A `windows-user` install is meant to run non-elevated. If the same user runs
`install()` elevated, the launcher runs elevated and a later non-elevated query
cannot read its command line. Between program restarts, during the launcher's
crash backoff, neither the launcher nor the daemon lock is visible, so a
non-elevated `inspectStoreServiceState` can report `stopped` while the launcher
is still waiting to restart the program. Install the user-scope service from a
non-elevated process.
