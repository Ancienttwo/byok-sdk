## Source and scope

The freeze base is main `0f8a35425`, the merge of #1307.
`git log --first-parent v0.33.0..0f8a35425` lists 11 commits, each one PR
merge. The commits are grouped by area.

Wire v5 and runtime names (#1290):

- The envelope wire is v5 (`PROTOCOL_VERSION = 5`). The runtime capability
  `durablePi` is renamed `durableLane`, the durable worker lane (Pi today), on
  `conn.hello` runtimes and harnesses, `task.claim`, presence and
  `RuntimeCapabilities`. Nothing else on the wire changes. There is no v4
  reader and no negotiation: a Host drains once, then starts the server side
  and the daemons together. Retained store rows open, so the stores need not
  be new; a pending v4 row stops startup and is left unchanged. A hosted
  terminal receipt written by a v4 build no longer decodes
  (`terminal_receipt_unreadable`). Breaking in protocol, core, client,
  server, cloud and cloud-dataplane (manifest `wire-v5-durable-lane`).
- Runtime names are generic. `DaemonConfig.durablePi` is removed
  (`DaemonConfigFieldRemovedError`); set `runtimes.pi.durableLane`.
  `PiAdapterOptions.durablePi` is `durableLane`. The daemon wires the
  durable journal from an adapter's `capabilities.durableLane`, so
  `PiAdapter({ durableLane: true })` passed to `createDaemonWithAdapters`
  needs no daemon option. The launch resources are the exported
  `RuntimeLaunchResources`. Breaking in client (manifest
  `runtime-generic-names`).

The migration note is
[docs/migrations/wire-v5-durable-lane.md](../migrations/wire-v5-durable-lane.md).

Pi lanes and runtimes:

- #1302 (#1061 v2): `auto` tool authorization and `toolAuthorization.fileScope`
  run on Pi's prepared and durable lanes (darwin/linux) with the ordinary
  lane's contract, instead of declining before claim. The prepared session
  asks the gate before every counted tool call, and a scoped prepared task
  asks for every call. The durable worker asks after it records the tool
  intent, swaps `read`, `write` and `edit` for the six SDK scoped file tools,
  and re-verifies the scope on every spawn. `PiAdapter` with
  `durableLane: true` reports `toolAuthorizationAuto: true`. A custom adapter
  that declares both `preparedLane` and `toolAuthorizationAuto` must enforce
  `startInput.toolAuthorization` on its prepared starts. No manifest entry;
  the contract is in the
  [spec](../spec.md#tool-authorization-auto-and-all-1061).
- #1299 (fixes #1295, #1296): the bundled pi-web-access and rpiv-todo are Pi
  replaceable extensions, so a user's own copy takes their place instead of
  stopping the task at start. Under `agentUserContext: 'excluded'` Pi keeps
  the user's `defaultProvider`, `defaultModel` and `defaultThinkingLevel`, and
  a new session without an explicit model refuses to start unless Pi selects
  exactly that default.
- #1308 (fixes #1303): on the durable Pi lane the model sees the text a task
  MCP tool or SDK reserved MCP tool returns.
- #1301 (fixes #1297, #1298): runtime disposal reads the process table with
  `/bin/ps` on macOS, and a failed read reaches the Host as a
  `RuntimeDisposalFailure` (`stage: 'signal'`). On POSIX the SDK records a
  Grok or dsh agent's descendants before it sends `session/cancel`, and close
  ends the recorded tools a cancel orphaned.
- #1306 (fixes #1305): a refused native cancel on Grok, dsh or Hermes rejects
  `session.interrupt()` with a `RuntimeExecutionFailure`
  (`category: 'infrastructure'`, reason `<runtime> interrupt refused: …`),
  and Hermes records its gateway's descendants before its cancel.
- #1307 (fixes #1304): the system tools the SDK starts come from fixed trusted
  paths, never `PATH`. A tool missing from its location starts nothing and
  fails with the new exported `SystemToolUnavailableError`. Additive in
  client and keys (manifest `system-tool-trusted-paths`).
- #1293: the vendored OAR source moves from 0.80.1 to 0.83.0
  (`vendor/oar/ddec7e5/`). API surface is unchanged; all sixteen BYOK deltas
  are kept. Research note:
  [2026-11-01-oar-0.83.0-upgrade.md](../researches/2026-11-01-oar-0.83.0-upgrade.md).

Host execution core:

- #1300 (fixes #1105): the 10k-task retention soak drives the K4 Host ledger
  (`HostLedger`). It asserts that `ignoredWakes` stays within 128 entries and
  that `compact` empties the per-task tables; the permanent identity
  tombstone growth is measured and documented, not asserted (see Known
  limitations).

Records and docs:

- #1294 records 0.33.0 as published, rebaselines the upgrade manifest on
  0.33.0 and adds the 0.33.0 store fixture.
- #1292 (#1291) retires `docs/plans` and places its decisions and research
  under `docs/adr` and `docs/researches`.

Wire and persistence. `packages/protocol/src` changes since `v0.33.0` only for
#1290. The v4 corpora and `v4.releases.json` are retired and read-only at
0.33.0. The v5 corpus has 342 envelope lines and 30 HTTP lines, and
`v5.releases.json` registers it for 0.34.0, the first v5 release. The
published 0.33.0 decoder (`byok-protocol-previous`) rejects every v5 line.
There is no new Postgres migration and no SQLite schema change: 0.34.0 opens
the stores 0.33.0 wrote, schema 8 included.

## Known limitations

- Wire v5 has no negotiation: a v5 build reads no v4 envelope, and the
  published 0.33.0 decoder rejects every v5 envelope. The migration note
  describes no way back to 0.33.0 after the cut; keep the backups taken
  before it. A hosted terminal receipt a v4 build stored is unreadable to
  0.34.0; read the results you still need before the cut.
- The K4 Host ledger has no total bound. Each compacted caller intent leaves
  an identity tombstone with no expiry (about 112 serialized bytes before
  SQLite overhead), so that table grows with the number of compacted intents
  for the life of the database
  ([storage layout](../host-local-storage-layout.md#k4-host-ledger)).
- File scope still declines before claim on Windows, for memory-reader
  offers and on adapters other than Pi. `auto` still declines before claim on
  Codex, Grok, Hermes and dsh.
- Process-tree reaping on POSIX still reaches only processes a
  once-a-second read saw below the root, as in 0.33.0.
- The 0.33.0 limitations on sealed memory projections, the version 3 memory
  outbox, the Postgres task events wake, file scope v1, the lexical tool
  authorization classifier, the per-process Postgres rate budget and the
  path-mutation gate scope are unchanged (see the
  [0.33.0 notes](v0.33.0.md#known-limitations)).
- `docs/migrations/1113-durable-activity-log.md` and
  `deploy/runbooks/activity-tail-cutover.md` still say A1 is not deployable,
  as in 0.33.0. Their cutover steps for 0034 still apply.
- The local checks in the PR bodies are targeted. The full suite and the
  release matrix run on the exact `release_sha`.

## Upgrade notes for Hosts and deployments

The upgrade manifest (`packages/client/upgrade-manifest.json`, shipped in the
client package) lists each Host-visible change from 0.33.0 with its impact,
summary and migration link. The CHANGELOG 0.34.0 section names the breaking
changes by package. The [Host upgrade checklist](host-upgrade-0.34.0.md)
covers a Host that moves from 0.30.2, 0.31.0, 0.32.0 or 0.33.0 to 0.34.0. In
short:

**Drain, then cut over.** Stop new submissions, let every pending mailbox row
be acknowledged, every execution reach a terminal and every daemon pending
terminal be acknowledged. Read the hosted terminal results you still need.
Then stop the v4 Host and daemons and start the 0.34.0 server side and
daemons together.

**Host code.** Replace `DaemonConfig.durablePi` with
`runtimes.pi.durableLane`; read `durableLane` from presence and
`RuntimeCapabilities`; build `PiAdapter({ durableLane: true })` for
`createDaemonWithAdapters`; type `runtimeLaunch` as `RuntimeLaunchResources`
in a custom adapter. A Host may catch `SystemToolUnavailableError`.

**Pi behavior.** `auto` and file-scope tasks now run on the Pi prepared and
durable lanes. A user's own pi-web-access or rpiv-todo replaces the bundled
one. Under `agentUserContext: 'excluded'` the user's default model applies,
and a session whose model does not match it refuses to start.

**From before 0.33.0.** The 0.33.0 store, migration and sealing steps still
apply in full: SQLite schema 8, Postgres 0035 to 0037 and the opt-in sealed
payload v2. The 0.34.0 checklist links them.
