# 0.33.0 — source candidate

This is the release preparation record, not a publication record. It does not
approve any merge, tag or publish. The previous published version is 0.32.0
(see the [0.32.0 notes](v0.32.0.md)), npm `latest` for all nine packages from
2026-11-01 (UTC), tag `v0.32.0` on main `5f975955`. A read-only registry
read on 2026-11-01 (UTC), during the version commit, showed `latest` 0.32.0
for all nine packages.

The fixed source of 0.33.0 is the release PR's final merged SHA on `main`. It
is not known yet. The scope below is counted from the freeze base, main
`970ab899d` (see "Final cut").

0.33.0 is a MINOR release under the default pre-1.0 policy, with no PATCH
exception. Breaking changes ship only in a MINOR (Q8, owner 2026-10-29), and
the upgrade manifest from 0.32.0 holds 7 breaking and 6 additive entries. All
nine public packages move to 0.33.0. Private packages remain unchanged.
`docs/spec.md` names the current aligned release and records no exception
([version policy](../spec.md#pre-10-package-version-policy)).

These notes do not say that 0.33.0, or a Host on it, is ready for production.
0.33.0 is the fixed revision for the product loop gate (#977) and the Host
upgrade checklist acceptance (#978) (decision 1 below). Until a gate records a
result, no statement about production use follows from this release.

## Source and scope

The freeze base is main `970ab899d`, the merge of #1286.
`git log --first-parent v0.32.0..970ab899d` lists 8 commits, each one PR
merge. #1272 is a batch merge of the reviewed PRs #1253, #1254, #1255,
#1257, #1265, #1266, #1267 and #1268, #1280 one of #1274, #1276 and #1277,
and #1286 one of #1279 and #1281 to #1285; those PRs were closed into the
batches. The commits are grouped by area.

Durable task events (#1113 A2b to A5, all through #1272):

- #1253 (A2b): the embedded server persists the activity log in its SQLite
  file (schema 8) instead of process memory. A schema 6 or 7 file is upgraded
  in place when it opens; 7→8 creates `activity_log_head` and
  `activity_log_entry` empty, since no activity history was persisted
  before. The terminal task archive removes activity content in its own
  transaction. Breaking in server (manifest `server-sqlite-v8`).
- #1257 (A3): a task's activity log and approval timeline close in the same
  commit as its first terminal or accepted Host cancellation, in every
  built-in composition. Later `task.progress`, `task.artifact` and
  `task.await_approval` are refused with `task_settled_by_cloud`; both expire
  ten minutes after the close without renewal. An open approval timeline no
  longer idle-expires; it keeps at most 50 observations and 1 MiB, never
  evicting the pending request. Postgres migration 0035 adds the closing
  trigger and backfill; SQLite schema 8 carries the same trigger. Breaking in
  cloud, cloud-dataplane and server (manifest
  `task-output-closes-at-terminal`, `approval-timeline-closes-with-task`).
- #1265 (A4): a content-free `TaskEventsWake` names only the tenant and task
  whose state, activity or approval timeline changed. In-memory and SQLite
  compositions expose one; `createPostgresTaskEventsWake` listens for the
  triggers that migration 0036 adds, on a session-mode DSN. A reader no hint
  reaches re-reads within 5 seconds. Additive (manifest `task-events-wake`).
- #1254 (A5): `ByokServer.tasks.events` and `TaskHandle.events()` read the
  durable activity log, task state and approval timeline. Cursors resume
  across a restart over the same SQLite file; cursors from 0.32.0 and
  earlier are refused as `cursor_unknown`; state is coalesced, not replayed;
  terminal tasks stay readable (`feed_expired` is gone).
  `taskEventBufferLimit`, `taskEventRetentionMs` and their `DEFAULT_*`
  exports are removed. Breaking in server (manifest
  `task-events-durable-cursor`).

#1113 is closed.

Runtimes:

- #1255 (#1094): `DaemonConfig.runtimes.grok` takes `compatInstructions`,
  `agentUserMcpServers` and `versionPolicy`, and `createDaemon` builds the
  Grok adapter from configuration when `runtimeAllowlist` lists `grok`.
  Additive (manifest `daemon-config-runtimes-grok`).
- #1266, #1267, #1268 (#1258): `DshAdapter` runs DeepSeek Harness
  (`@deepseek-ai/dsh`, qualified 0.2.1-rc.5) over ACP on the custom-harness
  path (`harnessId: 'dsh'`), on macOS and Linux, with an SDK-owned `DSH_HOME`
  and a per-execution `--patch` route. The runtime contract suite and
  nightly matrix gain a dsh leg. #1256 is the design note. Additive
  (manifest `dsh-adapter`).
- #1263 (fix, #1261): `byok-agent runtimes` and offline `doctor` build their
  adapters with the daemon's factory, so a configured
  `runtimes.<id>.versionPolicy` reaches their version verdict; an invalid
  `piByokLauncher` throws the same error as `createDaemon`.
- #1280 (#1274, fix #1273): the pi-durable shell gate starts `/bin/bash` with
  `--norc`, so `~/.bashrc` no longer runs before shell ownership is
  acknowledged. This removes the 0.32.0 known limitation F16-2.
- #1280 (#1276, #1269): on POSIX the owned process tree reads the process
  table once a second for every running runtime root, and disposal ends the
  descendants it observed, including those in process groups of their own.
  A dsh root killed from outside no longer leaves its shell tools running,
  and `dsh.sigkill` runs again. The same applies to a root that exits by
  itself: its observed descendants are ended at disposal. No manifest entry;
  the behavior is in the [spec](../spec.md).
- #1280 (#1277, #1271): a `quota` failure may carry `scope: 'account' |
  'model'`, sent only to a server that advertises `runtime-quota-scope`. The
  Claude adapter maps its per-model weekly limits to `model`. Additive in
  protocol, client and cloud (manifest `task-fail-quota-scope`).
- #1278: `RuntimeAdapterDescriptor.fileScope` and `providerProfileBinding`
  and `RuntimeAdapter.projectMcpEnvironment(env)` let an adapter declare what
  the daemon used to infer from the runtime id `pi`; `PiAdapter` declares all
  three. Every SDK JSONL line transport uses one LF-only decoder, so the
  durable Pi host no longer splits a frame at a raw U+2028 or U+2029. Additive
  in client (manifest `adapter-admission-declarations`).

Sealed payload v2 (#1045 first batch, all through #1286). Agent message
bodies (C2) and hosted memory projection snapshots (C4) can be sealed end to
end, with the v1 suite, keys, member chain and binding rules. Nothing is
sealed unless the Host asks: a task seals a category only when its offer's
`sealing.categories` names it, and a projection only under a grant with
`sealing`. Nothing falls back to plaintext. The Host guide is
[docs/migrations/1045-e2ee-v2.md](../migrations/1045-e2ee-v2.md).

- #1279: the plan, with the owner decisions O1 to O4 (decision 7) and the
  threat model.
- #1281 (S1): the protocol adds the `agent-message` and `memory-projection`
  categories behind the new `sealed-payload-v2` flag; `memory-projection`
  needs `task-output` in the same policy. `agent.message.publish`,
  `agent.message.disposition` and the projection mutation and receipt become
  unions of a plaintext and a sealed branch, with the plaintext branch under
  its own name. `SEALED_PAYLOAD_V1_CATEGORIES` and `SealedPayloadV1Category`
  are replaced by `SEALED_PAYLOAD_CATEGORIES` and `SealedPayloadCategory`.
  Breaking in protocol (manifest `sealed-payload-v2-protocol`).
- #1282 (S2): the daemon seals Agent messages once, when the draft enters its
  outbox; it moves a task's memory evidence into the sealed terminal; and it
  seals each projection snapshot under a grant's `sealing { scopeId, epoch }`.
  Without a usable key it sends nothing. It advertises `sealed-payload-v2`
  whenever it advertises `sealed-payload-v1`. Additive in client (manifest
  `agent-memory-projection-grant-sealing`).
- #1283 (S3): the cloud admits sealed Agent messages and hands them to the
  new `agentMessage.consumeSealed`; `ByokCloudOptions.agentMessage` is an
  `AgentMessageConsumers`, and a submission that seals `agent-message`
  without `consumeSealed` is refused with
  `agent_message_sealed_consumer_missing`. Breaking in cloud (manifest
  `cloud-sealed-agent-message`).
- #1284 (S4): the cloud stores a sealed projection as received and refuses a
  snapshot whose form does not match its grant with 409
  `agent_memory_projection_sealing_mismatch`;
  `AgentMemoryProjectionCommitInput` becomes a plaintext/sealed union.
  Postgres migration 0037 adds the sealed forms with one-form checks and
  rewrites no data. Breaking in cloud and cloud-dataplane (manifest
  `cloud-sealed-memory-projection`).
- #1285 (S5): the Host guide, the spec and the security table, split by O3.

## Known limitations

- Process-tree reaping on POSIX reaches only processes a once-a-second read
  saw below the root. A process re-parented before any read, or started
  within one second of the root's death, is not ended; a background job
  (`cmd &`) from a shell that exits at once can outlive `close()` and
  `daemon.stop()`. The host-exit sweep does not use these observations.
- A sealed memory projection is inline only: a snapshot whose padded form
  exceeds 256 KiB is not sent, so that Agent's projection does not advance
  (O2). A Host whose backend must read message bodies server-side keeps
  `agent-message` out of `sealing`.
- Once a sealed projection row exists, code older than 0.33.0 cannot read
  that head or its receipts; that Agent's projection fails closed until the
  new code returns or `eraseAgentMemoryProjection` clears it.
- Postgres task events wake: each notifying commit takes PostgreSQL's
  notification queue lock, so at high write rates these commits serialize on
  it, alongside the mailbox wake. Hyperdrive and transaction-mode poolers
  cannot carry `LISTEN`.
- File scope v1, the lexical tool authorization classifier, the per-process
  Postgres rate budget and the path-mutation gate scope are unchanged from
  0.32.0 (see its known limitations).
- `docs/migrations/1113-durable-activity-log.md` and
  `deploy/runbooks/activity-tail-cutover.md` still say A1 is not deployable
  and ask for final A1–A5 acceptance. With A2b to A5 merged in 0.33.0 the
  stack is complete; the two documents are not updated by this preparation.
  Their cutover steps for 0034 still apply.
- The local checks in the PR bodies are targeted. The full suite and the
  release matrix run on the exact `release_sha`.

## Upgrade notes for Hosts and deployments

The upgrade manifest (`packages/client/upgrade-manifest.json`, shipped in the
client package) lists each Host-visible change from 0.32.0 with its impact,
summary and migration link. The CHANGELOG 0.33.0 section names the breaking
changes by package. The [Host upgrade checklist](host-upgrade-0.33.0.md)
covers a Host that moves from 0.30.2, 0.31.0 or 0.32.0 to 0.33.0. In short:

**Back up first.** Stop the embedded server and copy its SQLite file before
0.33.0 first opens it. The 7→8 upgrade is one-way; 0.32.0 and earlier refuse a
schema 8 file.

**New SQL.** Postgres 0035, 0036 and 0037. Apply them only through
`deploy/scripts/migrate`, together with the new code, in one maintenance
window: 0035 scans `task`, rewrites `approval_timeline_tail` and blocks writes
to `task` until it commits. After 0035, rolling back only the code breaks
approval writes. 0036 is additive. 0037 validates its one-form checks on the
two projection tables under `ACCESS EXCLUSIVE` locks, so projection writes
pause until it commits; it rewrites no data.

**Host code.** Remove `taskEventBufferLimit` and `taskEventRetentionMs`;
discard stored `tasks.events` cursors (they return `cursor_unknown`); expect
coalesced state and `task_settled_by_cloud` for late progress and approvals
after the output closes, cancellation included; drop `ttlMs` from approval
timeline appends and read `terminalAt`; pass `agentMessage` as an
`AgentMessageConsumers` object, also to `handleInboundEnvelope`; narrow the
protocol's Agent message and projection unions or use their plaintext names;
handle the sealed commit input in a custom `AgentMemoryProjectionStore`; a
custom composition closes its
activity log and approval timeline with its first terminal; a hosted Host that
wants cross-instance wake-ups uses `createPostgresTaskEventsWake` on a
session-mode DSN.

**Runtimes.** Configure Grok through `DaemonConfig.runtimes.grok`. Construct
`DshAdapter` to use dsh on macOS or Linux. On POSIX, disposal now also ends the
descendants a runtime root left when it exited by itself, if a read observed
them. A Host that switches models on a quota failure can read
`failure.scope` and treat a missing scope as unknown. A custom adapter that
reuses the id `pi` declares `fileScope` to keep admitting file-scoped offers.

**Sealing v2 (opt-in, hosted only).** A Host that seals Agent messages
registers `agentMessage.consumeSealed` and opens the bodies on a member; one
that seals projections issues grants with `sealing` and returns it from its
authorizer. A Host that does neither sees the 0.32.0 behavior apart from the
type changes above. AiphaBee, on Topology L, is unaffected until it moves to
a hosted Host.
