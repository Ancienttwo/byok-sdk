# BYOK SDK 0.19.0 · keys 0.6.0

Prepared for release; not published. The ten aligned dispatch packages align at
0.19.0. Independently versioned keys 0.6.0 pins core 0.19.0. The bundled Pi
runtime moves to the SDK's own fork build `@byok-sdk/pi-coding-agent@0.86.1001`
and `@byok-sdk/pi-ai@0.86.1001` (upstream base 0.86.1 at `13cbf77`).

The previous train, 0.18.0 / keys 0.5.0, is published: it has been the registry's
`latest` since 2026-09-10, built from the `v0.18.0` tag (`7b26ef5f`). Read it
back with `npm view byok-sdk version` and `npm view @byok-sdk/keys version`.

- The prepared-input lane is rebased onto the fork's 0.86 line. The fork no
  longer renders the system prompt itself: one exported `buildRequestPayload`
  builds both the prepared body and the live session's, so the wire carries the
  inputs that renderer reads instead of a pre-rendered block. Consume is
  assert-only — the prepared session runs the ordinary stream path and refuses
  unless the live payload is byte-identical to the compiled body.
- The prepared launch can now run under a BYOK device profile. The keys launcher
  is the parent of the prepared host and delivers the device credential into its
  environment; before any model runtime exists, the host reads the
  launcher-minted projection and refuses unless it declares exactly one provider
  and one model equal to the record's. The projection's `apiKey` is always the
  `$PI_PROVIDER_API_KEY` reference, never a literal secret.
- Configured Pi detection measures the selected installation through its own
  authority, without executing a version child or discovering another binary.

## Breaking wire boundary

The input-preparation contract has no reader for the previous shapes. Request
version moves 3 → 4, record schema version 4 → 5, and the compiler/structural
projection contract 2 → 3. On the snapshot, `prompt.formattedSkills` is REMOVED
and replaced by `prompt.skills`, a closed `{name, description, filePath,
disableModelInvocation}` record; `prompt.toolGuidelines` is added; and
`selection.options.toolChoice` narrows to `auto | none`, because 0.86's simple
stream path cannot express `required`. A stored record prepared under another
compiler contract is refused at readiness with the new `runtime_contract_superseded`
reason, and an older record schema is refused at log replay, untouched and
pending explicit operator disposition. `PROTOCOL_VERSION` stays 1: this wire
surface entered the repository on 2026-09-15, after 0.18.0 was published, so no
released peer speaks any of it.

## Breaking keys launcher argv

`byok-pi-provider-launcher` now REQUIRES `--runtime-entry {pi-rpc, pi-prepared}`;
it is not defaulted, so a client/keys version skew fails closed instead of
launching a prepared host under the rpc grammar. **Upgrade `@byok-sdk/client` and
`@byok-sdk/keys` together.** The `pi-prepared` grammar accepts exactly
`--config <absolute path>` and appends nothing — no `--provider`, `--model` or
`--thinking`, because a prepared host composes nothing.

## Availability caveat: a preparation record log from a pre-release build

A device whose input-preparation record log still holds record schema version 4
cannot start its daemon when the preparation service is configured: replay
refuses the older record before the store is open, which aborts the service open
and therefore daemon start. No PUBLISHED client contains the preparation store,
so only devices that ran this repository's own builds are affected — in practice
the Salesko integration development machines.

The disposition is manual, and it is the operator's:

1. Stop the daemon.
2. Move aside (or delete) the record log at
   `<storeDir>/input-preparation/records.jsonl`, where `<storeDir>` is the
   daemon config's `storeDir` when set, otherwise `~/.byok/<productId>`. The
   retained artifacts sit beside it in `<storeDir>/input-preparation/artifacts/`
   and can be moved with it.
3. Restart the daemon.

Nothing is migrated in either direction: both the replay check and the readiness
check fail closed by design. An operator-invoked isolation/disposal path for a
superseded record log is a deferred goal, not part of this release.

## Declared limits of the prepared lane

The compile boundary admits only user/assistant TEXT history — a history
carrying tool calls or tool results is refused — and a prepared context must end
on a user turn. `strict: "require"` and grammar constrained sampling are refused.
An explicit `compat.thinkingFormat` is admitted only as `zai`. The model keys
`promptCache`, `samplingParams` and `headers` are refused, so a `models.json`
entry carrying a real one fails closed as `prepared_model_drift`. A prepared
launch carries no `prompt_cache_key` and warms no cache, because the forced
option set leaves `sessionId` undefined; that is an accepted cost, not a
correctness claim.

The single `prompt_prepared` response is now written at the byte-gate verdict
rather than at admission, so success means "the first provider request passed
the byte assertion" — verified, not sent. Six session events precede the response
frame. The fork's refusal codes pass through verbatim; `prepared_body_drift` is
new and `prepared_aborted` is gone.

## Host follow-up

A Host composing prepared requests must move with the wire: state
`snapshot.prompt.skills` instead of `formattedSkills`, add
`snapshot.prompt.toolGuidelines`, stop sending `toolChoice: "required"`, and send
request version 4. Until then the daemon refuses such a request fail-closed, with
`bad_request` or an unknown-key refusal; nothing is silently rewritten.

No Host data migration, live profile update, deployment, real credential use or
provider inference is part of this release preparation. Salesko ContextPack,
budgets/Summary and production rollout remain downstream acceptance work. See
the [release handoff](v0.19.0-handoff.md) for the evidence boundary and the
publication sequence.
