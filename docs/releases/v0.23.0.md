## Packages and version decision

The eight aligned packages `@byok-sdk/core`, `@byok-sdk/protocol`,
`@byok-sdk/client`, `@byok-sdk/server`, `@byok-sdk/cloud`,
`@byok-sdk/cloud-dataplane`, `@byok-sdk/ui-runtime` and
`@byok-sdk/implementation-identity` move to 0.23.0; `@byok-sdk/keys` moves to
0.8.0. The published set stays exactly nine packages.

Both are MINOR under the [version policy](../spec.md#pre-10-package-version-policy):
the train adds public API, a new device capability and a new wire message, and
carries #236's pre-1.0 breaking input-preparation v8 cut (below); keys
adds a new security authority (credential custody, sealed provisioning) and
makes a pre-1.0 breaking change to its store port. keys' packed core and
implementation-identity edges must both resolve to 0.23.0; implementation-identity
0.23.0 also gains #236's closed `sdk-helper` subject (`agent-memory`).

## What is new

A Host web page can let a user enter a provider API key that only the target
device can read ([spec](../spec.md#sealed-remote-provider-provisioning),
[protocol §2.3](../protocol.md#23-task-free-sealed-provider-provisioning-notice)).

- **core** — sealed provider secret v1: one-shot HPKE base mode
  `DHKEM(P-256, HKDF-SHA256) / HKDF-SHA256 / AES-128-GCM` on WebCrypto only,
  with the request header bound into the AAD, and
  `providerProvisioningRequestDigest(request)` as the request's digest.
- **protocol** — the task-free `provider.provisioning.available` notice
  (strict `{ requestId }` payload) behind the `provider-provisioning.v1` device
  capability; closed completion, readback, rejection-code and key-check sets.
  The completion's `operationDigest` is the core request digest.
- **client** — the daemon's `providerProvisioning` handler seam. A handler
  failure surfaces as a closed `ProviderProvisioningNoticeError(reason,
  requestId)` with no original message or cause, and the row stays
  unacknowledged. Every read of the handler's returned readback happens inside
  that containment: the value is copied once into inert plain data (accessors,
  Proxies, class instances and symbol keys are refused as `readback_invalid`)
  and only the copy is schema-parsed.
- **cloud** — `enqueueProviderProvisioningNotice(tenant, deviceId, { requestId })`,
  refused for a device without the capability; idempotent per request.
- **keys** — crash-safe credential custody (configuration lock, durable
  pending marker, monotonic operation generation, receipts),
  `applySealedProviderProvisioning`, the readback-only
  `readSealedProvisioningResult`, `replaceSecret`, and the device sealing key
  store.

## Breaking changes

- **`ProviderProfileStore` requires custody methods (keys).** A custom store
  must now implement `acquireConfigurationLock`, `getPending`, `markPending`,
  `getOperationWatermark`, `getReceipt`, `getReservation`, `commitCustody` and
  `recordKeyCheck` in addition to the 0.7.0 profile methods, and
  `ProviderCustodyPending` now carries `requestDigest`. `markPending` for a
  provisioning request also writes a store-wide request-id reservation
  (`requestId`, `requestDigest`, `profileRef`, generation) in the same
  transaction; the request's receipt replaces it on commit. A known id with the
  same digest settles to its stored or interrupted result; a different digest
  is `request_conflict` on any profile, with no write. The bundled SQLite and
  in-memory stores implement all of this; a custom store written against 0.7.0
  no longer type checks.
- **`applySealedProviderProvisioning` takes `readIdentity` (keys).** The
  pre-release `isPlacedHere(): boolean` and static `enrollment` inputs are
  replaced by `readIdentity(agentId)`, which returns
  `{ tenantId, deviceId, enrollmentRevision, placement: { agentId, placementRevision } | null }`.
  It is read before decryption and again inside the configuration lock right
  before any credential-store write; a mismatch rejects with
  `enrollment_mismatch` or `agent_not_placed` and writes nothing. A placement
  or enrollment writer is inside that fence only when it updates its record
  under the exported `withConfigurationLock(profileStore, …)`.
- **Requests carry `expectedEnrollmentRevision` and `expectedPlacementRevision`
  (core).** Both are required in the sealed request header and bound into the
  AAD (opaque `[A-Za-z0-9._:-]{1,128}`). A Host must issue both on every
  request.
- **Receipt-first handler order (keys, protocol).** After tenant/device
  ownership, a durable result for the same `requestId` and request digest is
  returned before the sealing-key, placement or open step; a different digest
  is `request_conflict`. The Host's device fetch must therefore return
  `{ requestId, requestDigest }` even for a terminal request whose ciphertext it
  already deleted.

## Prepared Agent memory and the one-shot input-preparation v8 cut (#236, BREAKING)

Sources: [spec](../spec.md) "Prepared Agent memory (scoped v8 cut)", "Operator
step" and "Operator precondition for the one-shot v8 cut"; protocol.md "Scoped
input-preparation cut"; the
[prepared memory contract](../researches/2026-09-28-prepared-agent-memory-contract.md).

- **Capability, wire and record version.** The prepared-lane capability moves
  from `agent-input-preparation-v7` to `agent-input-preparation-v8`;
  `INPUT_PREPARATION_WIRE_VERSION` and the durable record schema version are both
  8, and the binding and observation digests use domain v2. The outer envelope
  stays v1. There is no v7 reader, no dual token, no mode default and no
  fallback: v7 or missing-field inputs fail strict admission, and the cloud's
  enqueue gates accept only the v8 token.
- **Explicit `agentMemory`.** Local and remote preparation requests, receipt
  bindings and `task.offer_prepared` require
  `agentMemory: 'none' | 'read' | 'read-write'`, with no default. A trusted device
  authority grants a ceiling, and both preparation and execution check it.
  `none` starts no memory helper; `read` exposes recall only; `read-write` also
  exposes save, and both the helper and the daemon reject writes outside the
  grant. `readonly` permits only `read`; `confirm`/`plan` cannot select memory.
  The SDK memory helper's descriptor and identity take part in the existing
  compile/count/digest and admission comparison. Memory file contents are not
  frozen.
- **Known limitation: memory stays fail-closed on Windows.** Agent memory is
  available on Linux (native descriptor-relative operations) and on macOS only
  with the external helper. Windows reports it unavailable until a real
  reparse/junction proof exists. No fallback is selected.

### Operator actions (Host and device operators must do these)

1. **Before upgrading:** drain preparation requests, prepared Executions,
   required message dispositions and old mailbox entries.
2. **Upgrade cloud and devices together.** A skewed pair is refused at enqueue
   (`agent_capability_missing`), and a completion that crosses versions stalls
   that device's whole mailbox.
3. **Recreate preparations** with the Host's own `systemPrompt`, the official
   identity and an explicit `agentMemory` selection.
4. **Devices with leftover v7 records:** the input-preparation lane (not the
   daemon) refuses with `input_preparation_record_log_unsupported`. Nothing is
   migrated automatically. `retire-input-preparation` exists only in the
   0.23.0 CLI; a 0.22.0 `byok-agent` does not have it. Procedure:
   1. stop the daemon (still on the old version);
   2. stage or install the 0.23.0 CLI **without starting the daemon**. How the
      new CLI is staged (side-by-side path, package update with autostart held,
      and so on) is decided by the host product's installer;
   3. with that 0.23.0 CLI, against the device's original config and store, run
      `byok-agent retire-input-preparation`: a read-only preview (record counts
      per version, pinned records, artifact files, unparseable lines);
   4. with the same CLI, run `byok-agent retire-input-preparation --yes`;
   5. complete the coordinated cloud/device switch (step 2 above), then start
      the daemon on 0.23.0.

   `--yes` refuses, typed and with zero writes, while the daemon control socket
   is reachable, the store owner lease is held, any record holds a live pin, or
   any row is unparseable or at the current or an unknown record version. It
   moves the whole `<storeDir>/input-preparation/` namespace unchanged into
   `<storeDir>/input-preparation-retired/<timestamp>-v<versions>/` beside a
   `manifest.json` (per-version counts, sha256 and size of every file). It never
   deletes or converts anything and does not touch Agent home or Agent memory.
   An absent or empty namespace is a no-op.
5. **Skipping the drain and upgrading directly does not repair old entries.**
   They need explicit operator handling.

## Upgrade order for Hosts adopting 0.23.0

1. Fence new prepared work and drain it: preparation requests, prepared
   Executions, required message dispositions and old mailbox entries (v8 step 1).
2. Stop each device daemon while it is still on the old version.
3. Stage or install the 0.23.0 device CLI/SDK (keys 0.8.0) without starting the
   daemon; the host product's installer decides how. If the device holds v7
   records, run the **new** CLI against the original config and store:
   `byok-agent retire-input-preparation` (preview), then `--yes` (v8 step 4).
4. Switch the cloud/Host to 0.23.0 in coordination with the devices, then start
   the device daemons on 0.23.0. Confirm devices advertise
   `agent-input-preparation-v8` and, where the Host injected a handler,
   `provider-provisioning.v1`.
5. Recreate preparations with the Host `systemPrompt`, official identity and an
   explicit `agentMemory` on every preparation and prepared offer.
6. Adopt sealed provisioning (Salesko H1/H3 handoff):
   - Host issues `expectedEnrollmentRevision` and `expectedPlacementRevision`
     on every sealed request.
   - The device fetch returns `{ requestId, requestDigest }` even for terminal
     requests whose ciphertext was deleted.
   - The local-agent placement/enrollment writer updates its record under
     `withConfigurationLock`.
   - A custom `ProviderProfileStore` implements the custody methods, including
     `getReservation`.
   - The device handler implements `readIdentity` and the receipt-first order
     through `readSealedProvisioningResult`, and the Host maps rejection and
     key-check codes 1:1.
7. Only then enqueue `provider.provisioning.available` notices
   (`enqueueProviderProvisioningNotice`), which refuse devices without the
   capability.

## Fixed

- **Windows Credential Manager store bridge.** The keys PowerShell bridge
  imported both `System.Runtime.InteropServices` and
  `System.Runtime.InteropServices.ComTypes` and used an unqualified `FILETIME`,
  so `Add-Type` failed with CS0104 and every operation exited 1: the Windows
  store never compiled in any earlier release. The bridge now compiles; an
  absent credential still reads as `undefined` and deletes as `false`, and any
  other failure stays fail-closed with one bounded, secret-free stderr class.
  A real-backend Windows CI suite now exercises it.
- **Generation fence.** A pending operation consumes its generation in the
  same store transaction, so an older generation is
  `operation_generation_stale` while a newer one is pending; an interrupted
  request is recorded as `local_commit_interrupted` and never redone.
