## keys joins the release train version

The owner's 2026-10-22 decision puts keys on the release train version. From
0.28.2, all nine public packages use one version, so keys moves from 0.13.1 to
0.28.2. This is a version alignment, not a breaking change. The keys changes in
this train are listed below, as for every other package.

The dependency rules do not change. keys depends only on `@byok-sdk/core`, and
no dispatch package depends on keys. The packed keys manifest depends on
exactly `@byok-sdk/core` 0.28.2.

The release gates follow the new rule:

- `check:release-graph` requires every public package, keys included, at the
  train version. It no longer requires keys to differ from the train.
- `check:version-authority` reads one version. Every README mention of a
  public package, keys included, must name it, and the spec states it once.
- `publish.mjs` checks keys with the rest of the train. `pack-and-smoke.mjs`
  packs and installs keys at the train version.
- `registry-readback.mjs` keeps its logic. It reads keys back against the keys
  manifest, which the release graph now holds at the train version.

## Security updates

- **Node 24.22.1 (CI, release, all public packages).** CI and the release job
  use Node 24.22.1. It is the 24.x fix in the Node.js security releases of
  2026-10-21. It fixes four high CVEs: CVE-2026-111497, CVE-2026-105483,
  CVE-2026-106069 and CVE-2026-105482. It also updates the undici copy that
  Node bundles for its global `fetch`. That copy is separate from the undici
  npm package. The nine public packages now declare `engines.node`
  `>=24.22.1`. See the Node floor upgrade note (#702).
- **undici (client).** The client depends on exactly undici 8.12.3. Before, it
  depended on 8.11.2. 8.11.2 is in the range of eight advisories from
  2026-10-15. Four are high: GHSA-qrxm-fqhp-jwvm, GHSA-2m5v-pch6-74hx,
  GHSA-4w7w-5xrc-9h26 and GHSA-xjj6-f33q-929c. Four are medium:
  GHSA-55wc-3pg8-jfw6, GHSA-f72v-6w45-q472, GHSA-4qv8-2p9j-2685 and
  GHSA-9fm3-97px-rjf6. 8.12.2 is the first 8.x release that fixes all of them.
  The cloud-dataplane test dependency moves to the same version. The published
  cloud-dataplane package does not depend on undici (#704).
- **Not fixed by #704.** `@earendil-works/pi-coding-agent` 1.3.0, a client
  dependency, pins its own undici 8.10.2. Its CLI bundle inlines another
  unpatched undici copy. The SDK host does not call Pi's
  `configureHttpDispatcher()`, so its global `fetch` keeps Node's dispatcher.
  Pi's undici loads with Pi, but the SDK host sends no request through it.
  #700 stays open for these copies.

## Upgrade notes for Hosts

- **Node floor.** This is a compatibility change. The nine public packages
  declare `engines.node` `>=24.22.1`. On a Node older than 24.22.1, npm and
  pnpm print an engine warning at install. Yarn 1 fails the install, and so do
  npm and pnpm with `engine-strict` on. Nothing refuses an older Node at run
  time. The reason is the Node security release of 2026-10-21 (#702).
- **keys version range.** keys 0.28.2 follows keys 0.13.1. A range such as
  `^0.13.1` does not match 0.28.2. Change the keys range to the release
  version.
- **Stateless MCP HTTP.** A `tools/call` with `_meta.progressToken` now gets
  HTTP 400. 0.28.1 had no progress support and did not reject the token. Send
  no progress token in stateless mode, or use stateful mode (#631).
- **Codex deadlines.** One 30 s budget now covers the open: initialize,
  `thread/start` and the read-back. A prompt or steer timeout now ends the
  session and kills the app-server. Before, it rejected only that control.
  `CodexAdapterOptions.operationTimeoutMs` sets the budget (#652).
- **Relocated memory-helper assets.** The SDK checks a relocated helper
  directory against the release identity compiled into the running SDK. Copy
  the assets from the same SDK build that bundles the Host (#603).
- **Agent memory off switch.** With `DaemonConfig.agentMemoryMcp: 'off'`, an
  Agent task instruction gets no memory guidance. A `memory-reader` instruction
  keeps only the final-reply line. A `memory-reader` Attempt now gets a `read`
  memory MCP that lists only `memory_recall` (#614).
- **Platform support.** Grok and Hermes detection refuses a platform other than
  macOS and Linux with `platform_unsupported`. The daemon declines an explicit
  offer for such a runtime with `retryable: true` (#635).
- **Message publish retries.** A retry that arrives after the cloud committed
  the message now settles as `duplicate`, not `accepted`. It adds 1 to the
  client `outbound.duplicate` counter and to the server `dedupDrops` counter.
  Before, it added 1 to `accepted`. `observer.onInboundCommitted` now fires
  once for each message (#693).
- **Wire.** `task.progress` `events[].mcp` is a registered strip-safe wire
  addition. A receiver without the field, such as the published 0.27.0 floor
  decoder, strips it (#633).
