# Pi 1.4.0 and OAR 0.71.0 upgrade

The owner asked on 2026-10-24 to raise the Pi dependencies to 1.4.0 and OAR to
0.71.0 in one PR, and to check first whether any API changed. OAR v0.71.0
(commit `c88a514458b3d80f18d32f29863f2b8fea5b1c96`) moves its own Pi
dependencies to 1.4.0 and its `pi-durable` and `chord` peers to `~1.4.0`.

## P1: Boundary

Pi is nine npm packages pinned exactly in the root, client and cloud-do
manifests; the client and cloud-do import pi-coding-agent, pi-ai,
pi-agent-core, pi-durable, pi-tui and chord, including subpaths. OAR is
SDK-owned source under `packages/client/vendor/oar/<sha>/`, consumed through
the Codex, ACP and process-tree bridges. The keys package carries a table
generated from the pinned pi-ai catalog.

## OAR

All 82 selected paths (81 source files and LICENSE) were hashed at v0.71.0
against the manifest's `upstreamSha256`. None changed. The only upstream
source change is `runtimes/pi-durable/index.ts`, outside the fork:
`PiDurableRuntimeOptions.models` also accepts a supplier. OAR's lockfile keeps
`@agentclientprotocol/sdk` at 1.4.0, the SDK's exact pin.

The fork moves from `44d7d61` to `c88a514`. The nine maintained files keep
their deltas; the eight whose change notice names the base now name c88a514,
and only their `vendoredSha256` changes. Bridges, tests, scripts, docs and the
CI reviewed-scope regex move to the new directory.

## Pi pins

All nine official packages move from 1.3.0 to exactly 1.4.0 (upstream commit
`4a080252f06caf63a525d7873c5d94d3c23887e0`, from the SLSA provenance; npm
omits `gitHead`). `piRuntimePin` is 1.4.0.

- `bun.lock` resolves one instance of each package, all 1.4.0. One new
  transitive package enters: `marked-cjk-friendly` 0.1.2 (pi-coding-agent).
- `collect-official-pi-closure.mjs` verified the registry signature, Sigstore
  provenance and tarball integrity of all nine. The new closureDigest is
  `79c414be071768df15f0a107595564b11c67d904c601e7b2ccf1495fc3053fcc`.
- The provider env list from pi-ai 1.4.0 is unchanged; only the generated
  header names the new version. The todo build input keeps its bytes.
- The pinned catalog table changes in data only: models added, removed and
  retuned. The generator's existing refusal rules cover every entry; the new
  `stepfun-ai/step-5-preview` row refuses `headers`. `PiModelConfig` gains no
  field. `api-surface/keys.d.ts` changes only `PI_MODEL_CATALOG_PI_AI_VERSION`.

## API review

The `.d.ts` files of all nine packages were compared between 1.3.0 and 1.4.0,
then the changed JS where the SDK depends on behavior. Every subpath the SDK
imports still exists in the 1.4.0 exports maps, and `bun run typecheck`
passes with no source change.

### Export HTML needs a sixth asset (adapted)

Pi 1.4.0 fixes CJK emphasis in HTML export. `export-html/index.js` now reads
`vendor/marked-cjk-friendly.min.js` and fills `{{MARKED_CJK_FRIENDLY_JS}}` in
`template.html`; a missing file throws. `pi-export-asset-layout.json` and
`pi-export-assets.source.json` add it, so `copyPiRuntimeAssets` copies six
files. `template.html`, `template.js` and `marked.min.js` also change bytes.
The assets come from the installed pin, as before, so no SDK notice is added.

### pi-durable SQLite types move to chord

`SqliteDatabase`, `SqliteExecutor` and `SqliteValue` are now re-exported from
`@earendil-works/chord/sqlite`. The shapes are unchanged, including the async
`transaction` callback that cloud-do relies on.

### Request identity

pi-ai 1.4.0 adds `ClientIdentity`. Every request sends
`User-Agent: pi/<version> (<platform>; <runtime>/<version>; <arch>)`; 1.3.0
already sent `pi (<os> <release>; <arch>)`. Provider attribution
(`HTTP-Referer`, `X-OpenRouter-Title`, `X-OpenRouter-Categories` for
OpenRouter, `X-BILLING-INVOKE-ORIGIN` for NVIDIA, `x-opencode-client` for
OpenCode) moves from the coding agent into pi-ai. In coding-agent sessions it
is still gated by install telemetry, as in 1.3.0, so the prepared lane sees
the same attribution headers as on 1.3.0; its header allowlist checks names
and already admits `user-agent`. pi-agent-core agent loops
(`DEFAULT_AGENT_IDENTITY`) and the pi-durable Harness
(`DEFAULT_HARNESS_IDENTITY`) now attribute to pi without that gate: decision
D3 below turns it off on the client durable lane.

### Compile closure gains pi-telemetry (reviewed)

pi-ai's request span schema imports `@earendil-works/pi-telemetry`, so the
A1' compile closure now reaches it, plus `telemetry.js`, `utils/identity.js`
and `utils/version.js`; `utils/pi-user-agent.js` is gone. The compile passes no
telemetry context, so pi-ai uses `NOOP_TELEMETRY_CONTEXT`. pi-telemetry has
no exporter and no network access. `pi-compile-purity.test.ts` passes
unchanged, and the indirect-version test still shows that preparation reads
no indirect manifest. The two pi-runtime-host entry facts list pi-telemetry
and marked-cjk-friendly as bundled packages, and the cloud-do entry lists
pi-telemetry; no budget moves.

### Agent loop emitter

`pi-agent-core/dist/agent-loop.js` changes only by merging the request
identity into stream options. Event emission and tool pairing are unchanged,
so the Octop T0 evidence still holds; its binding test now pins the 1.4.0
bytes and closure.

### Resumed tools

Pi 1.4.0 (#11062) activates a load-time extension tool that a resumed
transcript did not declare. It still keeps the transcript's pending tool names,
so a tool that registers during `session_start` with `defaultActive: false`
is still active without the SDK reset. `resetResumedPiTools` stays.

### Breaking changes the SDK does not use

- pi-ai: `StreamOptions.telemetryContext` becomes `telemetry`;
  `resolveTranscriptTools` takes a mode instead of a boolean;
  `TranscriptTools.anchorsAdditions` becomes `foldedSystemMessages`;
  `utils/pi-user-agent.js` is removed.
- pi-durable: `TaskRuntime.sleep()` is removed (`sleepUntil()` and `setTimer()`
  are added); tasks gain a `sleeping` status; `defineDoc()` and
  `defineDocFamily()` require `checkpointWhen`; `ToolControl.terminate` is a
  `boolean`; `ToolExecutionApi` gains `now()`. The SDK builds none of these
  objects and has no exhaustive status switch. Both Harness lanes disable
  retry, so the new durable retry sleeps do not occur.
- chord: `Context` requires `telemetry`. The only hand-built context,
  `{ abortSignal } as Context` in `fix-pi-durable-shell-exit.test.ts`, still
  compiles through the cast, and the code it reaches never reads `telemetry`.
- pi-coding-agent: `generateSummary()` ignores `reserveTokens` (unused); the
  `grep` tool runs `rg --no-config`; the NVIDIA, Copilot and Xiaomi default
  models change (SDK lanes always pass provider and model).

## Decisions

These pi-durable 1.4.0 changes have more than one reasonable answer. The
owner ruled on 2026-10-24: D2 「接受迁移」, D3 「关掉 attribution」, D4
「设为 Infinity」.

- **D2: one-way SQLite schema v2.** Opening a SQLite store migrates it to
  schema version 2 and rebuilds the task table; 1.3.0 cannot open it, so a
  deployment cannot roll back past 1.4.0. This applies to the client durable
  store (`openNodeSqliteStorage`) and to cloud-do. The 1.3.0 ruling said 1.3.0
  opens a 1.2.0 database without migration; that no longer holds. The cloud-do
  storage contract (59 tests on workerd, including the new sleeping-task scan
  and the prefixed `tasks_v2` rename) passes. Options: accept the one-way
  migration with a release note, or hold pi-durable at 1.3.0 (which conflicts
  with OAR 0.71.0's `~1.4.0` peer). Ruled: accept the one-way migration.
- **D3: Harness attribution.** The client durable lane (`engine.ts`, real pi-ai
  streams) will send `HTTP-Referer: https://pi.dev`, `X-OpenRouter-Title`,
  `X-OpenRouter-Categories`, `X-BILLING-INVOKE-ORIGIN` or `x-opencode-client`
  to OpenRouter, NVIDIA and OpenCode endpoints. cloud-do is not affected:
  `provider-fetch.ts` rebuilds the request with a fixed header set. Options:
  accept upstream, or pass `identity: { attribution: null }` to `Harness.open`.
  Ruled: attribution off. `engine.ts` passes `DURABLE_HARNESS_IDENTITY`
  (`{ attribution: null }`); `pi-durable-engine.test.ts` runs the engine
  through pi-ai's real `openai-completions` serializer against an OpenRouter
  model and checks that no attribution header is sent.
- **D4: crash-loop guard.** `restartLimit` defaults to 5. A task that a crash,
  eviction or reset cuts off 5 times in a row without committing is parked:
  blocked `restart_limit`, not active in `wake()`, reported as `task_parked`,
  and it runs again only after `Harness.retryTask`. Neither
  `CLOUD_HARNESS_SETTINGS` nor the client engine settings set it, and Durable
  Object evictions count. By reading the engine, a parked `pi.generation`
  task passes its inspection but never runs. Options: set `restartLimit: Infinity` in both
  settings (old behavior), or adopt the guard and map `task_parked` from
  `onReport` to a visible failure. Ruled: `restartLimit: Infinity` in
  `CLOUD_HARNESS_SETTINGS` and the client `DURABLE_HARNESS_SETTINGS`, the 1.3.0
  behavior. `harness-settings.test.ts` (cloud-do) and
  `pi-durable-engine.test.ts` pin the setting.

The compile-closure classification is also a choice, but not blocking:
pi-telemetry is recorded as a third-party edge, like `openai`. Listing it in
`OFFICIAL_COMPILE_PACKAGES` would walk and pin its files too.
