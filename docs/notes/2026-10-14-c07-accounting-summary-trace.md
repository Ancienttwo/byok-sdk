## 计划审查与 P1 / P2 / P3

**P1 — 权威。** [spec 的 bounded admission](../spec.md#prepared-operations) 是现行 product truth：SDK 记录实际冻结 D 的 UTF-8 `requestBytes`，验证 Host ruling 的适用性并在真实首个发送前比较 D；Host 决定 `requestBytes + C + max_tokens <= window`、Main/Summary 各自预算及 CAS。Counter 可选，只能收紧；没有 counter 仍可 ready，不新增 counter 门槛、token estimate 或默认 C。`ready` 只回答 preparation 能否被消费，不回答是否装得下窗口。

当前记录身份由 `official-pi-installation.mjs` 对 checked-in provenance 求值得到：Pi `1.2.0`、closureDigest `99b01e3c2e80412e1a09afcd5289d1ed0297bfbfed37ef59dadf30783baab0d1`、compiler `4`、envelope `4`。Preparation wire `9`、record `10` 与整体协议 `PROTOCOL_VERSION=2` 是三个不同版本；不能把计划中的未来 wire v3 当成已经交付。旧 0.87.1 的 C 标定不能为此身份背书。

**P2 — 路径。** Host 冻结 source/prompt/model/tool/policy → preparation service 先授权并 durable reserve → SDK compiler 通过 injected fetch 捕获实际 D（不发模型请求）→ 保留 artifact、判断 ruling/text-only/optional-counter 并产生 receipt → Host 独立预算/CAS → prepared offer admission 对同一 record 比较设备、Agent、profile、policy、request、runtime、memory、tool/observation digests → pin/claim/start → artifact verifier 与实际 send gate 拒绝漂移。网络/计数不持有 Host 行锁的证明仍属于 Host；SDK 的幂等记录不证明 Host CAS。

**P3 — 决定。** 保留这一个 D/record/readiness authority，不重新计数、添加 serializer、兼容 reader、feature flag 或生产 Conversation store。采用计划推荐的 S1 → K7 → S2 → S3 顺序：当前 `recurring.submit` 仍存在，TaskRunner 仍调用 `resultDocument.extract`，prepared Summary 仍是零工具，所以不提前写将在 `submit_result` / v3 切换时整段重做的 S2 fixture。10× 历史规模首先压力落在 Host ContextPack/Summary 调度与输入大小，不以这张表冒充性能或生产启用证明。

> 2026-10-15 更新：上面的顺序后来有变。#474 已用 `executions.submit` 取代 `recurring.submit`；S2 的 synthetic Host fixture 在 K7 之前先合入（#466），并补了已接受回复后被 Host cancel 的一轮。K7 落地后该 fixture 仍要迁到 `submit_result`。
