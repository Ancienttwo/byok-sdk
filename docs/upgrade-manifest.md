# Upgrade manifest

For the device operator workflow, see [Device setup: upgrade](device-setup.md#upgrade).

`@byok-sdk/client` ships `upgrade-manifest.json`: a machine-readable list of
every Host-visible change between the previous release and this one (#1102).
A Host reads it before upgrading to learn which changes need code, config or
store work, without diffing type declarations or reading every release note.

```js
import { readFile } from 'node:fs/promises';
import { createRequire } from 'node:module';
const require = createRequire(import.meta.url);
const file = require.resolve('@byok-sdk/client/package.json').replace(/package\.json$/, 'upgrade-manifest.json');
const manifest = JSON.parse(await readFile(file, 'utf8'));
```

The file is not a package export, so resolve it next to `package.json`.

## Format

```jsonc
{
  "schemaVersion": 1,
  "package": "@byok-sdk/client",
  "from": { "version": "0.30.2", "snapshotSha256": "…" },   // the previous release
  "to": { "version": "0.31.0", "snapshotSha256": "…" },     // this tree
  "configFields": { "status": "tracked", "source": "packages/client/daemon-config.schema.json", "owner": "#1094" },
  "entries": [                                               // authored
    {
      "id": "server-sqlite-v6",
      "impact": "breaking",                                  // additive | breaking
      "acceptance": "new-path-repair",                       // stores only
      "summary": "What changed and what the Host does.",
      "migration": "docs/spec.md#embedded-sqlite-device-and-receipt-authority",
      "items": ["store:server-sqlite"]
    }
  ],
  "changes": [                                               // generated
    { "item": "store:server-sqlite", "change": "changed",
      "before": "schema_version=5", "after": "schema_version=6", "entry": "server-sqlite-v6" }
  ]
}
```

- `entries` are written by the author of a change. Each groups one or more
  items under one impact, a summary that is the migration note, and a
  `migration` link: a repo-relative `.md` path with a heading anchor, or a
  byok-sdk issue or PR URL.
- `acceptance` is required on an entry that changes a store. It says what the
  new release does with a file the previous release wrote: `accept`,
  `new-path-repair` (start on a new path and pair or enroll again) or
  `reject` (refused at open, left unchanged; the operator resolves it).
- `from`, `to`, `configFields` and `changes` are generated. `changes` lists
  every changed item with the entry that covers it. Store, bin, example,
  config and interprocess items carry their `before` and `after` values;
  export digests and union markers do not, because they mean nothing to a
  reader.

## Items

The snapshot is computed only from checked-in files of one tree, with no
build, so two checkouts of the same commit give the same snapshot. It is
generated by `scripts/release/upgrade-manifest/snapshot.mjs`.

| Item id | Source |
| --- | --- |
| `entry:<specifier>` | `api-surface/entries.json`, kind `exports` |
| `export:<specifier>#<name>` | Exported names of each entry, resolved through the `api-surface/<pkg>.d.ts` golden. The value is a digest of the declaration (comments and whitespace removed) and of every non-public declaration it reaches. A public declaration it references is its own item, so one change is reported once. |
| `bin:<name>` | `bin` of the nine public `package.json` files |
| `union:wire#<type>` | Keys of `MESSAGE_PAYLOAD_SCHEMAS` (protocol golden) |
| `union:agent-event#<type>` | `type` literals of `AgentEventSchema` (protocol golden) |
| `union:session-event#<member>` | `Session.events` members besides `AgentEvent` (client golden) |
| `union:daemon-event#<kind>` | `kind` literals of `DaemonEvent` (client golden) |
| `union:timeline-item#<kind>` | `kind` of each `TimelineItem` member (ui-runtime golden) |
| `store:server-sqlite` | `SQLITE_SCHEMA_VERSION` in `packages/server/src/stores/sqlite/index.ts` |
| `store:client-journal` | Digest of the journal `SCHEMA` DDL in `packages/client/src/daemon/journal/sqlite-journal.ts` |
| `store:keys-profile-store` | Digest of the profile store `SCHEMA` and `ENABLED_INDEX`, with interpolated enum arrays resolved from `packages/keys/src` |
| `store:cloud-dataplane-postgres` | Count, last name and digest of `deploy/sql/NNNN_*.sql` |
| `store:pi-durable` | The pinned `@earendil-works/pi-durable` version in the client manifest |
| `example:host-execution-core` (K4), `example:bot-collaboration` (K8) | Package version and a digest of `src/` without tests. Both stay at 0.0.1, so a Host that vendors one compares the digest. |
| `interprocess:<id>` | An exported integer protocol version (`interprocess:path-mutation-gate`: `PATH_MUTATION_GATE_PROTOCOL` in `packages/client/src/util/path-mutation-gate.ts`, #1149). SDK processes whose versions differ do not exclude each other, so a change is breaking. |
| `config:<field>` | Each top-level field of the generated `packages/client/daemon-config.schema.json` (#1094). The value is the tier (`required`/`optional`, plus `embedded-only` or `distribution-owned`) and a digest of the field schema without its documentation. |

Each extractor fails when the source shape it reads is gone, so moving an
authority breaks the gate rather than emptying a category.

## Gate

`bun run check:upgrade-manifest` runs in CI on every PR and in release
validation. It fails when:

- an item changed since the baseline and no entry lists it;
- an entry lists an item that did not change, or one another entry lists;
- a removed item is in an additive entry;
- a changed store has no `acceptance`, or its acceptance is not `accept` and
  the entry is additive;
- an entry has no summary, or its migration file or heading does not exist;
- the tree version is a PATCH after the baseline and any entry is breaking
  (Q8). Before 1.0 a breaking entry needs a MINOR, from 1.0 a MAJOR. While the
  tree version still equals the baseline, the gate prints the bump the next
  release needs;
- the generated fields differ from what the tree produces.

## Workflow

1. Change the code, regenerate the api-surface goldens, then run
   `node scripts/release/check-upgrade-manifest.mjs --write`. It rewrites the
   generated fields and lists each changed item that has no entry.
2. Add or extend an entry for those items, with a Host-facing summary and a
   migration link, and run `--write` again until it passes.

`--snapshot` prints the snapshot of the tree.

## Release steps

1. Release preparation bumps the version. The gate then checks the bump
   against the entries: a breaking entry needs a MINOR.
2. Point every entry at its final migration notes, for example the release
   record instead of `CHANGELOG.md#unreleased`.
3. After the release is tagged and published, make the release the new
   baseline from a checkout of its tag:
   `node scripts/release/check-upgrade-manifest.mjs --rebaseline <tag checkout>`.
   It writes `scripts/release/upgrade-manifest/baseline.json` and starts an
   empty manifest from that version. It refuses a version that is not newer
   than the current baseline.

## Store compatibility precheck

The manifest states what a release does with a store an older release wrote.
The precheck applies that to the stores actually on a machine: run the
*candidate* build against the current stores before switching to it (#1097
does this before a switch). Each store is checked by the package that owns it,
which copies the files to a private temporary directory and runs its own open
on the copy. The store code therefore stays the only authority on what it
accepts, and the originals are only read, never opened, locked or changed.

| Store | Inspector |
| --- | --- |
| `client-journal`, `pi-durable` | `inspectDaemonStores({ storeDir })` in `@byok-sdk/client`; also `byok-agent upgrade check --store [--json] [--config <path>]` |
| `server-sqlite` | `inspectSqliteStore(path)` in `@byok-sdk/server` |
| `keys-profile-store` | `inspectProviderProfileStore(path)` in `@byok-sdk/keys` |

`@byok-sdk/client` cannot depend on `@byok-sdk/keys` (`check:release-graph`)
or on `@byok-sdk/server` (device/SaaS boundary), so a Host that has those
stores calls their inspectors itself. Every inspector returns the
`StoreCompatibility` type from `@byok-sdk/core`, with one `verdict`:

- `accepted`: the build opens the store and keeps its data. pi-durable
  migrates an older replica forward on open; the old build cannot read it
  afterwards.
- `new-path-repair`: refused as an older format (server `schema_version`,
  keys `PROVIDER_STORE_SCHEMA_STALE`). Start on a new path and pair or
  provision again.
- `rejected`: refused for another reason, such as a newer format, a damaged
  file, or a journal from before `withheld_bytes`. `code` and `reason` carry
  what the store reported, and the operator resolves it.
- `absent`: no store at the path.

The CLI exits 0 when every store is `accepted` or `absent`, and 2 otherwise.
Stop the owner of a store before checking it: a file that changes while it is
copied makes the check fail with an error instead of a verdict.

`scripts/release/fixtures/stores/` holds the stores each recent release writes
on first open. `generate.mjs` installs the release from npm, or uses this
workspace for `main`, and writes them. `index.json` lists the fixtures with
the verdict this tree gives each store (`expected`). The server, keys and
client tests check every fixture against `expected`. They also check that a
store written by the baseline release gets either `accepted` or the
`acceptance` of the manifest entry for that store. After a rebaseline, the
new baseline release therefore needs a fixture:
`node scripts/release/fixtures/stores/generate.mjs --release <version>`.
When a store format changes on `main`, regenerate the `main` fixture with
`--main` and update `expected`.

## Not covered yet

- CLI subcommands and flags, and the SDK reserved helper kinds (#1104), are
  not items yet.
- The manifest is not a package export, so it is not in the api-surface
  goldens.
