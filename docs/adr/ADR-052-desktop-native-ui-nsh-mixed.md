# ADR-052：本地桌面端原生 UI 采用 NSH Mixed + `byok-shell` 底座（Proposed）

> **来源与追踪**：总 issue [#2457](https://github.com/Ancienttwo/byok-sdk/issues/2457)（子 issue [#2458](https://github.com/Ancienttwo/byok-sdk/issues/2458)、[#2459](https://github.com/Ancienttwo/byok-sdk/issues/2459)、[#2460](https://github.com/Ancienttwo/byok-sdk/issues/2460)、[#2461](https://github.com/Ancienttwo/byok-sdk/issues/2461)、[#2462](https://github.com/Ancienttwo/byok-sdk/issues/2462)、[#2479](https://github.com/Ancienttwo/byok-sdk/issues/2479)），承接 [#1499](https://github.com/Ancienttwo/byok-sdk/issues/1499)。
> **依据文档**：[可行性调研与 Council 记录](../researches/2026-11-23-desktop-native-ui-nsh-feasibility.md)、[NSH Mixed PoC 实测证据](../researches/2026-11-24-nsh-mixed-poc-evidence.md)。
> **状态说明**：`proposed`。Owner 已否定 Electron（体积过大）与 Tauri（不走 WebView 路线），并于 2026-11-24（[D2 书面签核评论](https://github.com/Ancienttwo/byok-sdk/issues/2457#issuecomment-7129367051)）单独书面确认了 D2 的架构取舍；2026-11-25 经 NSH 指南与 `2964346` 实测修订后，Owner 已再次书面重签 D2 `capabilities`/更新条款并选定凭据**方案 A**（[PR #2472 书面签核评论](https://github.com/Ancienttwo/byok-sdk/pull/2472#issuecomment-7139209349)、[#2457 决议归档](https://github.com/Ancienttwo/byok-sdk/issues/2457#issuecomment-7139214218)）。现阶段 PoC 与 `2964346` 跨平台冒烟已实证：macOS 单机 Gate P1（30/30 hardened fixture）、`2964346` macOS `arm64` Mixed 桥接与 `app.compose`、Windows `2964346` 预编译运行时 150% DPI 多行 CJK 与 `WM_CLOSE` A/B、Linux `arm64` Docker GTK4 预编译运行时启动；D5 原生更新交棒契约已由 [#2479](https://github.com/Ancienttwo/byok-sdk/issues/2479) 落盘（更新清单签名私钥归属与保管仍标注 `owner decision pending`），真实 SEA Host + 真实 custody 三端联调、Windows Mixed MSVC 编包、Linux Mixed 编译运行及三端更新/打包验证仍待 [#2461](https://github.com/Ancienttwo/byok-sdk/issues/2461)–[#2462](https://github.com/Ancienttwo/byok-sdk/issues/2462) 闭环。本 ADR 晋升为 `accepted` 须待按生产 rev 重打的 [`#2458`](https://github.com/Ancienttwo/byok-sdk/issues/2458)（实体中文 Windows 11 150% DPI 物理微软拼音候选窗验签，允许采用与生产 rev 同源的 Windows 运行时产物，Windows Mixed MSVC 编译另归 Windows Mixed CI 门禁）通过（与已重签的 D2 并列为晋升双前提）。若 `#2458` 暴露阻塞性且无法规避的 IME 错位缺陷，或并行 Linux/Windows Mixed release 冒烟构包失败，按 D1 触发切换至 `longbridge/gpui-kit` 评审。**独立后续发布门禁**：D2 所要求的 release 打包产物隔离验收（证明 `nsh.json` 的 `capabilities` 等于 D2 预期集合、打包后的 `capabilities.json` 符合 golden 文件与关键字段断言、`Policy::harden` 生效、`byok-shell` native bridge 拒绝未在 `bridge-contract.json` 声明的方法，且各平台 quit 路径按 D2 验收）**不随 `#2458` 绿灯关闭**，而作为独立门禁阻塞 [#2461](https://github.com/Ancienttwo/byok-sdk/issues/2461) / [#2462](https://github.com/Ancienttwo/byok-sdk/issues/2462)（Gate P4 切流与发布）。
> **2026-11-25 修订与签核状态**：D2 的 `capabilities`/更新条款及「凭据在 UI 中的生命周期（**方案 A**）」均已获 Owner 书面签核（[PR #2472 签核](https://github.com/Ancienttwo/byok-sdk/pull/2472#issuecomment-7139209349)），并已同步 `2964346` 源码与实机证据（[#2457 实测评论](https://github.com/Ancienttwo/byok-sdk/issues/2457#issuecomment-7139014589)）；ADR 整体仍待 `#2458` 实体真机验签后从 `proposed` 晋升为 `accepted`。

## 1. 背景

[`examples/desktop-bot-app`](../../examples/desktop-bot-app/README.md) 现行实现基于 Electron 45 + React 19 + Node SEA Host（[`origin/main@b0930ea36`](https://github.com/Ancienttwo/byok-sdk/tree/b0930ea36)）。根据 A7 基线实测，其 Unpacked 整包达 `432.6–502.9 MiB`（其中 Electron + Renderer 占 60%–71%）。在 Owner 明确排除 Electron 与任何 WebView 方案（含 Tauri）的约束下，技术选型必须在非 WebView 原生桌面方案中兼顾体积收敛、保留原 Electron 四进程模型中的 Host 与 Custody 进程隔离不变量（同时明文界定 QuickJS UI 改为与 Shell 同进程后的权限取舍，见 D2），以及对 [`@byok-sdk/keys/model-route`](../../packages/keys/src/model-route.ts) 与 Bridge 契约的单一权威复用。

经 2026-11-24 隔离 PoC 实测：
- 纯壳体积显著收敛：macOS NSH Mixed release `.app` 为 `53M`（`54,528 KiB`），Windows 为 `24.91–25.83 MiB` zip（解包 `64.85 MiB`）；
- 硬化的 QuickJS release VM（`Policy::harden` + 空 capabilities `{}`）以 30/30 通过 `@byok-sdk/keys/model-route` + `zod@4.6.7` 全量 fixture 向量，但也暴露出 `hasStructuredClone === false` 以及 Windows `<Input>` 默认 `"Segoe UI"` 在英文 Win11 下将输入中文渲染为 `□□□□` 等平台约束；
- 同时因上游 `longbridge/nsh` 迭代较快（且其 `docs/dev/compatibility.md` 仅约束 JS 运行时与组件导出而不覆盖 Rust `#[native_module]` 嵌入 API），本架构精确钉死 NSH 生产 rev（权威是仓库 pin 脚本中的 `nsh` CLI，`Cargo.lock` 只记录解析结果，见 D1「NSH 生产 rev」），并显式隔离 UI 框架与宿主进程监督底座，保留向 `gpui-kit` 迁移时的 `byok-shell` 底座复用接缝。

## 2. 决定

### D1. 技术路线与 UI 无关底座（保留 `gpui-kit` 回退接缝）

- 私有桌面前端（仅限 `examples/desktop-bot-app`，不进入 `packages/*`）目标采用 **`longbridge/nsh` Mixed 模式（Rust 宿主 + QuickJS TSX UI）**。
- 所有进程生命周期、协议读写、防休眠、恢复命令行调度与秘钥管道均抽离进 **UI 框架无关的独立 Rust crate `byok-shell`**（[#2460](https://github.com/Ancienttwo/byok-sdk/issues/2460)），严禁在 `byok-shell` 中依赖任何 `nsh-*` 或 UI crate。
- **NSH 生产 rev（单一权威）**：mixed 模式下 `nsh-*` crates 跟随正在运行的 `nsh` CLI 版本，版本不同的 app 会被 retarget 到该 CLI（上游 nsh skill 的 tooling 参考，main `552dfae`），单靠 `Cargo.lock` 钉不住 NSH。生产 rev 由仓库内的 [`scripts/nsh-pin.json`](../../examples/desktop-bot-app/scripts/nsh-pin.json) 与 [`scripts/nsh.mjs`](../../examples/desktop-bot-app/scripts/nsh.mjs) 固定 CLI 的版本、40 位 commit 与分平台 SHA-256（沿用 [PoC 证据 §1](../researches/2026-11-24-nsh-mixed-poc-evidence.md) 的校验方式），开发与 CI 只经 `scripts/nsh.mjs` 调用 `nsh` 并断言 `nsh --version`。在 nightly rev 下，接入层 [`ext/byok-nsh-adapter/Cargo.toml`](../../examples/desktop-bot-app/nsh-app/ext/byok-nsh-adapter/Cargo.toml) 对 `nsh-*`（`[dependencies]` 与 `[dev-dependencies]` 中的 `nsh-core`，以及后续 D5 引入的 `nsh-updater`）**直接写 `git = "https://github.com/longbridge/nsh", rev = "<40-char commit>"`**（与 `scripts/nsh-pin.json` 的 `commit` 完全一致），确保 CI 在独立 `[workspace]` 的 adapter crate 内执行 `cargo test --locked` 时也始终解析到同一 nightly git rev，而不是落回 crates.io；正式发版 tag（`channel === "stable"`）则写精确版本 `=x.y.z`。单一来源校验由 `node examples/desktop-bot-app/scripts/nsh.mjs verify-lock`（生成 `.nsh/rust/Cargo.toml` 后附带 `--all`）执行：调用 `cargo metadata --format-version 1 --locked`，逐一校验全部 `nsh`/`nsh-*` 依赖与 `scripts/nsh-pin.json` 一致，**拒绝 `path+`/缺失来源及多来源分裂**（不再使用 `--nsh-source`）。每次升级 NSH pin 必须在同一 PR 内同步更新 `scripts/nsh-pin.json`、`Cargo.toml` 与 `Cargo.lock`。
- **生产 rev 与 gate 产物同源**：2026-11-24 Owner 决议要求 [#2458](https://github.com/Ancienttwo/byok-sdk/issues/2458) 用含上游 [longbridge/nsh#2978](https://github.com/longbridge/nsh/pull/2978)、[longbridge/nsh#2992](https://github.com/longbridge/nsh/pull/2992) 的新 rev 重打验签包。这两个修复与 [longbridge/nsh#2829](https://github.com/longbridge/nsh/pull/2829)（`ext/` 布局）、[longbridge/nsh#3024](https://github.com/longbridge/nsh/pull/3024)（Windows 组字过程中经 `onCompositionChange` 回报 `text`）均不在 v0.6.1，也不在早期 `f577c51`；截至 2026-11-25，上游最新正式版仍是 v0.6.1。目标候选生产 rev 为 nightly `2964346c285f57004f2531fb768cc9840b8d7ff5`（已验证严格领先 `#2338`/`#2497`/`#2701`/`#2760`/`#2829`/`#2978`/`#2992`/`#3024`）或包含上述全部修复的首个正式版。按 2026-11-25 Owner 决定，[#2458](https://github.com/Ancienttwo/byok-sdk/issues/2458) 已于同源 rev `2964346c285f57004f2531fb768cc9840b8d7ff5` 重打 Windows 运行时验签包（`_ops/nsh-poc/ByokP3Win-2964346.zip`，`27,241,613` B，SHA-256 `b4fd69fe33a81c375757b8345bd5cc26f95f2e2504557801475f7359f23db8f1`，`prebuilt-ts` 因受控节点 `win-ci` 无 `rustc`/MSVC），macOS Mixed 桥接、Windows Mixed MSVC 编译、P1 fixture 重放与 release 隔离验收均以同一生产 rev 校验。旧版 `f577c51` 的 `ByokP3Win.zip` 已移至 `#2458` 底部归档，不再作为验签依据。
- **接入层 crate 与布局**：`nsh-*` 依赖只出现在独立的接入层 crate，它依赖 `byok-shell` 并持有唯一的 `#[native_module]`；`byok-shell` 仍禁止依赖 `nsh-*`。生产 rev 不含 `ext/` 布局（[longbridge/nsh#2829](https://github.com/longbridge/nsh/pull/2829)，不在 v0.6.1）时，以 `nsh.json` 的 `"rust"` 列出该 crate，含 `ext/` 之后迁到 `ext/<name>` 加 `"dependencies"`。NSH app 放在独立目录，不与 Electron renderer 共用 TypeScript 根，避免 `nsh check` 的 tsc 扫到 React 代码。
- **回退触发与切换路径**：若以下任一触发条件成立，保留 `byok-shell` 底座并将 UI 接入层评估/切换为 `longbridge/gpui-kit`（UI TSX 需重写，且需在 `BRIDGE_VERSION` 内补暴露无 secret 的 Host route view 方法）：(1) 包含上游修复重打后的 [#2458](https://github.com/Ancienttwo/byok-sdk/issues/2458) 实体中文 IME 验签失败且上游无解；(2) Linux x64 / Windows x64 并行 NSH Mixed release 冒烟编包或出窗失败且无合理成本修复方案；(3) [#2462](https://github.com/Ancienttwo/byok-sdk/issues/2462) 三端打包、签名或 NSH 生产 rev 升级出现不可调和阻塞。（若 D2 被整体否定，则非 WebView 同进程原生路线整体重议，不仅 NSH。）

### D2. OS 进程隔离边界、进程内 VM 权限取舍与 Rust 监督权威

- **保留的 OS 进程隔离（三进程形态）**：`Shell ↔ Host`（`BRIDGE_VERSION = 2` NDJSON stdio 子进程）与 `Shell ↔ Custody`（一次性 stdin 短生命周期子进程，secret 绝不进入 Host 内存或主管道）依然保持独立 OS 进程隔离。
- **变更的边界（显式架构取舍，已获 [Owner 2026-11-24 书面确认](https://github.com/Ancienttwo/byok-sdk/issues/2457#issuecomment-7129367051)）**：原 Electron 的独立 OS Renderer 沙箱进程（`sandbox + contextIsolation`）**不再存在**。在 NSH Mixed 下，QuickJS-NG 与 Rust `byok-shell` 运行在**同一 OS 进程内**（见[可行性调研 §4.1](../researches/2026-11-23-desktop-native-ui-nsh-feasibility.md#L97-L105)）；原 OS 级 renderer 进程边界改为依赖「静态 release 字节码 + `Policy::harden` + 只含 UI 生命周期权限的 `capabilities`（不授予 `process` / `fs` / `network` / `webview` / `host`，见下方「TSX VM 权限边界」；2026-11-24 签核时为空 `{}`） + Rust `byok-shell` 严格 Bridge 方法白名单」的进程内 VM 权限约束。除 QuickJS 原生桥接代码本身的内存安全漏洞外，该取舍还明确承接**不可信的模型/工具输出文本由建仓约六周的 NSH 原生 Markdown / TextView 解析器引擎在持有 spawn Host 与 custody 权限的同一 OS 主进程内直接解析渲染**这一攻击面；VM 层面权限无法在 OS 进程内形成二次隔离缓解。
- **禁止 TSX-only 与 Rust-only 模式**：TSX-only 会对子进程组强杀且破坏 custody 配置写锁语意，Rust-only 则失去直接执行 `@byok-sdk/keys/model-route` 的能力。
- **Rust 持有进程权威**：Node Host 子进程与短生命周期 custody 子进程全部由 `byok-shell` 派生监督，继承并过滤 `FOREIGN_RUNTIME_VARIABLES`，保持 `1s..30s`（60s 重置）指数退避、`50ms` `state-changed` hint 聚合与 `10s` 优雅 `shutdown`。
- **Supervisor 的 TSX 暴露形态**：NSH 接入层把 Rust 持有、进程内唯一的 supervisor 暴露给 TSX：`#[module]` 方法加返回 `Stop` 的 `on_*` 监听，启动幂等；Host 只在 quit 路径（`on_quit_request` / `on_app_quit`；macOS 另设 `QuitRequestOptions::default().system(true)` 以接住系统注销）、显式 restart、recovery 或更新交棒（D5）时停止。不以 `#[class]` 或 TSX 模块级实例持有 supervisor：class 实例在 QuickJS GC、`dispose()` 或 `using` 块结束时 Drop，TSX 热更新重跑改动过的模块级代码时会新建实例。这是对 NSH Coding Guides「class 优于带全局状态的 module」的有意偏离，依据是每个 storage root 只能有一个 Host（`MaintenanceLock`、recovery），以及 mixed 模式文档的边界判断（须跨 TSX 热更新存活的状态归 Rust）。生命周期确由 TSX 持有的其他对象照常用 `#[class]`。接入层不另起 async runtime（不引入 tokio）：阻塞调用经 NSH 的 `blocking(..)`，跨线程事件经 `Callback::post` 回到引擎线程。
- **Custody 隔离不变式**：API key / secret 只经 `byok-shell` 临时内存写一次 stdin 到 custody 子进程并立即清零；`keys.submit` 超时（30s）后 UI 返回超时，**但绝不杀死正在持 OS 钥匙串或 SQLite 锁写入的 custody 子进程**（并安全忽略或排干超时后的尾随 `stdout` 以免引发子进程异常）；`keys.list` 超时则强杀。
- **凭据在 UI 中的生命周期（Owner 于 2026-11-25 选定方案 A）**：TSX `masked` 输入框的值是 QuickJS 字符串，保存在 signal 中，`@byok-sdk/keys/model-route` 也在 TSX 内校验它（[`isPortableSecretValue`](../../packages/keys/src/model-route.ts)、`secretFieldError`）。JS 字符串无法清零，清空 signal 不会抹掉已有副本；`byok-shell` 的 `SecretBytes` 清零只覆盖 Rust 侧。原 §3 写的「凭据不经 QuickJS 泄露」在这一架构下无法成立；Owner 已于 [PR #2472 书面签核](https://github.com/Ancienttwo/byok-sdk/pull/2472#issuecomment-7139209349) 选定 **方案 A**：
  - **方案 A（已选定）**：保留 TSX 输入框，不变量改为：key 在 QuickJS heap 中存在至被 GC；调用 `keys.submit` 前清空受控 signal；除 `keys.submit` 的参数外不序列化、不写日志、不持久化，Bridge 与日志中不回显。无需改动 `@byok-sdk/keys/model-route`。残余风险是同一进程内的内存泄露（crash dump、D2 已承接的 Markdown / TextView 解析攻击面），概率低；UI 与 shell 已按 D2 同处一个进程，方案 B 只能缩短 key 的驻留时间而不能增加隔离边界。
  - *（已否决）方案 B*：在接入层实现 Rust 原生 `SecretField` 组件使 key 不进入 QuickJS；因需把 secret 格式校验移出 `model-route`（破坏 §3 单一权威）并增加三端原生输入组件，Owner 未采用。
- **TSX VM 权限边界与独立隔离验收**：`nsh.json` 的 `capabilities` 须与下列预期集合逐字一致：

  ```json
  { "capabilities": { "application": true, "openUrl": { "schemes": ["https"] } } }
  ```

  - `nsh build` 写出的 `capabilities.json` 是展开后的规范化形式（[PoC 证据 §3.1](../researches/2026-11-24-nsh-mixed-poc-evidence.md)：输入 `{}` 时输出逐项列出 `network`、`process`、`fs` 等禁用值，且没有 `application` 键），不能与上面的输入逐字比对。release 验收改为与生产 rev 实际构建出的 golden 文件比对，并断言 `process.execute`、`fs.read`、`fs.write`、`network.hosts` 为空，`openUrl` 只允许 `https`，`application` 已授予；构建文件的具体键布局不在本 ADR 规定。
  - 确需第二个窗口时才加 `windows`（不含 `overlay`）。**永久禁止授予 `process`、`fs`、`network`、`webview`、`host`，并禁止以 signed package（`nsh publish` / `.nshpkg`）热更新 TSX**：package 只含 TSX，会让 TSX bundle 与 Rust 接入层、SEA Host 的 `BRIDGE_VERSION = 2` 脱节。
  - **需要 `application` 的原因（已在 `2964346` 源码与 Windows 实机 A/B 实证）**：上游 [`sandbox-and-capabilities.md`](https://github.com/longbridge/nsh/blob/v0.6.1/website/docs/sandbox-and-capabilities.md) 规定主窗口（含 title bar）、应用菜单、tray、全局快捷键、`quit` / `quitRequest`、`restart` 与 `setLaunchAtLogin` 都需要 `"application": true`，未授予时这些调用不生效；PoC P1 在 `{}` 下运行时输出 `WARN js: the application (its main window, menu, tray, global shortcuts, quitting and restarting) is not granted: add "application": true to capabilities in nsh.json`（本地日志 `_ops/nsh-poc/p1-run.log`）。NSH `2964346` 源码实证：`crates/nsh-core/src/core/mod.rs:3824, 3997-4008` 在 `!self.access.allows_application()` 下拒绝并丢弃 `ROOT_ID` 上的 `Command::Desktop`（含 `Quit`、`SetQuitOnRequest(false)` 等，`SetQuitMode` 与 `login_item_action` 亦在 `mod.rs:3109-3113`、`components.rs:6157` 同受限制）；`win-ci` 实机 A/B 对照也证明，`capabilities: {}` 的 `ByokP3Win.exe` 在 `WM_CLOSE` 后销毁窗体但进程 3s 内未退出（`exited=False, stillWindow=False`），授予 `"application": true` 的 `ByokP3G2.exe` 立即干净退出（`exited=True, code=0, remaining_hwnds=0`）。tray、关窗驻留 tray 与 login item 是现行 Electron 壳已有的功能，且 `application` 只涉及 UI 生命周期，不给 VM 任何 OS 进程、文件或网络权限，本条保护的边界不变。
  - **外部链接**：[`nsh-app/nsh.json`](../../examples/desktop-bot-app/nsh-app/nsh.json) 声明的原生能力 `openUrl: { schemes: ["https"] }` **只在原生能力层保证 HTTPS-only**（仅限制 scheme，不做 origin 过滤）；精确的 origin allowlist（`brand.externalOrigins`）在 TSX 单一入口 [`nsh-app/src/links.ts`](../../examples/desktop-bot-app/nsh-app/src/links.ts)（`openAllowedExternalUrl` / `parseAllowedExternalUrl`）强制执行。禁止在 `TextView` 上使用 `links="open"`，并禁止在 `nsh-app/src/links.ts` 之外直接调用 `openUrl`；**不新增 Rust URL broker**（若后续 Owner 在 `#2457` D-O3 选择原生能力级 origin 强制，则另开独立 PR 实施）。注：现行 gallery 演示页 [`nsh-app/App.tsx`](../../examples/desktop-bot-app/nsh-app/App.tsx) 在 `brand.externalOrigins` 为空时提供演示回退 origin，[`nsh-app/src/links.ts`](../../examples/desktop-bot-app/nsh-app/src/links.ts) 顶部旧注释亦仍提及 Rust broker，均在 `#2461` 正式接线时按本条清理对齐，产品代码不得提供空配置回退 origin。
  - **整包更新**：`nsh/updater` 替换整个打包应用（Rust 接入层、TSX 与 SEA Host 一并替换），不属于上面禁止的 `.nshpkg` TSX 热更新；[#2479](https://github.com/Ancienttwo/byok-sdk/issues/2479) 已定案采用由 Rust 接入层独占编排的 `nsh/updater` 整包更新，具体交棒契约、失败恢复、quit 路径规则与 Electron 升级路径见 D5。任何整包更新都先执行 Host 停止与 S1 snapshot；严禁 TSX 直接 import `nsh/updater`，并永久禁止配置 `updater.packages`（`.nshpkg` OTA）。
  - **验收区分**：[#2458](https://github.com/Ancienttwo/byok-sdk/issues/2458) IME 验签仅验证输入体验，不替代隔离边界验收；隔离验收须在可运行的 release 打包产物中独立证明：`capabilities.json` 符合上面的 golden 文件与字段断言、`Policy::harden` 生效、`byok-shell` native bridge 拒绝任何未在 `bridge-contract.json` 声明的方法；平台 Quit 键（Cmd+Q / Ctrl+Q）与托盘 Quit 都经 `"application": true` + `on_quit_request` + `quit()` 完成 Host `10s` 优雅 `shutdown` 与 `MaintenanceLock` 的 quit 等待；系统注销或关机时，macOS 须设置 `QuitRequestOptions::default().system(true)`（TSX：`Application.setQuitRequestOptions({ system: true })`）并完成优雅 `shutdown`，Windows 与 Linux 上游在系统关机路径只运行 `on_app_quit` cleanup 后退出且 `crates/nsh-core/src/element/quit.rs:29` 硬编码 `QUIT_TIMEOUT = 200ms`（无法等待 Host `10s` 优雅关闭），须证明快速 cleanup 被调用并记录 `200ms` 硬上限下的快速收尾路径。
  - 本条改动（`capabilities` 预期集合及 `.nshpkg`/`nsh/updater` 界定）已于 2026-11-25 获 [Owner 书面重签](https://github.com/Ancienttwo/byok-sdk/pull/2472#issuecomment-7139209349)。

### D3. S1 / S2 单一权威接缝与共用包复用约束

- **S1（收回 Host 布局与快照）**：`byok-desktop-snapshot` 与 `byok-desktop-restore` 全部收归 Host argv 重入命令（沿用 `START_FRESH_COMMAND` 单行 JSON receipt 协议，[#2459](https://github.com/Ancienttwo/byok-sdk/issues/2459)）；原生壳与现有壳不再 import `@byok-sdk/client/host-layout`。
- **S2（生成式 Bridge 契约）**：由 `examples/desktop-bot-app/src/bridge/domains/*.ts`（唯一权威）生成只读 `bridge-contract.json`（`schemaVersion: 2`，含 `bridgeVersion`、`rendererMethods`、`mainMethods`、`hostMethods`、`shellToHostMethods` 及 `hostCommands`）与生成器防漂移测试，确保 `keys.profilesChanged` 等壳→Host 内部调用同时受白名单声明；`byok-shell` 编译期嵌入并 fail-closed 校验该契约，不做版本协商或兼容性别名。
- **NSH 接入层 transport**：Bridge RPC 只经一个通用的 `call(method, params)` 暴露给 TSX（参数与结果为 `JsonValue`）；supervisor 生命周期与状态监听是 D2「Supervisor 的 TSX 暴露形态」所述的另一组少量 `#[module]` 导出，不经 `call`。`call` 由 `ShellRouter` 按 `bridge-contract.json` fail-closed 校验方法名；TSX 侧类型复用 `src/bridge/domains/*.ts`，不在 Rust 侧逐方法声明 `#[derive(JsObject)]` 类型，避免出现第二个类型权威。失败一律以 Promise reject 表达并携带稳定的 `code`（沿用 `BridgeCallError.code` 的现有取值）；若生产 rev 的 `Err` 映射不能携带 `code`，在 transport 统一定义一种错误信封。每个导出都写 doc comment（`nsh build` 会对未文档化的导出告警）。`keys.submit` 另按 D2「凭据在 UI 中的生命周期」处理。
- **`@byok-sdk/keys` 与 `@byok-sdk/ui-runtime` 使用边界**：
  - QuickJS 仅直接运行纯函数状态机 `@byok-sdk/keys/model-route`（随 release `Policy::harden` 持续回归全部 30 个 fixture vectors）；不得要求 `packages/keys` 修改实现以迎合非标准 JS API，且 TSX 侧禁止依赖 `globalThis.structuredClone`。
  - `@byok-sdk/ui-runtime` 仅在 Node Host 侧运行（避免把 `@byok-sdk/cloud` 与 Hono 拉入 QuickJS），UI 仅消费 Host 投影后的序列化 JSON `ActivityCard`。

### D4. Windows 可编辑文本字体不变量与 `ui` 层封装

- 基于 PoC 在 `v0.6.1` 与 `nightly (f577c51)` 的 A/B 实测证据（默认 `"Segoe UI"` 导致 Win32 RichEdit `<Input>` 输入中文渲染为 `□□□□`），桌面 UI 的可编辑文本控件只在 app 的 `ui` 层实现（`ui/Input`，含 `masked` 变体；`ui/Textarea`），功能页面不直接使用 NSH 原生 `<Input>`。Windows 字体 `"Microsoft YaHei UI"` 作为平台排版 token 由这两个组件读取，直至生产 rev 的上游 NSH 从底层修复 RichEdit CJK font-link 并通过同等视觉回归为止。
- `2964346` 150% DPI 实测补齐了多行 RichEdit A/B 验证（[#2457 实测评论](https://github.com/Ancienttwo/byok-sdk/issues/2457#issuecomment-7139014589)，本地截图 `_ops/nsh-poc/win-dpi-ime/nightly-2964346-150dpi-cjk.png`）：`2964346` 下多行默认字体（`cjk-default`）与多行 `font-cjk` token（`cjk-multiline` -> `"Microsoft YaHei UI"`）中文均清晰渲染无豆腐块；仍继续保留平台排版 token 与 `nsh test --target windows` 截图检查作为防御性不变量，防止后续字体回退或字符串断言掩盖视觉回归（[PoC 证据 §4.3](../researches/2026-11-24-nsh-mixed-poc-evidence.md)）。
- `masked` 密码输入框在调用 `keys.submit` 前必须清空 UI 受控信号（与现行 Electron 实现及 `keys-submit.browser.mjs` 的断言一致），且不在 Bridge/日志中保留回显，key 的驻留按 D2「凭据在 UI 中的生命周期」；跨平台需补齐 `App.tsx` 针对 Linux 桌面托盘与窗口关闭退出的验证。

### D5. 三端打包、原生更新交棒契约、签名、许可与借鉴边界

- **三端打包、嵌套签名与许可门禁**：由 [#2462](https://github.com/Ancienttwo/byok-sdk/issues/2462) 补齐 `nsh package` 之外的 `resources/host/` 注入、macOS 从内向外嵌套 Developer ID 签名（含 SEA `allow-jit` 与 `agent-memory-fs`）及 DMG 公证、Windows MSVC Mixed 构建 + `signtool` + **`koffi.node` SHA-256 与 SDK pin 严格核验**、Linux `.deb`/`AppImage`（`GTK >= 4.14` / `glibc >= 2.39` / `libsecret-tools` 依赖声明）以及 Rust `Cargo.lock` 与系统动态库许可门禁。
- **原生更新机制决定（单一机制，[#2479](https://github.com/Ancienttwo/byok-sdk/issues/2479)）**：采用 **NSH `nsh/updater` 整包更新，且严格由 Rust 接入层 `byok-nsh-adapter` 通过 `nsh-updater` crate（与 `nsh-core` 同一 `git + rev` 钉版，Apache-2.0）+ `sys.updater`（`UpdaterHost`）+ `byok-shell::MaintenanceLock` 独占编排**。
  - **为何选定该机制**：
    1. 复用已钉版 NSH `2964346` 工作区自带的 `nsh-updater` 与平台原生 HTTP 栈（`UpdaterHost`），**不引入 `tokio` / `reqwest` / 第二套 TLS 栈**，且**不增加任何 `nsh.json` `capabilities`**（`capabilities` 保持 `{ "application": true, "openUrl": { "schemes": ["https"] } }`，不放行 `network`/`fs`/`process`）。
    2. 与 `resources/host/` 注入、macOS 嵌套签名公证（`Installation::stage()` 内置 `/usr/bin/codesign --verify --deep --strict` + `swap_directory` 两次 rename 交换）及 Windows 非管理员每用户目录安装（`swap_entries` 逐项 rename 交换 + 下次启动清理受控残留 + `NSH_RESTART_AFTER` 等待旧进程退出）天然契合，并把 `koffi.node` SHA-256 绑定在 Ed25519 签名的归档哈希内（注意：NSH `2964346` 的两次/逐项 rename **均非崩溃原子**，实际交换保障、完整性校验与异常恢复见下方交棒契约）。
    3. **更新配置、Feed URL 映射与新增公钥输入**：延续 `FORKING.md`「未配置 feed 则无更新器」的开关语义，但将 **`BYOK_UPDATE_PUBLIC_KEY` 明确登记为 NSH 新增打包输入**（现行 `FORKING.md` 的 Electron 路径仅声明 `BYOK_UPDATE_FEED_URL` 基址而无公钥变量；NSH 打包须成对提供 `BYOK_UPDATE_FEED_URL` 与 `BYOK_UPDATE_PUBLIC_KEY`，仅设其一在打包期 fail-closed 报错；均未设置时不写 `nsh.json` 的 `"updater"`，由 `nsh package` 跳过生成 `nsh-updater.json`，运行期无更新器）。因 `FORKING.md` 的 `BYOK_UPDATE_FEED_URL` 为通用 HTTPS feed 基础 URL，而 NSH `nsh.json` 的 `updater.url` 要求直指清单文件，打包脚本将其规范化映射为 `<BYOK_UPDATE_FEED_URL 去除尾部 />/latest.json`（已以 `/latest.json` 结尾则原样保留，拒绝非 `https://` 或含查询串/片段的值），连同 `publicKey` 与 `"features": ["updater"]`（因 TSX 不 import `nsh/updater`，`nsh-cli/src/native_features.rs:41` 需显式保留该 feature 以向运行期注入 `sys.updater`）写入构建期 `nsh.json`，并由 **`nsh package`（`nsh-cli/src/updater.rs:add_config`）自身生成并嵌入 `assets/nsh-updater.json`**。**强制要求 `publicKey`**（拒绝未签名清单）并**永久禁止配置 `updater.packages`**：不以 `UpdaterHost::runs_packages()` 作为禁用依据（`nsh-engine/src/lib.rs:932` 中该函数反映编译期引擎能力，桌面端恒为 `true`，与 `updater.packages` 无关），而是通过三层校验保障 `.nshpkg` OTA 永不开启——(a) 打包与 release 隔离门禁断言 `nsh.json` 与 `nsh package` 生成的 `nsh-updater.json` 均无 `updater.packages` 且 `Config::package_roots().is_empty()`（`nsh-engine/src/updates.rs:185` 据此跳过全部 OTA 加载）；(b) 静态禁止 TSX import `nsh/updater`；(c) Rust 检查清单时拒绝任何携带 `package` 字段的清单。
    4. **静态禁止 TSX 直接 `import "nsh/updater"`**（包括禁止 TSX 调用 `installAndRestart()` / `installOnQuit()`）：NSH JS 侧 `installAndRestart()` 会绕过 `MaintenanceLock`、Host 停止与 S1 snapshot，且其内部 `desktop::restart()` 后返回 `pending()` 会在持锁时令 `on_app_quit` → `drain_for_quit` → `begin_quit()` 死锁；改由 Rust 接入层拆分调用 `Installation::stage()` 与 `Staged::finish()`，即可把 `MaintenanceLock`、S1 snapshot 与替换前后完整性校验精确包在目录交换边界外。
  - **各平台安装形态准入与手动下载降级**：`Installation::can_install()`（`install.rs:97-102`）仅探测安装父目录能否创建临时目录，**不能单独作为打包形态判定依据**（例如 Linux `AppImage` 挂载于 `/tmp/.mount_*` 时其父目录 `/tmp` 仍可写，但挂载镜像不可原地替换）。Rust 接入层必须按**安装形态 + 可写性 + 已验证的可恢复保护**联合判定 `inAppEligible`：
    - **允许应用内替换（`inAppEligible == true`）**：macOS 可写 `.app` bundle（不在只读 DMG 卷或 App Translocation 路径且 `can_install() == true`）；Windows 非管理员每用户可写目录安装（非只读管理员目录且 `can_install() == true`）；Linux **独立用户可写 `.tar.gz` 解包目录**（明确排除 `AppImage`——无 `APPIMAGE`/`APPDIR` 环境变量且非 FUSE 挂载，明确排除 `.deb` 系统包——不在 `/usr/`、`/opt/` 且无 `.deb` 打包标记，且 `can_install() == true`）；同时该平台须在 `#2462` 通过下文目录交换完整性校验与故障注入恢复门禁（若某平台尚未具备可持久化的恢复/修复方案，该平台先走明示手动安装）。
    - **仅手动下载提示（`inAppEligible == false`）**：Linux `.deb`、Linux `AppImage`、macOS 只读 `/Applications` / DMG / App Translocation 路径、Windows 只读管理员目录安装，以及未通过可恢复门禁的平台形态。
    - **手动下载链接来源与外链白名单**：`nsh update-manifest` 的 `--link` 仅接受 `ios` / `android`（`nsh-cli/src/updater.rs:424-431`），桌面端 `platforms.<target>.url` 为供自动更新消费的 `.tar.gz`/`.zip` 原始归档 URL，并不对应 `.deb`/`AppImage`/`.dmg`/Windows 安装器。因此当 `inAppEligible == false` 时，UI **不得返回或打开 `manifest` 中的归档 URL**，而是展示已验签的新版本号、变更说明与一个**固定的、其 origin 已列入 `brand.externalOrigins` 白名单的 HTTPS 发布页 URL**（由发布/品牌配置显式声明，例如 `brand.config.ts` 的可选 HTTPS 发布页地址，经 `nsh-app/src/links.ts` 的 `openAllowedExternalUrl` 校验打开；若未配置或不在 `brand.externalOrigins` 内，则仅展示版本说明与手动升级指引而不调用 `openUrl`），由该发布页提供对应平台的 `.dmg` / Windows 安装器 / `.deb` / `AppImage` / `.tar.gz` 手动下载制品。绝不尝试 `osascript` / `pkexec` 提权或覆写系统包。
  - **为何未选另外两种机制及各自所需代价**：
    - 否决 **`cargo-packager-updater`**：其 Windows 实现通过 `powershell.exe Start-Process` 拉起 NSIS/WiX 时使用 `.expect(...)`（失败直接 panic 而非可恢复错误）并立即调用 `std::process::exit(0)`，既无可验证接管信号也绕过 Rust `Drop` 清理，无法在安装器失败或闪退时执行 `cancel_pending` 并恢复旧 Host；同时拉入 `reqwest`（内嵌 `tokio` 运行时，违背 D2 接入层不引入 `tokio` 约束）、`rustls`/`ring` 与 `minisign-verify`，将整包（含 `resources/host/` 约 200 MiB）全量读入内存 `Vec<u8>`；macOS 侧先 `remove_dir_all` 再 `rename`（直接销毁旧包而无备份回退、无 `codesign` 校验、权限不足时调 `osascript` 提权），不支持 `.deb` 且不含跨平台重启；此外还需在 `nsh package` 之外引入仍处公开预览期的 `cargo-packager` 工具链。若采用，需分叉重写其 Windows 进程交棒与 macOS 备份交换及签名校验、豁免 D2 的 `tokio` 禁令或自建 HTTP 传输，并维护双打包工具链与独立的 minisign 密钥体系。
    - 否决 **首个 NSH 版本不含应用内更新器（仅手动下载、更新移至后续 issue）**：相对现行 Electron 壳（`src/main/updater.ts` + `FORKING.md` 的应用内检查/下载 + S1 安装前快照 + 重装旧版后 `shell.restore` 回滚）造成功能倒退，且导致 `#2462` 无法对真实“旧版 → S1 snapshot → 安装新版 → 新版启动；重装旧版后由旧版执行 `shell.restore` 回滚”闭环做自动化与实机验收。若采用，需单开命名后续 issue 补齐应用内更新、在过渡期为三端提供手工下载升级说明，并接受 `#2462` 退化为手工替换或合成脚本验证。
- **映射到 [`MaintenanceLock`](../../examples/desktop-bot-app/native/byok-shell/src/maintenance.rs) 的逐步交棒契约与失败恢复**：
  - **交棒前阶段（不持有 `MaintenanceLock`，Host 保持正常运行；但按安装实例严格串行化准备与暂存）**：
    - **准备与暂存互斥不变量**：尽管交棒前阶段不阻塞 Host，但 NSH `install.rs:119-180` 存在两处并发风险——`Installation::remove_leftovers()`（`install.rs:119-138`）会在**不检查 PID 存活**的情况下删除其他 PID 的 `.nsh-updater-staged-<other_pid>-<name>`，而同进程二次调用 `Installation::stage()`（`install.rs:174-180`）会无条件 `remove_dir_all` 覆盖并破坏第一个 `Staged` 目录。因此 Rust 接入层必须强制：(a) **进程内串行状态机**，同一时间仅允许一个检查/下载/暂存/交棒流程，并发请求直接返回 `update_in_progress`，严禁在已有存活 `Staged` 句柄时再次 `stage()`；(b) **按安装根路径隔离的跨进程安装锁**（如 `<data_dir>/updates/install-<root_hash>.lock`，使用 OS 内核文件锁 `File::try_lock()`，进程崩溃时由内核自动释放）串行化准备、暂存、清理与交棒，并在 `Staged` 句柄存活期间持续持有直至交棒结束或丢弃 `Staged`；同时对共享哈希命名的 `<data_dir>/updates/download-<sha256>.part` 全程持有独立独占文件锁 `<part>.lock`（至校验并原子重命名为 `download-<sha256>` 后释放；锁忙返回 `update_in_progress`）；(c) **只清理经证实陈旧的残留制品**——禁止在未持有跨进程安装锁时盲调 `Installation::remove_leftovers()`，仅在成功持锁（证明本安装根无其他活跃更新进程）且确认不存在未解决 `pending-swap.json`（不误删其指向的备份目录）后，在检查/启动阶段（含已是最新版无更新时，以清理 Windows 旧版运行遗留）清理历史 `.nsh-updater-old-*`、非活跃哈希且未上锁的过期 `download-*` 以及已证实无活跃持有进程的过期 `.nsh-updater-staged-*`。
    1. **检查清单**（失败向 UI 上报 `update_check_failed`；验签/策略失败上报 `update_verify_failed`）：先检查是否存在未解决的 `pending-swap.json`（若存在则拒绝原地更新并直接提示 `update_install_corrupted` 手动修复）；再通过 `sys.updater`（`UpdaterHost`）读取 `nsh package` 打包的 `nsh-updater.json`，断言 `Config::package_roots().is_empty()`，按「各平台安装形态准入」判定 `inAppEligible`（为 `true` 时在安装锁保护下执行上述受控陈旧残留清理，即便随后检查结果已是最新版亦覆盖 Windows 残留清理）。接着经 HTTPS 获取 `latest.json` 与 `latest.json.sig`，用嵌入的 Ed25519 `publicKey` 验签后额外校验 `manifest.id == "io.byok-sdk.byok-desktop-bots"`（`nsh-updater` 的 `Config::open()` 本身不校验 `id`）并拒绝任何携带 `package` 字段（`.nshpkg` OTA）的清单，再经 `Config::check()` 校验 `semver > current`。若有新版本且 `inAppEligible == false`，直接返回 `{ canInstall: false, version, notes, releasePageUrl }`（`releasePageUrl` 为白名单发布页 URL 或 `null`，绝非 manifest 归档 URL）走手动下载提示，不进入下载与交棒。
    2. **流式下载与校验**（传输失败上报 `update_download_failed`；大小/SHA-256 校验失败上报 `update_verify_failed`）：在安装锁与 `<part>.lock` 保护下，经 `UpdaterHost::get` 支持 HTTP `Range` 续传写入 `<data_dir>/updates/download-<sha256>.part`（可选优先 zstd delta 补丁、失败回退整包），校验大小与 SHA-256 后原子重命名为 `download-<sha256>`。
    3. **交换前归档布局校验与预解包验签**（失败上报 `update_stage_failed`）：在 NSH `2964346` 中，`Staged` 的 `target` 与 `executable` 字段均为私有（`install.rs:248-259`），`Staged::finish()` 仅在交换完成后才返回目标路径，且 `nsh_core::restart::set_program` 为 `pub(crate)`（`restart.rs:50`），接入层无法改写重启目标路径。因此必须在**交换之前直接校验已验签下载归档的目录布局**（读取 `.tar.gz`/`.tar`/`.zip` 目录项，或在封装的 staging 访问器上显式校验）：(a) 归档内唯一顶层目录名与当前安装根目录名（含 macOS `.app` 名）完全一致，确保 `Installation::target()` 不会重命名目录；(b) 与当前 `nsh_core::restart::program_path()` 对应的相对主可执行路径存在于归档中；(c) 归档内包含 `resources/host/` 负载。校验通过后，在安装锁保护下调用 `Installation::stage(&archive)` 解包至 `.nsh-updater-staged-<pid>-<name>`，校验可执行权限并在 macOS 执行 `/usr/bin/codesign --verify --deep --strict`。此阶段未动任何已安装文件，任一步失败直接丢弃 `Staged` 并释放安装锁，不打断 Host。
  - **交棒阶段（由显式用户命令触发，在持有上述安装锁前提下按以下严格顺序在 Rust 接入层执行）**：
    1. **`MaintenanceLock::try_begin()`**（`maintenance.rs:78`）：获取独占 `MaintenanceGuard`（互斥 `shell.restore`、`shell.startFresh`、`keys.submit`、并发更新，并令 `begin_quit()` 等待）。失败向 UI 上报 **`maintenance_busy`**，Host 不受影响。
    2. **`MaintenanceGuard::begin_pending()`**（`maintenance.rs:176`）：交棒状态由 `None` 迁至 `Pending`（阻塞对等维护操作，尚未封死锁）。
    3. **`HostSupervisor::stop()`**（`host.rs:550`，10 s 优雅 NDJSON `shutdown` + 校验退出码 `0` + 释放 `KeepAwakeGuard`）：注意 `HostSupervisor::stop()` 入口即置 `paused = true, stopping = true`（`host.rs:550-558`）。若停止失败或超时，向 UI 上报 **`update_host_stop_failed`**，**禁止**继续快照或替换，保持 `MaintenanceGuard` 不释放并立即转入下方「交棒未确认时的维护窗内回滚与 Host 恢复」。
    4. **S1 `byok-desktop-snapshot <current_version>`**（`recovery.rs:run_snapshot`）：以 argv 重入当前 Host 二进制执行快照（全程持有 SQLite `acquireConfigurationLock`，完成标记最后落盘，中途不强杀）。若快照失败，向 UI 上报 **`update_snapshot_failed`**，销毁 `Staged`（自动清理旁路目录），保持 `MaintenanceGuard` 不释放并立即转入下方「交棒未确认时的维护窗内回滚与 Host 恢复」。
    5. **退出竞态复核**：检查 `maintenance.is_quitting()`；若步骤 3–4 期间收到普通用户/系统退出请求，则销毁 `Staged`、执行 `guard.cancel_pending()` 并 `drop(guard)`，让正常退出路径收尾（此时 Host 已干净停止且 S1 快照已安全落盘）。
    6. **目录交换、实际保障边界与三态结果**（`nsh_core::restart::remember_program()` → 捕获 `expected_program = nsh_core::restart::program_path()?` → 落盘交换日志 → 经可注入 `UpdateInstaller` 接缝执行 `Staged::finish()`）：
       - **先记录并捕获重启路径**：`remember_program()` 返回 `()`（`restart.rs:34`），必须紧接调用 `let expected_program = nsh_core::restart::program_path()?`（`restart.rs:57`）保存当前可执行路径，并在交换前向 `<data_dir>/updates/pending-swap.json` 写入持久化记录（旧安装根路径、预期 `.nsh-updater-old-<pid>-*` 备份路径、当前与目标版本号）。
       - **NSH `2964346` 实际交换保障（非崩溃原子）**：macOS / Linux 的 `swap_directory`（`install.rs:466-482`）执行**两次独立 `fs::rename`**（先 `root → .nsh-updater-old-<pid>-<name>`，再 `new → target`）——第二次失败时的回退 `fs::rename(&old, root)` 本身也可能失败，进程在两次 rename 间中止则不会执行回退，导致旧 `root` 路径缺失；Windows 的 `swap_entries`（`install.rs:488-506`）在失败回退循环中执行 `let _ = fs::rename(to, from)`，**静默忽略回退 rename 错误**，中断或未完成的替换同样可能导致旧 Host 路径缺失或新旧文件混杂；且 **S1 快照只保护 `<hostStorageRoot>/host/` 用户数据，不会补回应用程序目录与 `resources/host/`**。
       - **三态结果判定（禁止将所有 `Err` 一律视为旧包已复原）**：`UpdateInstaller` 必须区分三种结果：
         - **`Swapped { executable }`（替换成功，唯一可验证接管信号）**：`Staged::finish()` 返回 `Ok(new_exe)`、规范化后与预先捕获的 `expected_program`（`program_path()`）一致，且磁盘确认新主程序与 `resources/host/` 入口存在；清除 `pending-swap.json` 并进入步骤 7。**仅启动一个 launcher/外部进程而无已提交的接管信号，或路径不匹配时，绝不允许调用 `confirm()`。**
         - **`RolledBackVerified`（替换失败且回退后已验证旧包完整可执行）**：`Staged::finish()` 返回 `Err`（或测试注入的 fake installer 未发接管信号即失败/退出），且接入层在**仍持有 `MaintenanceGuard` 的维护窗内**完成旧包完整性校验——确认旧主程序可执行、`nsh/app.json` 与当前运行 `id`/`version` 一致、旧 `resources/host/` Host 入口完整（macOS 须通过 `/usr/bin/codesign --verify --deep --strict`；Windows 须校验关键旧包文件完整且无未还原混杂残留）——**仅当全部校验通过**，才清除 `pending-swap.json`、销毁 `Staged`、向 UI 上报 **`update_install_failed`**，并转入下方维护窗内旧 Host 恢复。
         - **`InstallCorrupted`（安装需要修复——回退失败、中断残留或旧包完整性校验未通过）**：凡 swap 失败后上述旧包完整性校验未通过（包括两次 rename 间中止、二次 rename 与回退 rename 皆失败、Windows 回退 rename 错误被忽略导致旧 Host 路径不可用或文件残缺），**严禁调用 `supervisor.restart()`，也严禁向 UI 回报旧 Host 可恢复**；保留 `pending-swap.json`（含备份目录与原始错误供诊断/支持）、销毁 `Staged`、执行 `guard.cancel_pending()` 并 `drop(guard)`，向 UI 上报独立错误码 **`update_install_corrupted`**（明示应用目录受损需修复、用户数据与 S1 快照未受损，并提供白名单发布页手动重装入口），绝不调用 `confirm()`。若某平台在 `#2462` 缺乏可验证的旧包完整性检验或持久化恢复/修复方案，该平台不得开启应用内替换，先走明示手动安装。
    7. **封锁提交与重启**（`guard.confirm()` → `drop(guard)` → `nsh_core::element::desktop::restart()`）：仅在步骤 6 判定为 `Swapped { executable }` 后调用 `guard.confirm()`（`maintenance.rs:192`，永久封死锁为 `HandoverState::Confirmed` / `QuitOutcome::HandedOver`），**并在调用 `desktop::restart()` 之前显式 `drop(guard)`**（将 `busy` 归 `false`，确保随后触发的 `on_app_quit` → `drain_for_quit` → `maintenance.begin_quit()` 立即返回 `QuitOutcome::HandedOver` 而不会在 `while guard.busy` 处死锁或重复 `stop()`），删除已消费的下载归档、释放安装锁并调用 `desktop::restart()`。平台 runner 退出事件循环后调用 `nsh_core::restart::spawn_after_exit()`（macOS/Linux 由 `/bin/sh` 最多等待旧 PID 10 s 后执行 `open -n` / `exec`；Windows 带 `NSH_RESTART_AFTER=<old_pid>` 启动新版并等待旧进程退出）。若进程退出后的 `spawn_after_exit()` 失败，因磁盘上的旧包与 `resources/host/` 已被新版替换，旧壳不再重启旧 Host 而是干净退出；按旧版本号写入的 S1 快照保留在磁盘上，用户下次启动即进入新版。**升级后数据回滚规则**：因步骤 4 写入的是 `<old_version>` 快照，而接入层调用 `shell_restore` 传入当前运行构建的 `shell.app_version` 并严格校验该版本的完整快照（`recovery.rs:429-434`，与 `FORKING.md` §5 一致），若新版出现 store 异常或需回退旧版数据，用户须**先重新安装旧版本（`<old_version>`），再启动该旧版本并通过其自身的 `shell.restore` 恢复 `<old_version>` 快照**（新版不提供也不执行旧版快照恢复）。
  - **交棒未确认时的维护窗内回滚与 Host 恢复（硬性不变量）**：`HostSupervisor::stop()` 会将 supervisor 置为 `paused/stopping`（`host.rs:550-558`），而 `MaintenanceGuard::cancel_pending()`（`maintenance.rs:183-189`）仅重置交棒状态、不会触碰 supervisor；同时，若在重启旧 Host 之前先释放 `MaintenanceGuard`，`shell_restore()`（`recovery.rs:409`）等维护操作可能在 Host 尚处停止态时抢入维护锁并与后续 `supervisor.restart()` 在同一数据根上并发竞争。因此，凡在步骤 3（`update_host_stop_failed`）、步骤 4（`update_snapshot_failed`）或步骤 6 **`RolledBackVerified`**（`update_install_failed`，**绝不适用于 `InstallCorrupted`**）失败且交棒未确认时，**必须在持续持有 `MaintenanceGuard` 的同一维护窗口内按序执行**：(1) 调用 `guard.cancel_pending()`（重置 `handover = None`，但保持 `guard` 存活即 `busy == true`）；(2) 立即检查 `maintenance.is_quitting()`——若期间已有退出请求到达，**不再重启 Host**，直接 `drop(guard)` 放行等待中的 `begin_quit()` 完成干净退出（`QuitOutcome::Quit`）；(3) 若无退出请求，在**继续持有 `MaintenanceGuard`** 的前提下，从**同一数据根**调用 `supervisor.restart()`（清除 `paused`/`stopping` 并重置退避计数）并等待 Host 完成 NDJSON v2 `hello` 握手进入 `SupervisedHostState::Running`（受启动 hello 超时约束，并通过 `maintenance.on_quit_requested` 在新到达退出请求时中止等待、不饿死退出流程）；(4) 待 Host 恢复到达 `Running`、失败/超时或因退出中止后，才 `drop(guard)` 释放维护窗口与安装锁；(5) **仅当步骤 (3) 实际达到 `Running` 且此前已确认旧包完整**时，才向 UI 上报旧版服务已恢复（`hostRecovered: true`）；若恢复本身失败或超时（且非退出中止），**单独上报 `update_host_recovery_failed`**（与原始更新失败码并列展示）并在 UI 提供显式重试入口（`ByokShell.restart()`），**绝不退出旧程序，也绝不 `confirm`**。
  - **`#2462` 交棒测试硬性要求**：在 Rust 中将步骤 6 封装为可注入的 `UpdateInstaller` 接缝，并在临时目录中使用可注入文件操作（不对真实安装做故障注入）编写自动化集成测试，至少覆盖：(a) fake installer 启动后立即退出且无接管信号（`RolledBackVerified`）→ `MaintenanceLock` 未被 `confirm`、恢复期间持 `MaintenanceGuard`（并发 `shell_restore` 收到 `maintenance_busy`）且旧 Host 恢复至 `hello/ready`；(b) `byok-desktop-snapshot` 失败 → 维护窗内恢复旧 Host 至 `hello/ready`；(c) `HostSupervisor::stop()` 失败、Host 恢复失败（上报 `update_host_recovery_failed` 且不退出）以及失败恢复期间到达退出请求（中止重启、释放锁并干净返回 `QuitOutcome::Quit`）；(d) 目录交换故障注入测试——模拟两次 rename 间中止、二次 rename 与回退 rename 均失败（macOS/Linux `swap_directory`）以及 Windows 回退 rename 错误被忽略（`swap_entries`），断言归类为 `InstallCorrupted`（上报 `update_install_corrupted`）、保留 `pending-swap.json`、**绝不重启旧 Host 且绝不回报 `hostRecovered: true`**；(e) 准备与暂存互斥测试——验证并发检查/下载/暂存返回 `update_in_progress`、`<part>.lock` 防止共享 `.part` 交错写入、清理逻辑不删除其他存活 PID 的暂存目录；(f) 确认 `Swapped` 后 `drain_for_quit` 无死锁返回 `QuitOutcome::HandedOver`；(g) 三端实机/CI 升级与回滚验证——执行“旧版 → S1 `byok-desktop-snapshot(<old_version>)` → `nsh-updater` 替换 → 新版启动；**重新安装旧版后由旧版执行 `shell.restore` 恢复 `<old_version>` 完整快照**”，并验证 Linux `.deb`/`AppImage` 走 `inAppEligible == false` 的白名单发布页手动下载降级。
- **Quit 路径规则**：更新交棒**绝不在 `on_app_quit` 内执行**——NSH `2964346` 在 Windows 与 Linux 上于 `crates/nsh-core/src/element/quit.rs:29` 硬编码 `QUIT_TIMEOUT = 200ms`，无法承载 10 s Host 优雅停机 + S1 `byok-desktop-snapshot` + 目录交换与校验；亦**严禁使用 `nsh/updater::installOnQuit()`**（其把替换延迟到进程退出后的 `run_at_exit()`，脱离交互式失败反馈与旧 Host 恢复）。交棒只能由**显式用户命令**（如“重启并更新”）在退出/重启之前触发。

  - **密钥持有人与保管位置（I1）**：[Owner 于 2026-11-25 签核](https://github.com/Ancienttwo/byok-sdk/issues/2479#issuecomment-7152403100)：本仓库和白标模板保持无 feed，不提交 `.secret` 或硬编码 `publicKey`；fork 用 `nsh keygen` 生成自己的 Ed25519 密钥对，并在打包时注入 `BYOK_UPDATE_FEED_URL` 和 `BYOK_UPDATE_PUBLIC_KEY`。官方发布启用后使用 Owner 持有的专用 Ed25519 清单签名密钥对，与 npm token 和 OS 代码签名证书分开，离线加密备份存入 Owner 的保险库。CI 私钥仅存于受保护的 GitHub Actions release environment 的 secret 中，该环境需 Owner 人工批准且仅限经批准的 `main` / `release/*` commit。公钥通过 `BYOK_UPDATE_PUBLIC_KEY` 注入，始终拒绝无签名清单。创建官方密钥对和发布环境由 Owner 执行。
- **从现行 Electron 安装（`io.byok-sdk.byok-desktop-bots`）升级至 NSH 的路径**：
  - **App ID / Bundle ID 复用**：沿用完全一致的 `id`（`CFBundleIdentifier` / Windows AppUserModelID / Linux `.desktop` 标识）`io.byok-sdk.byok-desktop-bots`（[`nsh-app/nsh.json`](../../examples/desktop-bot-app/nsh-app/nsh.json) 已对齐）以及 `brand.productId = "byok-desktop-bots"`、`brand.productName = "BYOK Bots"`，保持单一产品身份。
  - **数据目录与凭据连续性（零迁移）**：全部持久数据与凭据均由 Host/Custody 经 `resolveHostLayout` 按 `brand.productId` / `productName` 维护——SDK store `~/.byok/byok-desktop-bots`、Host 存储根（macOS `~/Library/Application Support/BYOK Bots`、Windows `%LOCALAPPDATA%\BYOK Bots`、Linux `${XDG_DATA_HOME:-~/.local/share}/byok-desktop-bots`）下的 `host/`（`server.sqlite`、`keys.db`、`settings.json`、`snapshots/`）与 `agents/`，以及 macOS 钥匙串 / Windows Credential Manager / Linux Secret Service 凭据条目——切到 NSH 后原样承接，无需迁移脚本。Electron 遗留的 `<hostStorageRoot>/shell/` 仅存 Chromium 缓存与会话状态，NSH 忽略且不读写；NSH 自身的窗口布局与更新下载缓存存放在按 `id` 隔离的平台应用数据目录（`sys.data_dir`），与 `<hostStorageRoot>/host/` 互不重叠。
  - **首个 NSH 版本不由 `electron-updater` 投递**：现有 Electron 用户不通过 `electron-updater` 自动跳变到 NSH，而是经**一次性手工下载并原生安装**完成切流（原因：Windows 端 `electron-updater` 依赖 NSIS `/S` 静默参数与旧 NSIS 安装路径/卸载项，与 NSH 的 Inno Setup / 每用户目录布局不兼容；Linux 端 `electron-updater` 仅覆盖 `AppImage` 而不支持 `.deb`；维护双 feed 格式与桥接安装器违背单一权威与无兼容路径原则，且模板仓库默认 `publish: null` 无内建 Electron feed）。切流步骤：正常退出旧 Electron 应用（确保 Host 落盘关闭）→ 手工安装 NSH 正式包（macOS 拖入 DMG 覆盖 `/Applications/BYOK Bots.app`；Windows 卸载旧 Electron NSIS 条目后运行每用户 NSH 安装器；Linux 安装 `.deb` 覆盖 `byok-desktop-bots` 或替换 `AppImage`/`.tar.gz`）→ 启动 NSH 直接衔接既有数据根。自首个 NSH 正式版起，后续所有 NSH → NSH 更新统一走上述 `nsh/updater` 契约。
- **外部产品借鉴（仅限语义与安全机制）**：吸收 `OpenBot` 的“本机目录会话级显式只读授权（临时 token 不跨重启持久化）”、“双入口审批 `(taskId, approvalId)` 同步与凭据手交人类回执”与三端打包验证脚本；**严禁引入** `OpenManus` 明文 key/自建 agent loop，以及 `OpenBot` 的 Docker/PostgreSQL/CEL/AG-UI 或非 permissive 的 `CopilotKit Intelligence`。

### D6. UI 层规范与状态归属

- UI 层以生产 rev 对应版本的 NSH Coding Guides 与 Design Guides 为规范权威（按生产 rev 的 tag 取 `website/docs/coding-guides.md` 与 `design-guides.md`），本 ADR 只记录本项目的硬约束。部分指南条目晚于 v0.6.1（如 `ext/` 布局、桌面默认自绘 title bar），以生产 rev 实际具备的能力为准。
- 第一个页面之前建立 `src/ui/` 核心组件集，以及展示全部变体与 light / dark 的 gallery 页；功能页面只组合 `ui` 层，不直接 import `nsh/base` 控件，不写颜色、圆角、字号字面值。主题色以语义 token 定义在 `nsh.json` 的 `"theme"`，light 与 dark 都给值。
- 目标平台只有桌面（macOS、Windows、Linux）。NSH app 目录下的 `DESIGN.md` 记录主题 token、motion token 与每个页面的 motion inventory；inventory 在页面代码之前写好，完成前在运行中的 app 上逐条核对。只用键盘、只用读屏都能完成主要任务，是验收项。
- 会增长的集合（对话 transcript、activity 卡片与 timeline）用 `List`，key 用 Host 提供的稳定标识（`e<seq>`、`t<turnId>`、`q<questionId>`、`taskId`），展开等逐项状态存放在以 id 为 key 的数据中，不放在行内 signal。
- 页面状态集中在 `store.ts` 的私有 signal：只镜像 Rust 持有的状态，由一个 `on_*` 监听驱动刷新；不按 section 各自订阅、各自拉取快照。

## 4. 不在本 ADR 内

- 消除或重构 `resources/host/` 约 `144–173 MiB` Node SEA 体积地板与解除 `pi_background_unavailable`（归属独立的 `templates/packaging/bun` 或 Host 打包工作流）。
- 向 `packages/*` 导出或发布任何 NSH / GPUI UI 框架公共 npm 包（所有桌面壳与 `byok-shell` 保持为私有示例资产，遵守 `#1499` 所有权边界）。
- 移动端（iOS / Android）应用方案与远程云端部署模型调整。
- Electron renderer 到 NSH 页面的逐项移植对照（属实现设计，写入 [#2461](https://github.com/Ancienttwo/byok-sdk/issues/2461) 正文）。
